# FINDING 1 — `wr suspend`/`resume`/`status -i <substr> -z` does an unbounded,
# uncancellable archived-history scan: the control RPC times out, the operator
# cannot un-suspend at all, and the manager heap goes 0.35GB → 12.1GB

**Severity: blocks the operator from controlling the queue, and risks OOMing the
production manager. This is the first thing that happens when you try to
reproduce the freeze — it stops you before you get there.**

## Symptom

manager** — no slow-request warning, no error; the operator has no diagnostic.

## Root cause (two independent defects that compose)

1. **Client sends no state filter unless `-a` is used.** `cmd/suspend.go`
   `getSelectedJobs` (shared by `wr suspend` and `wr resume`):

   ```go
   var state jobqueue.JobState
   if cmdAll { state = allState }   // resume: JobStateSuspended; suspend: ""
   return getJobs(jq, state, cmdAll, 0, false, false)
   ```

   With `-i … -z` (or `-i` alone) `state` stays `""`.

2. **`getJobsByRepGroup` fetches ALL complete jobs whenever state is unset.**
   `server.go:5413` loops over every matching RepGroup and unconditionally adds
   `getDBJobsByRepGroup(rg, opts.State, …)`, which only short-circuits when a
   *non-complete* state is set (`server.go:5471`:
   `if state != "" && state != JobStateComplete { return nil }`).
   `retrieveCompleteJobsByRepGroup` (db.go:2039) then cursor-scans
   `bucketRTK` under the `repgroup+delim` prefix and `codec`-decodes **every
   archived job**, appending them all to one slice — no limit, no offset, no
   streaming, no context. The caller's `Limit`/`Offset` are applied *afterwards*
   in `limitJobs`, so even `-l 1` pays the full cost.

   Complete jobs can never be suspended or resumed, so for these two commands
   100% of that work is discarded.

## Aggravating factors (each is its own finding-sized problem)

- **No request cancellation.** The client's timeout/disconnect does not stop the
  server; the work runs to completion and the reply is fully encoded before the
  send fails. Every operator retry stacks another multi-GB scan, unkillable
  short of restarting the manager.
- **Unbounded reply materialisation.** All matching jobs are held in RAM twice
  (decoded + encoded) before anything is sent. On this DB that is GBs; with
  enough history it is an OOM of the production manager, caused by a read-only
  status query.
- **Long-lived bbolt `View` transactions.** Each scan holds a read tx open for
  minutes. Per the 2026-07-28 diagnosis, a long read tx pins freed pages and
  bloats the freelist, making every write commit slower — i.e. this path directly
  feeds the freeze amplifier.
- **Silent.** No log line, no metric, no warning that a request has been running
  for minutes or has allocated GBs.
- **DEVELOPERS.md rule 6 in spirit** ("never make cost scale with completed-job
  history") — enforced today only for *startup*; the same class of cost is wide
  open on this control path.

## Immediate operational workaround

`wr resume -a` — with `-a` the state filter *is* sent (`suspended`), so
`getJobsCurrent` serves it from the in-memory queue and the DB path is skipped
entirely. Do **not** retry `-i … -z` and do **not** raise `--timeout` (a
"successful" run would try to return millions of archived jobs in one RPC).

### It gets worse as concurrency rises, and it is NOT the backup

Re-measured at ~15:55 (686 running): `archiveCompletedJob` cumulative delay
588,132s over **16,663** events = **mean 35.3s**, and over just the interval
since the 15:41 sample `(588,132-84,312)/(16,663-4,940)` = **43.0s mean**, i.e.
**72% of the 60s client budget**. Archive is 34.75% of all block delay.

The mechanism is simple queueing, and the numbers close:

- the archive queue is **persistently ~600 deep** — goroutines blocked in
  `bbolt.(*DB).Batch` under `archiveJob` measured 483, 522, 572, 607, 592, 592,
  593, 616, 672, 526, 612 at 2-minute intervals from 15:39 to 16:00;
- it drains at **~12 archives/s** (23,666 compress completions in ~35 min);
- Little's law: 600 / 12 = **~50s wait**, matching the measured 43s mean and
  putting the tail past 60s. 234 concurrent `bbolt.(*batch).run` goroutines were
  counted at 15:39 — i.e. the work is spread over *hundreds of separate write
  transactions*, not coalesced into a few.

**Ruled out: the DB backup.** The tracker classified every 20s goroutine sample
for `backupToBackupFile|copyBackup|Tx.WriteTo`; backup frames appear **only at
15:35** (load onset) and are **absent at 15:47**, when the runner-side archive
timeouts fired. This is pure write-lock queueing, not backup I/O.

Root inefficiency: **archives commit one bolt transaction per job.** bbolt's
`Batch()` is supposed to coalesce concurrent callers, but (as the 2026-07-28
diagnosis established) it detaches `db.batch` the instant a batch starts and arms
a fresh `MaxBatchDelay` timer, so under continuous arrival the batches stay tiny.
The fix direction is the one that worked for the best-effort lane: a **coalescing
archive writer that folds all pending archives into ONE `db.Update` and then
replies to each waiter**.

# THE USER-VISIBLE SYMPTOM, EXPLAINED — "compress jobs go to `delayed` at a low
# but continuous rate"

This was the operator's question during the run, and it is Finding 2's
consequence end-to-end. Chain, with the evidence for each link:

1. **The archive RPC blocks ~43s mean on the bolt write lock** (Finding 2).
2. **Some cross the client's 60s receive timeout.** Runner logs, clustered at
   `15:47:14-15` across several nodes:
   `failed to update server with cmd's final state ... err="receive time out"`
   (10 occurrences; `client.go:2251`).
3. **The runner disconnects and enters its 24h retry loop** (`reportFinalState`,
   `client.go:2220`). `receive time out` is correctly NOT in the definitive-reject
   set (`isDefinitiveReject`), so it retries rather than discarding — but **it
   stops touching the job** while it does.
4. **No touches → TTR expires → the job is marked lost → `confirmJobDead` finds
   the command's pid genuinely gone** (it really did exit) → confirmed dead →
   released → **`delayed`**, awaiting retry. *(This link is inference from the
   state counts — `lost:1..3` transiting continuously — plus the 39,190
   `handleRelease` block events. It is silent in the manager log precisely because
   the confirmation SUCCEEDS; only the one host that could not be confirmed at
   15:36:52 logged a warning.)*
5. **The runner's retry re-delivers the final state and it is accepted** →
   `complete`.

**Proof it is not a command failure:** the `delayed` compress jobs carry
`Exitcode 0, Exited true, FailReason "", Attempts 1` — the command succeeded. And
the two specific keys from the timeout logs
(`3125ed011c92203d1ce058a381dcf27c`, `31301cfc65409434a1276e94d67a2bbe`) were
later `complete` with **`Attempts` still 1** and `Walltime` 3.8s — so the work was
**not** re-run.

**So no work is lost — the L2 ownership/idempotency fixes (`f4b9b55`) hold.** The
cost is a runner slot held for 60s+ per event, plus a feedback loop:
release→ready grows the ready backlog → Finding 3's O(backlog) rac pre-pass costs
more CPU → the committer gets less CPU → archives get slower → more timeouts.
That is why the rate is "low but continuous" rather than a one-off, and why the
mean archive block doubled (17.1s → 43.0s) as concurrency went 600 → 686.

# FINDING 3 — 28–42% of the manager's CPU is spent recomputing an invariant:
# `schedulerGroupSnapshot` over the whole ready backlog, every rac cycle
# (proven by a 245× A/B on the live manager — see PROOF below)

Live 30s CPU profile at 15:42 (28.16s of samples):

```
10,090ms  35.8%  jobqueue.(*Job).schedulerGroupSnapshot     <- cum
  |-> 3,510ms 50.7%  jobqueue.schedulerGroupString  (-> Requirements.Stringify)
  |-> 1,380ms 19.9%  jobqueue.reqForScheduler
  |-> 1,350ms 19.5%  jobqueue.(*Job).Key
 5,240ms  18.6%  bbolt/internal/freelist.(*hashMap).freePageIds
 4,390ms  15.6%  runtime.scanObject          } GC, driven by the garbage
 3,460ms  12.3%  runtime.tryDeferToSpanScan  } the above allocates
 2,380ms   8.5%  sort.partition              <- inside Requirements.Stringify
```

`-peek` attributes **96.7% of `schedulerGroupSnapshot` to
`Server.snapshotReadyJobs`** (server.go:2100), which does this for **every**
ready item on **every** rac cycle:

```go
for _, inter := range allitemdata {
    candidates = append(candidates, readyJobCandidate{
        job:      job,
        snapshot: job.schedulerGroupSnapshot(),   // <- per ready job, per cycle
    })
}
```

and each snapshot (job.go:1139) does, per job:

- `reqForScheduler(j.Requirements)` — fresh allocation
- `j.Key()` (job.go:1073) — build `Cwd + Cmd + mountKey` then **MD5** it
- `schedulerGroupString` → `Requirements.Stringify` (scheduler.go:311) — allocate
  the `Other` key slice, **`sort.Strings`** it, build a string, **MD5** it, then
  `fmt.Sprintf`

**Every one of those inputs is invariant for the lifetime of a job** (Cmd, Cwd,
Requirements, LimitGroups). It is recomputed from scratch for ~70,000 ready jobs
on every cycle. Real job shape confirms both MD5 paths are live: `CmdLen 348`,
`CwdMatters true` (long lustre path), `LimitGroups ['results_portal']`,
`OtherRequests ['scheduler_queues_avoid:interactive,inference']` — a non-empty
`req.Other`, so the sort+MD5 branch of `Stringify` runs for all of them.

Why it matters (not just "wasted CPU"):

- It **starves the bbolt committer**, which needs CPU for freelist/spill
  (18.6%). That is Finding 2's 17.1s mean archive block.
- The garbage it creates is most of the GC load (`scanObject` +
  `tryDeferToSpanScan` = 28%).
- rac cycles are frequent under churn: `scheduleRACRecheck` re-arms on
  `CheckRunnerTime` (1 min), but the ready-added callback also fires whenever
  jobs enter ready — and with ~14 completions/s plus the dedupe
  release→retry→ready cycle, that is continuous. So this O(backlog) pre-pass runs
  back-to-back.
- **The 260725-2 bounded-rac fix (`85db7b2`) bounded the wrong half.** Its
  docstring is explicit that "limit-blocked jobs are recorded as skipped WITHOUT
  that expensive work, so a rac cycle's per-job work stays bounded by the
  schedulable count" — that is true of `prepareReadyJob`, but the *pre-pass* that
  decides who is schedulable still pays 2 MD5s + a sort + several allocations per
  ready job. At a 70k backlog the pre-pass IS the expensive half.

Fix direction: memoise the snapshot on the `Job` (invalidate when
`Requirements`/`LimitGroups`/`Cmd`/`Cwd` change — i.e. on requirement bumps and
`Job.Key()` never), so a rac cycle over an unchanged backlog is O(n) cheap
field reads instead of O(n) MD5+sort+allocate.

## PROOF: a 245× A/B on the live production manager

The operator's suspends at the end of the run produced a controlled experiment
that isolates this cost perfectly. **Same process, same 10.3GB DB, same ~91k jobs
in the queue, no runners, no jobs completing, `results_portal` limit = 0 in both
samples** — the ONLY difference is whether those jobs sit in the *ready* subqueue
or the *suspended* one:

| idle manager, nothing schedulable | CPU per 25s | `schedulerGroupSnapshot` |
|---|---|---|
| **61,000 ready** jobs (limit 0) | **19,640ms** (0.79 cores) | **41.8%** |
| **1 ready** job (91,115 now suspended) | **80ms** (0.32% of one core) | **absent** |

**245× less CPU for exactly the same amount of real work: none.** In the first
sample the remaining CPU is the 10.3GB DB backup (`Syscall6` 32.5% =
`syscall.pread` 43% + `unix.SyncFileRange` 40%, the `619c09c` incremental-fsync
pacing) and GC at ~24% (`scanObject` 11.2 + `tryDeferToSpanScan` 9.1 +
`scanObjectsSmall` 4.4) — GC that exists only because of the snapshot garbage; it
fired every 1.8–2.4s throughout, and stopped when the backlog went away.

This is the cleanest evidence in any of the reliable* investigations that the cost
is a pure function of ready-backlog SIZE — not DB size, not queue size, not load.
A limit-blocked backlog burns ~0.8 cores forever for zero benefit, and that is CPU
the bbolt committer needs (Finding 2).

It also gives the reproducer its exact shape and its expected answer: **N ready
jobs in a limit-0 group, no runners, no load → per-rac-cycle work must be O(1) in
N; today it is O(N) MD5+sort+allocate.**

# FINDING 4 — `killExcessCmds` hands `bkill` an unbounded argv, with no timeout,
# and retries the identical failing kill every cycle

35 occurrences by 15:45, starting the moment runners were submitted:

```
warn checkCmd bkill failed err="exit status 255" out="No matching job found"
  toKill="[-b 339466[7] … 339466[1000] 339472[1] … 339472[949]]"   (~1,900 ids)
```

`jobqueue/scheduler/lsf.go:1400` `killExcessCmds` builds ONE `bkill -b` argv
containing every excess element id and execs it:

```go
kc := &killCollector{ …, toKill: []string{"-b"}, maxAllowed: maxAllowed }
err = s.parseBjobs(jobPrefix, kc.consider)
if len(kc.toKill) > 1 {
    killcmd := exec.Command(s.bkillExe, kc.toKill...)   // no ctx, no timeout
    out, errk := killcmd.CombinedOutput()
    if errk != nil && !strings.HasPrefix(string(out), "Job has already finished") {
        clog.Warn(ctx, "checkCmd bkill failed", …, "toKill", kc.toKill, …)
    }
}
```

Four distinct problems:

1. **Unbounded argv** — DEVELOPERS.md rule 7 ("cap what you hand external
   tools", the 260722-1 uncapped-`bsub` outage) applies here and is not
   implemented. We measured ~1,900 ids in one call; at `limit 20000` it would be
   proportionally larger.
2. **No timeout and no context** — rule 7 also says to put a timeout on the exec.
   A hung `bkill` blocks the excess-runner reclamation path indefinitely.
3. **All-or-nothing outcome, silently assumed successful.** The whole call
   returns 255 / `No matching job found`; wr logs a warning and moves on, with no
   idea whether *any* element was killed. Whether these ids were already-gone
   (benign noise) or live over-provisioned runners (the reliable3 "lost slots
   never reclaimed" symptom) is exactly what the current diagnostics cannot
   distinguish.
4. **Identical failing kill retried every cycle** — e.g. `339390[7..13]` was
   killed at 15:36:09 and again, identically, at 15:36:10; the same array ids
   recur across cycles. Rule 7's "back off, don't retry an identical failing
   submit forever" is not applied to the kill path.

Plus a diagnostics cost: each warning dumps the full id list, so the manager log
grew **~75KB/min** of pure `toKill=` text (240KB by 15:45, from a 1KB idle log),
which is what makes the log unreadable during an incident. By 16:07 there were
**116** of these warnings and the log was 627KB.

# FINDING 5 — a command that can NEVER exec (`argument list too long`) is treated
# as a transient failure and retried ~31 times

From the runner logs (`--runner_filelog`, new this run — this class of failure was
invisible before):

```
warn  could not start command [export PORTAL_ID="portal_20260724T115039"; \
  "/software/hgi/utils/portal_builder" -input … -output … <a JSON array of \
  thousands of lustre paths> ]: fork/exec /usr/local/bin/bash: argument list too long
```

- **608 such events across 150 distinct runner logs** in ~25 minutes.
- One runner alone (`15-38-51.node-14-12.350828`) logged **109** of them.
- Log-line length distribution over **76,113** `reserved a job` events (the line
  embeds the full `cmd=`, so this is an upper-bound proxy for command size):
  `min 382, p50 595, p90 823, p99 24,261, max 1,345,498` bytes.
- A sampled buried dedupe job was at **`Attempts: 31`** (`FailReason "command
  exited non-zero"`), showing the retry ceiling being reached.

`E2BIG` from `fork/exec` is **permanent and deterministic**: Linux caps a *single*
argv element at `MAX_ARG_STRLEN` = 128KB regardless of total `ARG_MAX`, and wr
passes the command as one argument to the shell. Such a job cannot ever run, on
any host, at any time. wr nonetheless releases and retries it like a transient
failure, and each retry costs: a scheduled runner + a reservation + the full
command moved over RPC + a state change written to bolt.

The operator's position (correct, and worth recording): *a portal bug that the
commands can be too long, but a wr bug if wr does not handle them appropriately.*

Fix direction: classify exec-impossible failures (`E2BIG`, `ENOENT` on the shell,
`EACCES`) as **non-retryable** — bury on the first occurrence with a clear
`FailReason` naming the real cause, rather than consuming N runner slots to learn
the same answer N times. Ideally also reject/flag an over-long `Cmd` at `wr add`
time, where the user can still act on it.

Cross-finding amplifier: those giant `Cmd` strings are MD5'd by `Job.Key()` on
**every rac cycle** while the job is ready (Finding 3) and rewritten to bolt on
every state change (Finding 2). A ~400KB command is ~1000× the per-job cost of a
normal one on both paths.

# FINDING 6 — operator control RPCs are serialised behind the archive backlog on
# the same single bolt write lock

Observed: `wr limit -g results_portal:0` took **minutes** to return, while a
goroutine dump taken during the wait showed **no `getSetLimitGroup` frame at all**
and 232 archives queued in `bbolt.(*DB).Batch`.

The code explains it exactly — setting a limit persists to bolt:

```go
// server.go:6229  setLimitGroup
_, removed, err := s.db.storeLimitGroups(map[string]*limiter.GroupData{name: limit})
// db.go:931
func (db *db) storeLimitGroups(...) (…) { err = db.bolt.Batch(func(tx *bolt.Tx) error { …
```

`db.bolt.Batch` is **the same single write lock the archive queue is sitting on**.
So the limit change waited its turn behind ~232 archives draining at ~12/s — and
it was invisible in the dump because at that instant it was one more anonymous
waiter on `db.rwlock`, and the next sample was 60s later. Having got the lock,
`setLimitGroup` then calls `triggerReadyAddedCallback` → a **full rac cycle over
the 61k ready backlog** (Finding 3) before returning.

**The controlled contrast, from the end of the run:** with the archive queue
drained and the write path idle, suspending **38,321** dedupe jobs and then
**52,794** compress jobs was *fast both times* — so fast that a 10s sampler never
caught either in flight. Heap moved only 382MB → 541MB → ~1GB peak → 370MB.

Two conclusions:

1. Control-RPC unresponsiveness (the symptom reported throughout `.docs/reliable`,
   `reliable2`, `reliable3` and `reliable4`) is **not** intrinsic to suspend/resume
   or to limit changes; it is contention with the archive path on one global bolt
   writer. Fixing Finding 2 should largely fix this by itself.
2. The July concern that "re-suspending ~100k jobs pumps the change-update
   backlog" is **resolved** by `ed763b0`: a 52,794-job mass suspend is now cheap.

Worth considering on top of Finding 2: give operator/control writes their own
lane or priority so a burst of job traffic can never delay them past a client
timeout.

## Priority 1 — Finding 3: memoise `schedulerGroupSnapshot` → `/bugfix`

**Fast, deterministic, main-suite reproducer (target <1s).** This is the ideal TDD
test:

- Add N (e.g. 20,000) jobs into a limit group whose limit is **0**, so they are
  ready-but-blocked and nothing is schedulable; no runner command configured.
- Drive several rac cycles (`triggerReadyAddedCallback`, or the
  `s.racScanWork`/`recoveryPauseHookForTest`-style seams already used by
  `reliable2_*_test.go`).
- Assert per-cycle work is **O(1) in N**, not O(N). Cheapest robust signal: a
  counter incremented inside `schedulerGroupSnapshot` (or `Job.Key`), asserting it
  does not grow with cycles once the backlog is unchanged. `testing.AllocsPerRun`
  or `runtime.ReadMemStats` deltas make a good second assertion.
- RED today: N snapshots (2 MD5s + a sort + allocations each) per cycle.
- Also add a `Benchmark` so the win is recorded.

**Fix constraints for the implementer:**

1. Memoise the snapshot on the `Job` under its existing `RWMutex`; invalidate on
   any write to `Requirements`, `LimitGroups`, `Cmd`, `Cwd`, `MountConfigs`,
   `WithDocker`/`WithSingularity`/`ContainerMounts` (the `Job.Key()` and
   `Requirements.Stringify()` inputs). `Job.Key()` is invariant after add — cache
   it unconditionally.
2. `priority` and `previousGroup` DO change; keep reading those live. Only the
   expensive derived strings (`key`, `group`, `requirements`) are cacheable.
3. Do not change `schedulerGroupString`'s output format — scheduler group names are
   persisted and matched elsewhere (`~results_portal` suffix parsing, LSF job
   names).
4. Watch `prepareReadyJob`, which legitimately recomputes requirements
   (learning/override) and calls `setSchedulerGroup` — it must invalidate.
5. DEVELOPERS.md rule 2: no new server-wide exclusive lock on the transition path.

**Scale gate (`wrdev.sh`), for the reviewer:** new mode, e.g.
`wrdev.sh idle-backlog-cpu [jobs]` — isolated manager, N (≥50k) jobs in a limit-0
group, **no runners**, then sample `/debug/pprof/profile` and assert
