# Bugfix checklist 260727-3 — owner-report reconciliation + idempotency (Layer 2)

- [x] Final-state report handlers resolve the job via getij(cr,true) requiring the queue item in ItemStateRun, so under a freeze/overload that moved the item out of Run (TTR->lost->release->Delay/Ready, or a processed-then-reply-timed-out archive), the runner's archive/release/bury RPC is rejected 'bad job (not in queue or correct sub-queue)' and the client re-runs already-successful work.

  Root cause: `handleArchive`/`handleRelease` gated final-state reports on the queue SUB-QUEUE (getij's checkRunning == ItemStateRun). A busy/frozen manager routinely moves an exiting job's item out of Run before its owner's report lands (TTR->lost->confirm-dead->release, a winning double-reservation, or a first archive that was processed but whose reply timed out). The report was then rejected ErrBadJob, which the client treats as permanent -> discards the SUCCESSFUL result and re-runs. (Prod 2026-07-26: 6128 archive rejections on ~2000 succeeded compress jobs.)

  Fix — implemented per `.docs/reliable4/layer2-report-reconciliation.md` ("f4b9b55 done PROPERLY"). This re-applies the reverted `f4b9b55` (which was reverted because it LACKED the applyReleaseQueueChange regression fix below) plus that missing fix:
  - `jobqueue/serverCLI.go`: new `getijForReport(cr) (*Job, string)` resolves a FINAL-state report by OWNERSHIP + in-flight state, NOT sub-queue: accepts while the item is Run/Delay/Ready and `job.ReservedBy == cr.ClientID`; `ErrMustReserve` when a new owner took over (new-run-wins); `ErrBadJob` for terminal (Bury)/other/missing-outside-recovery; `ErrRecovering` when the item is missing during recovery. New `jobAlreadyComplete(key)` checks the complete bucket (`db.retrieveCompleteJobsByKeys`) so a retry of an already-archived job returns success (idempotent) instead of ErrBadJob->re-run. `handleArchive` and `handleRelease` (the latter also serves `jbury` via forceBury) now use `getijForReport` + the `jobAlreadyComplete` idempotency shim. `markJobComplete`'s doc comment updated (gating now via getijForReport). Byte-identical to f4b9b55 EXCEPT one deliberate cleanup: the pre-existing "for the many j* methods" doc comment is kept attached to `getij` (its function) rather than f4b9b55's mechanical insertion leaving it drift onto `getijForReport` — functionally identical.
  - `jobqueue/client.go` `handleFinalStateError`: also give up on `ErrMustReserve` (new-run-wins) so a stale runner abandons instead of looping the 24h retry. Byte-identical to f4b9b55.
  - `jobqueue/server_test.go` `TestSuccessfulArchiveOverridesLostReclaimBeforeRerun` sub-test 1: the v0.36.5 "released -> archive REJECTED, Complete==0" boundary becomes "owner's archive ACCEPTED, Complete==1". Byte-identical to f4b9b55. Sub-test 2 (ErrMustReserve / new-run-wins) unchanged.
  - NEW regression fix f4b9b55 lacked — `jobqueue/server.go` `applyReleaseQueueChange`: added an idempotent Ready case before the `default` q.Release branch, mirroring the existing Delay case. Without it, a release for an item already in the ready sub-queue falls through to `q.Release` -> ErrNotRunning -> ErrInternalError, which is NOT in the client give-up set, so the client loops the release retry (churn). This is the reason f4b9b55 was reverted.

  applyReleaseQueueChange DECISION (the design doc flagged "verify the return value"): the doc's literal snippet was `case ...ItemStateReady: return currentState == JobStateReady, nil`. I implemented `return currentState == JobStateDelayed, nil` instead. Justification (verified against `releaseJobSnapshot`/`finalizeReleasedJob`): `currentState` is `job.State`, and `finalizeReleasedJob` sets a released job's State to `JobStateDelayed` (or Buried) — it NEVER sets `JobStateReady`. So a released job whose item sits in the ready sub-queue has `job.State == JobStateDelayed`. The literal `== JobStateReady` would therefore ALWAYS be false for a real release report, running `finalizeReleasedJob` a SECOND time (double UntilBuried + group-count decrement) — contradicting the doc's own stated intent ("the runner's release is redundant" -> skip finalize -> idempotent). Mirroring the Delay case's actual `job.State` check (`== JobStateDelayed`) is the true idempotent mirror and matches the intent. (wr jobs are added with Delay==0, so queue.Release with a zero item-delay would send the item STRAIGHT to ready; setItemDelay on reserve sets a ReleaseDelayMin-based backoff, so in practice the item passes through Delay first then to ready — either way job.State is "delayed".)
