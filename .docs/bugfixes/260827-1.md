# Bugfixes 260827-1

Both items come from the static read of the completion path recorded in
`.docs/reliable4/prod-validation-260827.md` ("The completion path, read - and a
reframe"), during the production investigation of tens-of-seconds request
latency. They are independent of, and additional to, the three larger confirmed
mechanisms in that document (add-path lock contention, backup copy I/O, the
mmaplock remap freeze).

- [ ] **`decrementGroupCount` runs the LSF scheduler synchronously inside the
  archive RPC, and `bjobs -w` is unbounded.** `archiveCompletedJob` ->
  `decrementGroupCount` (`jobqueue/server.go:7055`) calls `s.scheduleRunners`
  directly, not in a goroutine (`server.go:7081`) - contrast `scheduleGroup`
  (`server.go:5271-5289`), which deliberately spawns one "because the external
  scheduler command (eg. bsub) can be slow". That path reaches `lsf.schedule`
  (`jobqueue/scheduler/lsf.go:1566`) -> `checkCmd` -> `killExcessCmds`, and
  `parseBjobs` (`scheduler/lsf.go:2053-2084`) runs `bjobs -w` over all of the
  user's LSF jobs with no timeout and no context - plain `exec.Command`, `Start`,
  scan, `Wait`. Production's LSF account had 22,500+ foreign pending jobs during
  the incident, so a steady fraction of archive RPCs each absorb one whole LSF
  round trip before replying. `Scheduler.Schedule`'s per-cmd limiter
  (`scheduler/scheduler.go:566`) de-duplicates one-at-a-time, so it does not
  multiply, but it does serialise. `parseBjobs` was missed when
  `bsubExecTimeout`/`bkillExecTimeout` were added (`.docs/bugfixes/260824-1.md`,
  which touched only `submitToQueue`/`runBsub` and `bkillBatch`); its
  `//nolint:gosec,noctx` comment dates from commit `69ab307` "Modernise (#534)",
  not from that bound.

- [ ] **The limiter holds its exclusive mutex across a bolt read transaction.**
  `markJobComplete` -> `limiter.Decrement` (`limiter/limiter.go:242`) takes
  `l.mu`, and `vivifyGroup` (`limiter/limiter.go:212`) calls the group-getter,
  which reaches `db.retrieveLimitGroup` (`jobqueue/db.go:2232`) -> `db.retrieve`
  -> `db.bolt.View`: a bolt read transaction under the limiter's exclusive mutex.
  A DEVELOPERS.md rule 1 violation on a lock every completion needs. `Decrement`
  deletes a group when its count reaches 0, so a limit group that drains and
  refills re-vivifies - and re-reads - each time; when the DB's read side is
  stalled (as the confirmed mmaplock freeze does for the duration of a backup
  copy), one vivify freezes every completion's `Decrement` and every reservation
  behind it.
