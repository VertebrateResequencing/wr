# Bugfixes 260827-1

Both items come from the static read of the completion path recorded in
`.docs/reliable4/prod-validation-260827.md` ("The completion path, read - and a
reframe"), during the production investigation of tens-of-seconds request
latency. They are independent of, and additional to, the three larger confirmed
mechanisms in that document (add-path lock contention, backup copy I/O, the
mmaplock remap freeze).

- [x] **`decrementGroupCount` runs the LSF scheduler synchronously inside the
  archive RPC, and `bjobs -w` is unbounded.** `archiveCompletedJob` ->
  `decrementGroupCount` (`jobqueue/server.go:7055`) calls `s.scheduleRunners`
  directly, not in a goroutine (`server.go:7081`) - contrast `scheduleGroup`
  (`server.go:5271-5289`), which deliberately spawns one "because the external
  scheduler command (eg. bsub) can be slow". That path reaches `lsf.schedule`
  (`jobqueue/scheduler/lsf.go:1566`) -> `checkCmd` -> `killExcessCmds`, and
  `parseBjobs` (`scheduler/lsf.go:2053-2084`) runs `bjobs -w` over all of the
  user's LSF jobs with no timeout and no context - plain `exec.Command`, `Start`,
  scan, `Wait`. Production's LSF account had 22,500+ foreign pending jobs during
  the incident, so a steady fraction of archive RPCs each absorb one whole LSF
  round trip before replying. `Scheduler.Schedule`'s per-cmd limiter
  (`scheduler/scheduler.go:566`) de-duplicates one-at-a-time, so it does not
  multiply, but it does serialise. `parseBjobs` was missed when
  `bsubExecTimeout`/`bkillExecTimeout` were added (`.docs/bugfixes/260824-1.md`,
  which touched only `submitToQueue`/`runBsub` and `bkillBatch`); its
  `//nolint:gosec,noctx` comment dates from commit `69ab307` "Modernise (#534)",
  not from that bound.

  **Scope, stated plainly so nobody later credits this with more than it
  deserves: this is a latent hazard, NOT production's bottleneck.** A
  2,715-goroutine dump taken under deliberate load at job limit 500 contained
  **no `os/exec`, `bsub`, `bjobs`, `RunCmd` or scheduler frames at all**, and
  99.9% of the archive handler's blocking was the archive writer. So at that
  instant the synchronous LSF call was blocking nothing. It is fixed here because
  an unbounded external command on an RPC's own goroutine is a hazard whatever
  today's profile says - the bound is what stops a slow farm from becoming a
  stalled manager - not because it explains the observed latency. The three
  confirmed mechanisms are handled separately.

  **Fixed (2026-08-27, branch `reliable4`):**

  - `jobqueue/server.go`: new `scheduleRunnersAsync` holds the one goroutine
    shape both callers need (`s.wg.Add`/`Done` so shutdown still waits,
    `internal.LogPanic`, and an exclusively-owned clone/snapshot because
    `scheduleRunners` mutates `failures`/`retryBackoff` without the sgroup lock).
    `scheduleGroup` now calls it instead of inlining that goroutine, and
    `decrementGroupCount` calls it instead of `scheduleRunners` directly. The
    decrement itself stays synchronous, so the count is correct the moment the
    caller returns.
  - Verified before making it async: none of the three callers
    (`archiveCompletedJob` `serverCLI.go:1401`, `releaseJob` `server.go:5955`,
    `finalizeDeletedJobs` `server.go:6130`) reads a result or depends on
    scheduling having happened - each ignores the call and proceeds to unrelated
    work. Concurrent RPC handlers already gave the synchronous call no ordering
    guarantee over which count reached the scheduler last, and
    `Scheduler.Schedule`'s per-cmd limiter returns immediately when a schedule
    for that cmd is in flight, so this defers work without multiplying
    goroutines.
  - `jobqueue/scheduler/lsf.go`: `parseBjobs` now takes a ctx and runs its exec
    under `exec.CommandContext` with a `bjobsExecTimeout` (30s) derived from
    `context.Background()` - not the scheduling ctx, matching `bsubExecTimeout`'s
    stated reasoning - plus a non-zero `WaitDelay` of `bjobsPipeCloseGrace`
    (10s). Both are test-lowerable package vars with defaults documented against
    their siblings. `countCmds` gained the ctx to pass through.
  - The **load-bearing** part of that change: `parseBjobs` hands the exec an
    `io.Writer` Stdout (the new `bjobsLineParser`, which splits chunks into whole
    lines and feeds `parseBjobsLine` as they arrive, keeping the old streaming
    memory profile and the `scanBufferSize` line cap) instead of scanning
    `Cmd.StdoutPipe`. os/exec force-closes only pipes it owns, so with
    `StdoutPipe` a read blocked on a descendant that inherited the pipe is
    interrupted by neither the exec context nor `WaitDelay` - measured below.
  - A `bjobs` that did not deliver its whole list is an error, never a silently
    short callback set: the counts it feeds (`countCmds`, `killExcessCmds`)
    decide whether wr submits more runners or kills some, and `schedule()` turns
    the error into a retryable failure under the group's existing backoff. An
    `exec.ErrWaitDelay` after a complete read and a successful exit is accepted
    as success via the existing `lingeredOnPipes` predicate and warn-logged,
    mirroring 260824-1's decision for bsub.
  - 260824-1 is intact: `bsubPipeCloseGrace`/`bkillPipeCloseGrace`, their
    non-zero `WaitDelay`s and the `lingeredOnPipes` acceptances are untouched,
    and `TestReliable4BsubPipeLinger`/`TestReliable4BkillPipeLinger`/
    `TestLSFSubmitToQueueStderr` still pass. `fakeBsubDelays` was renamed
    `fakeLSFDelays` (it now holds bjobs knobs too) with its call sites updated;
    no assertion changed.
  - Regression tests: `jobqueue/scheduler/reliable4_bjobs_bound_test.go`
    (`TestReliable4BjobsBound`) and `jobqueue/reliable4_schedule_async_test.go`
    (`TestReliable4ArchiveSchedulingAsync`), reusing `newFakeLSFScheduler` and
    `ConfigMock.ScheduleBlock` rather than new harnesses.

- [ ] **The limiter holds its exclusive mutex across a bolt read transaction.**
  `markJobComplete` -> `limiter.Decrement` (`limiter/limiter.go:242`) takes
  `l.mu`, and `vivifyGroup` (`limiter/limiter.go:212`) calls the group-getter,
  which reaches `db.retrieveLimitGroup` (`jobqueue/db.go:2232`) -> `db.retrieve`
  -> `db.bolt.View`: a bolt read transaction under the limiter's exclusive mutex.
  A DEVELOPERS.md rule 1 violation on a lock every completion needs. `Decrement`
  deletes a group when its count reaches 0, so a limit group that drains and
  refills re-vivifies - and re-reads - each time; when the DB's read side is
  stalled (as the confirmed mmaplock freeze does for the duration of a backup
  copy), one vivify freezes every completion's `Decrement` and every reservation
  behind it.
