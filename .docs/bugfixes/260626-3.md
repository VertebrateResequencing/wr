- [x] CI `test` job (PR #533) flakes with `'receive time out'` on client requests (e.g. `jq.Add`) under `make test` and `make race`. CI was green at 12f6f81 and started failing at 6d104da+ as the suite gained heavier tests; different heavy/contended tests fail each run (TestClientRepGroupStatusCounts, TestJobqueueExecutionAndDependencyScenarios, TestAddBulkDependentJobsRequeuesPersistedLiveOrphans), all `'receive time out'`. Root cause: the test client's `clientConnectTime` (1500ms, jobqueue_test.go:1041) is passed to `Connect()` and becomes the mangos `OptionRecvDeadline` (client.go:413), so `c.request()` waits at most 1.5s for ANY reply; under the race detector + contended CI runner the server's reply to a (bulk or merely contended) `Add` exceeds 1.5s -> spurious timeout. Production is unaffected (real `wr add` of 10000 jobs works, using a generous timeout). Fix in the spirit of prior reliability bugfixes (preserve what each test proves; remove the brittle timing): give the test client a generous per-request recv deadline so contention can't cause spurious receive timeouts, WITHOUT re-slowing the suite (the same 1.5s is relied on for fast connect-failure in negative-connect tests, so do not simply lengthen it globally) and without changing what any test asserts.
  - Fix (`jobqueue/client.go`, +38 lines, purely additive): added `ClientMinRequestTimeout = 60s` and `requestTimeout(t) = max(t, 60s)`. `Connect()` keeps the short passed `timeout` for connect-readiness/`Ping` AND for the lifetime mangos SEND deadline (so connecting to a down server, and a request issued after the server dies, still fail fast), but after a successful initial `Ping` raises ONLY the per-request RECV deadline to `requestTimeout(timeout)`. A generous recv deadline is free for successful requests (it only caps the wait) and does not slow server-death detection (the short send deadline / TCP close fires first), so it removes the contention-induced spurious `'receive time out'` without lengthening anything else. Production callers get a strictly more generous recv floor (a robustness improvement): `cmd/runner.go` passes `max(--timeout, reserveint+5)`, CLIs pass 120s; `max(timeout, 60s)` preserves headroom for callers passing more.
  - Regression: new `jobqueue/client_connect_test.go` connects with a short (1s) timeout then does a blocking `Reserve` whose reply deliberately outlasts that timeout; it fails pre-fix with `'receive time out'` and passes after. The reviewer independently confirmed fail-without / pass-with by neutralising `requestTimeout`.
  - Verified: `go build`, `make lint` (0 issues), and `-race` of the flake victims (`TestClientRepGroupStatusCounts`, `TestAddBulkDependentJobsRequeuesPersistedLiveOrphans`) plus the new test all pass; negative-connect stays fast (no-server `Connect` -> `ErrNoServer` in ~1ms); diff is additive with no behaviour/assertion changes.
  - Known, accepted caveat (pre-existing mangos property): if a request's `Send` lands in the exact instant the server dies, the in-flight message is rescheduled and the request waits the full 60s recv floor before erroring (it is bounded, never a hang; the old code had the same race bounded by the shorter timeout). It did not slow the real suite (`TestJobqueueProduction` shuts the server down twice in ~18s with no stall).
  - Separate/out-of-scope: full `make test`/`make race` on this shared 4-core box also flakes on `TestJobqueueSignal` (jobqueue_test.go:1699, a pure `os.Stat` marker poll for an all-cores runner subprocess, running before any server kill and making no client requests). Confirmed independent of this fix and environmental (24 race lanes on 4 cores under heavy external tenant load); it has consistently passed on CI. To be tracked separately if it ever surfaces on CI.
