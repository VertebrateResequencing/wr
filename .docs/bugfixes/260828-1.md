- [x] Fix the add path's write-transaction fragmentation: concurrent `wr add`s
      must coalesce into one bolt write transaction.

      `db.storeNewJobData` (`jobqueue/db.go`) calls `db.bolt.Batch`. bbolt's
      `DB.Batch` sets `db.batch = nil` at the TOP of `batch.run()`, before it
      calls `db.Update`, so every arrival during a commit forms a new batch on a
      fresh 10 ms timer and opens its own write transaction, which then queues on
      bbolt's single writer lock. bbolt coalesces WITHIN a 10 ms window and never
      ACROSS a commit - backwards when a commit on a production-sized database
      costs 50-120 ms. Production symptom, profiled 2026-08-27
      (`/nfs/hgi/wr/sb10-pprof/prof260827/`): 28,815 slow `add` warnings in 23
      minutes, 20,524 of them adding ONE job, p50 12.8 s; 763 goroutines parked
      in `DB.Batch`; 85% of the writer-lock delay under `bbolt.(*batch).run`.

  - red command (scale gate, ~7.5 min):

- [ ] `TestJobqueueWithMounts` can leave an orphaned fuse mount and a process
      that `kill -9` cannot reap.

      Found while clearing this host on 2026-08-28. Four stale
      `jobqueue.test -test.run ^(TestJobqueueWithMounts)$` processes were alive at
      30, 8 and 3 days old. `kill -9` reaped only the one in `S` state; the other
      three were in `D` with `wchan=request_wait_answer` - blocked inside a FUSE
      request whose userspace daemon had already died - so SIGKILL sat queued in
      `ShdPnd` and could never be delivered.

      The cause was three orphaned `MuxFys` mounts under
      `/tmp/TestJobqueueWithMounts*/…/jobqueue_cwd/…/cwd`, still listed in
      `/proc/mounts` with `user_id=11346`. `fusermount -u` returned "Device or
      resource busy"; `fusermount -uz` detached them from the namespace without
      aborting in-flight requests; only writing `1` to
      `/sys/fs/fuse/connections/<n>/abort` released the processes.

      **This is the mechanism behind the `/tmp` exhaustion above**: a wedged run
      never reaches any cleanup, so its temp dirs survive whatever the suite does.
      The temp-dir fix does not address it, because that fix runs at package exit
      and these processes never get there.

  - **REPRODUCED ON DEMAND, so this has a red command after all.** Start
    `make test` and kill it (or let a `timeout` wrapper kill it) while
    `TestJobqueueWithMounts` is running. Every time: the parents die, a child
    survives in `D` state with `wchan=request_wait_answer`, and
    `/proc/mounts` still lists a `fuse.MuxFys` mount under
    `/tmp/TestJobqueueWithMounts*/…/cwd` with a live entry in
    `/sys/fs/fuse/connections/`. Observed twice on 2026-08-28, the second time
    within ten minutes of the first, from a tool timeout killing the suite.
    Recovery is `fusermount -uz <mp>` then `echo 1 > /sys/fs/fuse/connections/<n>/abort`;
    `kill -9` alone never suffices and `fusermount -u` returns "Device or
    resource busy".
  - so the temp-dir reaper added for the item above does clean up *after* it (the
    creating pid is dead by then), but the wedged process and the fuse connection
    survive on a shared login node until someone aborts them by hand.
  - suggested
    direction: unmount with a bounded timeout in the test's cleanup and abort the
    fuse connection if the unmount does not complete, so a failed mount test
    cannot outlive its own process; and consider a test timeout well under the
    40m `-test.timeout` so a wedged mount fails the run instead of hanging it.
  - a leftover mount is also a farm-citizenship problem, not only a disk one: it
    holds a fuse connection and a D-state process on a shared login node
    indefinitely.
