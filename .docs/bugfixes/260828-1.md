# Bugfixes 260828-1

- [x] Adding one new job to a dep group re-runs already-complete jobs in the same Add batch, whenever some archived job depends on that dep group. Reported from another repo using `AddJobsAndWait` with `ignoreComplete` true: a stable-key job in dep group A ran once and was correctly skipped on later runs, until a job depending on A was added; from then on, every add of a new member of A re-ran all members of A, including the complete ones.
  - Cause: `jobqueue/db.go:1442` in `prepareNewJobs`. When `retrieveDependentJobs` resurrects archived dependents, the branch appends the raw `jobs` input slice instead of `keptJobs` (the input minus jobs `checkIfComplete` reported as complete), so already-complete jobs are re-queued. The `else` branch at line 1444 uses `keptJobs` correctly.
  - Extra severity: the wrongly re-queued complete job is skipped before encoding, so it never returns to `bucketJobsLive` - it runs while invisible to the DB, and a manager restart mid-flight drops it silently.
  - Red command (db seam and client seam, both in a throwaway probe file `jobqueue/zz_depgroup_probe_test.go` to be replaced by the real regression test):
    `CGO_ENABLED=1 go test -tags netgo --count 1 ./jobqueue -v -run 'TestProbe'`
  - Red evidence, db seam (`TestProbeCompleteJobNotRequeuedOnResurrection`, exit 1): second `storeNewJobs([m1 complete, m2 new], ignoreAdded=true)` returned `alreadyAdded=1` but `jobsToQueue` = `[echo n1, echo m1, echo m2]`; assertion `queued["echo m1"] ShouldBeFalse` gave `Expected: false / Actual: true`.
  - Red evidence, client seam (`TestProbeClientCompleteJobNotRerun`, exit 1): second `jq.Add([]*Job{m1, m2}, envVars, true)` reported `inserts=3 already=1` for 2 submitted jobs (expected `inserts=2`), and the subsequent reserve/execute loop ran `map[echo probe m1:true echo probe m2:true echo probe n1:true]`; assertion `ran["echo probe m1"] ShouldBeFalse` gave `Expected: false / Actual: true`.
  - Not a bug, for the record: resurrecting an archived dependent of dep group A is by design (`retrieveDependentJobs`, pinned by `TestSameBatchAndLiveDepGroupReblocking`), so `echo probe n1` re-running is expected. A dependent whose `Key()` changes every run leaves a new archived dependent behind each run, so those stale re-runs accumulate; that is a consequence of the design, not of this bug.
  - Fixed: `jobqueue/db.go` `prepareNewJobs` now ends the `len(encodedJobs) > 0` block with a single `jobsToQueue = append(jobsToQueue, keptJobs...)`, replacing the three old branches. `keptJobs` is authoritative in both `ignoreAdded` modes (`keptJobs = jobs` is set in the same block when `!ignoreAdded`), so the collapse is equivalent on every path apart from returning a copy rather than aliasing the caller's slice - which is what the doc comment always claimed. Doc comments on `storeNewJobs` (`jobqueue/db.go`) and inside `itemDefsForNewJobs` (`jobqueue/server.go`) corrected: both described `jobsToQueue` as all input jobs plus resurrected jobs.
  - Regression tests: `TestCompleteJobsNotRerunWhenDepGroupGrows` (`jobqueue/jobqueue_test.go`) drives the client boundary and asserts the complete job neither re-runs nor gains an attempt (`Attempts` stays 1), that the new member and the resurrected dependent both do run, and that `inserts=2`/`already=1` agree. A new Convey in `TestDBDepGroups` (`jobqueue/db_test.go`) pins the persistence half the client cannot see: every job returned in `jobsToQueue` must also be in `bucketJobsLive` (`checkIfLive`), which without the fix fails first.
  - Verified: both new tests confirmed red against the restored old branches (`db_test.go` `So(live, ShouldBeTrue)` gave `Expected: true / Actual: false`; `jobqueue_test.go` gave `Expected the container ([]string) NOT to contain: 'echo grow first member' (but it did)!`). Not flaky over 29 runs including `--count 20`. `make test` 353 passed / 9 skipped, exit 0; `make lint` 0 issues, exit 0. Throwaway probe file deleted.
