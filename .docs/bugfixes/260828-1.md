- [ ] Fix the add path's write-transaction fragmentation: concurrent `wr add`s
      must coalesce into one bolt write transaction.

      `db.storeNewJobData` (`jobqueue/db.go`) calls `db.bolt.Batch`. bbolt's
      `DB.Batch` sets `db.batch = nil` at the TOP of `batch.run()`, before it
      calls `db.Update`, so every arrival during a commit forms a new batch on a
      fresh 10 ms timer and opens its own write transaction, which then queues on
      bbolt's single writer lock. bbolt coalesces WITHIN a 10 ms window and never
      ACROSS a commit - backwards when a commit on a production-sized database
      costs 50-120 ms. Production symptom, profiled 2026-08-27
      (`/nfs/hgi/wr/sb10-pprof/prof260827/`): 28,815 slow `add` warnings in 23
      minutes, 20,524 of them adding ONE job, p50 12.8 s; 763 goroutines parked
      in `DB.Batch`; 85% of the writer-lock delay under `bbolt.(*batch).run`.

  - red command (scale gate, ~7.5 min):
    `WR_AS_DB=/nfs/hgi/wr/sb10-bigdb/prod.db WRDEV_AS_WORK=/nfs/hgi/wr/sb10-bigdb/aswork ./developers/wrdev.sh add-storm 20 700 120 2000`
  - red evidence at `8d6cd0a`, exit status 1:

    ```
    ## VERDICT: low=20@9.47/s high=700@18.66/s throughputFactor=1.97x (min 10x)
    lowP50=124ms highP50=30138ms (max 5000ms) highP99=51352ms highMax=51431ms
    overSlow=1930 overClientFloor=0 clientTimedOut=0 txnsPerAdd=0.58 (max 1.00)
    maxBatchParked=693 maxBeginRWTx=573 adds=3375 addErrors=0 backupMb=29935 goExit=0
    FAIL: 1930 adds crossed the manager's own 10s slow-request threshold, which is
      production's symptom exactly (28,815 slow adds, 20,524 of them adding ONE job)
    ```

  - a fast unit-level red is also required, in the NORMAL build so `make test`
    covers it: N concurrent single-job adds must cost far fewer than N bolt write
    transactions. Pre-fix it costs ~N.
  - trial log, measurements and reference implementation:
    `.docs/reliable4/addstorm-fix-trials.md` (sections T2 and T4, and SUMMARY).

  - **Real-LSF Tier-B validation is REQUIRED for this item** (`DEVELOPERS.md` §3:
    "in-process tests have repeatedly passed while real LSF failed"). `add-storm`
    is end-to-end but in-process: real server, real socket, real clients, **mock
    scheduler**, no command ever runs. Nothing existing covers the add path on
    real LSF, so the tooling is part of this fix.

    What Tier-B has to prove for THIS change, in order of value:

    1. **Acknowledged adds survive a manager kill.** The fix moves the commit off
       the calling goroutine onto a shared writer, so a defect there would lose
       adds the client was already told had succeeded - silently, and only under
       concurrency. Kill -9 the manager mid-storm, restart the same
       (DB-preserving, isolated prod-mode) manager, and every add the client saw
       succeed must be present.
    2. **The critical path is intact on real LSF**: added jobs reach real runners
       via real `bsub`, run once, and archive. `add → ready → Reserve → Started →
       Touch → Archive`, per `DEVELOPERS.md` §1.
    3. **Concurrent adds stay fast while real runners report.** The new writer
       must not starve against `archiveWriter`/`bestEffortWriter` under real LSF
       traffic, which the mock scheduler cannot exercise.

    Farm-safety rules that apply (`DEVELOPERS.md` §3): isolated prod-mode manager
    with its own config/ports/managerdir, LSF jobs namespaced
    `${PROD_JOB_PREFIX}*` and cleaned up by that namespace only - **never**
    `bkill -J 'wrp_*'`; never touch a real production manager. Reuse the
    scaffolding in `cmd_report_storm_lsf` (`developers/wrdev.sh`), which already
    does exactly this shape.

- [ ] The test suite fills `/tmp` and then fails with "no space left on device".

      `isolateTestConfig` (`jobqueue/jobqueue_test.go:1074`) leaks one
      `/tmp/wrtest*` directory per call by design ("left for the Makefile (or the
      OS) to clean up"), but `make clean` only removes `/tmp/wr`. 25,023 such
      directories (~105 GB) had accumulated and filled this host's 127 GB `/tmp`,
      and a `make race` run at HEAD failed on it mid-suite. Freed by hand for now
      (`/tmp` back to 18% used, 104 GB free), so this is latent again rather than
      fixed.

  - suggested direction: `t.Cleanup` the directory, or extend `make clean` to
    cover `/tmp/wrtest*` and `/tmp/wrrace*`.

- [ ] `TestOwnMemoryMB` (`jobqueue/utils_test.go:59`) flakes under `-race`:
      `Expected '480' to be less than or equal to '479'`.

      Its documented 1 MB truncation tolerance is too tight when Pss drops by more
      than 1 MB between the two `/proc` reads. Passed on re-run; opens no database,
      so it is unrelated to the add path. Per testing-principles a flake is a bug
      in the test, not a reason to skip it: widen the tolerance to what the
      measurement can actually guarantee, or make the two reads consistent.
