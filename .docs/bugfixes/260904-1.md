# The upward tidy strands every level above a parent that has already gone

- [ ] `dirChain.removeEmptyParents` stops on ANY error from removing a parent,
      including `ENOENT`. A parent another process already removed therefore
      strands every hashed level above it, for good.

## Evidence

`jobqueue/utils.go`, on `origin/develop` (`44be38e3`):

```go
func (c dirChain) removeEmptyParents() {
	parents := c.names[:len(c.names)-1]

	for i := len(parents) - 1; i >= 0; i-- {
		if c.roots[i].Remove(parents[i]) != nil {
			return
		}
	}
}
```

The loop runs deepest-first and returns on the first failure, so one level that
is already gone ends the walk with every level above it still on disk. There are
`mkHashedLevels` (4) of them plus the workspace below `<Cwd>/<AppName>_cwd`.

**The same function's own leaf handling disagrees with this.** `removeUpward`
treats a leaf that has gone as removed and carries on:

```go
err := c.roots[last].Remove(c.names[last])
if err != nil && !os.IsNotExist(err) {
	...
}

c.removeEmptyParents()
```

So "gone counts as removed, keep tidying upward" is already the intended rule
for the leaf. Only the parents break it.

## Why it matters

This is the shape of the complaint that started the `--cwd_matters` work: wr
directories not being cleaned up. Two cleanups of one lost job run in different
processes (see `triggerLostRunBehaviours` and the runner's own `on_exit`), so one
taking a level the other is about to take is an ordinary race, not an exotic one.

## Not introduced by any open PR

Verified pre-existing. At `a1a1c861` the body was
`if c.roots[i].Remove(parents[i]) != nil { return }` - the same behaviour - so
it predates PR #575, #577 and #578. It was noticed while reviewing #578, whose
`.run_token` record has since been dropped at the user's direction; the leak is
in the upward tidy of the hashed levels and is untouched by that redesign, so it
needs its own branch.

## Fix sketch (not implemented)

Treat a parent that has gone as removed and continue:

```go
for i := len(parents) - 1; i >= 0; i-- {
	if err := c.roots[i].Remove(parents[i]); err != nil && !os.IsNotExist(err) {
		return
	}
}
```

**Unmeasured, and to establish before implementing:**

- That the strand is a real on-disk outcome, not only a wrong control flow. The
  test must assert which directories survive, not a return value. No such test
  has been run.
- Whether `ENOENT` is the error actually seen. The removal goes through a pinned
  parent handle (`c.roots[i]`), so a directory removed after the handle was
  opened may report something else - `ESTALE` is plausible - which
  `os.IsNotExist` would not match. Measure it rather than assuming; the same
  question applies to `openVerifiedDir`'s three failure exits
  (`parent.OpenRoot`, `dirRoot.Stat(".")`, `proveSameDir`), only the first of
  which plausibly surfaces as `os.IsNotExist` despite a doc comment asserting it
  does.
- Whether continuing past a gone parent can reach a directory that is NOT wr's
  to remove. It should not - every level is named by the chain the descent
  proved - but it is the question a reviewer will ask.
