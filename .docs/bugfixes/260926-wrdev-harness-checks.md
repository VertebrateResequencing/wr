# wrdev.sh harness checks

- [x] `developers/wrdev.sh report-storm-lsf` exits 1 even when the run drains. The last command in `cmd_report_storm_lsf` is `[ -n "${WRDEV_PROD_BKFILE:-}" ] && rm -f ...` (about line 1828). When WR_RS_BKDIR is unset the test fails, so the function returns 1. The monitor's verdict was never returned, so a stall and a clean drain gave the same status. Seen in both sweeps: /nfs/hgi/wr/sb10-bigdb/sweep-260925/lsf-report-storm-lsf.log and sweep-260926/lsf-report-storm-lsf.log both print `FULLY DRAINED` and then `=== report-storm-lsf exit 1`.
  - Red command: `red-rsl.sh developers/wrdev.sh <complete>`, a scratchpad script (not committed). It extracts the real `cmd_report_storm_lsf` and `report_storm_lsf_monitor` bodies with sed and stubs the manager, `wr`, LSF and `sleep`. The fake `wr status` reports `complete: <complete>` out of 5 jobs, and WR_RS_BKDIR is unset. Before the fix, a drain (`5`) and a stall (`3`) both gave `exit=1`.
  - Fix: `report_storm_lsf_monitor` sets `drained=1` when it prints FULLY DRAINED and ends with `[ "$drained" -eq 1 ]`. `cmd_report_storm_lsf` records that status as `verdict`, still runs cleanup (the script uses `set -u`, not `set -e`), and ends with `return "$verdict"`. After the fix a drain gives `exit=0` and a stall gives `exit=1`.
  - Pattern scan: an awk pass over every function lists those whose last statement is an `&&`/`||` list. `cmd_report_storm_lsf` is the only `cmd_*` function that ends with `[ ... ] && cmd`. `cmd_status` ends with `... || echo "  (none)"`, which returns 0 and carries no verdict.
- [x] The limit-drain monitor's `confirmed_dead` column always reads 0. The brief assumed #613 changed the manager's wording. It did not. `git log -S'killed a job after confirming it was dead' -- jobqueue` shows only #412, and the line is still `clog.Info(ctx, "killed a job after confirming it was dead", "key", d.key)` in `killLostJobAndTriggerBehaviours` (jobqueue/server.go:6069), which confirmdead.go's `applyVerdict` calls. The real cause is the log level. `setupManagerLogging` (cmd/manager.go) gives the server's context handler level `warn` unless the manager runs with `--debug`, so this Info line never reaches the manager log. The sweep's limit-drain runs did not set WRDEV_DEBUG. backup-stall-check and report-storm-lsf count the same line and have the same problem.
  - Evidence: `grep -ac 'killed a job after confirming it was dead' /nfs/hgi/wr/sb10-bigdb/sweep-260926/ld{1,2}-limit-drain.manager.log` gives 0 and 0, although ld1 and ld2 had 14 and 22 jobs lost at about t+140s. `grep -aoE 'lvl=[a-z]+'` over the same logs finds only warn lines plus 2 info lines from the cmd-level logger ("wr manager started"). No sweep manager log in sweep-260925 or sweep-260926 contains the kill line.
  - Resolution (harness only; product log levels unchanged): a new `confirmed_dead_count <rundir>` helper counts the kill line only when that manager's command line has `--debug`, and otherwise prints `n/a (needs WRDEV_DEBUG=1)`. The daemonised manager keeps its `os.Args`, so `ps -o args=` shows the flag. The limit-drain monitor, backup-stall-check and report_storm_lsf_monitor now use it. `cmd_prod_start` now adds `--debug` when WRDEV_DEBUG=1, as `cmd_start` already did, so the hint also holds for backup-stall-check.
  - Red command: `red-modes.sh developers/wrdev.sh <mode> 5 [1]`, a scratchpad script (not committed). It evals every function in wrdev.sh and stubs `wr`, LSF, the manager and `sleep`. The fake manager is a background process whose command line has `--debug` only when the last argument is 1, and the fake log holds one kill line. Before the fix, limit-drain, backup-stall-check and report-storm-lsf printed `confirmed_dead=1` from a non-debug manager. After it, they print `confirmed_dead=n/a (needs WRDEV_DEBUG=1)`, and `confirmed_dead=1` with `--debug`.
- [x] `limit-drain` exits 0 even when it prints STALL REPRODUCED. `cmd_limit_monitor` leaves its loop with `break` on both a drain and a stall, and a `for` loop that ends in `break` returns 0. The same verdict-lost-at-exit problem affects the other monitor-style modes. `churn` (`cmd_monitor`) ends with `break` after NO PROGRESS. `backup-stall-check` and `unsuspend-burst` print their REPRODUCED or NO STALL/NO WRITE-STORM verdict and then end with cleanup `rm -f`, which returns 0. `crash-recovery` prints PASS or FAIL and returns the status of its final `safe_kill`.
  - Red command: `red-modes.sh developers/wrdev.sh <mode> <complete>`, the same scratchpad script as item 2. A drain is `5`, and a stall is `3`: the fake `wr status` then never reaches 5 complete, backup-stall-check sees 100 delayed, and unsuspend-burst's stub sampler reports 9000 Batch-blocked goroutines. For crash-recovery, `1` passes and `0` fails. Before the fix, every mode exited 0 for both outcomes, except report-storm-lsf, which was fixed in item 1.
  - Fix: `cmd_limit_monitor` and `cmd_monitor` set `drained=1` when they print FULLY DRAINED and end with `[ "$drained" -eq 1 ]`, so `limit-drain` and `churn` return that status. Running out of samples without draining also fails. `cmd_backup_stall_check` and `cmd_unsuspend_burst` set `verdict=1` in their REPRODUCED branch and end with `return "$verdict"` after cleanup. `cmd_crash_recovery` sets `verdict=0` only on PASS and returns it after cleanup. After the fix, each mode exits 0 for a drain or pass and 1 for a stall or fail.
  - The in-process `go test` wrappers lose their status through a pipeline instead; that is item 4.
- [x] The in-process `go test` wrappers pipe the test through `grep`. The script does not set `pipefail`, so a pipeline's status is the last `grep`'s, which is 0 whenever any line matched, and a failing test still exits 0. The `|| rc=$?` in `writestorm-freeze` and `report-storm` also captured the `grep` status. This affects `backup-stall-fast`, `writestorm-freeze`, `confirm-dead-leak`, `ttrmiss-check`, `report-storm` and `report-storm-profile`, which calls `cmd_report_storm`. `bash -c 'rc=0; { echo "--- FAIL: TestX"; exit 1; } 2>&1 | grep -aE "PASS|FAIL" | grep -avE "no test files" >/dev/null || rc=$?; echo $rc'` prints 0.
  - Pattern scan: every other `go test` call writes to a file or a `$(...)` capture and takes its status there (`|| gorc=$?`, `|| rc=$?`, `; rc=$?`), or deliberately ignores it (`|| true` for fixture seeding). The only other pipeline whose status is kept is flicker-check's `node` calls, which are not piped.
  - Red command: `red-modes.sh developers/wrdev.sh <mode> <5|3>`, the same scratchpad script, with a fake `go` on PATH that prints go-test-like PASS or FAIL lines and exits 0 for `5` or 1 for `3`. Before the fix, all six modes exited 0 for both.
  - Fix: each wrapper takes `${PIPESTATUS[0]}` right after its pipeline. That is the status of `timeout ... go test`, so a timeout gives 124. Wrappers with cleanup store it in `rc` and return it after the cleanup; `confirm-dead-leak` and `ttrmiss-check` return it directly. The printed output is unchanged. After the fix, each mode exits 0 when the fake test passes and 1 when it fails. Items 1 to 3's modes still exit 0 for a drain and 1 for a stall.
- [x] `wrdev.sh help` and any unknown mode (whose `*)` branch calls `usage`) execute commands. `usage()` prints through an unquoted heredoc (`cat <<EOF`, which must stay unquoted so `$WRDEV_ROOT` expands), and its text had 11 backtick spans, so each ran as a command substitution. Running `help` ran the real `wr` from PATH as `wr resume`, which stopped at its argument check, ran `go db.bolt.Batch`, and ran `newgrp` twice, which opened a subshell and hung. The other spans (`running`, `reserved a job` and so on) failed with "command not found".
  - Red command: `red-help.sh developers/wrdev.sh help`, and the same with `no-such-mode`, a scratchpad script (not committed). It puts stub `wr`, `go` and `newgrp` first on PATH, each appending its argv to a marker file, runs the mode under `timeout 20`, and reports the stub calls and the "command not found" lines on stderr. Before the fix, both runs gave `stub-calls=4 not-found=7` (`wr resume`, `go db.bolt.Batch`, `newgrp` twice). After it, both give `stub-calls=0 not-found=0`, and `PATH=<stubs>:$PATH developers/wrdev.sh help > /dev/null` leaves no marker file.
  - Fix: the 11 backtick spans in `usage()` are single-quoted instead, as other entries already quote literal text. The heredoc stays unquoted, so `$WRDEV_ROOT` and the escaped `\$WRDEV_ROOT` render as before.
  - Pattern scan: the other heredocs are the two config files in `ensure_config`, the add-storm fixture manifest and `cmd_dump`'s hint. None contains a backtick. The manifest's `$(stat ...)`, `$(date -Is)` and `$(git ... rev-parse ...)` are meant to run, since they record the fixture's size, mtime, time and commit. No line of wrdev.sh outside a comment contains a backtick.
- [x] PR #620 review (PRRT_kwDOAKD33M6mO4TL): `confirmed_dead_count` read the manager's command line with `ps -o args=`, which cuts it to the terminal width when COLUMNS is set, even when piped. A manager with `--debug` near the end of a long command line then read as not in debug mode, and the count showed n/a.
  - Red command: `COLUMNS=40 red-modes.sh developers/wrdev.sh limit-drain 5 1`, the item 2 scratchpad script, with a fake manager started with `--debug`. Before the fix it printed `confirmed_dead=n/a (needs WRDEV_DEBUG=1)`.
  - Fix: `ps -ww -o args=`, so the width is unlimited. After the fix the same command prints `confirmed_dead=1`, and with no `--debug` (last argument 0) it still prints n/a.
