# Bugfixes 2026-09-14

fix-world-readable-manager-dir

- [x] `wr manager start` creates `~/.wr_<deployment>` with `os.ModePerm`
  (0777), so the directory holding the database, the TLS key and the client
  token is world-readable, and world-WRITABLE under a permissive umask.
    - `cmd/root.go:246`, in `createWorkingDir()`:
      `os.MkdirAll(config.ManagerDir, os.ModePerm)`. Called from
      `cmd/manager.go:183` (`wr manager start`) and `cmd/cloud.go:324`
      (`wr cloud deploy`).
    - RED COMMAND, run against develop d3bd4b8:

      ```
      rm -rf $FH && mkdir -p $FH
      (umask 000; HOME=$FH wr manager start --deployment development)
      stat -c %a $FH/.wr_development
      ```

      Actual `777`. Under `umask 022` it is `755`. Expected `700`.

      ```
      drwxrwxrwx 2 ubuntu ubuntu 4096 .wr_development     # umask 000
      drwxr-xr-x 2 ubuntu ubuntu 4096 .wr_development     # umask 022
      ```

    - What is in that directory, modes as created:

      ```
      -rw-rw---- ca.pem
      -rw-rw---- cert.pem
      -rw------- client.token
      -rw------- db
      -rw------- key.pem
      -rw------- log
      -rw------- manager.addr
      ```

      The FILES are fine. The directory is the hole: unlinking a file needs
      write permission on the DIRECTORY, not on the file, so at 0777 any
      local user can delete or replace `db`, `client.token`, `cert.pem` or
      `key.pem` however tightly those files themselves are locked down. That
      is the same fact that made 260910-3 dangerous, one level up.
    - At 0755 the exposure is smaller but real: another user can list the
      directory and stat its contents. `ca.pem` and `cert.pem` are 0660, so
      group members can read them.
    - The repo already has the right constant and uses it elsewhere:
      `userOnlyPerm = 0700`, and `workSpaceNamePerm = 0700`. This is an
      unconverted call site, not a policy.
    - The other `os.ModePerm` directory creations are triaged on their own
      branches; see "Split out of this branch" below.

## As fixed

- `createWorkingDir()` makes the directory with `managerDirPerm` (`0o700`), a
  new named constant beside `daemonPidFilePerm` in `cmd/root.go`, following
  that file's convention. `userOnlyPerm` was NOT reused: it is unexported in
  `client/testing`, a test-support package `cmd` does not import, so it is not
  in scope. `jobqueue`'s `workSpaceNamePerm` is likewise another package's
  unexported constant. This is a third site for the same policy, not a missing
  import.
- Reproduced on develop `d3bd4b8` before touching anything, and on the branch
  build after: `umask 000` gave `777` and `umask 022` gave `755` before, `700`
  under both after. Every manager started for that was started on ports
  31701/31702 and stopped again.
- `createWorkingDir()` leaves a path that is not a DIRECTORY entirely alone.
  wr dies on it moments later either way, but a plain file somebody else left
  where the working directory should be is theirs, and chmodding it on the way
  past is a side effect nobody asked for.

## An EXISTING directory has ONLY its other-write bits cleared

Three options were on the table. The middle one is what the code does.

1. LEAVE IT ALONE. Argued for on the grounds that `createWorkingDir()` runs on
   every `wr manager start` and every `wr cloud deploy`, so a chmod there is
   not a one-time migration but an enforcement point with no config and no opt
   out, and `os.MkdirAll` does not chmod an existing directory either. REJECTED
   on review, and the rejection is right: everybody who ran wr before this
   release on a box with `umask 002` or `000` would keep a group- or
   world-writable directory for ever, and the warning that was supposed to tell
   them is a log line on a command routinely run under nohup or systemd with
   stderr redirected. A fix nobody sees is not a fix.
2. FORCE 0700. Rejected: this is the option the argument above really lands on.
   A user who ran `chmod 750` so a group member can read `ca.pem` - the token
   they also need having been handed over out of band - gets it silently undone
   on every single start, with no way to say no.
3. CLEAR ONLY `0o022`, `perm &^ 0o022`, and log the one line saying what
   changed. CHOSEN. It closes the hole for everybody automatically, and the
   objection that killed option 2 does not reach it: 0750 has no other-write
   bits, so that user's directory comes back 0750, untouched and unlogged. The
   only modes it changes are ones nothing legitimate wants, because write for
   another user buys a colleague nothing here - `db`, `client.token` and
   `key.pem` are 0600 and owned by one uid, and sharing a deployment needs read
   on the two public certs plus a token handed over separately. It is also the
   narrowest thing that works: the read bits, the execute bits and the sticky
   bit all survive.

The sticky bit is preserved rather than stripped, and a sticky directory is
still closed rather than exempted. `fi.Mode().Perm()` would have dropped
`ModeSticky` from the value passed to `os.Chmod`, silently de-stickying a
`chmod 1777` directory, so the whole `fi.Mode()` is carried through and only
the two write bits are cleared: 1777 becomes 1755. Exempting it was considered
and rejected - sticky stops another user REMOVING a file they do not own, but
it still lets them CREATE one, and a file they own sitting where wr is about to
write `client.token` is a file they can read after wr fills it in.

There is no standalone warning about a mode wr has just fixed. `warn` is
reached only when wr cannot make the change - a symlink, or somebody else's
directory - where the user really is left with something to do. What remains
after the clear is read access, which is not the hole, since the only things
another user can then read are `ca.pem`, `cert.pem` and the 0644 `pid`. The
CHANGELOG says that out loud so an upgrader knows their repaired directory is
0755 rather than 0700, and what to run if they want the rest shut.

What a user with an existing 0777 directory must do: nothing. Their next
`wr manager start` leaves it 0755 and logs `changed the working directory
'...' from drwxrwxrwx to drwxr-xr-x`. The modes are logged as Go spells a
mode rather than in octal, because `os.FileMode.Perm()` has no digit for the
sticky bit and an octal message would have said "from 0777 to 0755" about a
directory that was, and remains, sticky. Go's spelling is NOT `ls`'s for that
bit - Go writes `dtrwxrwxrwx` where `ls -l` writes `drwxrwxrwt` - and the code
comment says so, because anyone diffing the log against `ls` would otherwise
think one of them is broken. If the user also wants the read bits off, wr will
not argue: `chmod 700` sticks, though `chmod 770` will not, since the clear
takes `g+w` off again on the next start.

The 0700 on a NEW directory does change one thing for everybody, and the
CHANGELOG says so rather than hiding it: `ca.pem` and `cert.pem` are created
0660 under the default `managerumask: 007`, and group members could read them
through the old 0755 directory. They can no longer. Nothing in wr depended on
it - the token they would also need is 0600.

## The symlink question, and what no test pins

This fix INTRODUCES a chmod that follows symlinks: `os.Stat` then `os.Chmod`,
both of which resolve one. HARDENED rather than recorded and left. Before
chmodding, `takeOtherWriteOff` does an `os.Lstat` and refuses a path that is
itself a symlink, warning instead. It costs 5 lines and removes a primitive
that would otherwise be real for a manager run as root with `managerdir` under
a world-writable parent: plant a symlink where wr expects its directory and the
chmod lands on a target of your choosing. Planting it needs write permission on
an ancestor - normally the user's own `$HOME` - so it was never a hole in the
ordinary layout, which is why this is hardening and not a second bug fix.

The refusal covers the FINAL component only. A symlink at an ancestor ABOVE
`ManagerDir` is still followed, because `os.Lstat` resolves everything before
the last element; planting one there needs write permission above the user's
home, which is a different and larger compromise. The repo's heavier idiom,
`openBaseRoot`/`os.Root` in `jobqueue/utils.go`, is aimed at attacker-influenced
JOB paths and is more machinery than one chmod of wr's own directory needs -
but see `fix-existing-upload-tree-perms`, where a WALK of N directories does
use it, and where relying on this Lstat alone was proved to be a hole.

`TestCreateWorkingDirRefusesSymlinkedDir` pins it, using `/tmp` as the symlink
target precisely because it is world-writable, root-owned and must come back
untouched.

The chmod-FAILURE branch has no test, and this is how it was checked by hand.
Removing the `ModeSymlink` refusal from `takeOtherWriteOff` and running that
same test turns it into a real EPERM: wr follows the link to `/tmp`, the chmod
fails because the process does not own it, and the warn reads

```text
the working directory '/tmp/.../.wr_development' is dtrwxrwxrwx, so users
other than you can delete or replace the database, the client token and the
TLS key in it, and wr could not change that: chmod /tmp/.../.wr_development:
operation not permitted. Run 'chmod g-w,o-w /tmp/.../.wr_development'
yourself, or ask the directory's owner to
```

`/tmp` was `1777` before that run and `1777` after it. The remedy clause is
there because an earlier wording named the path, the mode, the risk and the
errno but never said what to do about it. The SYMLINK warning quotes no mode
at all, for a reason worth keeping: the mode `closeWorkingDirToOthers` is
handed came from a stat that followed the link, so it describes the target,
and quoting it would tell the user their working directory is something it is
not.

## Deliberately not done

- No `Chmod` after `MkdirAll`, unlike `BackupDB`'s staging in 260910-3. A umask
  can only CLEAR bits, and every bit it can clear here is either one this fix
  exists to clear or one the owner deliberately dropped, so the mode can only
  come out tighter than 0700, never wider. A `Chmod` would instead force 0700
  on an owner whose umask said otherwise.

## Split out of this branch

This started as one branch and became three, because `cmd/root.go` was gaining
80 lines of code for a bug whose fix is one identifier, and the additions were
not one topic. All three are based on develop `d3bd4b8` except the third:

- `fix-upload-dirs-world-readable`: the same `os.ModePerm` defect at the three
  upload sites in `jobqueue/server.go`.
- `fix-existing-upload-tree-perms`: repairing an upload tree an older wr
  already made, which needs `takeOtherWriteOff`'s constants from this branch
  and so is based on it rather than on develop.

The other `os.ModePerm` directory creations in non-test code -
`jobqueue/client.go:2031` (`job.Cwd`) and `jobqueue/utils.go:984`, `:1027`,
`:1033` - are triaged and deliberately left alone; that argument is recorded
in `fix-upload-dirs-world-readable`'s checklist, beside the upload sites it is
contrasted with.
