# Bugfixes 260829-1

Follow-up branch to PR #557. Carries the hardening of #557's BUG 12 and the two
flaky tests left open on PR #558, so that neither holds up the data-loss fix.

- [x] BUG 12 HARDENING: #557 fixed the `--runnermode`/`--servermode` children
  running most of the test suite by passing `-test.run` on each child's cmdline,
  at all four call sites. That restores the pattern the suite already used, but it
  is a rule a fifth call site can forget - which is exactly how the bug arose: two
  of the four call sites had it, and the two added later did not.
  - Consequence when forgotten: the child is a copy of the test binary, so it runs
    every test that does not itself guard on the mode. Those tests start managers,
    and `jobqueueTestInit` only isolates ports and the manager dir when NOT in one
    of these modes, so those managers take the default config - the user's real
    manager port, 5023. One child was measured holding 16498 sockets on it.
  - Fix: `dispatchSubprocessMode()` (jobqueue/subprocess_mode_test.go) does the
    runner/server work and exits the process before any test can run. `TestMain`
    calls it in both builds - the `!race` build gains a `TestMain`, and the
    existing `race` one (which already existed, to clean up its compiled binary)
    calls it first. One `TestMain` per package, hence the shared function.
  - The `-test.run` flag is deliberately KEPT as a second layer: each child's
    cmdline must stay consistent because crash recovery matches a recovered runner
    by its exact cmdline. The point of this change is that the guarantee no longer
    depends on remembering it.
  - Red/green, by simulating the forgotten call site: with
    `runnerModeTestRun` neutered to `""`, `go test -run TestJobqueueRunnerScheduling`
    on develop (no TestMain dispatch) peaks at **16498** sockets on :5023 and takes
    **119.6s**; on this branch it peaks at **0** and takes **9.1s**. Restored
    byte-exact afterwards, md5 `9aa80fa4b59c9b8f766523de0033a6c8`.
  - `TestJobqueueRunnerModeEntrypoint` no longer performs the dispatch (TestMain
    exits first, so its old body was unreachable). Rather than delete it and leave
    `runnerModeTestRun` naming a test that does not exist, it now asserts the
    invariant TestMain enforces - `runnermode` and `servermode` are both false by
    the time any test runs - so the dead code became the regression test for this
    fix. The now-unreachable `servermode` branch of `TestJobqueueSignal` is removed.
  - Gates: `make test` `359 passed / 9 skipped`, `make race` `359 passed / 9 skipped`,
    `make lint` `0 issues.`

- [x] BUG 19 (defect in this branch's OWN first commit, found by Copilot and by CI):
  `jobqueue/subprocess_mode_test.go` was created by copying another file's header,
  which carried `//go:build !race` with it. `dispatchSubprocessMode()` was therefore
  absent from the race build, while the race build's `TestMain` calls it - so
  `make race` failed to compile with `undefined: dispatchSubprocessMode`. The
  non-race build was fine, which is why `make test` and `make lint` both passed.
  - Red: `go vet -race ./jobqueue/` ->
    `vet: jobqueue/runnerbinary_race_test.go:45:2: undefined: dispatchSubprocessMode`.
  - Fix: drop the build constraint. The file must be in BOTH builds precisely
    because both TestMains call into it; that is the whole reason the dispatch was
    factored out of TestMain in the first place.
  - **Process gap this exposed, worth keeping**: CI runs `make test` AND `make race`
    (.github/workflows/tests.yml), but the gates being run locally for this work were
    `make test` and `make lint` only. A build-tag error is invisible to both. `make
    race` is now part of the local gate set for these branches.

- [ ] BUG 20 (flaky test observed on THIS branch's CI, run 33273433200, head 18128ef;
  recorded rather than waved through): `TestJobqueueSignal` failed at
  `jobqueue_test.go:2037` - `Expected: jobqueue.JobState("lost")` - i.e. the job whose
  runner was killed mid-run never came up `lost` on the restarted server within
  `runnerStartWait`. The test took **182s**, meaning it sat out the full 3-minute wait.
  - **Not caused by this branch's change, established two ways rather than assumed.**
    (1) The ONLY Go difference between 7efa29f and 18128ef is the deletion of a
    `//go:build !race` line, and in the norace build that CI's `make test` compiles,
    that file was ALREADY included - so `make test` behaviour is identical at the two
    commits. At 7efa29f CI's `make test` PASSED (`359 passed / 9 skipped`); that job
    failed later, at `make race`, on the compile error of BUG 19. Same behaviour,
    one pass and one fail. (2) A CI re-run of the failing job on the UNCHANGED commit
    18128ef passed.
  - A binary md5 comparison of the two commits was tried first and is worthless here:
    Go embeds a build ID derived from the source, so deleting even a comment line
    changes the hash. Recorded so nobody repeats it.
  - Locally green 8/8 at 16-17s (2 plain, 6 with `WR_TESTSUITE_MAX_PARALLEL=4` to match
    CI). Not reproduced on this box.
  - Still worth chasing here, and NOT dismissed as pure CI noise, because one mechanism
    remains unexcluded: this branch makes the `--servermode` child call `runServer`
    immediately from `TestMain`, where it previously ran only after the test framework
    had started and several guarded no-op tests had returned. That is a small timing
    shift in a crash-recovery test, so it could widen an existing race without being
    deterministic. Checked and excluded: `runServer` needs no test context (it uses
    only `log.Fatal`, no `So()`/`t.`), and the parent detects the child with
    `cmd.Start()` rather than reading its output, so neither explains the failure.
  - Next: run `TestJobqueueSignal` under DISK load (per BUG 5's finding that disk, not
    CPU, reproduces this family) and, to test the timing-shift hypothesis directly,
    compare failure rates with the dispatch deliberately delayed to mimic the old
    ordering.
