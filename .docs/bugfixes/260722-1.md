# Bugfixes 260722-1

- [ ] The LSF scheduler submits a **single, uncapped `bsub` job array** (`-J name[1-N]`) for a scheduler group of N jobs. When a large batch of jobs shares **identical `Requirements`** they collapse into one scheduler group, so N equals the whole batch size; for N in the tens/hundreds of thousands (e.g. adding ~160,000 immediate-exit `false` commands with one memory/time/cpu spec), `bsub` blocks for **minutes** on the oversized array, so the scheduler never launches any runners and the batch makes **zero forward progress** — with **no error logged**. This makes the natural "reproduce at scale with simple identical commands that exit immediately" workload un-runnable, and is a latent DoS of the manager's scheduling for any single large same-requirements batch. NB the user's real production workloads avoid this only incidentally, because learned per-ReqGroup recommendations give their jobs *varied* requirements, splitting them across many smaller groups/arrays.

  **Reproduced (farm22-wrstat01, real LSF, branch `reliable2` HEAD `7229449`, isolated dev manager ports 51780/51781):**
  - Add 160,000 jobs, all `cmd:"false #<i>"`, `queue:"normal"`, identical requirements → one scheduler group `1024:60:1:0:<hash>` with `count=160000`. Debug log shows `rac scheduling jobs group=... count=160000` then `rac finished`, but **0** `wrd_` jobs ever appear in `bjobs`, **0** `Server scheduling runners error` lines, and the batch sits at `ready:160000` indefinitely.
  - A **5-job** and a **3,000-job** batch of the same jobs schedule and run fine (`[1-5]` / `[1-3000]` submit quickly; runners come up).
  - Direct confirmation of the mechanism: running the exact array `bsub` by hand — `bsub -q normal -M 1024 -R 'select[mem>1024] rusage[mem=1024] span[hosts=1]' -J 'wrd_arraytest[1-160000]' -o /dev/null -e /dev/null false` — **did not return within 2 minutes** (had to be killed). So the cost is in `bsub` itself accepting a huge single array, not in wr.
  - This farm's `bparams` reports `MAX_JOB_ARRAY_SIZE = 200000`, i.e. 160,000 is *within* the configured limit — so this is a **performance cliff / hang on large arrays**, not a hard size rejection. There is also a per-user pending cap (~50,000 observed) that interacts once arrays are large. A robust fix must not assume a specific LSF limit; it should cap the array wr itself emits.

  **Root cause (code paths, `reliable2` HEAD):**
  - `jobqueue/server.go` `buildSchedulerGroups`/`countJobInGroup` do `group.count++` per ready job (~`server.go:3593-3614`) with **no cap** — all identical-requirement jobs accumulate into one group count.
  - `scheduleRunners` (`server.go:5200-5227`) calls `s.scheduler.Schedule(cmd, group.req, group.priority, group.count)` with that full count.
  - `jobqueue/scheduler/lsf.go` `schedule()` (~`lsf.go:797-820`) computes `stillNeeded := count - scheduledCount` and passes the **entire** `stillNeeded` to `generateBsubArgs`.
  - `generateBsubName` (~`lsf.go:980-988`) builds the array as `name + fmt.Sprintf("[1-%d]", needed)` — **no cap, no chunking** anywhere in `jobqueue/scheduler/*.go`.
  - `submitToQueue` (~`lsf.go:825-844`) runs `bsubcmd.Output()` with **no timeout** (the `//nolint:noctx` comment deliberately detaches it from the scheduling context: "must complete regardless of scheduling ctx cancellation"), then `waitForBjob`. So a slow/hung `bsub` blocks this group's scheduling indefinitely with no deadline.

  **Secondary defects to address in the same fix (all contribute to the "silent stall"):**
  1. **No bound on the emitted array size.** wr should cap the per-`bsub` array length to a safe maximum and submit the remainder as additional arrays (or top up over subsequent scheduling cycles). Preserve the unique-name-per-cmd contract that `checkCmd` relies on (`generateBsubName` comment: the name must correspond to the cmd and be unique).
  2. **No timeout on the `bsub` exec.** A pathological/oversized `bsub` can wedge a group's scheduling forever. Add a bounded timeout (independent of the scheduling ctx if cancellation-safety is the concern) so a hang is turned into a logged, retryable error rather than a silent block.
  3. **Infinite identical retry.** On a non-`ErrImpossible` schedule error, `scheduleRunners` logs `warn "Server scheduling runners error"` and calls `retryScheduleRunnersLater` (`server.go:5282-5299`), which re-runs with the **same** count forever. With a permanently-failing submit this is an infinite identical-failure loop (observed separately: a queue that rejects via `esub` produced 3 identical failures then silence). Add backoff and surface the condition (and ensure a fatal/persistent submit failure is visible, not swallowed).

  **Suggested fix direction (implementer decides specifics):** introduce a configurable maximum array size (e.g. `maxBsubArraySize`, conservative default ~1000 — the common LSF `MAX_JOB_ARRAY` default — overridable), and in `lsf.schedule`/`generateBsubArgs` split `stillNeeded` into ceil(stillNeeded/max) arrays of ≤ max each (unique names per array), submitting them in one scheduling pass (or a bounded number per pass). Add a bsub exec timeout. Confirm the **local** scheduler (`jobqueue/scheduler/local.go`) needs no change (it does not use LSF arrays). Internal-only change; **no user-facing behaviour change** beyond making large same-requirement batches schedulable (per the project's speedups-internal-only rule).
