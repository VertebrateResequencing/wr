# Bugfixes 260903-2

RECORDED, NOT FIXED. These are findings from adversarial probing of wr, filed as
backlog items so they are not lost. Nothing on this branch changes any code, and
none of these has a fix or a test yet. Each entry names the mechanism, where it
lives, what a user sees, and where the evidence came from.

Topic: `mkHashedDir` and its hold file (`jobqueue/utils.go`).

## 1. Concurrent creation of the SAME key still fails outright

`mkHashedDir` (utils.go:711) makes `<Cwd>/<AppName>_cwd/a/a/a` with
`mkHeldDir`, then `os.MkdirTemp` inside it, then `mkCwdAndTmp`. Cleanup walks
the other way: `dirChain.removeUpward` (utils.go:1061) removes the leaf and then
each empty parent up to the base (`removeEmptyParents`, utils.go:1090). When no
run of a key is left standing, those three hashed levels go empty between runs,
so one run's upward walk can unlink them while another run of the same key is
between `mkHeldDir` and `MkdirTemp`. The hold file plus `mkHashedDirMaxTries`
(3, utils.go:111) narrows the window - the retry loop only covers the
`mkdirAllManaged` and hold-file `OpenFile` calls in `tryMkHeldDir`
(utils.go:806-819), not the `MkdirTemp` or the two `mkdirManaged` calls after
it - but does not close it.

The user sees a job fail to start, buried with `FailReasonCwd` ("working
directory does not exist", client.go:1294-1301). Nothing is lost; the job can
be kicked.

Evidence: a probe harness driving `mkHashedDir` concurrently on one key
reported `mkdir .../jobqueue_cwd/3: no such file or directory` and
`stat .../3/a/a: no such file or directory`, roughly 2 runs in 15 at 4
goroutines x 40 cycles, and 6 of 40 rounds in a tighter harness. That harness
was NOT re-run while filing this; what is verified here is the code path above.

## 2. The hold file is shared by every key with the same first three characters

`mkHashedLevels` is 4 (utils.go:68), so `calculateHashedDir` uses the first
three characters of the key as directory levels and the rest as the `MkdirTemp`
prefix. The hold file is `filepath.Join(dir, ".hold")` (utils.go:714) - one file
per hashed DIRECTORY, not per job - and it is opened with
`os.O_RDONLY|os.O_CREATE` and no `O_EXCL` (utils.go:813), so a second job
happily opens the first job's file. `mkHashedDir`'s deferred `removeHoldFile`
(utils.go:715-717, 742) then unlinks it while another job whose key shares those
three characters may still be inside `mkHashedDir`, which re-exposes the
directory to a concurrent `removeUpward`. Worst case is the same spurious
`FailReasonCwd` bury as above, for a job that has nothing to do with the one
that finished.

## 3. That same open follows a `.hold` symlink, creating a file anywhere writable

`openFileManaged` is `os.OpenFile` (utils.go:800), which follows a final
symlink. The hashed directory is inside the user's own `Cwd`, so a job's own
command can plant `<Cwd>/<AppName>_cwd/a/a/.hold` as a symlink to any path that
user can write, and the next job whose key starts with those three characters
has wr create (or update the mtime of) an empty file there, then unlink it. Low
severity - same-user, empty file, and the unlink follows - but it is wr writing
to a path a job's command chose, and `O_EXCL|O_NOFOLLOW` would refuse it.

## 4. The hashed levels are created with `os.ModePerm`

`tryMkHeldDir` (utils.go:807), `mkCwdAndTmp` (utils.go:846, 852) and
`Client.ensureCwdExists` (client.go:1440 - NOT utils.go, as originally
reported) all pass `os.ModePerm`, so those directories are 0777 minus the
runner's umask. With a permissive umask the shared base and hashed levels are
world-writable, which is what makes finding 3 reachable by another user too.
The leaf is saved by `os.MkdirTemp`'s fixed 0700, and the hold file itself is
0600 (`holdFilePerm`, utils.go:738).
