# Bugfixes 260903-4

RECORDED, NOT FIXED. A finding from adversarial probing of wr, filed as a
backlog item. Nothing on this branch changes any code, and this one is not even
demonstrated - see "How to demonstrate it" below.

**DELETION-ADJACENT.** If it holds on a given filesystem, the consequence is
cleanup deleting a LIVE MOUNT POINT or an un-uploaded cache, not a workspace
left behind. It belongs with the other keep-set deletion risks rather than in a
tidiness backlog.

## The mechanism

The keep set names what cleanup must not delete by STRING, and matches those
strings byte-for-byte against what the filesystem reports.

- `keptDirs.protect` (workspace.go:744) records workspace entries as the names
  `entriesLeadingTo` derived from the configured mount point or cache path.
- `jobWorkSpace.keptEntry` (workspace.go:890) answers
  `ws.keep.workSpaceEntries[name]`, plus `strings.HasPrefix(name,
  muxfysCachePrefix)`, where `name` is `entry.Name()` from the directory read.
- `removeWorkSpaceEntries` (workspace.go:903-919) `RemoveAll`s every entry
  `keptEntry` does not claim.

Go's map lookup and `strings.HasPrefix` are byte comparisons, so the keep set
holds only if the bytes wr derived from the Job's config are the same bytes the
kernel hands back from the directory read. On a filesystem that normalises or
folds names, they need not be:

- Unicode normalisation (APFS, HFS+, SMB, some NFS servers): a `MountConfig`
  spelled in NFC is stored NFC in the Job, while the on-disk entry comes back
  NFD (or the reverse). No match, so a live mount point is swept.
- Case folding (an ext4 directory with `+F`, i.e. `mkfs.ext4 -O casefold` plus
  `chattr +F`): `MyMount` in the config against `mymount` on disk. No match,
  same outcome.

`protect` is not the only route - `wholeWorkSpace`, `wholeActualCwd` and the
`inActualCwd` rels also carry strings - but `inActualCwd` is consumed by
`removeAllExcept` (utils.go:1340), which compares its rels against
`filepath.Join(dir, entry.Name())` in `removeWithExceptions` (utils.go:1376-1387),
so it has the same exposure.

## Why it is undemonstrated

Both filesystems are out of reach here: creating a casefold ext4 image needs
root (loopback mount plus `chattr +F`), and the normalising filesystems are
macOS or a server export, while wr requires `/proc` and so is Linux-only in
practice. No probe produced a swept mount by this route, and none of the
existing tests covers it. Treat this as a plausible risk with a named
mechanism, not an observed failure.

## How to demonstrate it, shortest path

1. As root: `truncate -s 100M fs.img; mkfs.ext4 -O casefold fs.img`, loop-mount
   it, `mkdir cwd; chattr +F cwd`.
2. Add a Job with `Cwd` on that filesystem and a `MountConfig.Mount` of
   `MyMount` (a name whose case differs from what the directory will report).
3. Run it with an `OnSuccess` `Cleanup` behaviour and check whether the mount
   point survives.

The macOS route is shorter if a Mac is available: a mount point name with a
combining accent, added from a config file written in NFC, on an APFS `Cwd`.
