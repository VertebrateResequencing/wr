# Bugfixes 260724-1

- [x] LSF runner over-provisioning — sibling scheduler groups that share one limit group each independently receive the limit group's FULL remaining capacity in a single ready-added-callback (rac) cycle. `countJobInGroup` (jobqueue/server.go) caps each scheduler group's ready-job count at the limit group's remaining capacity via `groupRemainingCapacity`, which caches remaining capacity in `groupLimits[schedulerGroup]` keyed by SCHEDULER GROUP; but the limit is per LIMIT GROUP, shared by several scheduler-group strings (same limit group, different requirements). So each sibling gets the full remaining capacity and the summed runner request across siblings reaches (number of siblings) × limit (production: 13,271 for a 2000 limit, 6.6×). Fix: share a single budget per limit group per rac cycle, decremented as each ready job is counted, so the aggregate ready request for a limit group never exceeds its remaining capacity; unchanged for the single-group and no-limit-group cases; do not change reserve-time enforcement or accountForRunningJobs. (2b — accountForRunningJobs adding running/lost Run entries on top under a non-atomic read — is OUT OF SCOPE here.) See .docs/reliable3/background.md finding 2(a) and prompt.md §2a.
  - Files: `jobqueue/server.go` (replaced the per-scheduler-group `groupRemainingCapacity` cache with a shared per-limit-group budget: new `seedLimitGroupBudgets` seeds each limit group's `limiter.GetRemainingCapacity` once per rac cycle into the fresh-per-cycle map; `countJobInGroup` skips a job if ANY of its limit groups has 0 budget and decrements each limited group's budget when counted; -1 "no limit" never blocks/decrements). New test `jobqueue/reliable3_overprovision_test.go` (`TestReliable3LimitGroupOverProvision`).
