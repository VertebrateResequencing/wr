# Bugfixes 2026-09-16

- [x] `wr status -f` cannot find commands added with `--cwd_matters` from `-c`
      alone, though `wr status -l` can and the `-c` help says it should.

  `wr status`'s `-c` flag is documented as "working dir that the command(s)
  specified by -l or -f were added with, whether or not --cwd_matters was
  used", and #588 delivered that for `-l` by way of
  `JobEssence.candidateKeys()`, which offers the CwdMatters key and then the
  non-CwdMatters one, with `pickCandidateJob` choosing between the answers.
  `-f` never got it, so the bulk mode still misses every `--cwd_matters` job.
  That is the mode that matters for a file of thousands of commands, and
  `wr status` has no `--cwd_matters` flag of its own, so today there is no way
  at all to ask about such a file.

  Root cause is one step earlier than it looks. `getJobsByFile` (cmd/status.go)
  turns each parsed job into an essence with `jobsToJobEssenses`, which calls
  `Job.ToEssense()`, and that returns `&JobEssence{JobKey: j.Key()}` - a single
  precomputed key. `candidateKeys()` short-circuits on a set `JobKey`, so the
  ambiguity is already destroyed before `Client.GetByEssences` is reached;
  `GetByEssences` then maps essences through `jesToKeys` (`Key()` only) rather
  than through candidate keys, and does no per-essence picking.

  So the fix needs both halves: `-f` must build essences that still describe
  the command (Cmd, Cwd, mounts, container options - as `-l` mode does), and
  `GetByEssences` must offer each essence's candidate keys and pick per essence
  with `pickCandidateJob`, whose "only if its Cwd really is the requested Cwd"
  rule is what keeps a loose key safe.

  Constraints worth stating, since `jesToKeys` has seven callers:
  - `Kick()` and `Delete()` share it, and `cmd/remove.go`/`cmd/retry.go` build
    their essences from jobs they already fetched, so those carry a `JobKey`
    and stay single-key. Do not widen destructive operations to a second key.
  - The `N/M cmds were not found` warning must stay truthful when one essence
    resolves to one job out of two candidate keys.

  The same contract fails a second way, found while verifying the first fix: a
  commands file that carries `cwd_matters` per line, handed back to
  `wr status -f` with no `-c` at all, still finds nothing - though the help
  says "In -f mode, provide the same file you gave to wr add", which is exactly
  what that is. The parse knows `CwdMatters` for such a line, so the essence
  should carry the cwd whenever the parsed job has CwdMatters set, as well as
  whenever the user named a cwd with `-c`.

  - Red command: `.tmp/agent/red-status-f-cwd.sh` (drives the real CLI against
    the isolated dev manager; ~60s). Exit 1 with one failing assertion; the
    control and both guard assertions already pass, so a fix that over-reaches
    is caught:

    ```
    --- control: -l mode resolves a --cwd_matters job from -c alone
      PASS  -l cwd_matters: found 1 job(s)
    --- the bug: -f mode must resolve the same jobs from -c alone
      FAIL  -f cwd_matters: expected 2 job(s), found 0
    --- must not regress: -f mode on jobs added WITHOUT cwd_matters
      PASS  -f plain: found 1 job(s)
    --- safety: a --cwd_matters job in another cwd must NOT be returned for -c /tmp
      PASS  -f other cwd excluded: found 0 job(s)

    RED: 1 assertion(s) failed
    ```

    The loop then grew the per-line scenario, red against the first fix:

    ```
    --- the file's own cwd_matters must be honoured with no -c at all
      FAIL  -f per-line cwd_matters, no -c: expected 2 job(s), found 0
    ```

  - Fixed in two halves. `cmd/status.go` gained `parsedJobsToJobEssences`,
    which describes each parsed command (Cmd, Cwd, mounts, the four container
    fields) instead of precomputing one key via `Job.ToEssense()`, carrying the
    cwd when the parsed job's own `CwdMatters` is set or the user gave `-c`;
    and `Client.GetByEssences` now asks for `jesToCandidateKeys(jes)` and picks
    per essence with `pickCandidateJobs`. The candidate rule itself moved into
    one `pickKeyedCandidateJob`, with the Jobs keyed once because a commands
    file brings thousands of essences.
  - `jesToKeys` is byte-identical to develop, so `Modify`, `Kick`, `Suspend`,
    `Resume`, `Delete` and `Kill` still send one key per essence: their cmd
    callers build essences from jobs they already fetched, which carry a
    `JobKey`. A new CLI test suspends the `cwd_matters` job of a same-cmd pair
    and reads the sibling's state back to prove it was left ready.
  - Reviewed PASS, including a differential replay of develop's old
    `pickCandidateJob` against the new one over 205 job-set/essence
    permutations with no mismatch, and a mutation table showing each half of
    the `job.CwdMatters || cmdCwd != ""` guard is load-bearing for a different
    case, with the pre-existing `TestSuspendCommand`/`TestResumeCommand`
    protecting the default-cwd half.
  - The help paragraph that promised this behaviour was six duplicated literals
    across status, kill, remove, retry, suspend and resume; it is now one
    `selectionDescriptionHelp` constant, stating the cwd rule for both modes,
    the file's own `cwd_matters`, and the `-c` narrowing. `wr mod` was left
    alone: it clears `cmdFile` and does not select this way.

- [x] There is no supported way to report what a manager knows about the
      commands in a `wr add -f` file, so diagnosing a duplicate report means
      hand-querying the database.

  Not a defect in wr itself; the deliverable is a reporting script under
  `developers/`, alongside `wrdev.sh` and out of the shipped binary. It exists
  because of the real case behind `.docs/bugfixes/260908-1.md`: a user whose
  `wr add` reported 19632 duplicates while `wr status -i` showed 18553, where
  the remaining 1079 had completed 10 days earlier under another identifier.
  `wr add` now names the identifiers itself, but three questions still have no
  single command: which of these commands does the manager not know at all,
  which were added but never started, and did some of them run in a different
  time window from the rest.

  Write it only after the first item lands, so it can rely on `-c` alone and
  drop the file rewriting the current prototype needs.

- [ ] `make test` collides with whatever else holds ports on the host, failing a
      different test each run, and the auto-selected `WR_TEST_PORT_BASE` span
      can sit on top of long-lived listeners.

  This supersedes the narrower `TestSuiteTempReaping` item in
  `.docs/bugfixes/260908-1.md`, which recorded the symptom without the
  mechanism. Three different tests have now failed this way on one host, none
  of them on an assertion:
  - `TestSuiteTempReaping` (internal/testsuite): `RunPlan` reports `could not
    find a free port range for WR_TEST_PORT_BASE=16016` / `=15888` / `=15746`
    at runner_test.go:94, so its reaping assertions never run. Passes 15/15 in
    isolation, because a one-test plan needs a far smaller span.
  - `TestSelectionByCmdLine` and `TestJobqueueRunnerKillRequests` (cmd,
    jobqueue): fatal `listen tcp 0.0.0.0:<port>: bind: address already in use`
    (44217, 42707), the port free again moments later. The test harness picks a
    port by binding `:0`, closing it, then letting the server rebind, so a
    concurrent lane can take it in the gap.

  Measured cause of the first kind: this host carries long-lived listeners
  inside the span the auto-selected base grows into - `clickhouse` on 19001,
  `uvicorn` on 17581, `next-server` on 17582, none of them wr's - and the bases
  the suite picks (15.7k-16.0k) span upward across them. Steering clear proves
  the suite is otherwise healthy: `WR_TEST_PORT_BASE=10000 make test` gives
  `660 passed · 20 skipped · 29 packages`, exit 0, repeatedly, where the plain
  gate failed three times in a row on the three tests above.

  Also worth fixing: the Makefile runner is fail-fast per package, so a
  `TestSuiteTempReaping` failure aborts the run before cmd and jobqueue ever
  execute, which reads as "everything after it is untested" rather than as one
  package's port problem.

  Fix directions, for its own change: have the port-base search skip a span that
  is already occupied rather than giving up on it, and close the harness's
  bind-`:0`-then-rebind window (hand the listener to the server, or retry the
  bind on collision). Do not paper over either with a retry around a test.

  Not caused by anything on this branch: the failures are in tests this branch
  does not touch, CI is green on the same code, and the same three tests pass
  here once the port base is steered.
  - Added `developers/wr-check-adds.sh`. It passes the user's own file straight
    to `wr status -f -o json` in chunks, joins the answers back by command
    line, and reports the three questions in order: not known to the manager,
    known but never started (broken out by state), and the run batches, naming
    each batch's time span, count, states and identifiers, and saying plainly
    when there is more than one. Per-command detail goes to files, not the
    terminal. Read-only, and it exits non-zero if any query failed so a total
    miss cannot read as "never added".
  - The landed `-f` fix is what let it drop a whole stage: the prototype
    rewrote the input into one JSON object per line with `cwd_matters` baked
    in, purely because `wr status -f` could not express that. The chunks are
    now slices of the user's file, so the script no longer depends on the
    file's format, and its `--cwd_matters` option is gone.
  - Verified against the isolated dev manager by reproducing the real case:
    3 commands completed under one identifier, then a file of those plus more
    under a second identifier 37s later, plus a command that can never start
    (dependency on an absent dep group) and one never added. It reported 1 not
    known, 1 dependent never started, and 2 batches naming both identifiers,
    with the add itself driven by `--cwd_matters` and the query by `-c` alone.
    Also checked at 20k lines (41 chunks, 6.6s), with wrong identity options,
    and against an unreachable manager.
  - `shellcheck` is not installed on this host, so it could not be run; `bash -n`
    is clean and the usual classes were hand-checked.

  on cmd/status.go:62 (thread PRRT_kwDOAKD33M6i5-hc, comment 4025479038), and
  correct: `grep -rhoE '"mounts?_json"' cmd/*.go` finds only `"mount_json"`.
  The wording is inherited, not new - `origin/develop:cmd/status.go:110` has
  the same typo - but extracting the paragraph into one constant moved it into
  one place and put it in front of six commands' `--help`, so it is fixed here.

  all six of status, kill, remove, retry, suspend and resume register `--cwd`,
  `--mounts`, `--mount_json`, `--with_docker`, `--with_singularity`,
  `--container_mounts` and `--container_image_user`. `--cwd_matters` is named
  deliberately as a flag of `wr add`, not of these commands.

- [x] `developers/wr-check-adds.sh` can under-report and still exit 0, because
      it ignores `jq`'s exit status.

  Raised by Copilot's review of PR #597 at head ea149a20, as a suppressed
  comment on developers/wr-check-adds.sh:125, and correct on its main point.
  The query loop counts `wr status` failing, but a chunk where `wr` SUCCEEDS
  and returns output `jq` cannot parse contributes nothing to `found.jsonl`
  while `failed` stays 0, so the script prints an authoritative-looking report
  and exits 0. For a tool whose whole job is to say which commands the manager
  does not know, that is the worst way to be wrong: a query that silently
  dropped reads as "never added".

  Its second point - that output from a failed query is still appended - is
  only theoretically live: `jq '.[]?'` emits nothing for unparseable input, so
  `found.jsonl` stays empty in practice (the red loop asserts this). It relies
  on that accident, so the append should be skipped for a failed query anyway.

  - Red command: `.tmp/agent/red-checkadds-underreport.sh`, which uses a fake
    `wr` so it needs no manager and runs in under a second:

    ```
    --- a query that succeeds but returns unparseable output
      FAIL  unparseable output: exited 0, so an under-reported result reads as authoritative
      FAIL  unparseable output: never warned that the report understates what the manager knows
    --- a query that fails outright (control: already counted)
      PASS  failed query: exited 1
      PASS  failed query: warned about the failure
    --- nothing from a failed query may reach found.jsonl
      PASS  failed query: appended nothing

    RED: 2 problem(s)
    ```
  - Fixed by counting the two ways a chunk can go missing separately:
    `askFailed` for `wr status` itself failing, which now also `continue`s so
    nothing from that query reaches `found.jsonl` by construction rather than
    by `jq` happening to emit nothing, and `parseFailed` for a successful query
    whose output `jq` could not parse. The script exits non-zero on the sum,
    and the warning names both counts and says plainly that nothing in the
    report can be read as "never added".
  - `wr`'s output is still captured rather than piped, so each counter still
    attributes one cause: a pipeline under `pipefail` would merge the two exit
    statuses, and an early-stopping consumer would make `wr` die of SIGPIPE.
    The comment now says what each counter means. Valid-but-empty answers
    (`null`, `[]`, no output) exit 0 from `jq` and are not miscounted.
  - Re-verified against a real manager after the change, including with `-n 2`
    so the per-chunk counters run across three chunks: still two run batches,
    both identifiers named, exit 0, no warning.
