- [x] F0: under manager saturation a still-running job that is being touched on schedule (well within its TTR) is falsely marked lost. Separate from #548 (which only accepts a late successful archive AFTER a false lost). Reproduction: jobqueue/reliable_cause_test.go TestReliableFalseLostUnderSaturation (touches every 120ms within a 500ms TTR under 120 saturating connections; asserts the job is never Lost while alive; FAILS on HEAD with everLost=1, finalLost=true). Root cause: item.touch() sets releaseAt only when the touch is PROCESSED (after single-reader socket + dispatch + queue.mutex contention), so under load touch processing lags past releaseAt and the TTR sweeper reaps a live, touching job; per-touch work is also ungated (emitLiveTouchSnapshot decompresses stdout/stderr + builds subscription updates on every touch even with no subscribers). Fix so lost-detection reflects when the runner last CONTACTED the manager (gate per-touch work; record touch arrival early; ttrCallback must not mark lost if contacted within TTR), while STILL detecting genuinely dead runners (no contact within TTR). Regression guards: TestReliableFalseLostRerun, TestReliableCompletedRepGroupRemovedOnRefresh, make test/race/lint.
