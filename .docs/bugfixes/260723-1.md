# Bugfixes 260723-1

- [x] **Web UI status feed drops non-idempotent deltas under a completion burst, causing the status bar to flicker and then freeze mid-progress** (regression on branch `reliable2` vs v0.36.5). Repro: `wr manager start` (local scheduler), then `perl -e 'for (1..10000){print "echo $_\n"}' | wr add -i echo`; watch the web status page. The CLI ends correct (`wr status -o s -i echo` → `complete=10000`), and v0.36.5's web page fills smoothly to a stable 10000-complete green bar. On `reliable2` the green (complete) segment flickers to not-display and then the page STOPS UPDATING ENTIRELY, stuck mid-progress, even though all jobs completed.

  **Root cause (confirmed by code trace + v0.36.5 comparison):** The Option-R counter-only revert restored v0.36.5's status *data model* (the `jstateCount` from→to DELTA type, the JS delta consumer `handleStateChangeMessage`, `+all+` aggregate, incomplete-only scan-on-connect) but did NOT restore v0.36.5's *transport*. It left in place the internal `caster` introduced by #533 (commit `c3fb550`). `casterMember.trySend` (`jobqueue/server.go:790`) does a non-blocking send into a **1-slot buffer** (`In` = `make(chan any, 1)`, `server.go:729`) and DROPS the value on overflow (the `default:` case). The per-connection writer goroutine (`setupUpdateListener`, `jobqueue/serverWebI.go:854`) blocks on `conn.WriteJSON` to a slow browser (no write deadline), so while one write is in flight every further `statusCaster.Send` beyond the 1 buffered slot is discarded. Because status deltas are NON-IDEMPOTENT increments, a dropped `running→complete` delta is a `complete` count that is never added and never re-derived — the JS only re-seeds on reconnect (`resetLiveCounts` + `{Request:"current"}`), never on a live open connection. Hence: flicker (uneven/out-of-order drops mid-burst) then permanent freeze at an undercount after the burst ends.

  v0.36.5 avoided this by using `github.com/grafov/bcast` (force-pinned via a `replace` to commit `e9affb593f6c`, with the load-bearing comment "must be commit e9affb… or status web page updates break in certain cases"). `bcast.Group.Broadcast` spawns one goroutine per message per member, each BLOCKING on delivery — so it NEVER drops (a slow client just queues delivery goroutines); out-of-order is tolerated by the JS `viewModel.ignore` logic. reliable2's `caster` is drop-on-overflow. The `trySend` comment claiming dropped status deltas are "accepted v0.36.5 flicker/overcount quality" and "there is no overflow-to-resync conversion anywhere" is factually wrong: v0.36.5 accepted out-of-order deltas, not dropped ones.

  **Fix direction (implementer decides specifics; internal-only, no user-facing change beyond fixing the bug):** restore never-drop delivery for the STATUS feed only. The `badServerCaster`/`schedCaster` carry idempotent full sets (a dropped update is recovered by the next set / a client re-request), so they MAY keep drop-on-overflow; only `statusCaster` carries non-idempotent deltas and must not drop. Smallest faithful fix: give the status caster member an effectively-unbounded in-memory queue (mutex-guarded slice or unbounded channel + spill), drained by the existing `setupUpdateListener` writer goroutine at client speed; make its `Send`/enqueue never-drop and return quickly. Prefer this internal fix over re-vendoring `bcast` (which would reintroduce the exact-old-commit `replace`-pin foot-gun). Do NOT use overflow→resync (the JS only re-seeds on reconnect; a server-initiated resync applied without `resetLiveCounts` would double-count). Do NOT reintroduce the removed absolute per-RepGroup counter.

  **N1b safety (preserve):** the enqueue must return quickly on the transition hot path, take NO server-wide exclusive lock, and NOT hold `queue.mutex` across a client write; only the per-member mutex + a fast append. Preserves the invariants documented at `jobtransition.go:68-79`. Tradeoff (as v0.36.5 accepted with bcast): unbounded memory under a permanently-stuck client — acceptable, boundable later with a high-watermark if desired.

  **TDD (failing test first):** add a deterministic Go regression test in `jobqueue` (same package, can use internals; reuse the `deltaCounts` helper at `reliable2_webrevert_test.go:238`). Wire a caster (`newCaster()` + `Join()`), start a DELIBERATELY SLOW member consumer (small sleep per item, modelling a throttled browser), and from the producer drive a burst of ~10000 jobs' worth of `new→ready`/`ready→running`/`running→complete` deltas (+ the `+all+` aggregates) via `Send`, faster than the consumer drains. After draining, assert the consumer's applied `deltaCounts` shows `complete == 10000` for the rep group and `+all+` live total == 0 (i.e. NOTHING was dropped). This MUST fail on current drop-on-overflow code (complete < 10000) and pass after the fix. Run under `-race`. Do NOT weaken existing tests; keep `badServerCaster`/`schedCaster` behaviour and the reliable2 web-revert / KEEP tests green. Note: `wsprobe` is a fast consumer and cannot reproduce this (needs a slow consumer) — the Go harness is the authoritative guard; a `--slow` wsprobe mode is being added separately for the real-LSF/local full-scale confirmation.

  **Fixed (2026-07-23, branch `reliable2`):**
  - `jobqueue/server.go`: added a `neverDrop` mode to `caster` (new
    `newCaster(neverDrop bool)`). `statusCaster` = `newCaster(true)`;
    `badServerCaster`/`schedCaster` = `newCaster(false)` (drop-on-overflow,
    unchanged). A never-drop `casterMember` has an unbounded `queue []any`
    (guarded by the existing `send` mutex) + a coalescing buffered-1 `notify`
    chan; `Join()` starts a per-member `pump()`/`drainQueue()` goroutine that
    drains the queue into `In` at client speed, blocking per-value on the slow
    consumer, exiting on `<-done`. `trySend` (never-drop) is a fast append +
    non-blocking notify — never blocks the producer, never drops.
  - N1b preserved: `statusCaster.Send` takes only caster RLock + per-member
    `send.Lock` fast append; the blocking `conn.WriteJSON` is decoupled in the
    pump, so `queue.mutex` is never held across a client write. Corrected the
    false `trySend`/`jobtransition.go`/`serverWebI_test.go` comments.
  - No `grafov/bcast` reintroduced (go.mod/go.sum untouched), no overflow→resync
    (would double-count vs the JS reconnect-only re-seed), no absolute
    per-RepGroup counter. Tradeoff: unbounded memory under a permanently-stuck
    client (as v0.36.5's bcast accepted).
  - Regression test `TestReliable2StatusFeedNeverDrops`
    (`jobqueue/reliable2_webrevert_test.go`): a slow consumer + a 10000-job
    delta burst → rep-group `complete==10000`, live states 0 (nothing dropped);
    fails before (complete≈5-16), passes after under `-race`. Companion sub-test
    confirms `newCaster(false)` still drops (scope limited to the status feed).
    `make lint` clean; `make browser-test` green (3 status fixtures intact).
