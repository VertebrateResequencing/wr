## How write transactions are counted here

bbolt's `DB.Stats().TxN` counts **read** transactions only (it is incremented in
`beginTx`, not `beginRWTx`), so the red commands below do not use it. bbolt
increments the meta txid once per **committed write** transaction and a read
transaction reports the current one, so

```go
db.bolt.View(func(tx *bolt.Tx) error { id = tx.ID(); return nil })
```

is an exact, zero-instrumentation count of committed write transactions.

Two tunings are measured, because they answer different questions:

- **default coalescing** (`ServerDBBatchDelay` 10ms, `ServerDBBatchSize` 10000):
  how many transactions the add path actually commits when it is the only writer.
  Sequential phases cannot coalesce with each other, so this counts phases.
- **coalescing disabled** (`MaxBatchSize` 1, a legitimate configuration via
  `WR_MANAGERDBBATCHSIZE`): how many transactions the add path *asks* for.
  `DB.Batch`'s full-batch check runs under `batchMu` before the append, so with
  `MaxBatchSize` 1 every `Batch` call deterministically gets its own transaction.

## The read-then-write hazard, and why items 2 and 3 do not widen it

`prepareNewJobs` computes `jobsToQueue`/`jobsToUpdate` from a **read**
transaction taken before the write (`db.go:2984`), so widening a fold widens the
window in which two adds that are each other's dependency-resolution input could
both observe "no live member".

Neither item 2 nor item 3 widens it, for the same reason: both act **entirely
after** that read has closed, and neither folds work from more than one request.

- Item 2 replaces a write transaction with a read one, or skips it. It runs
  before `storeNewJobs`, so it cannot move `prepareNewJobs`' read at all.
- Item 3 merges five write transactions that already all happen after the read,
  into one. The window's start is unchanged and its end arrives no later, since
  one commit of the same puts cannot finish after five sequential commits of
  them. The fold is intra-request: one add's five bucket puts, never several
  adds' puts.

Anything that folded *across* requests would widen it, and is out of scope here.

- [x] **5. `bjobAppeared` is an unbounded `bjobs -w` that can permanently wedge a
  scheduler group** (`jobqueue/scheduler/lsf.go:1816-1823`): no context, no

  removed from `parseBjobs`. `bjobsAppearTimeout` does not bound it, because the
  `<-limit` arm cannot be selected while `s.bjobAppeared(jobID)` runs in the
  `<-ticker.C` arm (`lsf.go:1792-1808`), so a hung call hangs `waitForBjob` ->
  `submitToQueue` -> `schedule()` forever and wedges `Scheduler.limiter[cmd]`
  (`scheduler.go:585-604`) so that scheduler group is never scheduled again.

  - Red command: `go test -tags netgo -count=1 -v ./jobqueue/scheduler/
    -run TestRedProbeBjobAppearedUnbounded`, with a fake `bjobs` whose
    `bjobs -w <id>` appearance check sleeps 25s. Exit status 1:

    `waitForBjob took 10.019558006s, ok=false`.

  **Fixed (2026-08-27, branch `reliable4`):**

  - `jobqueue/scheduler/lsf.go`: `bjobAppeared` now runs its exec under
    `exec.CommandContext` with a timeout derived from `context.Background()` (not
    the scheduling ctx, matching `bsubExecTimeout`/`bjobsExecTimeout`'s stated
    reasoning) plus a non-zero `WaitDelay`. The `//nolint:noctx` is gone. The
    `WaitDelay` is load-bearing for the same reason 260827-1 found for
    `parseBjobs`: os/exec force-closes only pipes it owns, and `CombinedOutput`'s
    pipes are its own, so a descendant that inherited them cannot hold the exec
    open past the timeout.
  - `waitForBjob` now enforces `bjobsAppearTimeout` on its OWN select as well,
    because a poll already running cannot be interrupted: with the deadline only
    inside the polling goroutine, a check that outlived the window extended the
    window by however long it took. The polling loop moved to `pollForBjob`, and
    `ready` is buffered so an abandoned poller's send cannot block.
  - `bjobsAppearTimeout` became a test-lowerable package var beside
    `defaultBjobsAppearTimeout`, following the `bjobsExecTimeout` /
    `bjobsPipeCloseGrace` house pattern.
  - The bounds are read on `waitForBjob`'s own goroutine and passed down as
    parameters rather than read inside the poller. `-race` proved this necessary:
    an abandoned poller reading a test-lowerable var races the next test's write
    with no happens-before edge to close it.
  - Two deliberate, narrow behaviour changes, both stated in the code: a job that
    appears AFTER the window now always yields false (before, an in-flight poll
    could still return true, but only by overrunning the bound, which is the
    bug); and `bjobAppeared` accepts `exec.ErrWaitDelay` after a complete read as
    an answer via the existing `lingeredOnPipes`, matching 260824-1 - without it,
    adding a non-zero `WaitDelay` would have turned a previously-succeeding check
    into a false.
  - Documented residual: after `waitForBjob` gives up, the abandoned poller can
    still hold one `bjobs` process for up to `bjobsExecTimeout` +
    `bjobsPipeCloseGrace`. The caller is not blocked and the process is bounded.
  - Regression test `TestReliable4BjobAppearedBound` in
    `jobqueue/scheduler/reliable4_bjob_appeared_test.go`, with a new
    `fakeLSFDelays.bjobsAppearSleepSecs` so the fake `bjobs` can be slow on the
    appearance check specifically. It asserts the two bounds separately - the
    whole wait ends when its window closes even though the poll outruns it, and
    one poll ends within its own exec bound - plus that a `bjobs` answering at
    once still reports the job as appeared, so neither bound can be met by never
    reporting one.
  - 260827-1 and 260824-1 are intact: `parseBjobs` keeps its context bound,
