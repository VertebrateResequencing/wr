## How write transactions are counted here

bbolt's `DB.Stats().TxN` counts **read** transactions only (it is incremented in
`beginTx`, not `beginRWTx`), so the red commands below do not use it. bbolt
increments the meta txid once per **committed write** transaction and a read
transaction reports the current one, so

```go
db.bolt.View(func(tx *bolt.Tx) error { id = tx.ID(); return nil })
```

is an exact, zero-instrumentation count of committed write transactions.

Two tunings are measured, because they answer different questions:

- **default coalescing** (`ServerDBBatchDelay` 10ms, `ServerDBBatchSize` 10000):
  how many transactions the add path actually commits when it is the only writer.
  Sequential phases cannot coalesce with each other, so this counts phases.
- **coalescing disabled** (`MaxBatchSize` 1, a legitimate configuration via
  `WR_MANAGERDBBATCHSIZE`): how many transactions the add path *asks* for.
  `DB.Batch`'s full-batch check runs under `batchMu` before the append, so with
  `MaxBatchSize` 1 every `Batch` call deterministically gets its own transaction.

## The read-then-write hazard, and why items 2 and 3 do not widen it

`prepareNewJobs` computes `jobsToQueue`/`jobsToUpdate` from a **read**
transaction taken before the write (`db.go:2984`), so widening a fold widens the
window in which two adds that are each other's dependency-resolution input could
both observe "no live member".

Neither item 2 nor item 3 widens it, for the same reason: both act **entirely
after** that read has closed, and neither folds work from more than one request.

- Item 2 replaces a write transaction with a read one, or skips it. It runs
  before `storeNewJobs`, so it cannot move `prepareNewJobs`' read at all.
- Item 3 merges five write transactions that already all happen after the read,
  into one. The window's start is unchanged and its end arrives no later, since
  one commit of the same puts cannot finish after five sequential commits of
  them. The fold is intra-request: one add's five bucket puts, never several
  adds' puts.

Anything that folded *across* requests would widen it, and is out of scope here.

## Items

- [ ] **1. `bucketEnvs` grows by one never-deleted record per add.** Claimed in
  the superseding analysis as "the upstream cause of the DB growth every other
  mechanism feeds on": `managerremotesameaslocal: true` makes `addEnvVars`
  (`cmd/add.go:713`) ship the client's whole `os.Environ()`, which on an LSF exec
  node includes `LSB_JOBID`, so `byteKey` (`jobqueue/utils.go:145`) is unique per
  add; `envCacheSize` is 12 (`db.go:69`) and `bucketEnvs` has only `Put` and
  `Get`, never `Delete` (`db.go:3224`, `:3243`).

  **The growth claim is FALSIFIED. Do not credit any fix here with relieving DB
  growth.** Measured on the read-only production copy
  `/nfs/hgi/wr/sb10-bigdb/prod.db` (7.93 GB, 2026-07-28, taken while
  `managerremotesameaslocal: true` was already set - the config has not changed
  since 2026-07-08):

  | bucket | KeyN | LeafInuse | mean record |
  | --- | --- | --- | --- |
  | `bucketEnvs` | **549** | **1.31 MB** | 2,392 B |
  | `bucketJobsLive` | 118,213 | 0.18 GB | 1,633 B |
  | `bucketJobsComplete` | 2,155,154 | **2.87 GB** | 1,427 B |

  549 env records against 2.27M jobs, 0.04% of the DB's leaf bytes. The code
  reason the env does not vary per add: a `wr add` that runs as a wr job does not
  inherit the runner's LSF environment, because `Client.Execute` sets
  `cmd.Env = env` from `job.Env()` (`client.go:1786-1814`), **replacing** the
  environment with the one stored at the originating add. So jobs that add jobs
  propagate one stable env rather than minting a new one, and `TMPDIR` is
  overridden only when `tmpDir != ""` (mounts).

  **What is real, and is what gets fixed:** on a cache miss `storeEnv` re-`Put`s
  bytes already identical in `bucketEnvs`, paying a full write transaction that
  writes nothing new, **sequentially before `createJobs`**. With 549 distinct
  envs in the DB and a 12-entry cache, that is the ordinary production case.

  - Red command: `go test -tags netgo -count=1 -v ./jobqueue/
    -run TestRedProbeStoreEnvRepeat` - store an env, evict it with
    `envCacheSize+5` others, store it again. Exit status 1:

    ```
    re-storeEnv of an unchanged, already-stored env: write transactions=1,
      bucketEnvs KeyN +0
    re-storing an unchanged env cost 1 write transactions (a full commit that
      writes nothing new, blocking before createJobs), want 0
    ```

  - Not changed, deliberately: shipping per-runner environments. The env volume
    is 1.31 MB, so there is nothing to win, and dropping it would change
    user-visible behaviour. The operator needs no config change either.
