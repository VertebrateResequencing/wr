- [x] Bug A — a release that happens before the job reported a start never decrements `UntilBuried`, so any pre-start release retries forever and ignores `--retries`. `releaseJobSnapshot` (`jobqueue/server.go:4956`) only sets `bury` when `!job.StartTime.IsZero()`, and `finalizeReleasedJob` (`jobqueue/server.go:5017`) only decrements `UntilBuried` under the same gate; server-side `StartTime` is set only by `applyJobStart` (`jobqueue/serverCLI.go:908`), which needs a real pid+host, and `resetJobForReservation` re-zeroes it on every reservation. So a job that never starts burns a runner slot per iteration forever, invisible except in runner logs (measured: `untilBuried=3` after 4 releases; a scale run sat at `delayed: 20, buried: 0` for 90s while exec attempts climbed 20 -> 47). `0d22eda` closed this only for the three permanent errnos it buries; the transient pre-exec path still loops unboundedly. The fix must NOT make a healthy-but-slow-starting job burn its retries — prove that with a test.
  - Root cause confirmed as written: `releaseJobSnapshot`/`finalizeReleasedJob`
    both gated the bury decision and the `UntilBuried--` on `!job.StartTime.IsZero()`,
    and server-side `StartTime` is only ever set by `applyJobStart` (real pid+host),
    so a job that never reported a start retried forever.
  - Fix: the **client now says explicitly whether it attempted the command**.
    New ADDITIVE wire field `clientRequest.Attempted` (ugorji Binc, no `toarray`,
    appended last, following the `Host`/`SchedulerID`/`Pid` precedent — old client
    sends nothing, decodes to `false`, keeps today's behaviour; new client against
    an old server is likewise a no-op). New unexported `Client.releaseAfterAttempt`,
    used by `reportStartFailure`'s transient branch and `applyFinalState`'s release
    branch; the public `Client.Release` stays `attempted:false`.
  - Pure candidate 1 from the handoff doc ("decrement on any owner-reported
    release") was **measured wrong**: `cmd/runner.go:252/269/292` release jobs they
    never tried to run ("not enough time to run", env-var failures), which would
    have started burning retries. Candidate 2 (a separate pre-start counter) was
    rejected: new per-job state with a reset lifecycle to get wrong, refilled
    silently by a manager restart, and it gives the operator a second ceiling they
    never asked for (`--retries N` means N, not N+N).
  - Server predicate `releaseSpendsARetry(job, rep) = rep.attempted ||
    !job.StartTime.IsZero()` is evaluated **exactly once**, in `releaseJobSnapshot`,
    and carried to `finalizeReleasedJob` on `releaseReport.spendsRetry`. The
    six-arg `releaseJob`/`finalizeReleasedJob` signatures became a `releaseReport`
    struct. Manager-initiated paths (`confirmOrReleaseLostJob`, `killJob`) use
    `lostJobReleaseReport()` (attempted=false) so they keep the StartTime-only
    rule — which is what DEVELOPERS.md rule 4 actually protects, and is why a
    healthy-but-slow-starting job cannot burn its retries.
  - Review cycle 1 caught: two doc comments made false by the change (`Release`'s
    exported retry contract, and `reportStartFailure`'s now-untrue "those retries
    are unbounded" rationale — swept in `developers/wrdev.sh` too); an unprotected
    guarantee (the `Client.finishRelease` mirror survived reverting with the whole
    `jobqueue` package green, 477s); and a **uint8 underflow** reachable because the
    predicate was evaluated twice against mutable `StartTime` under two separate
    lock acquisitions (`[2 1 0 255 254 253]`) — i.e. a silent restoration of
    near-unbounded retries. Fixed by the single evaluation above plus a clamped
    decrement.
  - Review cycle 2 caught a regression **introduced by that clamp**: `UntilBuried =
    Retries + 1` is uint8, and `--retries 255` is documented and accepted
    (`cmd/add.go`/`cmd/mod.go` "[0-255]", `restModifyUint8Max`), so it seeded a
    **live job at 0**. The clamp then blocked the decrement while
    `finalizeReleasedJob` still set `State = JobStateBuried` (`0 <= 0`), leaving the
    item in `delay` forever — measured `[0 0 0 0 0 0 0 0]` vs base's terminating
    `[255 254 253 ...]`. Fixed at source with `initialUntilBuried` (saturates at
    `MaxUint8`) at all three seed sites (`prepareInputJobs`, `kickJobs`,
    `resetJobStatusFields`; a repo grep confirms there are no others, and
    `JobModifier.applyScheduling` sets `Retries` without re-seeding).
  - `releaseJobSnapshot`'s bury test now **mirrors `finalizeReleasedJob`'s
    arithmetic** (`remaining := UntilBuried; if spendsRetry && remaining > 0
    { remaining-- }; bury := forceBury || remaining == 0`) rather than the
    reviewer-suggested literal `UntilBuried <= 1`, which was **measured
    insufficient** (mutation M2': it fixes only the spendsRetry branch and leaves
    the same item-state/job-state divergence on a manager release of a 0-budget
    job). Verified arithmetically identical to base for all ordinary `UntilBuried
    >= 1` jobs, so no off-by-one in the normal retry count.
