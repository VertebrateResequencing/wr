## Not taken

- A1, reordering `Job`'s fields so that `keyMemo`, the `RWMutex`,
  `schedulerGroup`, `derived` and `Priority` share one cache line, and C1, a
  batch prefetch pass loading `keyMemo` and `derived` for 16 jobs before
  locking them (with `derived` made an `atomic.Pointer`): rejected as
  fragile. C1's gain depends on how x86 locked instructions wait for earlier
  loads, and A1's on a hand-arranged field layout, so a later field insertion
  silently removes it.
- B1, per-group counts maintained incrementally on every queue transition:
  a missed transition would silently mis-count runners.
- B2, skipping the cycle when "nothing changed": it cannot be proven safe,
  since limits, remaining capacity and running counts change outside it.
- B3, reusing the candidates slice across cycles: it keeps about 14MB at 200k
  ready jobs.
- B4, a counting sort for mixed priorities: it needs a second backlog-sized
  buffer.
- B5, copying the scheduler group header into `Job`: a second copy of
  memoised state to keep in sync.
- B6, a seqlock snapshot, or merging `readyItemData` into the snapshot:
  concurrency risk, or a change to the queue's API.
- A2, putting `queue.Item`'s mutex and data first and adjacent (struct size
  unchanged): dropped for no measurable gain. The investigation saw -6.5%
  (p=0.007) on `readyItemData` alone; on this branch a benchmark of it gave
  25.1ms to 24.3ms (p=0.12), within the noise.

## Measurements

Built test binaries (`go test -tags netgo -c`) of each commit, run
interleaved base, A3, A4, A5 in each of 10 rounds (`-test.benchtime 1s
-test.count 1 -test.benchmem`), compared with benchstat
`v0.0.0-20260929162123-406019bb8b68`. Base is the benchmark commit
(`6c4b3d25` plus item 0, which only deletes code the cycle never called).
The runs were made before A2 was dropped, so the A3-A5 binaries also had A2;
it changes only `queue.Item`, which this benchmark does not touch. Another
worker's stress tests shared the 8-core host, load 2-6 during the runs.
