# Bugfixes 260906-3

- [x] wr pins `github.com/VertebrateResequencing/muxfys/v5 v5.0.0`, which loses
  data: `muxfys.Unmount()` uploads the cache and then deletes the cache
  directory without checking whether the upload succeeded. For a writable
  mount in CacheData mode that cache holds the only copy of everything the job
  wrote, so a failed upload destroyed the job's output. muxfys v5.1.0 fixes
  it: the cache directory that still holds un-uploaded files is kept, and the
  returned error names it. Update the dependency to v5.1.0 so wr users get the
  fix.
  - Not a bug in wr's own code, so there is no failing wr test to make pass.
    The red state is the pin itself:

    ```
    $ grep muxfys go.mod
        github.com/VertebrateResequencing/muxfys/v5 v5.0.0
    ```

  - v5.1.0 also changes the shape of the unmount error, which wr matches on at
    `jobqueue/client.go:2595`. muxfys now builds the error with `errors.Join`
    (separator `\n`, not `"; "`) and appends a second line naming the kept
    cache. The compatibility probe below reproduces the exact v5.1.0 error
    (verbatim from muxfys `muxfys.go:487-492`, asserted by its own
    `muxfys_test.go:535`), pushes it through wr's real wrapping chain
    (`jobqueue/job.go:1305` -> `multierror.Append` -> `job.go:1285` ->
    `client.go:1776`), and checks the substring test still fires:

    ```
    muxfys raw:
    failed to upload 1 files
    the un-uploaded data has been left in the cache directory /tmp/ws/.muxfys.abc123
    ---
    wr job.Unmount err:
    Unmount failure(s): 1 error occurred:
        * failed to upload 1 files
    the un-uploaded data has been left in the cache directory /tmp/ws/.muxfys.abc123

    ---
    strings.Contains(err, "failed to upload") = true
    ```

    `strings.Contains` is not line-based, so the join separator and the extra
    line are both irrelevant to it. wr's unmount error was already multi-line
    before the bump anyway, because `hashicorp/multierror`'s default formatter
    emits `N errors occurred:\n\t* ...`.

    `go mod tidy`. `go.mod` and `go.sum` only; no source change was needed or
    made. The transitive moves the bump pulls in are go-fuse v2.10.1 ->
    v2.11.0, minio-go v7.2.0 -> v7.3.0, klauspost/compress v1.18.6 -> v1.20.0,
    klauspost/cpuid v2.3.0 -> v2.4.0, gopherjs v1.20.2 -> v1.21.0, yaml/v3

    - `jobqueue/exec_outcome_test.go:125`'s `errTestUploadFailed` is a

    - wr's cleanup already keeps the cache directory muxfys now preserves:

- [x] Four documentation statements in wr described muxfys v5.0.0's
  delete-the-cache-regardless behaviour, and the bump above makes them false.
  muxfys v5.1.0 keeps the cache directory holding files that failed to upload
  and names its path in the returned error, so a reader who trusted these
  statements would conclude the data was gone when it is not.
  - No red command exists: nothing wr does is wrong, only what wr says about
    what muxfys does. The statements were checked against muxfys v5.1.0's
    source in the module cache rather than against a test:
    - `muxfys.go:460-466` (`Unmount` doc): "If a remote was not configured with
      a specific CacheDir but CacheData was true, the CacheDir will be deleted.
      The exception is when files fail to upload: their only copy is the one in
      the CacheDir, so that CacheDir is kept and the returned error says where
      it is, leaving you to recover or discard the data yourself."
    - `muxfys.go:484-499` (the code): `keepCache = fs.unuploadedCache()`, then
      `err = errors.Join(err, fmt.Errorf("%w %s", errKeptCache, keepCache.cacheDir))`,
      then the deletion loop's guard `if remote.cacheIsTmp && remote != keepCache`.
      v5.0.0's loop guard was `if remote.cacheIsTmp` alone.
    - `muxfys.go:164-167`: `errKeptCache = errors.New("the un-uploaded data has
      been left in the cache directory")`, documented as "followed by the path
      of the cache directory that was kept because it holds their only copy".
    - `muxfys.go:528-541` (`unuploadedCache`): returns `fs.writeRemote` when it
      has `cacheData` and `fs.createdFiles` is non-empty, else nil - so the
      keeping is exactly the writable CacheData case that lost data before.
    - muxfys `CHANGELOG.md` 5.1.0, Fixed: "Unmount() no longer deletes a
      temporary cache directory that holds files which failed to upload; the
      returned error now says where that directory is."
  - `jobqueue/client.go:2596`: the `strings.Contains(unmountErr.Error(),
    "failed to upload")` branch said the un-uploaded files "only existed in the
    mount's cache, which is deleted at unmount regardless, so the job must be
    redone". The cache is now precisely what is NOT deleted. The BEHAVIOUR is
    still right - wr cannot finish the upload and the job's output only counts
    once it is on the remote - so only the justification changed, to say that
    muxfys keeps the directory and names it in the error. A future reader
    deciding whether recovery is possible is no longer told the data is gone.
  - `cmd/mount.go:206` (`wr mount` help), `jobqueue/mount.go:145`
    (`MountTarget.CacheDir`, wr's public API) and `cmd/add.go:254` (`wr add`
    help, found by grepping the claim rather than briefed) all promised
    deletion on unmount. Each now carries the exception. `cmd/add.go` already
    had one exception - "a cache directory you named yourself, which unmounting
    deliberately leaves in place" - so the fix there was to widen it to cover
    the second kind of kept cache, not to add a new sentence.

  - `jobqueue/exec_outcome_test.go:125`'s `errTestUploadFailed` was left
