# Bugfixes 260825-3

Items 1-2 are carried from `.docs/bugfixes/260825-1.md` (its items 2 and 3);
items 3-6 are the findings carried forward from `.docs/bugfixes/260825-2.md`.
Item 3 of `260825-1.md` (the prod death and stall) is **not** in this batch: it is
largely answered by `.docs/reliable4/prod-restart-260825.md` Findings 6 and 7.

The dep-granularity memory work is being specced separately in
`.docs/dep-granularity/` and is not part of this batch.

- [ ] `wr manager status` and `wr status` cannot distinguish "recovering" from
  "the queue is empty". `recoveryProgress()` (`jobqueue/server.go:1281`) is read
  in exactly one place - the recovery completion log line - and `reportLiveStatus`
  never mentions recovery, so during the window `wr status -o counts` reports
  counts that silently omit every unrecovered job. This is the `manager status`
  half of `.docs/reliable/spec.md` section B1's "expose recovering/`restored`/
  `total` (via `manager status` and/or a ... log line) so a slow recovery is not
  mistaken for a hang", and it is what actually misled the operator on
  2026-08-25: 150,472 jobs read as 10.

- [x] `dbUpgradeReporter` (`jobqueue/db.go:1810-1930`) logs every progress and
  phase line via `clog.Info` on the same warn-filtered server context, so a long
  index rebuild or DB upgrade at startup is as silent to an operator as recovery
  was before `bf53de0`. It does write a status file
  (`internal.WriteDBUpgradeStatus`), so it is not wholly unobservable, but the log
  says nothing.

- [ ] `recoverIncompleteJobs` (`jobqueue/db.go:2497`) holds **one** bolt read
  transaction for the entire live-bucket decode - ~37 s at prod's 150,472 jobs -
  with `mmaplock.RLock()` held throughout. That is the same hazard `c96dcbf`
  chunked `resolveDependencies` to avoid, one function away: any concurrent write
  needing to grow the bolt mapping blocks for the transaction's remaining life,
  and because it holds `db.rwlock` every other write queues behind it. It runs
  before `Serve` returns, so concurrent writers are less likely today - but the
  round-3 spec decision to build per-group state before serving clients keeps this
  decode on the critical path, so it should be chunked the same way.

- [x] `max(1, dependencyResolutionChunkSize)` in `jobqueue/dependency.go` is an
  **unpinned guarantee**: no test drives the var to 0 or below, so deleting the
  `max` would fail nothing, while `slices.Chunk` panics below 1. Same class as the
  `case <-ctx.Done():` finding in `260825-1.md`: pin it or drop it.

  **Pinned (2026-08-26, branch `reliable4`).** The `max` is kept - a chunk size
  below one is a degenerate pass, not a crash - and a new Convey inside
  `TestReliable4RecoveryDependencyPass` ("A chunk size below one is floored to one
  rather than panicking") drives the var to **0 and to -1** and asserts the pass
  still resolves all 100 jobs and costs exactly one read transaction per job,
  which is what "floored to one" means. Both cases are counted and the two counts
  asserted once, so nothing is asserted inside the loop.

  Mutation-tested: with `max(1, ...)` reduced to `dependencyResolutionChunkSize`,
  `TestReliable4RecoveryDependencyPass` FAILs at
  `reliable4_dependency_tx_test.go:454` (the `resolveDependencies` call in the new
  block) with `- cannot be less than 1`, the `slices.Chunk` panic GoConvey catches
  and reports. Restored, it passes at 80 assertions.

- [x] `So()` inside a polled condition, second occurrence. `depTxJobStates`
  (`jobqueue/reliable4_dependency_tx_test.go:625`) contains `So(err, ShouldBeNil)`
  and is called from the closure handed to `pollUntil`, which polls every 20 ms
  for up to 30 s (~1500 iterations). go-conventions bans `So()` in loops over 20.
  Verbatim the finding already carried in `260825-1.md` about `readLogFile`. Fix:
  return an empty map on error and assert once outside the poll.

  **Fixed (2026-08-26, branch `reliable4`).** Phase 3's C2 rewrite of
  `reliable4_dependency_tx_test.go` did **not** carry this: the `So()` was still
  in the helper, and the helper was still called from the `ready` closure handed
  to `pollUntil`. `depTxJobStates` now returns `(map[string]string, error)`; the
  polled closure returns false on error, and each of the three call sites outside
  the poll asserts the error once. No new test, per the batch's own note above:
  the change moves an assertion, it does not change behaviour, and
  `TestReliable4RecoveryDependencyState` stays green at 33 assertions.

- [ ] `depGroupEverSeen` is dead in production. `(*Dependency).incompleteJobKeys`'s
  `d.DepGroup != ""` branch is unreachable - its only non-test caller
  (`jobqueue/dependency.go:314`) is guarded by `dep.DepGroup == ""` - and no test
  calls it either. `c96dcbf` added `depGroupEverSeenTx` plus a `depReader`
  interface method purely to serve that branch.

### Item 1 red (proven RED at `c96dcbf`)

`RED_ROOT=<scratch> NJOBS=300000 bash red-status-recovering.sh` (kept at
`.docs/bugfixes/260825-3-red-status-recovering.sh`). It adds 300,000 jobs to an
isolated production-mode manager, `kill -9`s it so they stay live, restarts it,
and polls **both** `wr manager status` and `wr status -o counts` hard through the
recovery window, stamping every sample so the ones falling strictly between the
`recovering prior state` and `prior state recovered` log lines can be counted:

```
counts before kill: complete:0 running:8 ready:299992 ...
recovery window: 2026-08-25T15:43:28+0100 -> 2026-08-25T15:43:29+0100
samples taken: 48, of which inside the window: 29
samples mentioning recovery: 0
RED: neither 'wr manager status' nor 'wr status' ever says the manager is recovering
```

The inside-the-window count is load-bearing: a first attempt at 30,000 jobs
recovered in under a second, so every sample landed *after* the window and the
red proved nothing. The script now hard-fails with `FAIL (NOT MEASURED)` if fewer
than two samples land inside, so it cannot pass or fail vacuously.

**Scope note for whoever fixes item 2:** the spec at `.docs/dep-granularity/` has
decided to extend the DB-upgrade **sidecar** (`internal.WriteDBUpgradeStatus`,
read by `wr manager start`'s `waitForLiveManagerStartupWith`) with new startup
phases. That is spec work, **not** part of item 2. Item 2 is only about the
reporter's existing lines being invisible in the manager log at the default level.
Do not add phases here; just avoid restructuring the reporter in a way that would
make that extension awkward.


### Item 2 red (proven RED at `c96dcbf`, as a differential)

`RED_ROOT=<scratch> DELBUCKET=<delbucket binary> NJOBS=2000 bash
.docs/bugfixes/260825-3-red-upgrade-visibility.sh`. Script kept alongside; the
helper it needs is `.docs/bugfixes/260825-3-delbucket.go.txt` (a ~20-line bbolt
program that deletes a named top-level bucket; build it in a scratch module
requiring `go.etcd.io/bbolt v1.4.3`).

It builds a DB with 2,000 jobs, kills the manager, **deletes the `depgroups`
bucket** so `initDB`'s `openedExistingDB && !hadDepGroups` rebuild fires on the
next open, restarts with default logging, and then repeats the same rebuild with
`--debug` as a control:

```
--- manager log, distinct msgs ---
      1 msg="wr manager  started on [REDACTED]:51982, pid 2594220
      1 msg="recovering: prior state recovered
      1 msg="recovering prior state
manager-log lines mentioning the rebuild/upgrade: 0
== control: same rebuild, this time with --debug ==
--- with --debug, lines about the rebuild: 6 ---
lvl=info msg="database upgrade started" db=...
lvl=info msg="database upgrade step started" state="rebuild dep-group index" detail="rebuilding database dependency-group index" processed=0
lvl=info msg="database upgrade step complete" state="rebuild dep-group index" detail="rebuilt database dependency-group index (0 entries processed)"
RED: the rebuild logs 6 line(s) under --debug and 0 at the default level
```

**The control run is what makes this non-vacuous.** Absence of log lines proves
nothing unless the rebuild ran, and the sidecar is deleted on success, so the
`--debug` arm is the proof: same fixture, same rebuild, six `lvl=info` lines. The
script also hard-fails `FAIL (NOT MEASURED)` if either manager does not start, or
if the default-level manager never logs `recovering prior state` (which would mean
it never opened the DB at all). Two earlier attempts were discarded for exactly
these reasons - one hit a port-bind race so the default arm measured a manager
that never started, and phase 1's original check could not detect a failed start
because the pipeline ended in `head`, which exits 0 on empty input.

Note the fixture's jobs have no dep groups, so the rebuild processes 0 entries.
That is sufficient for the visibility question (the phase lines are logged
unconditionally), but an implementor wanting progress lines as well as phase lines
will need jobs that actually populate `bucketDTK`, which needs the JSON `dep_grps`
field - `wr add` has no CLI flag for it.


## Item 2 fixed (2026-08-25, branch `reliable4`)

Same shape as `bf53de0`: the milestones an operator must see - upgrade started,
each phase started and complete, upgrade complete - move from `clog.Info` to
`clog.Warn`, the level the server context is filtered at. No new mechanism, and
the reporter is not restructured, so `.docs/dep-granularity/`'s planned sidecar
extension is unaffected.

Per-entry progress stays at `info` (`--debug` only), because a real rebuild
processes millions of entries and `53c323f` exists because this log was once
unusable. One **distinct** line per `dbUpgradeLogInterval` (30 s) is emitted at
warn - `database upgrade step still running`, carrying the same
`state`/`detail`/`processed` plus `took` - so a long phase visibly moves. It is a
separate message rather than a promotion of `database upgrade progress`, matching
`bf53de0`'s `recovering: still recovering prior state`: a default-level log can
then never be mistaken for the full per-point stream, and the `--debug` sequence
stays gapless.

The interval is compared through an **injectable clock** (`now func() time.Time`
on the reporter, defaulted to `time.Now`, used only in `startPhase`'s seed and the
rate-limit comparison), so the cadence assertion is exact rather than a tolerance
band on a host at load 121.

### Verification

- Red: **0 default-level lines -> 6**, matching the `--debug` control exactly.
- **The rate limit is now pinned.** Cycle 1 failed because deleting
  `r.lastLog = time.Now()` turned the guard into a one-shot latch - every point
  promoting after the first interval, i.e. entry-count-bounded again - and the
  whole package still passed (7 promoted correct vs 87 mutant at 1M entries). It
  now fails `reliable4_upgrade_log_test.go:309`, **25 vs 97**.
- Seven mutations verified caught by the reviewer, including the test-side one
  (deleting the clock advance gives 25 vs 0, so the test is not vacuous).
- **The sidecar is byte-identical** to `c96dcbf`: `writeStatus` and `progressDue`
  unchanged, `writeProgress` differing only in its trailing log call,
  `dbUpgradeProgressEntries` (10000) and `dbUpgradeProgressInterval` (2 s) still
  pacing it against real time. `r.now` appears in exactly two places, both in the
  promotion path.
- Volume re-measured: **6 default-level lines flat** at N = 50,000 / 200,000 /
  1,000,000, with zero progress lines at any N; a simulated 12.5-minute phase gives
  25 promoted lines whether it has 100 or 100,000 progress points. Bounded by
  elapsed time, not entries.
- Gates: `make lint` 0 issues; `make test` **421 passed - 9 skipped - 29
  packages**; `go vet -tags netgo ./jobqueue/ ./cmd/` clean.
- Red script hardened: jobs now go to a limit group capped at 0 so no child
  process exists to orphan (a previous run left 24 `sleep`s with ppid 1 on this
  shared host; now 0 before and after each of four runs), and its gate went from
  `n >= 1` to `n == d`, which was proven to reject a partial-promotion mutant that
  the old gate passed (1 vs 6).

### Known limitation - the interval's MAGNITUDE is not pinned

The implementor claimed the "far coarser than the sidecar" property was pinned
behaviourally by the 50,000-entry rebuild promoting nothing at the production
interval. **That is false, and measured to be false:** the reviewer set
`dbUpgradeLogIntervalDefault` to 2 s and the whole package still passed, then
bisected - 100 ms passes, 10 ms and 5 ms fail. So that test discriminates only
somewhere between 10 ms and 100 ms, two orders below the sidecar's 2 s and three
and a half below the shipped 30 s.

No new test is warranted: the property that matters - **time-bounded rather than
count-bounded** - is pinned by the rate-limit test, and the interval's magnitude
is a tuning knob. This is recorded so a later reader does not believe the value is
guarded when it is not.

### Non-blocking, carried forward

- `took` on the promoted line is unpinned; deleting it fails nothing.
  `bf53de0` pins its analogue by parsing `elapsed` and asserting it is above zero.
  One line in `TestReliable4LongDBUpgradeReportsProgress` would close it.
  `processed` carries the "visibly moves" guarantee and *is* pinned.
- `logProgress` mixes clocks: the rate limit reads `r.now()` while `took` reads
  `time.Since(r.phaseStartedAt)`, seeded from `time.Now()`. Identical in
  production; inconsistent only under an injected clock. Widening the seam would
  put it back into the sidecar path, so the narrow version is the right trade.
- The red script's gate counts the prefix `msg="database upgrade`, which also
  matches the info-only progress line. It works today only because the fixture's
  jobs carry no dep groups, so the rebuild processes 0 entries. **If anyone gives
  that fixture real dep groups, the `--debug` arm will legitimately outcount the
  default arm and a correct fix will read RED.** Counting only `lvl=warn` lines
  would make it robust.
- The info/warn rationale is stated twice, on the type doc and on `logProgress`.
- The final `commit database upgrade` phase still cannot heartbeat: it is the bolt
  commit, with no progress call reachable between `startPhase` and `finish`. It
  logs its start and a `took=` on completion. Historically this is *the* long quiet
  phase (`.docs/bugfixes/260708-5.md`, `260708-6.md`: "still take 6mins on a large
  database"), so if it recurs the follow-up is a `startPhase`-scoped ticker in the
  style of `bf53de0`'s `startRecoveryHeartbeat`.


### Item 3 red (proven RED at `8b9ba00`)

Measured with bbolt's built-in `db.bolt.Stats().TxN`, the same mechanism
`c96dcbf` used. A throwaway harness in package `jobqueue` opened a dev DB via
`initDB`, stored 5,000 live jobs through `db.storeNewJobs`, and took the `TxN`
delta across `db.recoverIncompleteJobs()`:

```
RED MEASUREMENT: recovering 5000 live jobs (got 5000 back)
  live-bucket decode cost 1 bolt read transaction(s)
  one transaction is held for the WHOLE decode, with mmaplock.RLock throughout
BUG REPRODUCED: the decode of 5000 jobs runs in 1 transaction; chunked at 1000
it would take 5, bounding the mmaplock hold
--- FAIL: TestZZRedRecoverDecodeTxCount (0.23s)
```

At prod's 150,472 jobs that single transaction is held for the ~37 s cold decode.
The harness was deleted after measuring; the regression test that replaces it is
part of the fix.

**A semantic question the fix must answer, not assume.** Chunking a read means
the decode is no longer one consistent snapshot: a job added between chunks could
appear in a later chunk. Today `recoverIncompleteJobs` runs *after* `serveClients`
has started, so concurrent `add`s are real, and a job that both the add path
enqueues and recovery recovers would be enqueued twice. `.docs/dep-granularity/`
section E1 later moves publication so nothing is served during recovery, which
removes the concurrency - but that spec has not been implemented yet, so this fix
cannot rely on it.


## Reordered 2026-08-26: the spec goes first, and three of these four items die with it

The operator's call, and the right one: do not spend review cycles on defects that
`.docs/dep-granularity/` removes. Reassessing each remaining item against the
implemented spec:

**Item 3 (chunk the live-bucket decode) - DEFERRED, probably moot.** Its entire
justification is the `mmaplock` hazard: one read transaction held for the ~37 s
decode blocks any concurrent write that must grow the bolt mapping, and that
writer holds `db.rwlock` so every other write queues behind it. Spec section E1
makes the manager externally invisible until recovery completes, so **there are no
concurrent client writes during the decode at all** - the spec says as much where
it requires tolerating a chunked decode ("nothing is served and there are no
concurrent writers"). With the hazard gone the chunking buys almost nothing.

Worse, the chunking actively *introduced* a correctness hole in the pre-E1 world,
which is what failed review: a job added, run and archived during the decode
window is picked up by a later chunk, is not in the queue so the queue-filter
misses it, and is re-enqueued as `ready` - a completed command queued to run twice,
against DEVELOPERS.md rule 1. Proven end to end (`after archive: complete=true
live=false inQueue=false` then `RESURRECTED: sub-queue ready`). The fix for it
(also dropping prior jobs whose live-bucket record has gone) is sound but exists
purely to guard a race E1 deletes. **Work reverted; tree back to `8b9ba00`.**
Revisit only if E1 does not land, and re-measure the hazard first.

**Item 4 (pin `max(1, dependencyResolutionChunkSize)`) - still relevant.** C1 keeps
the per-chunk transaction, so the guard and its unpinned-guarantee finding survive
the spec. Small; fold into the spec's phase 3 or do it after.

**Item 5 (`So()` inside a `pollUntil` condition) - subsumed.** It is in
`reliable4_dependency_tx_test.go`, and spec C2 rewrites three of that file's four
tests. The rewrite should carry the fix; check it did rather than doing it twice.

**Item 6 (`depGroupEverSeen` dead in production) - fully subsumed.** Spec A2
deletes `Dependencies.incompleteJobKeys` and the sentinel machinery, which is the
only thing that branch serves.

So the queue after the spec lands is item 4, plus verifying that C2's rewrite
picked up item 5. The red evidence above stays recorded either way.
