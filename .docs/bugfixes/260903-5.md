# Bugfixes 260903-5

RECORDED, NOT FIXED. A finding from adversarial probing of wr, filed as a
backlog item. Nothing on this branch changes any code.

**DATA LOSS, and it lives in the dependency.** The defect is in muxfys, not in
wr, but wr is the caller that exposes users to it, and the mitigation available
to wr changes where every user's caches live - so the decision is the repo
owner's, which is why this is filed rather than fixed.

## The mechanism

`muxfys.Unmount` (muxfys/v5@v5.0.0 muxfys.go:455) uploads and then deletes, and
the deletion does not ask whether the upload worked:

    uerr := fs.uploadCreated()        // muxfys.go:474; error recorded in err
    ...
    for _, remote := range fs.remotes // muxfys.go:485
        if remote.cacheIsTmp          // muxfys.go:486
            errd := remote.deleteCache() // muxfys.go:487

`deleteCache` is `os.RemoveAll(r.cacheDir)` (remote.go:474-478). For a WRITABLE
mount, that cache directory is the only copy of everything the job wrote: in
CacheData mode nothing reaches S3 until `uploadCreated` runs
(`fs.writeRemote.uploadFile` per created file, muxfys.go:535-547). So a failed
upload - expired credentials, a bucket policy change, a network partition, a
full remote - is followed immediately by the deletion of the output that failed
to upload. `Unmount` returns the upload error, so the caller is told the upload
failed; it is not told that the data is already gone.

`cacheIsTmp` is the switch: it is true only when muxfys chose the cache
directory itself, i.e. when `CacheData` was on and `CacheDir` was empty
(remote.go:186-195). An explicit `CacheDir` sets it false and the cache
survives - and an explicit `CacheDir` is exactly the option most users omit,
since muxfys picking a `.muxfys_cache*` dir for you is the documented default.

## What a user experiences

A job writes its output to a writable mount, the command succeeds, the upload at
unmount fails, and the output exists nowhere - not in S3, not on local disk. wr
reports an unmount/upload failure and (for a message containing "failed to
upload") releases the job to run again, so the work is redone; where the command
is not reproducible, the output is simply lost.

Reachable from both callers: `Job.Unmount` (jobqueue/job.go:1046 ->
`unmountAll`, job.go:1074) on the runner's path, and `wr mount`'s signal
handler (cmd/mount.go:265), which is the command wr's own help text tells users
to test their mount options with.

## Why this defeats a protection wr deliberately built

wr keeps muxfys's own cache directories out of cleanup on purpose:
`keptEntry` (jobqueue/workspace.go:890-895) protects any workspace entry with
the `muxfysCachePrefix`, and the comments on `keptDirs.protectCaches`
(workspace.go around 700-712) spell out why - those directories hold the job's
output until `Unmount` uploads it, and output deleted before upload is not
recoverable. That care is undone by the dependency deleting the same directory
itself, one line after recording that the upload failed.

## Evidence

Demonstrated by a probe with a real FUSE mount and a `RemoteAccessor` whose
`UploadFile` always fails: after `Unmount` returned the upload error, the cache
directory was gone. Re-verified here by reading muxfys v5.0.0 at the line
numbers above; the probe's own harness was not re-run.

## Options, for whoever picks this up

- Fix muxfys: skip `deleteCache` for a remote whose `uploadCreated` failed, or
  keep the cache and say where it is in the returned error. Correct, but a
  dependency release.
- Mitigate in wr: default a writable mount to an explicit `CacheDir`, so
  `cacheIsTmp` is false and the cache is never auto-deleted. This changes where
  caches live for every user of a writable mount, and it hands cleanup a
  directory it must then account for (see the keep-set records) - hence a
  decision for the repo owner, not a drive-by fix.
- Document it: at minimum, say in `wr add --mounts` help that a writable mount
  without an explicit `CacheDir` loses its output if the upload fails.
