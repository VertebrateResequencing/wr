- [x] Since master branch, an improvement was made to better explain real reason for a job exiting vs too much memory used. The feature was not supposed to stop the system increasing expected memory reservation on retries. However in this following test, it gets up to 3 attempts with no increase in the reserved memory so they all fail:

  wr manager start -s lsf

  printf '%s\n' 'python3 -c \"import time; x=bytearray(512*1024*1024); time.sleep(30)\"' | wr add --memory 16M --time 1m --override always --req_grp \"mem-underreserve-test-$(date +%s)\"

  wr status -I manually added
  [...]
  Previous problem: runner received a signal to stop; note: command used too much RAM
  Stats of previous attempt: { Exit code: -1; Peak memory: 543MB; Peak disk: 0MB; Wall time: 746.800492ms; CPU time: 281.929ms }

  - Cause: high-peak non-RAM failures kept the clearer primary Previous problem message but did not seed req-group RAM recommendations; normal retries still grew directly, while override-always jobs intentionally kept explicit user reservations.
  - Fix: persist RAM recommendation stats when a failed attempt exceeded its requested RAM while preserving the primary fail reason and preserving override-always semantics.
  - Coverage: added `TestDBHighPeakMemoryRecommendation` for high-peak non-RAM recommendation learning plus an explicit override-always guard; adjusted existing fixtures so disk/time and retry-modification tests do not accidentally trigger high-memory learning.
  - Verification: focused high-peak recommendation, memory attribution, status-details, broad bounded `go test ./jobqueue`, and `golangci-lint run` gates passed.
