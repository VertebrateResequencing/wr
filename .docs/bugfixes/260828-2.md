- [ ] BUG 4 (PRODUCT bug, found and reproduced during LAYER 6's review — the flaky-test fix models around it, so it must not be forgotten): a client reconnecting to a manager that is mid-`Stop` can hang for up to 60s, far past its own retry budget. Two causes. (1) `shutdown` (jobqueue/server.go:6052) calls `closeClientSubscriptions()` at :6102 BEFORE `close(s.stopClientHandling)` (:6103), `waitForClientHandling` (:6104), `time.Sleep(ShutdownSocketWait)` (:6105, default 50ms) and `s.sock.Close()` (:6107) — so for >=50ms every client subscription has been killed while the command port still accepts connections. `handleSubscribe` (serverCLI.go:690) / `registerClientSubscription` (server_subscription.go:444) have NO shutdown guard, so a subscribe arriving after the :6102 sweep repopulates `s.clientSubscriptions` with a `serverSubscription` nothing will ever `close()`, and the client long-polls a manager that is gone. (2) `reconnectOnce` -> `Client.reconnect(timeout)` -> `Connect` succeeds against the still-listening port, and `Connect` then widens the recv deadline to `requestTimeout(timeout)` >= `ClientMinRequestTimeout` = 60s (client.go:518, 3203-3208), discarding the cap `subscriptionReconnectTimeoutFor` (subscription.go:381) deliberately computed; since `reconnect` only checks `time.Now().After(retryEnd)` BETWEEN attempts (subscription.go:368), a single attempt can overrun the whole retry budget by up to 60s. User-visible: `wr add -w` / `AddAndWait` against a manager being stopped can hang far past `retryTime`. Likely the same family as item 10's "receive time out". Reviewer's evidence bounds it at >=3s against a 200ms budget (15x); the mechanism points at 60s.
  - Red evidence (at commit b0b9180 + the LAYER 6 fix, with only the dead-port redirect removed, 8 busy loops, `-count=6`): `--- FAIL: TestSubscriptionReconnectResync`, `subscription_test.go:1587 Expected: true / Actual: false` on `So(closed, ShouldBeTrue)` — the subscription did not close within 3 seconds.   - Red command (deterministic, no load needed, built on this branch): `cp $SP/zz_red_bug4_test.go jobqueue/zz_red_bug4_test.go && CGO_ENABLED=0 go test ./jobqueue/ -run 'TestRedBug4ShutdownWindowHang' -count=1 -v` where `SP=/tmp/claude-1000/-home-ubuntu-wr-clone2/5d7020f8-4042-4274-8df6-eefdd9469e3c/scratchpad`. It sets `serverConfig.Timings.ShutdownSocketWait = 2s` to widen the window in which subscriptions are dead but the command socket still listens, gives the subscription a 200ms retry budget, stops the manager, and asserts the subscription gives up within 1s.
  - **CORRECTION — that red command is NOT a valid discriminator, and must not be used as one.** It calls `server.Stop(ctx, true)` SYNCHRONOUSLY and then measures `time.Since(wentAway)`, so the elapsed figure includes `Stop`'s own duration, which the test itself inflates by setting `ShutdownSocketWait = 2s`. Verified by the orchestrator: it fails identically with and without the fix (`2.062253677s` at base vs `2.063484377s` with the fix applied). Instrumenting the poll loop showed the subscription itself had already given up at ~204ms in that run — the test was measuring the manager, not the client. The real 60s form was reproduced instead by instrumenting a baseline run, where a real client's budget runs while the manager finishes shutting down: `DBG client.reconnect ok after 7.46ms` / `DBG dialSub ok after 11.56ms` / `DBG subscribe req err after 1m0.012723686s: receive time out` / `EXP closed=true after 1m0.064282419s (retry budget 200ms; Stop returned at 2.05s)`. The permanent test runs `Stop` in a goroutine for exactly this reason. Original (misleading) evidence, kept for the record: `closed=true after 2.061261913s (retry budget 200ms)`, `Line 61: Expected '2.061261913s' to be less than '1s' (but it wasn't)!`, `--- FAIL: TestRedBug4ShutdownWindowHang (2.82s)`. So the subscription does eventually give up — but only when the manager's socket finally closes, i.e. it waits on the manager's shutdown schedule instead of its own retry budget, overshooting it by 10x here and by however long `ShutdownSocketWait` plus the rest of shutdown takes in reality. The reviewer that found this separately measured >=3s against a 200ms budget under load with default timings, and the `ClientMinRequestTimeout` mechanism (client.go:518, 3203-3208) bounds the worst case at 60s.
