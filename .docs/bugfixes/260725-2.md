# Bugfix checklist 260725-2 — reliable4 LSF-scale stall (rac rescan + false-lost)

Root-cause investigation: `.docs/reliable4/background.md`. Both bugs have
deterministic build-tagged reproducers (`jobqueue/reliable4_repro_test.go`,
run via `developers/wrdev.sh backlog-rescan-check` /
`runner-started-timeout-check`) that FAIL on pre-fix HEAD and must PASS after
the fix.

- [x] BUG 1 (rac backlog rescan): jobqueue/server.go buildSchedulerGroups runs the per-job scheduling work (prepareReadyJob) for EVERY ready item every rac cycle, including jobs whose limit group is already saturated and cannot be scheduled. At ~80k ready behind a 2000 limit this is ~40x wasted work per cycle, and the cycle runs back-to-back (recall loop), pinning the manager and starving the RPC/status paths (this is also the cause of the web/CLI status timeouts). Fix: make a rac cycle's per-job work bounded by the SCHEDULABLE count (~limit + siblings), NOT the ready backlog size, while preserving priority-fair selection within a limit group, reservability of jobs that ARE schedulable, and that limit-blocked jobs get scheduled once capacity frees. Gate: `developers/wrdev.sh backlog-rescan-check` (TestReliable4BacklogRescan) must pass; racScanWork <= limit+100 for a 50000-job backlog behind a 2000 limit — bound the actual work, do not weaken the counter or bound.
  - `jobqueue/server.go`: split `buildSchedulerGroups` into a cheap O(backlog) pre-pass (`snapshotReadyJobs`, single RLock, no DB/no writes) + a bounded expensive pass (`scheduleReadyJobsByPriority`) that sorts candidates highest-priority-first and only runs `prepareReadyJob` for jobs that win the shared per-limit-group budget (`seedLimitGroupBudgets`). `racScanWork` increment moved into `prepareReadyJob` so it faithfully counts only the expensive path. `ensureReserveGroup` keeps limit-blocked siblings reservable via a one-time reserve-group write (no-op on steady-state cycles). `countJobInGroup` refactored to share `ensureGroup` (no behaviour change; reliable3 tests still green).
  - Deferred (limit-blocked) jobs re-scheduled when capacity frees via existing `decrementGroupCount → hasSkippedScheduledGroups → triggerReadyAddedCallback` + CheckRunnerTime backstop; no stranding.
  - Result: `TestReliable4BacklogRescan` scanWork=2000 for a 50000 backlog (was 50000). New unit test `TestReliable4RacBoundedBySchedulable` (untagged, in `jobqueue/reliable4_rac_bound_test.go`) covers bounded work + priority-fairness + deferred scheduling. Reviewer PASS; lint/vet/build + focused Reliable/Limit/Schedul/Rac/SuspendResume/RunnerScheduling tests green; reliable3 invariants intact. Also lands the investigation (`.docs/reliable4/background.md`) and both reproducers (`jobqueue/reliable4_repro_test.go`, `developers/wrdev.sh backlog-rescan-check` + `runner-started-timeout-check`).

- [x] BUG 3 (transient Started() timeout kills a healthy command): jobqueue/client.go after exec calls c.Started(job, pid); if that outbound RPC errors (e.g. "receive time out" under server saturation) Execute KILLS the still-healthy command and returns "started running, but I killed it due to a jobqueue server error". The touch loop already tolerates touch errors and retries — Started() must do likewise. Fix: a transient failure of the post-exec Started() report must NOT kill a healthy running command; keep it running and re-establish contact in the background (the ongoing touch loop keeps the job alive). Preserve genuine kills (server-requested kill, resource/time/signal limits, real command failure) and avoid double-run hazards. Gate: `developers/wrdev.sh runner-started-timeout-check` (TestReliable4StartedTimeoutKillsHealthyCommand) must pass; the `sleep 1; echo ran > marker` command whose first Started() RPC fails once must still write its marker.
  - `jobqueue/client.go`: split `Started()` into `startedRequest` (build+lock the request once, mutating job.Pid under lock) + send. In `Execute`, classify the send error via `isDefinitiveStartReject` (ErrBadJob / ErrBadRequest / ErrMustReserve — the only definitive server rejections from handleStart→getij; ErrRecovering and all transport/timeout errors are treated as transient). Definitive reject → kill + behaviours (unchanged genuine termination). Transient → do NOT kill: log, record contact, and launch `retryStartReport`, a background goroutine that re-sends the SAME pre-built request every retryWait until it lands or is definitively rejected, stopped via `defer close(stopReporting)`. Re-sending the pre-built request (not re-calling Started) avoids re-mutating job.Pid and thus a data race with the resource monitor. The concurrent touch loop keeps the job's TTR alive meanwhile; applyJobStart is idempotent and markJobComplete's owner check prevents any double-run.
  - New untagged unit test `TestReliable4StartedReportFailure` (jobqueue/reliable4_started_test.go): transient first-jstart failure → command completes + marker written + Execute returns nil; definitive ErrBadJob → command killed + marker absent. Reviewer PASS; build/vet/lint clean; race run (Execute|Started|Touch) clean; focused Execute/Client/Touch/Lost/Recover/Archive/Reliable/Signal suite green; both reliable4 reproducers PASS. server.go untouched. Minor benign note: a genuine timeout whose reply was lost double-increments job.Attempts on retry (could bury one attempt early at the retry limit) — strictly better than destroying healthy work.
