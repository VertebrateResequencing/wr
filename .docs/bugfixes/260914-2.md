# Bugfixes 2026-09-14

fix-upload-dirs-world-readable

Split out of `fix-world-readable-manager-dir`, whose checklist
(`.docs/bugfixes/260914-1.md`) found these while triaging the other
`os.ModePerm` directory creations. Based on develop `d3bd4b8`.

- [x] The manager makes the directories holding uploaded files with
  `os.ModePerm`, so under a permissive umask any other local user can delete
  or replace an uploaded file, or rename a whole level of the tree aside and
  substitute their own.
    - 3 sites, all `jobqueue/server.go`, at their pre-change lines: `:4866`
      the parent of a client-chosen `savePath`, `:4887` `uploadDir` itself,
      `:4918` the md5-hashed directory under it.
    - `uploadFile`'s own doc comment already promises "Files stored will only
      be readable by the user that started the server", and the file is
      written `ownerReadWrite` (0600). The directories were the half of that
      promise nobody kept.
    - RED, measured under `umask 000` so the mode shown is the one the code
      asked for: every directory an upload creates comes out `0777`.

- [x] Copilot, PR #601 thread comment 4097527154: a file that already exists
  at a caller-named `savePath` keeps its mode. `openUploadDestination` opens
  it with `os.OpenFile(..., O_TRUNC, ownerReadWrite)`, and that mode only
  applies when `OpenFile` CREATES the file, so an upload over an existing 0644
  file wrote the new credentials into a file still readable by everyone.
    - RED: `CGO_ENABLED=0 go test -tags netgo -count=1 -run
      'TestServerUpload' ./jobqueue/`, new Convey "Uploading to a caller-named
      path that holds a world-readable file leaves it owner-only" in
      `TestServerUploadFile`, at `server_upload_test.go:114`:
      `Expected: fs.FileMode(384) Actual: fs.FileMode(420)`, that is 0600
      wanted, 0644 got. The test chmods the old file to 0644 after writing it,
      so the umask cannot make the starting mode 0600 and the test vacuous.
    - Fixed at `jobqueue/server.go:4902`: `file.Chmod(ownerReadWrite)` right
      after the open, closing the file and returning the error if it fails.
      It runs BEFORE `uploadFile`'s `io.Copy`, so nobody can open the file
      once the credentials are going in. It does NOT cut off a descriptor
      that was already open: Unix checks permissions only on open, so a
      reader who opened the file while it was 0644, before the upload or
      between the open and the chmod, still reads everything written after.
      Review proved it: a reader opened on a 0644 file, then
      `OpenFile(O_TRUNC)`, `Chmod(0600)` and a write of "secret", and the
      reader printed "secret". Closing that completely would mean writing to
      a temp file in the same directory and renaming it over `savePath`, so
      the upload lands in a new inode; that is not done here.
    - The md5-named path needs nothing. `os.CreateTemp` always makes a NEW
      file (`O_EXCL`) at 0600, `os.Rename` keeps that mode, and when
      `placeUploadedFile` finds the final path already there it keeps the
      file an earlier upload put there the same way.
    - Not fixed, same shape as the directory caveat below: the chmod governs
      only the file itself. An existing parent directory of `savePath` keeps
      whatever mode it had, since `MkdirAll` does not touch directories that
      exist, and anyone with write permission on it can still replace the
      file.

- [x] Found in review: `uploadFile` returned without closing the upload file
  when `io.Copy` failed, leaking the descriptor. It now closes it on that
  path, logging a close error as the success path does. No test: the only
  visible effect is a descriptor count, and nothing else in the package
  asserts on that.

## Why this is not academic

`--cloud_script` does NOT come through here, and an earlier draft of the
manager-dir checklist said it did. `cmd/add.go:712` binds it to
`cmdPostCreationScript` (`cmd/add.go:1104`), and what crosses the wire is the
script's CONTENT, not its path: `wr add` calls `jvj.Convert(jd)` at
`cmd/add.go:1258` in the CLIENT process, and `Convert` ->
`resolveErrorProneFields` -> `putCloudScript` (`jobqueue/serverREST.go:781`,
`:797-808`) reads the file off the SUBMITTER's disk with
`internal.PathToContent` and stores it in `Other["cloud_script"]`.
`putCloudScript` runs server-side only on the REST door, where the handler
calls `Convert` at `jobqueue/serverREST.go:1677`.

The only `add`-side caller of `jq.UploadFile` is `copyCloudConfigFile`
(`cmd/add.go:1315`), reached from `copyCloudConfigFiles` (`cmd/add.go:1071`
and `:1255`) and only when the manager is REMOTE - that is
`--cloud_config_files`. Which makes the exposure worse, not milder:
`cloudconfigfiles` defaults to `~/.s3cfg,~/.aws/credentials,~/.aws/config`
(`internal/config.go:146`), and the manager copies what it finds at those
uploaded paths to every cloud server it spawns. So another user of the
manager's machine could choose the cloud credentials somebody else's servers
run with.

## As fixed

- All 3 sites use `ownerOnlyDir` (`0o700`), a new constant beside the
  `ownerReadWrite = 0o600` it pairs with, so the directory is no wider than
  the files it exists to hold.
- The `//nolint:gosec` comments above the 2 changed `os.MkdirAll` calls STAY
  (now `jobqueue/server.go:4877` and `:4929`). They read as if they excused
  the 0777, and dropping them with it made `make lint` red with 2 G703 "path
  traversal via taint analysis", at `:4877` and `:4928` - they are about the
  client-chosen PATH, not the mode, and that is still client-chosen.
    - Reproducing that by TEXT rather than by line gives 3, not 2, and review
      hit exactly this. A third `//nolint:gosec` sits at `:4884`, on the
      `os.OpenFile(savePath, ...)` 6 lines below the first, with byte-identical
      comment text, so any search-and-delete takes it too; with all 3 gone lint
      reports `:4877`, `:4883` and `:4927`. That third one has nothing to do
      with this change - the mode it guards is `ownerReadWrite`, which was
      already right - and it is untouched here.
- `:4866` creates the parent of a path the CLIENT named, and a reader will
  notice that `job.Cwd` below is the same "the user named this path" shape,
  decided the other way. The difference is not who named the path, it is
  whether anything legitimate ever needs in. What goes in an upload directory
  is one 0600 file that only the manager's own uid can ever read, by that
  function's stated promise - the mode of the directory cannot widen access to
  it, only expose it to tampering, so 0700 costs nothing and closes something.
  What goes in `job.Cwd` is the user's own output, at whatever mode their
  umask says, and that directory is the one other people are meant to reach in
  a shared-pipeline deployment.
- This branch only governs directories wr MAKES. `os.MkdirAll` leaves an
  existing directory's mode alone, so an install that has uploaded anything
  before this release keeps its open tree; repairing that is
  `fix-existing-upload-tree-perms`, which is based on
  `fix-world-readable-manager-dir` rather than on this branch.

## Triage of the remaining `os.ModePerm` directory creations

The manager-dir checklist said "4 more" existed. That is an UNDERCOUNT: non-test
code has 7 besides `cmd/root.go`'s - the 3 fixed here, plus these 4, all left
alone.

- `jobqueue/client.go:2031`, `ensureCwdExists` creating `job.Cwd`. The one
  directory in the list that the USER named, not one wr owns, and creating it
  is wr standing in for the `mkdir -p` they would otherwise have run
  themselves - so it should have the mode their `mkdir -p` would have given
  it, which is what `os.ModePerm` and their umask produce. A shared pipeline
  directory that two colleagues both submit jobs into is a real deployment and
  0700 would break the second of them. The job's own data does NOT rely on
  this mode: when `cwd_matters` is false the job runs in a workspace under
  here that `mkWorkSpace` already creates 0700 (`workSpaceNamePerm`, pinned by
  `TestCreatedCwdDepthMatchesMkHashedDir`), so the private thing is already
  private. When `cwd_matters` IS true the job writes directly into the
  directory the user named, at the mode the user's umask implies, which is
  again what they would have got by making it themselves.
- `jobqueue/utils.go:984`, the hashed levels above a workspace
  (`<cwd>/jobqueue_cwd/4/1/c`). Same argument, one level down: these live
  inside `job.Cwd`, are shared between every job key using that cwd, and in a
  shared-cwd deployment between users. Tightening them would break exactly the
  case `job.Cwd` is left open for. It would not buy NOTHING, though, and an
  earlier draft overstated that twice over: renaming a directory needs write
  permission on its PARENT, so at 0777 another user could move a workspace
  aside and put their own there, whatever the workspace's own 0700 says - and
  they need not GUESS the fresh v4 UUID to do it, because the hashed levels
  are world-readable too, so they can watch for the name instead. What makes
  the decision stand is the other half: `job.Cwd` itself is umask-shaped, so
  anybody positioned to do this could move the whole tree anyway. The gap here
  is not closable without closing `job.Cwd`.
- `jobqueue/utils.go:1027` and `:1033`, the `cwd` and `tmp` dirs
  `mkCwdAndTmp` makes. These sit INSIDE the 0700 workspace, so no other user
  can reach them whatever their own mode says; changing them would be churn
  with no effect on what anybody can do.
