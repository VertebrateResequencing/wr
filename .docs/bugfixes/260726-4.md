# Bugfix checklist 260726-4 — recovered-running jobs never reclaimed when their runner never reconnects

- [x] Recovered running jobs whose runner never reconnects (e.g. the runner died/was bkilled during the manager downtime) are never confirmed dead and never reclaimed — they stay "lost" forever, blocking their slots. Root cause: confirmOrReleaseLostJob (jobqueue/server.go) treats a job as un-confirmable if it is in the recoveredRunningJobs map, and that map is populated at recovery (server.go:3628) but NEVER cleared, so the protection is permanent and also bypasses BOTH the SSH dead-check AND the 1h backstop.
  - Deliberate behaviour change: this REMOVES the permanent recovered-protection introduced by #550 (commit 142ecef, 2026-07-17). That protection was a workaround from BEFORE the both-pid liveness check existed — added to avoid discarding an unrecorded success from a recovered job whose command finished while the manager was down (then confirmJobDead only checked the command pid, so it would wrongly confirm such a job dead and re-run it). That concern is now handled generally by confirmJobDead's BOTH-pid check (commit 39f9afc, checklist 260726-3): it will not declare a job dead while its RUNNER pid is still alive. So the recovered special-case is now redundant AND is the bug. Recovered jobs are treated exactly like any other lost job; no grace window (not even for RunnerPid==0) — the clean removal was chosen.
  - Fix (jobqueue/server.go): (1) confirmOrReleaseLostJob — deleted the recoveredRunningJobs lookup and changed `confirmedDead := !d.killCalled && !recovered` to `confirmedDead := !d.killCalled`. (2) Removed the now-unused machinery entirely (grep-confirmed zero references): the `recoveredRunningJobs map[string]bool` field, the `rrjMu sync.RWMutex` field, its constructor init, and the population block in recoverRunningJob. (3) Updated stale comments: the ttrCallback comment (recovered jobs are now confirm-checked like any lost job, with confirmJobDead's both-pid liveness check preserving an unrecorded success from a still-alive runner) and the stopBackgroundStartupTasks lock-list comment (dropped rrjMu).

Its assertions are UNCHANGED and still pass (its runner is os.Getpid(), alive).
  - Tests (run in make test): TestReliable4RecoveredRunnerDead (jobqueue/reliable4_recovered_test.go) — primary regression: a reserved+Started job, DB-preserving restart (recovered as running), whose command pid AND runner pid are DEAD, is CONFIRMED DEAD and RECLAIMED (re-reservable) after its TTR lapses; verified RED pre-fix (recovered-protection leaves it stuck lost forever, never re-reservable) / GREEN post-fix.
