# Performance: jobqueue critical-path throughput (speed branch)

Root cause established by prior investigation: PR #503 ("Add job subscriptions")
added per-job hot-path processing that reduced BoltDB `bolt.Batch` write
coalescing under concurrency. Both master and speed do 2 logical bolt writes per
job (job-start state via `updateJobAfterChange`, job-complete via `archiveJob`);
each bbolt commit issues 2 `fdatasync` (data + meta). Under concurrency master
coalesces to ~2.0 fdatasync/job, speed to ~2.8 (+38%). On a fast SSD this is
~free; on a normal disk it scales wall-clock by ~the same %, matching the
reported 80s -> 108s. Single-runner is identical (4.01 fdatasync/job both),
confirming a coalescing (not extra-write) regression.

- [x] (Fix A) Make BoltDB MaxBatchDelay/MaxBatchSize configurable and raise defaults so per-job writes coalesce under concurrency, without losing crash-recovery durability or hurting low-concurrency latency unacceptably.
  - Made both knobs configurable end-to-end: `internal.Config.ManagerDBBatchDelay` (ms) + `ManagerDBBatchSize` (`default:"0"` => use wr default; auto-wired as `WR_MANAGERDBBATCHDELAY`/`WR_MANAGERDBBATCHSIZE` and documented in `cmd/conf.go`) -> `cmd/manager.go` sets `jobqueue.ServerConfig.Timings.DBBatchDelay`/`DBBatchSize` -> `ServerTimings.withDefaults()` defaults them (new package vars `ServerDBBatchDelay`/`ServerDBBatchSize`) -> `Serve()` calls new `db.setBatchTuning()` to apply `db.bolt.MaxBatchDelay`/`MaxBatchSize` to the live DB (read-only/backup opens untouched).
  - Durability UNCHANGED: only MaxBatchDelay/MaxBatchSize are set; no NoSync/NoFreelistSync. `db.Batch` still commits via `db.Update` which fsyncs (2 fdatasync/commit). Verified in bbolt v1.4.3 source (`tx.write()`/`writeMeta()` each fdatasync; widening the window cannot drop a sync).
  - Effective default RAISED to 25ms (size 10000). Real-workload measurement (wr binary, local scheduler, 4 concurrent runner processes, 3000 echo jobs, fdatasync counted via strace) showed 10ms -> 8889 fdatasync (2.96/job) vs 30ms -> 6043 (2.01/job): a wider window DOES recover coalescing on the real workload because the two per-job writes (job-start + completion) are spaced apart by runner round-trips. (My in-process `BenchmarkArchiveJobs` could not see this: its 64 goroutines hammer archiveJob with no inter-arrival spacing, so coalescing is already saturated at 10ms there; and `TxStats.Write` is page-writes, not commit count, so it is not the coalescing signal — fdatasync count is.) 25ms chosen as a balance: most of the coalescing gain with less low-concurrency latency penalty than larger values; operators can override via WR_MANAGERDBBATCHDELAY (including back to 10ms). `cmd/conf.go` documents the 25ms default and prominent slow-storage (NFS/Lustre) guidance.
  - Tests: extended `TestServerTimingsWithDefaults` (defaulting references `ServerDBBatchDelay`/`ServerDBBatchSize` symbolically + positive-preserved); added `TestDBBatchTuning` (a freshly `initDB`-opened DB still shows bbolt's raw open defaults 10ms/1000 — the 25ms package default is applied only by `Serve`; `setBatchTuning` applies positive values and ignores non-positive). No failing-test-first (perf/config knob); existing behavioural persistence/completion tests unchanged and still pass.

- [x] (Fix B) Take the per-job "started" DB write off the synchronous hot path while GUARANTEEING: after a manager crash + restart, a job whose command was already started (a) is never started again if it is still running, (b) is still known to the manager, and (c) is still guaranteed to run at least once.
  - Finding: the start-write (`updateJobAfterChange` from `handleStart`) was ALREADY async (off the runner's synchronous path) and is REQUIRED for the guarantee (recovery puts `State==Running` jobs on the RUN queue, not re-run). The remaining cost is that it still consumes a per-job BoltDB commit. So Fix B = make that commit CANCELLABLE/coalesced for short jobs, without widening the crash window.
  - Implemented: `handleStart` -> new `(*db).updateJobAfterStart` records the encoded running-state in a `pendingStartWrites` map (guarded by `startWriteMu`) + signals a single background flusher started in `initDB`. The flusher coalesces all pending entries into ONE `db.bolt.Update` on a debounce bounded by a single non-resetting timer = bbolt's MaxBatchDelay snapshot (so the start->durable window is <= the previous async-Batch window, never wider). `archiveJob`/`updateJobAfterExit`/`updateJobAfterChange` call `cancelPendingStartWrite(key)` (a short job archived before its flush incurs NO start-commit). The live-bucket `Get(key)==nil -> skip` guard is retained as the resurrection safety net. `close()` stops+flushes pending entries (synchronous Update to the primary DB) before closing bolt, so a job still running at clean shutdown is durable for recovery.
  - Guarantees (reviewer-verified by code trace): G1 cancellation only happens on transitions structurally impossible for a still-running job (suspend/resume/kick require non-run queue states; archive/exit only after stop) and each writes a newer authoritative state; window <= prior; close() flush ordering correct (no deadlock — releases db lock while waiting on flusher); recovery DECISION logic unchanged. G2 jobs still in live bucket from add time. G3 never-started incomplete jobs still recovered runnable.
  - Tests (behavioural): `TestDBStartWriteRecovery` (started job recovers as RUNNING w/ Pid/Host => not re-run; never-started recovers runnable), `TestDBShortJobNotResurrected` (deferred start + archive => archived, absent from live bucket), `TestDBStartWriteCommitCoalescing` (200 short jobs => 0 start-commits), `TestDBStartWriteConcurrency` (16 workers, 400 short + 100 running; race target). Added `BenchmarkShortJobStartArchive` (~0.002 extra bolt_writes/job vs archive-only => redundant start-commit eliminated for short jobs).
  - Gates: `make lint` clean; `make test` PASS (~67s); `make race` PASS (full jobqueue -race ~391s, zero data races). Reviewer PASS (max-rigour crash-recovery review).
- [x] (Exploration) Reduce hot-path CPU/allocations in job-key generation. Profiling the add/update/archive benchmarks showed `Job.Key()` (uncached, 3+ `fmt.Sprintf`) and `byteKey` (`fmt.Sprintf("%016x%016x")`) are hot (byteKey ~33 calls/job in the benchmark; on add/update/archive/changed-callback paths) and a notable share of allocations. Replace the `fmt.Sprintf` key building with direct byte/hex construction, keeping the produced key VALUES byte-identical (they are BoltDB and map keys). Measurable via `make bench`.
  - `byteKey` (utils.go) now uses `newHexKey(l,h)` (two uint64 big-endian into [16]byte + `hex.EncodeToString`) instead of `fmt.Sprintf("%016x%016x")`; `Job.Key()` (job.go) uses a pre-Grown `strings.Builder`; `JobEssence.Key()` uses a preallocated byte append; `generateLookupKey` (db.go) uses one preallocated buffer. Same fields/order/delimiters throughout (no key DEPENDENCY changed, only HOW built).
  - Byte-identity is the hard constraint (keys are BoltDB/lookup/map keys). New test `TestKeyByteIdentity` (job_test.go) keeps the old `fmt` expressions inline as the ORACLE and asserts equality across 169 hash pairs (incl. 0, leading-zero halves, math.MaxUint64), all `Job.Key()` branches, and `JobEssence.Key()`. The pre-existing golden-hex `TestJob` assertions still pass (strongest regression net). Reviewer independently confirmed `farm.Hash128` return order and the big-endian/`%016x` equivalence.
  - Win (make bench, allocs/op, reviewer-measured baseline vs new): AddJobs -9.1%, UpdateJobState -7.0%, ArchiveJobs -2.7% (ns/op also down 2.5-15%). No caching added to Job (codec/copylock risk); pure computation cheapening.
  - Gates: `make lint` clean; `make test` PASS; `make race` PASS. Reviewer PASS.
  - Limit assessment: after these changes the per-job durable-write cost is dominated by BoltDB commit machinery + the job encoding (~15% CPU) + the unavoidable fsync — i.e. near the practical floor for a single-writer embedded DB with the coalescing now tuned. Further large wins would require structural changes (smaller persisted running-state record to cut encoding, or a different storage engine) beyond this performance pass.
