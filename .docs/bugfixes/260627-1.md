# Performance: jobqueue critical-path throughput (speed branch)

Root cause established by prior investigation: PR #503 ("Add job subscriptions")
added per-job hot-path processing that reduced BoltDB `bolt.Batch` write
coalescing under concurrency. Both master and speed do 2 logical bolt writes per
job (job-start state via `updateJobAfterChange`, job-complete via `archiveJob`);
each bbolt commit issues 2 `fdatasync` (data + meta). Under concurrency master
coalesces to ~2.0 fdatasync/job, speed to ~2.8 (+38%). On a fast SSD this is
~free; on a normal disk it scales wall-clock by ~the same %, matching the
reported 80s -> 108s. Single-runner is identical (4.01 fdatasync/job both),
confirming a coalescing (not extra-write) regression.

  ### ROOT CAUSE FOUND (2026-06-27, investigating ON the farm node `farm22-wrstat01`)

  **The +18ms/job is the RUNNER doing a per-job whole-process-table scan to sum
  child-process memory, via `gopsutil`'s `Process.Children()`. #503 bumped
  `gopsutil` v3 -> v4, which reimplemented `Children()` from a single `pgrep`
  fork into an in-process `filepath.Glob("/proc/[0-9]*/stat")` + `os.ReadFile`
  of EVERY process's stat file. On this busy farm node (thousands of entries in
  `/proc`) the v4 method is ~2x slower, and it runs per job (recursively),
  so it costs ~+18ms/job here. On a sparse-/proc VM it is cheap — exactly the
  reported "environment-specific" behaviour, and why a remote agent on a quiet
  box could not see it.**

  #### How it was localised (tooling notes for this machine)
  - **`ptrace_scope = 3` on this node — `strace`/`ltrace`/`gdb` CANNOT attach at
    all** (any ptrace is denied). Use the Go execution tracer instead.
  - **Daemonised managers DROP `WR_PPROF_ADDR`** (the daemonize path rebuilds the
    env from config via `config.ToEnv()`, which doesn't carry it). Run the
    manager in the FOREGROUND (`manager start -f`) for any pprof/trace work.
  - Forcing exactly 1 runner: `manager start --max_cores 1` (the default is
    `--max_cores=NumCPU`, i.e. 8 runners on this 8-core node — the old
    `--cpus=nproc` trick also yields 1 runner but `--max_cores 1` is explicit;
    runner count was verified by `pgrep`-counting during the run).
  - Captured a Go execution trace of the foreground MANAGER via
    `/debug/pprof/trace` and broke it down with `go tool trace -pprof=syscall|net|sync|sched`.
    Result: **the manager is ~99% idle** — 17.9s of an 18s window blocked in
    `FD.Read` waiting for the next request (`serveClients`/`receiveClientMessage`),
    only 476ms in syscalls (mostly normal `Fdatasync` ~1.5ms/job), 32ms
    scheduler-wait. So the time is NOT manager-side.
  - Instrumented the RUNNER (temp `runtime/trace` + per-phase timers gated by env;
    in `.tmp/agent/{speed,master}-instr` worktrees) and forced 1 runner. Note
    `exec.Command` runners get stdout/stderr = /dev/null, so log timing to a FILE.
    Per-phase result (1 runner, 200 echo jobs):

    | phase | master (v3) | speed (v4) | Δ |
    |---|---|---|---|
    | Reserve (one pure RPC round-trip) | 0.41 ms | 0.46 ms | ~0 |
    | **Execute** | **53.5 ms** | **74.2 ms** | **+20.7 ms** |
    | per job total | ~54 ms | ~75 ms | +21 ms |

    The pure RPC round-trip is identical, so the transport is not the cause.
    The entire regression is inside `Client.Execute`.
  - Diffing the runner trace `-pprof=syscall` between master and speed pinpointed
    it: master `currentMemory -> gopsutil/process.Children -> CallPgrepWithContext`
    (one `pgrep` fork, 2.14s/200 jobs); speed `currentMemory -> sumChildrenMemory
    -> gopsutil/v4/process.Children -> path/filepath.Glob` over `/proc` +
    `os.ReadFile` of every `/proc/<pid>/stat` (4.35s/200 jobs). v4 source:
    `ChildrenWithContext` = `filepath.Glob("/proc/[0-9]*/stat")` then read+parse
    every stat for `ppid==pid`, then `NewProcess` per child — done RECURSIVELY by
    `currentMemory`/`sumChildrenMemory` (utils.go:249/298), so ~3 full `/proc`
    scans per echo job (runner -> bash -> echo).
  - Per-job hot call site: `client.go:1879` `currentMemory(os.Getpid())` — run
    once per job in `Execute` to add the runner's own footprint to peak RAM. It
    recurses into ALL the runner's descendants (which also includes the job
    command, already tracked separately by the 1-second `resourceTicker` at
    client.go:1785 on `job.Pid`).

  #### RULED OUT this session (with the test that did it)
  - **Nagle / `TCP_NODELAY`.** The new `internal/mangostlstcp` transport never
    calls `SetNoDelay` (its `OptionNoDelay` handler is a no-op; `GetOption`
    falsely returns true) whereas the old `go-mangos` tlstcp did
    `conn.SetNoDelay(v)`. Looked like a smoking gun, BUT adding `SetNoDelay(true)`
    to both dial+accept in the new transport changed nothing: 76.1 vs 77.2 ms/job
    (master 55.6). So Nagle is NOT the cause (consistent with the prior
    "ping is fast on both boxes" finding). The missing `SetNoDelay` is still a
    latent correctness/quality bug worth fixing separately, just not THIS one.

  #### Confirmation (decisive)
  Neutralising `sumChildrenMemory` (env-gated early `return 0, nil` in the speed
  worktree) — i.e. removing the gopsutil `Children()` scan — dropped speed from
  **76.3 -> 42.9 ms/job** (execute 73.6 -> 41.0 ms). That -33 ms/job both erases
  the +21 ms regression vs master AND beats master (whose v3 `pgrep` scan still
  costs ~13-17 ms/job on this busy node). So the process-tree memory walk is
  conclusively the cost, and the v3->v4 change is the regression.

  #### Fixes considered and MEASURED (all 1 runner, 200 echo jobs; master=56ms)
  - **(rejected) single-pass /proc walk** replacing the recursive gopsutil
    `Children()`: prototyped (`currentMemoryFastTMP` in the worktree). Result
    **78.6 ms/job — NO improvement.** Why: the recursion's repeated scans hit the
    warm page cache, so the cost is essentially ONE `/proc` enumeration, and a Go
    `filepath.Glob`+`os.ReadFile`-per-stat enumeration of this node's ~370
    processes is itself the ~34ms; it is ~2x slower than v3's single `pgrep`
    (C). So reducing scan COUNT does not help; only avoiding the scan or using
    pgrep does. (Reverting gopsutil to v3 would restore ~56ms = master, but is a
    6-file dep change and still pays the scan.)
  - **(CHOSEN, VALIDATED) own-PSS-only at `client.go:1879`.** Realisation from
    reading the accounting: by line 1879 the job command has ALREADY exited
    (`cmd.Wait()` at 1838) and its peak RSS is ALREADY folded into `peakmem` via
    `cmd.ProcessState.SysUsage().Maxrss` (rusage, line ~1858) — with NO /proc
    scan. So `currentMemory(os.Getpid())` at 1879 scans all of /proc to sum the
    runner's *children*, but the only child (the job command) is gone — the scan
    finds nothing useful yet costs a full enumeration. The comment's intent
    ("include our own memory usage") is the RUNNER's own footprint. Fix:
    replace `currentMemory(os.Getpid())` with the runner's own PSS only
    (`scanSmapsPss(os.Getpid())` -> MB). **Measured: 45.4 ms/job — recovers the
    regression AND beats master** (master still pays a pgrep scan here).
    - Leave the 1-second `resourceTicker` call `currentMemory(job.Pid)`
      (client.go:1785) UNCHANGED: while the cmd runs, its tree IS alive and the
      child sum is needed for live over-RAM kill decisions; for sub-second echo
      jobs that ticker never fires, so it is not on the hot path. (Long-running
      jobs still pay the v4 scan once per second — a minor residual; the reported
      regression is the `wr add` of many trivial jobs, which this fix resolves.)
    - Correctness to verify in review: the only behaviour change is that any
      OTHER still-alive runner child at 1879 (e.g. a lingering mount helper) is
      no longer added to peakmem; the job command itself is unaffected (covered
      by Maxrss). Edge-case, typically negligible.
    - This is a pure perf change with no observable behaviour change for normal
      jobs (peak RAM stays correct via Maxrss), so there is no clean
      failing-test-first; follow the precedent of the perf items above

## FOLLOW-UP PERF (2026-06-27): further runner speed-ups after the memory fix

The user asked: even after the memory fix, most per-job time is still "wasted in
the runner" — find more wins. Re-profiled the FIXED runner (1 runner, 250 echo
jobs, `farm22-wrstat01`, cwd on NFS). Remaining ~42ms/job execute is dominated by
NFS metadata round-trips in the per-job working-directory lifecycle:
- `resolveWorkingDir`->`mkHashedDir` ~11.7ms (Mkdirat + the `.hold` file).
- cleanup (`Behaviours.Trigger`->`cleanup`) ~10.6ms (RemoveAll + `rmEmptyDirs`).
(Net-blocking is just idle connection waits; RPC round-trip is ~0.4ms. Manager idle.)

Root inefficiency: per job, `mkHashedDir` creates a hashed prefix `wr_cwd/c0/c1/c2`,
drops a `.hold` file, makes a unique leaf + `cwd`/`tmp`; cleanup removes the leaf
AND walks up removing the now-empty prefix dirs (`rmEmptyParentDirs`), which the
NEXT job recreates. The `.hold` file exists ONLY to stop a concurrent
`rmEmptyParentDirs` removing a prefix dir mid-creation. So the prefix
create/remove churn + the `.hold` create/remove are pure per-job NFS round-trips.
