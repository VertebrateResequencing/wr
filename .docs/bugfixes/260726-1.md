- [x] reliable4 DB-backup-freeze job churn: the manager's periodic full-file DB backup (jobqueue/db.go db.backupToBackupFile -> tx.CopyFile) writes the whole multi-GB DB to the backup file in one burst; on a shared filesystem this saturates writeback so a concurrent foreground write-transaction's fdatasync stalls, and because all archive/touch commits serialise behind BoltDB's single writer the manager freezes for ~the copy duration (up to ~108s in production on a 6GB DB). Jobs whose archive/touch isn't serviced within the 60s TTR are falsely marked lost -> confirmed dead -> rerun -> real archive rejected as "bad job" -> churn, though the commands cannot fail. Fix: pace the backup copy (force writeback every 8MB) so it never accumulates a large dirty-page backlog; Linux uses pipelined sync_file_range, other platforms fall back to fsync, with a final fsync for durability. Make this the default (drop the temporary WR_EXP_* investigation knobs).
