  - Fixed with a sentinel. There is now one command form, `processCheckCommand` (jobqueue/scheduler/scheduler.go): `echo wr-ps-batch $$; ps -o pid=,stat= -p <pid1>,$$,<pid2>,... 2>/dev/null || test $? -eq 1`. A shell's answer (a `wr-ps-batch <shellpid>` line) is trusted only if ps lists that shell pid as live and every line is `<pid> <stat>` for a requested pid. Otherwise nothing is confirmed and nothing is retried. A failed or timed-out command also confirms nothing, and is no longer retried per pid.
  - Forced commands: `$$` goes after the first real pid, so the cmd/conf.go examples, which take the FIRST `-p <pid>`, still check pid1, and the command starts with `echo`, so the kill-branching example takes its ps branch. Their answer has no marker. wr reads it for pid1 exactly as before (empty is dead, a stat is alive), then asks about each other pid with the same command, one round trip each. The trade-off: a forced command prints only the bare stat of its own `ps -o stat=`, so there is no room for a sentinel, and that path still relies on the node's ps printing nothing only for a missing pid. The fixed `-o stat=` it runs is standard. The CONTRACT WARNING, the cmd/conf.go privatekeypath docs and the CHANGELOG say so. The old `ps -o stat= -p <pid> ...` string is no longer sent. `ProcessNotRunningOnHost` uses the same path with one pid, so a forced command still takes one round trip there.
