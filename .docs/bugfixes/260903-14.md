# Bugfixes 260903-14

Branch `fix-same-key-workspace-identity`: a job's `on_exit cleanup` can delete
another live run's FUSE-mounted remote data, and its un-uploaded writable-mount
output, silently, returning `nil`.

- [x] `Job.Key()` treats as one job configurations whose live mounts and
  un-uploaded output are in different places, so the keep set a finished run
  computes from its own `MountConfigs` does not name what a live run of the same
  key has on disk - and the finished run's `ActualCwd` can name the live run's
  workspace byte for byte, because the leaf name `os.MkdirTemp` gave one run is
  free to be handed to the next run of that key once the first run's workspace
  has gone.

  Fixed by giving the workspace a name that is never reused: `mkHashedDir` mints
  a v4 UUID per run instead of asking `os.MkdirTemp` to name the leaf, and
  `relIsJobCreatedCwd` recognises the new shape. Files touched:
  `jobqueue/utils.go` (the mint, `isJobCreatedWorkSpaceName` and
  `isCanonicalV4UUID` replacing `isMkTempName`, and the comments that named the
  old shape), `jobqueue/workspace_name_test.go` (new),
  `jobqueue/workspace_test.go` (`TestRelIsJobCreatedCwd`'s three new arms, plus
  the `nonempty` fixture change kept from `5afb3a21`), and
  `.docs/cwd_matters_cleanup/readme.md`. Every other file this branch had
  touched is back to `origin/develop`'s content byte for byte.

## The chain, verified at file:line

1. `MountConfigs.Key()` (jobqueue/mount.go:248) substitutes `defaultMountDir`
   (`"mnt"`, mount.go:41) for an empty `MountConfig.Mount` (mount.go:255-257).
2. `Job.mountBaseDirs` (jobqueue/job.go:852-868) sets `defaultMount = cwd` - the
   working directory itself - for a job wr created a working directory for, and
   `resolveMountPoint` (job.go:127-137) returns that `defaultMount` unchanged for
   an empty `Mount`. So `wr add --mounts cw:bucket/path`, which leaves `Mount`
   empty (`mountParseSimple`, cmd/mount.go:451-461), mounts ON the working
   directory, while `--mount_json '[{"Mount":"mnt",...}]'` mounts at
   `<cwd>/mnt` - and the two are one job by key.
3. `MountConfig.writeTargetsKey` (mount.go:294-306) reads only `Target.Profile`
   and `Target.Path`. Nothing that decides where a cache lands is in the key:
   not `MountConfig.CacheBase`, not `Target.CacheDir`, not `Target.Cache`, not
   `Target.Write`.
4. The workspace leaf name was `os.MkdirTemp(dir, leaf)` (utils.go:729 at the
   branch point), which only ever avoided a name that existed WHEN IT LOOKED. So
   the name one run's workspace had was free to be handed to the next run of
   that key once that workspace was gone. Dedup is per-manager, so two managers
   sharing a filesystem can each hold a job with that key but independently
   spelled mounts.

The stale run's `ActualCwd` then names the live run's workspace byte for byte,
`createdCwdRel` (workspace.go:236-251 at the branch point) is satisfied because
the path really is one this key builds, and the sweep reads through the live
mount: `os.Root.RemoveAll` is bounded by `RESOLVE_BENEATH`, which does not imply
`RESOLVE_NO_XDEV`.

The four rows hit four distinct keep-set rules: `keptDirs.wholeActualCwd`,
`wholeWorkSpace`, `workSpaceEntries` via the separate `removeTmpDir` deletion,
and `muxfysNamesWorkSpaceEntry`.

The `"" -> "mnt"` normalisation dates to `8eead7ad` (2017-06-12, "Job mounts are
now part of the unique key"); `902eccf0` only renamed the literal to a const. It
predates the keep set by years and is only now load-bearing.

## Not fixed in `Job.Key()`

Two reasons, both checked:

- The key IS the persisted database key. `db.go` uses `job.Key()` as the BoltDB
  key in `bucketJobsLive` and `bucketJobsComplete` (db.go:1440, 2233, 2434) and
  as the value of every lookup bucket (db.go:316, 2773). Changing the algorithm
  orphans every existing record and changes dedup for jobs already in flight.
- Semantically the key is arguably right: two jobs with the same command and cwd
  but different cache locations are the same unit of work for scheduling and
  dedup. The defect is that cleanup assumes key equality implies on-disk layout
  equality.

## The fix: a workspace name that is never reused

`Job.Key()` is left alone, and the key-blindness in point 3 above is unchanged.
What changes is that wr can no longer hand two runs of one key the same
workspace path, which is the only route from that key-blindness to a deletion.

`mkHashedDir`'s own comment always said the leaf must be unique because several
users or queues may run the same command. `os.MkdirTemp` gave uniqueness at one
INSTANT; what is needed is uniqueness FOR ALL TIME.

- **The mint** (`jobqueue/utils.go`, in `mkHashedDir`, signature unchanged at
  `(cwd, tmpDir string, err error)`): a fresh v4 UUID from
  `github.com/gofrs/uuid/v5` - the repo's direct uuid dependency and
  `Job.ReservedBy`'s type - appended to the key tail after a `-`, and the
  directory made with the package's `mkdirManaged` at `0o700`, which is the
  permission `os.MkdirTemp` used.

      u, err := uuid.NewV4()
      ...
      dir = filepath.Join(dir, leaf+workSpaceNameSep+u.String())
      if err = mkdirManaged(dir, workSpaceNamePerm); err != nil {

  `uuid.NewV4`'s randomness is `crypto/rand.Reader`
  (`gofrs/uuid/v5@v5.4.0/generator.go:26,185`), so the 122 free bits are
  cryptographic, not `math/rand`.

- **The name shape**: `<key[3:]>-<canonical lowercase v4 UUID>`, eg.
  `695a4b69e0fa8e56e7ffaae15ad97-c4c10a8a-7dae-47a1-9793-3ea3873f1856`. The `-`
  separator is not a digit, so it also tells the minted name apart from the
  digits-only one an older wr left, with no ambiguity about where the prefix
  ends.

- **The validator** (`isJobCreatedWorkSpaceName`, replacing `isMkTempName`,
  called from `relIsJobCreatedCwd`'s tail) accepts two shapes and nothing else:

  1. `<prefix>-<uuid>`, where the UUID round-trips through
     `uuid.FromString` to a byte-identical string (which pins canonical
     lowercase, since `FromString` also takes braced, `urn:uuid:` and hyphenless
     forms in either case), with `u.Version() == uuid.V4` and
     `u.Variant() == uuid.VariantRFC4122`.
  2. `<prefix><digits>`, at most 20 of them.

## What the validator now accepts and rejects

**Newly accepted:** the minted shape. Nothing else.

**Newly rejected:** an arbitrarily long run of digits. `os.MkdirTemp`'s suffix
has always been the decimal form of an unsigned integer no wider than 64 bits -
on go1.26.3 it is `strconv.FormatUint(uint64(uint32(runtime_rand())), 10)`,
`/opt/go/src/os/tempfile.go:22-24` - so 20 digits is a ceiling no Go release
could have exceeded, and a longer run was never producible. That is the only
tightening of the legacy arm, and it is a small one; the honest summary is that
the check is **not** a superset-free tightening. It accepts strictly more than
it did, because of the decision below.

**Deliberately not tightened, and what that costs.** No minimum length and no
value ceiling on the legacy digits, because either would strand real
pre-upgrade workspaces: `nextRandom` returns the decimal form of a `uint32`, so
a value below 10^8 is a name of 8 digits or fewer, which is 2.3% of the space.

**What it still does not stop, deliberately.** A Job's own `Cmd` can read the
name wr gave it, so it can fabricate a sibling directory of either accepted
shape. That was true of the digits shape and is true of the UUID shape
(`uuidgen` is one command). It is not what this check defends: a fabricated
directory only causes loss if a STALE run's stored `ActualCwd` names it, and wr
only ever stores a name it minted itself. The gain over "some digits" is against
a user's own directory accidentally satisfying the shape, not against a Cmd
choosing to.

## Pre-upgrade workspaces: accepted, and why

A workspace an older wr created is on disk with a digits-only leaf and will
survive an upgrade. The legacy arm is kept so cleanup can still reach it.

**The cost of keeping it:** the digits shape stays acceptable, so the validator
is not the tightening it could have been, and two workspaces of one key that
were BOTH created before the upgrade retain the old exposure between them until
each has been swept once.

**The cost of dropping it:** every workspace made before the upgrade would be
unrecognised and so uncleanable for ever, stranding the real job output inside
it. Measured that this is what happens: mutation M4 below.

Keeping it does not reopen anything for a post-upgrade run. Every name wr mints
from now on is UUID-shaped, so a digits-shaped stale `ActualCwd` can only
coincide with a workspace created before the upgrade; that pair's exposure is
exactly the pre-existing one, unchanged.

## The testable invariant: the user's reasoning, tested

The design's author rejected this approach partly on the grounds that it makes
the collision "improbable rather than detectable, and untestable at a supported
boundary". Both halves were checked rather than accepted.

**Assertable at a supported boundary: YES.** The workspace paths wr hands out
are `Job.ActualCwd` - where the user's Cmd runs, what `wr status` reports, and
what cleanup deletes. `jobqueue/workspace_name_test.go`,
`TestWorkSpaceNameNeverRecurs`, encodes exactly the production sequence: build a
workspace for a key with the real `mkHashedDir`, remove it the way cleanup does
(`snap.cleanupWorkSpace()` then `snap.removeTmpDir()`, both asserted nil and the
workspace asserted gone), build another for a different `*Job` with the same
`Key()`, and assert the paths differ. Then the consequence: the stale snapshot's
cleanup runs again and the live run's planted file, working directory, tmp dir
and workspace all survive.

**A red command for the bug: NO, and this is the part of the reasoning that
does not hold.** The test passes on the unfixed code too, so it is not a
reproduction of the bug; it is a regression guard on the fix. Two measurements
say so:

- `os.MkdirTemp` draws a FRESH suffix per call rather than recycling a freed
  name. 20000 rounds of create/populate/remove/recreate through
  `os.MkdirTemp` with one fixed prefix, run outside the repo on go1.26.3:

      rounds=20000 reused=0
      example name: 6789abcdef0123456789abcdef012342696109173

  So the branch's earlier framing - "`os.MkdirTemp` hands the leaf name a
  finished run's workspace had to the next run of that key" - was wrong. The
  old exposure was a 2^-32 collision, not deterministic recycling.
- Mutation M1b below reverts the mint to `os.MkdirTemp(dir, leaf)` - the exact
  pre-fix naming - and the ENTIRE workspace and cleanup suite stays GREEN,
  `TestWorkSpaceNameNeverRecurs` included.

So the fix moves the odds from 2^-32 to 2^-122, and no sampling test separates
those. The previous agent was WRONG that the invariant is untestable at a
supported boundary, and RIGHT in kind that the guarantee is structural rather
than detected - but wrong in weight: it is 90 further bits, and the guarantee
lives in the name space, not in a sample. What makes the test a live guard
rather than a tautology is mutation M1, which makes the mint recur and reddens
it.

## Why not the alternatives

- **Not in `Job.Key()`**: see above. It is the persisted db key.
- **Not a per-run `.run_token` identity file** written into each workspace and
  checked in `prove()`, which is what this branch built first. Rejected by the
  user: wr's benefit is that it does not scatter small state files through the
  user's filesystem, and that put one in every working directory wr makes. It
  also detects the collision where a never-reused name prevents it, and the
  detection is only as good as the record's survival of every sweep - including
  its own removal, which needed a two-step unlink-and-restore that could not be
  atomic. Recorded in `.docs/cwd_matters_cleanup/readme.md` so nobody reinvents
  it. Its one measured advantage over what shipped: under a hand-forced
  collision it refused all four probe rows, where the shipped design leaves
  rows 2-4 lost. Under a collision wr can actually produce, both are moot.
- **Not the `.hold` file** that `mkHeldDir` already drops. It lives in the
  hashed PARENT, not the workspace, and `removeHoldFile` deletes it via `defer`
  before `mkHashedDir` returns.

## Kept from `5afb3a21`: the `nonempty` fixtures

`"nonempty"` to `mountLoopback` instead of emptying the workspace with
`os.RemoveAll` first. That change was made because the record broke those
mounts, but its stated reason is independent of the record and was re-verified
here:

- `jobqueue/utils.go:853-864`: `mkCwdAndTmp(dir)` creates `<dir>/cwd` and

So by the time a Job's own `Cmd` could mount over its workspace, the workspace
already holds `cwd` and `tmp`. It has been non-empty in production since long
before this branch, and the deleted `os.RemoveAll` lines only ever existed to
get past fusermount 2's emptiness check - they made the fixture unlike
production. Kept; the two comments were reworded to drop the record.
