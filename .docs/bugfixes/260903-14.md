# Bugfixes 260903-14

Branch `fix-same-key-workspace-identity`: a job's `on_exit cleanup` can delete
another live run's FUSE-mounted remote data, and its un-uploaded writable-mount
output, silently, returning `nil`.

- [x] `Job.Key()` treats as one job configurations whose live mounts and
  un-uploaded output are in different places, so the keep set a finished run
  computes from its own `MountConfigs` does not name what a live run of the same
  key has on disk - and the finished run's `ActualCwd` can name the live run's
  workspace byte for byte.

  Fixed by giving a workspace the identity of the run that created it and
  refusing to delete a workspace that is not this run's; see below. Files
  touched: `jobqueue/utils.go` (mint, record, and the one removal entitled to
  take it), `jobqueue/workspace.go` (`proveWSToken` in `prove()`, `keptEntry`),

## The chain, verified at file:line

1. `MountConfigs.Key()` (jobqueue/mount.go:248) substitutes `defaultMountDir`
   (`"mnt"`, mount.go:41) for an empty `MountConfig.Mount` (mount.go:255-257).
2. `Job.mountBaseDirs` (jobqueue/job.go:852-868) sets `defaultMount = cwd` - the
   working directory itself - for a job wr created a working directory for, and
   `resolveMountPoint` (job.go:127-137) returns that `defaultMount` unchanged for
   an empty `Mount`. So `wr add --mounts cw:bucket/path`, which leaves `Mount`
   empty (`mountParseSimple`, cmd/mount.go:451-461), mounts ON the working
   directory, while `--mount_json '[{"Mount":"mnt",...}]'` mounts at
   `<cwd>/mnt` - and the two are one job by key.
3. `MountConfig.writeTargetsKey` (mount.go:294-306) reads only `Target.Profile`
   and `Target.Path`. Nothing that decides where a cache lands is in the key:
   not `MountConfig.CacheBase`, not `Target.CacheDir`, not `Target.Cache`, not
   `Target.Write`.

`os.MkdirTemp`'s digits (utils.go:729) are not pinned to a run, so the workspace
leaf name one manager's run finished with is free to be handed to another
manager's run of the same key later - dedup is per-manager, so two managers
sharing a filesystem can each hold a job with that key but independently spelled
mounts. The stale run's `ActualCwd` then names the live run's workspace byte for
byte, `createdCwdRel` (workspace.go:236-251) is satisfied because the path really
is one this key builds, and the sweep reads through the live mount:
`os.Root.RemoveAll` is bounded by `RESOLVE_BENEATH`, which does not imply
`RESOLVE_NO_XDEV`.

The four rows hit four distinct keep-set rules: `keptDirs.wholeActualCwd`
(workspace.go:759), `wholeWorkSpace` (workspace.go:729), `workSpaceEntries` via
the separate `removeTmpDir` deletion (workspace.go:929), and
`muxfysNamesWorkSpaceEntry` (workspace.go:717).

The `"" -> "mnt"` normalisation dates to `8eead7ad` (2017-06-12, "Job mounts are
now part of the unique key"); `902eccf0` only renamed the literal to a const. It
predates the keep set by years and is only now load-bearing.

## Not fixed in `Job.Key()`

Two reasons, both checked:

- The key IS the persisted database key. `db.go` uses `job.Key()` as the BoltDB
  key in `bucketJobsLive` and `bucketJobsComplete` (db.go:1440, 2233, 2434) and
  as the value of every lookup bucket (db.go:316, 2773). Changing the algorithm
  orphans every existing record and changes dedup for jobs already in flight.
- Semantically the key is arguably right: two jobs with the same command and cwd
  but different cache locations are the same unit of work for scheduling and
  dedup. The defect is that cleanup assumes key equality implies on-disk layout
  equality.

## The fix: a workspace carries the identity of the run that made it

`Job.Key()` is left alone. What changes is that cleanup no longer assumes key
equality implies on-disk layout equality: it asks the workspace WHICH RUN made
it, and refuses a workspace that answers with another run.

- `mkCwdAndTmp` (jobqueue/utils.go) mints a random v4 UUID
  (`github.com/gofrs/uuid/v5`, the repo's direct uuid dependency and
  `Job.ReservedBy`'s type), writes it into the workspace as `.run_token`
  (`createdWSTokenName`) with `O_CREATE|O_EXCL`, and returns it;
  `mkHashedDir` passes it on.
- It travels PAIRED with `ActualCwd`, so neither can be stored without the
  other: `Job.ActualCwdToken` (exported, so binc persists it by name and a job
  recovered from the database keeps it), `setActualCwd(cwd, token)` and the new
  `clearActualCwd()`, `JobEndState.CwdToken`, `executeLiveState`, the `Started`
  request (`startRequestJob`) and `copyJobForClient`.
- `workSpacePaths.proveWSToken`, called from `prove()` (jobqueue/workspace.go),
  reads the record back through the handle already open on the Job's `Cwd`, at
  the workspace's already-proven relative path, and refuses with
  `errNotThisRunsWorkSpace` unless the run reporting the path is the run
  recorded. Absent allows; present-and-unmatched refuses, whether the reporter
  offers a different identity or none.
- The record outlives every deletion decision: `jobWorkSpace.keptEntry` claims
  it unconditionally, so no sweep takes it, and the ONE removal entitled to,
  `removeDirHoldingOnlyWSToken` (utils.go), is reached only from
  `dirChain.removeLeaf`/`removeParent` after a `Remove` has already failed with
  `ENOTEMPTY`, and only when the record is the sole remaining entry. It cannot
  take record and directory atomically - rmdir will not take a directory the
  record is still in, and no syscall removes a directory with its last entry -
  so it unlinks the record, and PUTS IT BACK if the directory then refuses to
  go, which is what happens when the run that owns it has created something in
  it since. What that guarantees is not atomicity but that no call of it leaves
  a LIVE workspace with no record. A directory another process removed while
  the record was down is not a failure at all - the same interleaving
  `removeLeaf` has always treated as ordinary. What stays returned is a restore
  that finds another run's record already at the name (nothing is left
  unprotected; only wr's ability to say whose workspace it was is lost) and a
  write that fails for any other reason (which does leave the workspace
  unrecorded for the rest of its life); the two are reported as different
  errors.

### Why not the alternatives

- **Not in `Job.Key()`**: see above. It is the persisted db key.
- **Not more entropy in the `os.MkdirTemp` leaf name** (a UUID instead of ~9
  digits, so a stale `ActualCwd` could never name a live workspace). It makes a
  collision improbable rather than DETECTABLE, and it cannot be proven by a
  test: the collision it prevents can no longer be arranged the way production
  would produce it, so a test could only assert the naming scheme, which
  testing-principles forbids.
- **Not the `.hold` file** that `mkHeldDir` already drops (utils.go). It lives
  in the hashed PARENT, not the workspace, and `removeHoldFile` deletes it via
  `defer` before `mkHashedDir` returns, so it is gone before any cleanup could
  read it.

## Answers to the four questions the brief asked

**Where the token comes from, and why it cannot collide.** A random v4 UUID per
call to `mkCwdAndTmp`, so per RUN rather than per job: 122 bits from
`crypto/rand`, and the values only ever have to be distinct among the
workspaces one filesystem holds at one time. NOT host+pid: `Job.Pid` becomes
the COMMAND's pid at `Started` (`applyJobStart`), so the runner's own pid does
not survive on the manager's side, and pids recycle. Nor the manager's existing
`runToken` (`Job.runID`, job.go): it is minted per manager, is zero for a run
recovered from the database, and two managers sharing a filesystem - the bug's
own premise - would both mint 1.

**Backwards compatibility.** Absent fails OPEN, present-and-unmatched fails
CLOSED. Absent has to be allowed or every workspace made before the upgrade
would leak for ever; present proves a token-aware wr created the workspace, so
a deleter with no identity of its own cannot be shown to be its run. The two
are distinguished, deliberately: `ENOENT` is absence and is allowed, while an
EMPTY (or non-regular) record is present and matches nothing, so it is refused.
The mixed-version cases are consistent in both directions - an old runner
writes no record AND sends no token, and a new runner's field is ignored by an
old manager. `reliable2_dbcompat_test.go`, which decodes a golden BoltDB, still
passes.

**Whether `prove()` is the right place.** Yes. It is the single point all four
consumers pass through - `cleanupWorkSpace`, the separate `removeTmpDir`,
`Job.rmEmptyMountDirs` and `resolveRunDir` - so one check covers all three
deletion paths, and it also stops a `run` behaviour executing the user's
command inside another run's live workspace, which is the same class of bug.
`cleanup()`'s `wholeWorkSpace` early return happens after `prove()`, so the
check cannot be skipped.

**The unstarted and lost-job paths.** Both reached, neither a hole.
`cleanupUnstartedWorkSpace` (client.go) snapshots the runner's own `*Job`, on
which `resolveWorkingDir` set both fields. `triggerLostRunBehaviours`
(server.go) acts on `pinnedBehaviours`, whose `workSpaceSnapshotLocked()` now
copies the token with the path, so a pin taken at `markJobLost` carries the
identity of the run it belongs to; the manager learns both from the `Started`
request and from every live touch. Mutating the `Started` report to drop the
token reddens `TestLostJobOnWeblessManagerCleansItsWorkSpace`, which is that
path measured rather than argued.

## Verified by test

    unset $(compgen -v | grep '^OS_')
    go test ./jobqueue/ -count=1 -timeout 10m -run \
      'TestCleanupOfAnotherRunsWorkSpace|TestWorkSpaceRunRecord|TestWorkSpaceRecordAfterUnmount'

- `jobqueue/workspace_run_identity_test.go`,
  `TestCleanupOfAnotherRunsWorkSpace`: the four key-blind pairs, each hitting a
  different keep-set rule, plus the live-run's-own-cleanup row. Every row
  asserts the survivors FIRST and the refusal's class second, since Convey
  halts a leaf at its first failure and a deletion is the failure that matters.
  Row one and the fifth row raise a real go-fuse loopback mount, so what they
  measure is the user's remote data rather than a stand-in directory.
- `TestWorkSpaceRunRecord`: the guard's own arms - the recorded run sweeps the
  workspace record and all; a reporter with no identity is refused; a
  non-regular record is refused UNREAD; an empty record is not no record; an
  absent record is swept, as a pre-upgrade wr's has none.
- `TestWorkSpaceRecordAfterUnmount`: the reclamation half, through the real
  `Job.Unmount` - a mounting job keeps mount point and record through its own
  cleanup, and `Unmount` then reclaims the mount point, the workspace and the
  hashed base. Without it, the record-tolerance in `removeEmptyParents` is
  undefended.

## Discovered while fixing this, and NOT fixed here

- [ ] `dirChain.removeParent` stops the upward walk on a parent another process
  has already removed, leaking every level above it. `jobqueue/utils.go`:
  `if !errIsDirNotEmpty(err) { return false, nil }` treats `ENOENT` as "will
  not go", which is the opposite of `removeLeaf`'s `err == nil ||
  os.IsNotExist(err) -> gone` six lines up. Predates this branch: at
  `a1a1c861`, `removeEmptyParents` was `if c.roots[i].Remove(parents[i]) != nil
  { return }`, so any error including `ENOENT` stopped the walk. It leaks
  rather than deletes, which is why it is recorded rather than fixed here, but
  it is the first thing a reader will notice beside the tolerance this branch
  added to the leaf.

- [ ] `make lint` does not report `0 issues.` on this branch point. With the
  `golangci-lint` version the Makefile pins (v2.12.2, Makefile:95), `make lint`
  exits 2 with **29 issues** at `a1a1c861` itself, measured in a throwaway
  worktree of that commit after `golangci-lint cache clean`, and 29 on this
  branch. The two issue lists are identical apart from two line-number shifts in
  files this change touches (`jobqueue/client.go:1174` -> `1182`,
  `jobqueue/job.go:1198` -> `1206`), so this change adds none. The 29 are

- [ ] A full `make test`/`make race` run leaves untracked `jobqueue/jobqueue_cwd/`

  then `wr mod --cwd`s it away, which is the documented "Leaks, the affordable
  half" residual - so wr creates a workspace inside its own source tree and
  nothing ever sweeps it. Predates this branch; this branch's run record is one
  more file inside that debris.
