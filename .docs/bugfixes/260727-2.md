# Bugfix checklist 260727-2 — DB backup coordination de-serialises the archive/exit hot path

- [x] Under LSF-scale load, the periodic DB backup serialises the archive/exit hot path, causing report-storm churn (jarchive bad job -> successful work discarded and re-run): (1) db.backgroundBackup() takes the exclusive db RWMutex and is called on every archive/completion just to check whether to back up; (2) backupToBackupFile holds db.wgMutex across db.wg.Wait(60s), blocking new async-write registrations at each backup's start.

  Root cause (confirmed by the design doc's real-manager block/mutex pprof + goroutine dump: 1828 archivers blocked in RWMutex.Lock -> db.backgroundBackup): the periodic backup coupled to the archive/exit hot path through two shared locks. Both are filesystem-independent, which is why moving the backup to a separate FS did not reduce churn.

  Fix — implemented EXACTLY per `.docs/reliable4/backup-coordination-fix.md` (Parts A + B; Part C copy-I/O relief is OUT OF SCOPE, deferred/stashed). All in `jobqueue/db.go`:
  - Part A (decouple triggering from the hot path): added a lock-free `backupDirty atomic.Bool`. Every per-completion `db.backgroundBackup(ctx)` call is now just `db.backupDirty.Store(true)` (NO lock): archiveJob, storeNewJobs, deleteLiveJobs, launchJobChangeUpdate, and modifyLiveJobs (the last was `go db.backgroundBackup(ctx)`; an atomic store needs no goroutine). One long-lived `backupTicker` goroutine (started in initDB iff backupsEnabled; stopped on close() via `backupTickerStop`) consumes the flag with `if db.backupDirty.Swap(false) { db.backgroundBackup(ctx) }`, so the backup lock is taken at most once per check, never per archive. Existing spacing is preserved by `waitBeforeBackup`/`backupWait`.
  - Part A bonus (field partitioning): backup-state fields (backingUp, backupFinal, backupQueued, backupLast, backupWait, slowBackups + a new `backupStopped`) now live under a dedicated `backupMu sync.Mutex`, NOT the db RWMutex. backgroundBackup/finishBackgroundBackup take only backupMu now — no backup-path code takes the db RWMutex, so backup coordination and exit-updates never contend. `closed` stays on the db RWMutex; the backup path does NOT read it — instead close() sets `backupStopped` under backupMu (checked by backgroundBackup) so no periodic backup starts after close; this cleanly avoids any db.Lock<->backupMu ordering.
  - Part B (drop the periodic drain): removed the pre-copy `db.wgMutex.Lock(); db.wg.Wait(60s); db.wg.Add(1); Unlock` block from backupToBackupFile. The periodic backup is now just `db.bolt.View(copyBackup)` (bbolt's read-tx is already a consistent committed snapshot). copyBackup's I/O is UNCHANGED (Part C untouched). The `wg` machinery (Add/Done in launch* funcs + the drain) is kept for close() only.
  - close()-path decision: close() sets `closed` under db.Lock (serialising with updateJobAfterExit/Change so no new write starts) and calls `finaliseBackup(ctx)` with db.Lock held (safe: no backup-path code takes db.Lock, so waiting for the in-progress backup cannot deadlock). finaliseBackup: stopBackupTicker (stop ticker; if a periodic backup is in progress, set backupFinal + cut its spacing wait short via backupStopWait, then wait `backupNotification`) -> drain `wg.Wait` -> final `backupToBackupFile` if there are un-backed-up changes (`backupDirty` set) or a periodic backup had been interrupted. The final backup runs AFTER the wg drain, so a clean shutdown still captures everything. Replaced the old waitForOngoingTransactions. Backups-disabled close still drains wg (unconditional), preserving prior behaviour.

  Deliberate, documented behaviour change (per design doc; user-confirmed "stale is acceptable"): a PERIODIC backup may now miss the last few in-flight async writes (they land in the next backup) since it no longer drains them under wgMutex — a periodic backup can be up to ~backupWait stale. This is a disaster-recovery fallback (initDB restores from it only if the primary DB is missing/corrupt), so staleness is fine. close()'s FINAL backup is unchanged in completeness (still drains wg first). DR restore in initDB and crash-recovery are unaffected (not touched).

  Deviation from the doc's literal wording (justified, to satisfy "don't break regression behaviour"): the doc says the ticker checks "every ~minimumTimeBetweenBackups (30s)". A literal 30s tick delays even the FIRST backup after activity by up to 30s, which breaks existing regression tests that expect a prompt first backup (jobqueue_test.go's "add 2 jobs creates a db backup" 5s window, and the S3 mounts backup test's 8s window — pre-fix, backgroundBackup fired on the Add and backupLast==0 made waitBeforeBackup return immediately). So the ticker CHECKS the dirty flag every `backupDirtyPollInterval` (1s), while actual backup FREQUENCY stays bounded by `backupWait` (>= 30s) via the unchanged waitBeforeBackup. This exactly preserves the pre-fix observable behaviour (prompt first backup, then ~30s-spaced) and honours the doc's own "honouring the existing spacing (backupWait)" clause, while still achieving the fix's point: the 1s check does only a lock-free atomic load + a spacing-limited backup, NEVER a per-archive db.Lock. (This let me drop the earlier backupPoll-field/backupKick-channel idea entirely — no test-timing changes needed beyond re-homing configureFastTestBackups to backupMu.)

  Regression test (runs in `make test`, no build tag): `jobqueue/reliable4_backup_coordination_test.go` `TestReliable4BackupCoordination`, two deterministic in-process sub-tests on a real backups-enabled db (initDB, forceBackups):
  - Part A "archive hot path does not serialise behind the db write-lock": holds db.Lock (stands in for the transient db.Lock hold during a backup) and fires 50 concurrent archiveJob; asserts they complete within 2s.
  - Part B "periodic backup does not hold wgMutex across wg.Wait": registers a controlled in-flight wg entry, triggers a real backgroundBackup, then fires updateJobAfterChange (exit path, needs wgMutex); asserts it returns within 1s.
  - Verified RED before the fix: Part A `completed`=false (line 163) — the 50 archivers blocked on db.Lock via backgroundBackup for the full 2s; Part B `proceeded`=false (line 196) — updateJobAfterChange blocked on the wgMutex-held wg.Wait (whole test ~3.23s of blocking). Verified GREEN after: both pass in ~0.24s, and race-clean (`-race`). (One test-only race fixed: `So(db, ShouldNotBeNil)` fmt-reflects the whole struct, racing the ticker's backupDirty; replaced with a plain nil guard. Production never reflects the struct wholesale.)

  Also updated (field re-homing): `jobqueue/jobqueue_test.go` configureFastTestBackups (sets slowBackups/backupWait=0 under backupMu now); `jobqueue/reliable4_backup_stall_test.go` reliable4BackupInProgress (reads backingUp under backupMu).
