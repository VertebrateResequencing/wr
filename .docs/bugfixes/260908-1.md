# Bugfixes 2026-09-08

- [x] `wr add` throws away the duplicate breakdown the server already computes,
      so an operator cannot reconcile `wr add` with `wr status -i`.

  - Fixed: `DuplicateBreakdown` (`Queued`, `Complete`, `CompleteSameRepGroup`,
    `OtherRepGroups []DuplicateRepGroup{RepGroup, Count, LastCompleted}`) now
    travels `db.prepareNewJobs` -> `createJobs` -> `serverResponse.Duplicates`
    -> `Client.AddWithDuplicates` -> `cmd/add.go`, instead of being summed away
    in `handleAdd`. `db.checkIfCompleteUnderRepGroup` attributes each skipped
    job by one `bucketRTK` Get in the transaction that already checked
    `bucketJobsComplete`, and decodes the archived record only when that Get
    says the key belongs to another identifier, so a re-add under the same
    identifier decodes nothing.
  - The client-facing `AddDuplicates` holds the server's authoritative total
    (unexported) plus an optional breakdown reachable only through
    `Breakdown() (DuplicateBreakdown, bool)`, and `NewAddDuplicates` keeps the
    breakdown only when it accounts for exactly that total. That is what makes
    a pre-fix manager - wr has no version handshake - fall back to the old
    single-line wording with the right count instead of `(0 were duplicates)`.
  - Files: cmd/add.go, jobqueue/{client,db,server,serverCLI,serverREST,
    serverWebI}.go; tests in cmd/add_test.go and the new
    jobqueue/dup_breakdown_test.go, plus five pre-existing `alreadyAdded`
    assertions retyped to pin all four breakdown fields.
  - The red script lives under .tmp/agent (ephemeral, not committed). What
    persists as the regression guard is `TestAddPrintsDuplicateBreakdown`
    (cmd, exact stdout including layout), `TestAddDuplicatesReporting` and
    `TestAlreadyCompleteDuplicateAttribution` (jobqueue). The cross-version
    scenario needs a pre-fix binary, so only the script covers it end to end;
    `TestAddDuplicatesReporting` covers it at the wire seam by decoding a
    response encoded without the `Duplicates` field.

  Real-world case (v0.37.2): `wr status -i RunCisEQTL_maineffect_autosomes -o s`
  reported `complete=18553` while `wr add -f <19632 unique lines> -i
  RunCisEQTL_maineffect_autosomes` reported `Added 0 new commands (19632 were
  duplicates)`. Both were correct: 18553 of the commands completed on 2026-09-07
  under that report group and the other 1079 completed on 2026-08-28 under report
  group `RunCisEQTL_maineffects`. Establishing that needed a copy of the bolt db
  and a throwaway decoder, because the add message says nothing about what kind
  of duplicates they were, or which identifier they belong to.

  Root cause: `Server.createJobs` (jobqueue/server.go) already returns `dups`
  (key already live in the in-memory queue, from `jobsNotAlreadyQueued`) and
  `alreadyComplete` (key already in `bucketJobsComplete`, from
  `db.prepareNewJobs`) as separate numbers. `jobqueue/serverCLI.go` logs both at
  debug level and then collapses them (`existed := dups + alreadyComplete`),
  returning only `serverResponse.Existed`; `cmd/add.go` prints that one number as
  `(%d were duplicates)`.

  Required output when there is at least one duplicate (counts left-aligned,
  indented as shown; the identifier lines only when the already-completed count
  is above zero):

  ```
  Added 0 new commands (19632 were duplicates:
    19632 already completed
      18553 under this identifier
      1079 under other identifiers:
        1079 as 'RunCisEQTL_maineffects', last completed 2026-08-28
    0 already in the queue) to the queue using default identifier 'X'
  ```

  Naming the other identifiers is the point of the fix: "under a different
  identifier" on its own tells an operator nothing they can act on, whereas the
  identifier plus its completion date sends them straight to the run that
  consumed those commands. One line per other identifier, biggest count first,
  at most 5 lines, then `and N more identifiers`. `last completed <date>` is the
  newest EndTime among that identifier's matched jobs, formatted YYYY-MM-DD, and
  the clause is dropped for a record with no end time. When the other-identifier
  count is zero, print `0 under other identifiers` with no colon and no list.

  With zero duplicates the wording stays exactly as it is today. Attribution uses
  each input job's OWN RepGroup (one add can carry per-job `rep_grp`), by looking
  up `bucketRTK` for `<that job's repgroup><dbDelimiter><key>`: one index Get per
  skipped already-complete job. Naming needs the archived record's own RepGroup,
  so decode ONLY the records that the index lookup already showed belong to some
  other identifier - the common same-identifier re-add then decodes nothing, and
  the value bytes are already in the page the Get touched. `alreadyComplete`
  counts input lines, so a command repeated twice in one file counts twice; keep
  that and do not let the attribution double-count differently. `--simple` and
  `--sync` add modes are unaffected.

  The printed TOTAL must come from the server's `Existed`, which every manager
  version sends, and the breakdown must be printed only when this server
  actually sent a consistent one (`dups.Total() == existed`). There is no
  client/server version handshake anywhere in wr (nothing compares
  `jobqueue.ServerVersion`, and `clientRequest`/`serverResponse` carry no
  version), so a new `wr add` talking to a long-running pre-fix manager - which
  is exactly the reported case, a v0.37.2 manager - gets no `Duplicates` field
  and must fall back to today's single-line wording with the correct count,
  never `(0 were duplicates)`.

- [ ] `TestSuiteTempReaping` (internal/testsuite) fails intermittently inside a
      full `make test`, because `RunPlan` cannot get a port range, not because
      of anything it reaps.

  - Captured failure, `make test` on 2026-09-14 (the run's only failure):

    ```
    Failures:

      Context:
      A run removes its own temp dir and reaps one a killed run left behind

      * internal/testsuite/runner_test.go
      Line 94:
      Expected: nil
      Actual:   'could not find a free port range for WR_TEST_PORT_BASE=16016'
    ```

    Line 94 is the `So(RunPlan(...), ShouldBeNil)` call, so the reaping
    assertions below it never ran: the plan itself failed to start. The same run
    logged heavy port pressure elsewhere ("The default ports couldn't be used
    for you, but ports 43333..43336 are available right now", four times, plus
    one `crit` from `internal/config`'s prompt path), which is the same
    contention seen from the other side.
  - Not reproducible in isolation: 40/40 passes with
    `go test ./internal/testsuite/ -run TestSuiteTempReaping -count=40`, and
    25/25 on an earlier day. It only fails inside the full suite, where the
    parallel lanes compete for port ranges. An earlier hypothesis that two
    concurrent processes race over the shared `/tmp` reaping was tested (two
    parallel processes, 16/16 pass) and is now superseded by this evidence: the
    reaping is not involved.
  - Fix direction, for its own change rather than this one: the port-base
    allocator gives up on `WR_TEST_PORT_BASE=16016` instead of trying further
    bases. Making it search on (or retry) would remove the flake without
    weakening any assertion. Do not mask it with a retry around the test.
  - Pre-existing on `develop` and untouched by this fix, which does not go near
    `internal/testsuite`.

- [x] `TestServerWebI`'s concurrent-clients case reads the first websocket frame
      after a `current` request as a `jstateCount`, but that frame is the
      `{"SeedBoundary":"begin"}` marker, so the assertion passes only when a
      live delta happens to arrive first.

  - Found by CI on PR #596 (run 34844405272, head c667c340), whose only failure
    was:

    ```
    Context:
    Once the jobqueue server is up
      The websocket handler connects and sends job status
        The websocket handler supports multiple concurrent clients

    * jobqueue/serverWebI_test.go
    Line 1606:
    Expected value to NOT be blank (but it was)!
    ```

    Line 1606 was `So(sc3.RepGroup, ShouldNotBeBlank)` - the last of the three
    clients to be dialled, and so the likeliest to still be joining
    `s.statusCaster` when the add's delta is broadcast.
  - `sendCurrentStatusCounts` writes `jstatusSeedBoundary{begin}` before the
    snapshot, unconditionally, and `jstatusSeedBoundary` decodes into a
    `jstateCount` with every field blank. The test therefore only passes
    because the `jq.Add` that precedes the request usually reaches each client
    as a live delta before the seed does. That is an ordering assumption, not a
    property of the protocol.
  - Red command: `go test ./jobqueue/ -run TestServerWebI -count=1`, after
    moving the case's `jq.Add` above the `ws2`/`ws3` dials so the new clients
    cannot receive that delta - which is also the real page-load case, a client
    connecting to a queue that already holds jobs. Deterministically red in 9s:

    ```
    Line 1602:
    Expected value to NOT be blank (but it was)!
    --- FAIL: TestServerWebI (8.70s)
    ```

    Unreproducible by repetition alone: 3/3 passes unloaded and 6/6 under a
    busy loop on every core, which is why the reordering is the reproducer.
  - Pre-existing on `develop`; PR #596 does not touch the status feed (its only
    serverWebI.go change is a debug log line). Keep the reordering, and make the
    readers skip boundary frames so the assertion is about the first count.
  - Fixed in jobqueue/serverWebI_test.go, test-only: the seed-boundary protocol
    is deliberate (see the `jstatusSeedBoundary` doc comment), so no production
    code changed. The case now adds its job before dialling the extra clients,
    and each client reads through non-count frames with a new
    `readFirstJStateCount(ws, timeout)` helper that discriminates on
    `RepGroup != ""` - the same test `deltaCounts.apply` uses - under a bounded
    read deadline, so a count that never arrives fails the test instead of
    hanging it. All three clients must still receive a count naming a RepGroup,
    each on its own line so a failure says which client, and the read error the
    old code discarded under `//nolint:errcheck` is now asserted. The three
    goroutines, WaitGroup and channels are gone: the claim is that every
    concurrent client receives the broadcast, not that the reads race.
  - The two dropped `ShouldNotBeNil` assertions were vacuous: `jstateCount` is a
    struct, and the assertion library treats only slice/chan/func/ptr/map as
    nilable, so they could never fail.
  - Mutation-verified: forcing the helper to return its first frame whatever it
    is reproduces the CI symptom (`Expected value to NOT be blank`), now on the
    first client rather than the third, because with the add moved above the
    dials no client gets an early delta.
  - The helper's doc comment records that its discriminator assumes a socket
    that has not requested details or subscribed, since a `JStatus` also carries
    a RepGroup.
  - Left alone as weak-but-not-wrong, both pre-existing and unable to false-FAIL:
    the tail of this same case, which asserts only that a frame still arrives
    after a peer closes, and `TestJobSubscriptions`' negative assertion that an
    unsubscribed client receives no push update.
