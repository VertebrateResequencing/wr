# Data race in TestSubscriptionReconnectDuringManagerShutdown

- [ ] `go test -race` intermittently reports a genuine data race between the
      test's own hook at `jobqueue/subscription_test.go:1911` and the goroutine
      `initDB` runs it on. Test-only, pre-existing, and it fails the whole
      `make race` gate when it fires.

## Evidence

Seen once during `make race` on a branch that touches neither file
(`jobqueue/subscription_test.go`, `jobqueue/db.go`). Log kept at
`/tmp/g578r2.log`; the report begins:

```
WARNING: DATA RACE
Read at 0x00c0437b85c8 by goroutine 20279:
  jobqueue.TestSubscriptionReconnectDuringManagerShutdown.func6()
      jobqueue/subscription_test.go:1911
  jobqueue.initDB()
      jobqueue/db.go:531
  jobqueue.initDB()
      jobqueue/db.go:456
  jobqueue.Serve()
      jobqueue/server.go:2793
  jobqueue.serve()
      jobqueue_test.go:1413
  jobqueue.TestSubscriptionReconnectDuringManagerShutdown.func6()
      jobqueue/subscription_test.go:1887
```

`--- FAIL: TestSubscriptionReconnectDuringManagerShutdown (74.79s)`, whole gate
`exit=2`.

The read happens inside `initDB`, which `Serve` calls on the goroutine the test
starts at `subscription_test.go:1887`, while the value is reached from the test's
own closure. So the hook the test installs is read on a goroutine other than the
one that set it, with nothing synchronising the two.

## Intermittent, and NOT waived

- Immediate `make race` re-run on the same tree: green,
  `445 passed · 9 skipped · 29 packages · 4m59s`. Log `/tmp/g578r3.log`.
- The one test run in isolation under `-race` on `origin/develop`
  (`44be38e3`): clean, `ok ... 18.771s`, zero DATA RACE warnings. Log
  `/tmp/race_dev.log`. That is weak evidence on its own - the failure appeared
  under whole-suite load, not in isolation - so it does not show the race is
  absent from develop, only that one isolated run did not trigger it.

**The race detector does not report false positives.** When it fires there is a
real unsynchronised access, so "it passed on the re-run" is not a fix and this
is recorded rather than dismissed. What is unproven is only how often it fires
and under what load.

## Not introduced by the branch that saw it

That branch's whole diff against develop is `jobqueue/utils.go`,
`jobqueue/utils_test.go`, `jobqueue/workspace_name_test.go`,
`jobqueue/workspace_test.go` and two docs. It touches neither file named in the
race, and nothing in the subscription, database or server paths.

## To establish before fixing

- Reproduce it deliberately. A single `-race` run of the one test does not do
  it; the sighting was under full-suite concurrency. Try
  `go test -race -run TestSubscriptionReconnect -count=N` with the rest of the
  suite's load alongside, and report the rate.
- Read what `subscription_test.go:1911` actually touches and which goroutine
  writes it. The fix is likely to give the hook its own mutex or to set it
  before `Serve` starts, but which one depends on what the test is trying to
  observe - it may be deliberately watching a value that changes during startup.
- Check whether the same hook pattern is used by other tests in the file, since
  a fix to one instance may need to cover all of them.

## Correction: the write side is PRODUCTION code, not a test hook

The first sighting only showed the read side, and this record described it as a
test hook read on the wrong goroutine. A second sighting caught the full trace,
and the write is production:

```
Write at 0x00c0281c62f8 by goroutine 19239:
  jobqueue.(*Client).reconnect()              subscription.go:928
  jobqueue.(*Subscription).reconnectOnce()    subscription.go:394
  jobqueue.(*Subscription).reconnect()        subscription.go:371
  jobqueue.(*Subscription).reconnectAfterPollError()  subscription.go:349
  jobqueue.(*Subscription).poll()             subscription.go:259
  jobqueue.(*Client).subscribe.gowrap1()      subscription.go:667

Previous read at 0x00c0281c62f8 by goroutine 18828:
  jobqueue.TestSubscriptionReconnectDuringManagerShutdown.func6()
                                              subscription_test.go:1911
  jobqueue.initDB()                           db.go:531
  jobqueue.Serve()                            server.go:2793
```

So a `*Client` field is written by the subscription's own **poll goroutine**,
inside `Client.reconnect`, with nothing synchronising it against a concurrent
reader. The reader that caught it happens to be the test, which is why this
first looked like a test-only problem. It is not: the unsynchronised **write**
is in shipped code, on a goroutine wr starts itself (`Client.subscribe`).

**What that changes.** Whether it can bite in production depends on whether any
production reader touches that field concurrently with a reconnect - which is
NOT established here and must be measured before anyone calls this benign. The
question to answer is what `subscription.go:928` writes and who else reads it;
if any path other than a test does, this is a live data race in the client.

**Still intermittent**: seen twice in many `make race` runs, each time on a
branch touching neither `subscription.go` nor `db.go`, and green on the
immediate re-run both times.
