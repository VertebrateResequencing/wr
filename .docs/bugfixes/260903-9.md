# Bugfixes 260903-9

RECORDED, NOT FIXED. Findings from adversarial probing of wr, filed as backlog
items. Nothing on this branch changes any code; none of these has a fix or a
test yet. Each entry names the mechanism, where it lives, what a user sees, and
where the evidence came from.

Topic: CLI selection, file paths the manager writes, and the database
(`cmd/`, `jobqueue/`, `internal/`, `fs/`).

## 1. A `Cwd` given for a non-`cwd_matters` job matches nothing

`JobEssence.Key()` (job.go:1564-1592) prefixes the key with `Cwd` whenever
`j.Cwd != ""`, while `Job.Key()` (job.go:1198-1240) prefixes it only when
`j.CwdMatters`. So an essence carrying a `Cwd` can only ever match a
`CwdMatters` job, and `getJobsByCmdLine` (cmd/status.go:1149-1161) builds
exactly that from `-l` plus `-c`.

`wr kill -l "cmd" -c /some/dir` (or `retry`, `remove`, `suspend`, `resume`,
`status`) therefore finds nothing for a job added as `wr add -c /some/dir`
without `--cwd_matters` - the common case, since `--cwd` is the ordinary way to
say where a command should run. The API returns 0 changed; the CLI dies with
"No matching jobs found" (cmd/kill.go:96-98), which does not hint at the cause.

Half-documented, which is what makes it a trap: each command's long help says
"you must provide the cwd the commands were set to run in, if CwdMatters (and
must NOT be provided otherwise)" (cmd/kill.go:63-65), but the `-c` flag's own
one-line help says "working dir that the command(s) specified by -l or -f were
set to run in" with no such condition (cmd/kill.go:155-156), and that is the
text `--help` shows against the flag.

Found while filing, same shape and worth fixing together: `JobEssence.Key()`
also omits the container image and `ContainerMounts` that `Job.Key()` appends
(job.go:1201-1207, 1219-1230), so `-l`-based selection can NEVER match a job
added with `--with_docker` or `--with_singularity`, with or without `-c`.

## 2. `Job.Key()` ignores `Cwd` unless `CwdMatters`, so two `--cwd`s are one job

Same lines (job.go:1216-1230). `wr add -c /a "cmd"` and `wr add -c /b "cmd"`
produce the same key, so the second is reported as already existing and never
runs; the surviving job runs in whichever `Cwd` was added first. Long-standing
and probably deliberate - `Cwd` for a non-`CwdMatters` job is only the BASE of a
workspace wr creates - but it is a real surprise, especially in `wr add`'s file
mode where each line may carry its own `cwd`. Recorded as a documented surprise:
the fix may be a doc line rather than a key change, since changing the key
changes what "the same command" means for every existing database.

## 3. `Client.BackupDB` clobbers whatever is at `<path>.tmp`

client.go:858-875:

    tmpPath := path + ".tmp"
    err = os.WriteFile(tmpPath, resp.DB, dbFilePermission)

`os.WriteFile` is `O_WRONLY|O_CREATE|O_TRUNC` - no `O_EXCL` - and on failure the
code `os.Remove`s that path (client.go:866-868). So `wr manager backup -p
mydb.db` destroys an unrelated `mydb.db.tmp` if one exists, whether the backup
succeeds (renamed over) or fails (removed). Same shape in the manager: the S3
backup download target is `dbBkFile + ".tmp"` or `dbFile + ".s3backup_tmp"`
(db.go:381, 421), written by `accessor.DownloadFile` and then `os.Remove`d in a
deferred call (db.go:474-490).

Correction to the original report: the `.upgrade` sidecar is NOT of this shape.
`internal/db_upgrade_status.go:100` uses `os.CreateTemp(dir, base+".tmp.")`, so
its temporary name is unique; only the final sidecar path (`dbFile +
".upgrade"`, db_upgrade_status.go:172) is fixed, and that is its designed
location.

## 4. Uploads create 0777 directories and can leave a world-readable file

`openUploadDestination` (server.go:3644-3668) takes a path the CLIENT chose,
`MkdirAll`s its parent with `os.ModePerm` (server.go:3654), then opens the file
`O_RDWR|O_CREATE` with `ownerReadWrite` (server.go:3661).

Two consequences. Directories the manager creates on its own machine are 0777
minus its umask, in a tree the client named. And `uploadFile`'s doc promise -
"Files stored will only be readable by the user that started the server"
(server.go:3609) - holds only when the file is CREATED by that open: an existing
destination keeps its own mode, so uploading over a world-readable file leaves
config data (the reason this API exists is passing config files to cloud
servers) world-readable. The 0600 is never applied to an existing file.

## 5. A read-only database file is DELETED and replaced from backup

`initDB`'s existing-db branch (db.go:471-520): if `bolt.Open(dbFile, ...)`
fails - for ANY reason, including `EACCES` because the file is mode 0400 - wr
treats the database as corrupt, and if a backup opens cleanly it does

    err = os.Remove(dbFile)      // db.go:506
    err = copyFile(bkPath, dbFile)

So chmod-ing the manager's database read-only, which is exactly what an
administrator does before inspecting or copying it, causes the next
`wr manager start` to DELETE it and restore the (older) backup. Everything
between the last backup and the crash is gone, and the message says "recreated
corrupt (?) db file", so the user is told the file was corrupt rather than
unreadable. The remove succeeds because the containing directory is writable,
whatever the file's own mode. Distinguishing a permission error from corruption
(`errors.Is(err, fs.ErrPermission)`) is the obvious first fix.

## 6. `TildaToHome` uses a cutset trim

`internal/utils.go:216-224` and `fs/filepath/filepath.go:50-62` both do:

    if strings.HasPrefix(path, "~/") {
        path = strings.TrimLeft(path, "~/")
        path = filepath.Join(home, path)
    }

`strings.TrimLeft` takes a CUTSET, not a prefix, so it strips every leading `~`
and `/`: `"~/~bk/db"` becomes `<home>/bk/db`, `"~///a"` becomes `<home>/a`, and
`"~/~/x"` becomes `<home>/x`. A user whose backup directory or upload path
begins with `~` (or who writes a doubled slash) silently gets a different path
from the one they configured, and wr reports the resolved path nowhere.
`strings.TrimPrefix(path, "~/")` is the intended operation, in both copies.

## 7. `wr mount` resolves nothing, and dies with a mount already live

Two defects in `cmd/mount.go`.

`mountRemoteConfigs` passes `CacheDir: mt.CacheDir` straight through
(cmd/mount.go:318), and `mountConfig` passes `Mount`/`CacheBase` the same way
(cmd/mount.go:283-285) - unlike the jobqueue path, which resolves a relative
`CacheDir` through `resolveCacheDir` (jobqueue/job.go:977-997). muxfys then
`filepath.Abs`es it (muxfys remote.go:176) against the PROCESS's working
directory, and `wr mount` daemonizes with `WorkDir: "/"` (cmd/mount.go:209). So
`wr mount -m ... ` with a relative `CacheDir: "mycache"` caches at `/mycache`
(or fails with permission denied), while the same config under `--foreground`
caches where the user expected. The user's cached data, and for a writable mount
their un-uploaded output, is not where they told wr to put it.

Second: `mountAndWait` loops over the parsed configs calling `mountConfig`
(cmd/mount.go:245-252), and every failure inside `mountConfig` and
`mountRemoteConfigs` is `die()` (cmd/mount.go:289, 293, 307, 312), i.e.
`os.Exit(1)` (cmd/root.go:223-226). With two `--mount_json` configs, a failure
on the second exits while the first is already mounted and never unmounted - so
the user is left with a live FUSE mount, no process to signal, and a path that
`ls` hangs on until they find `fusermount -u` themselves. The unmount loop that
would have handled it is only reached via the signal wait (cmd/mount.go:262-269).

## 8. `--change_home` breaks a job's own `wr` commands

`Execute` sets `HOME=<actualCwd>` for a `ChangeHome` job (client.go:1781-1783).
wr's own config is rooted at `ManagerDir`, default `~/.wr`
(internal/config.go:108), expanded with `TildaToHome` at load time
(internal/config.go:471) - and every other manager path, the client token file
included, is joined onto it (`convRelativeToAbsPath`, internal/config.go:488,
498-501). `os.UserHomeDir()` reads `$HOME`.

So a nested `wr` invoked by the job's own command looks for
`<actualCwd>/.wr_production/client.token`, which does not exist, and fails to
connect. That path is one the runner explicitly supports: cmd/runner.go:180-181
says "in case any job we execute has a Cmd that calls `wr add`, we will override
their environment to make that call work", and it overrides
`WR_MANAGERHOST`/`PORT`/`CERTDOMAIN` (cmd/runner.go:190-194) - but there is no
env var for the token (no `WR_MANAGERTOKEN` anywhere in the tree), so the token
can only come from the config directory that `--change_home` has just moved.
`--change_home` and a job that calls `wr add` are mutually exclusive today, and
nothing says so.

## 9. `go test ./cmd/` fails on a full-package run

Pre-existing on develop, and a test-suite defect rather than a product one.
`countGetJobArgs` (cmd/status.go:746-769) counts `cmdRecent` among the
mutually-exclusive selectors, and `validateSelectedJobsCommand`
(cmd/suspend.go:120-134) uses it. But `resetSelectionCommandForTest`
(cmd/suspend_test.go:392-404), which the suspend/resume tests call before each
run, resets `cmdFileStatus`, `cmdIDStatus`, `cmdLine`, `cmdCwd`, `cmdAll` and
the mount globals - and NOT `cmdRecent`.

`TestStatusRecentMutualExclusion` and `TestStatusRecentRejectsStateFilters`
(cmd/status_test.go:909-985) each call `resetStatusForTest` at the START of a
Convey and leave `cmdRecent = "1h"` set at the end. Test functions run in file
order, and `status_test.go` sorts before `suspend_test.go`, so the suspend tests
run afterwards with `cmdRecent` still set, count two selectors, and get
`errSelectedJobsExclusive` ("-f, -i, -l and -a are mutually exclusive") instead
of their expected result. Running the suspend test alone passes, and
`resume_test.go` sorts before `status_test.go` so it passes either way -
matching the reported symptom.

Verified by reading the tests, not by running them (the cmd package's tests
start real managers, and this filing task was not to spend the box's time on
them). The cheap fix is one line in `resetSelectionCommandForTest`, or resetting
in a `defer` in the status tests.

## 10. `PrepareCmdFile` writes to the system tmp, not the job's TMPDIR

`container/run.go:53-79`: `os.CreateTemp("", "container.cmd")`, i.e. `$TMPDIR`
of the RUNNER process, which is not the per-job TMPDIR wr creates beside the
job's working directory (`mkCwdAndTmp`, jobqueue/utils.go:844) and points the
COMMAND at (`TMPDIR=<tmpDir>`, client.go:1779). Deletion is by the returned
cleanup function, deferred in `Execute` (client.go:1577-1581), so a runner that
is SIGKILLed - lost job, scheduler timeout, host reboot - leaves the file
behind. It is small, but it accumulates in a shared `/tmp` for every
containerised job that dies that way, and it escapes wr's own workspace
accounting, which is the thing that makes such files findable and removable.
