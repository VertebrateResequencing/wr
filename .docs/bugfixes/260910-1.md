# Bugfixes 260910-1

RECORDED, NOT FIXED. Loose ends found while fixing #588 to #593, filed as
backlog items so they are not lost in the fix records that mention them.
Nothing on this branch changes any code.

Each says where it was found, why it was not fixed there, and what a fix would
have to establish. Several were deliberately left out of scope at the time;
that reasoning is repeated here rather than assumed.

## 1. `wr add`'s other comma-separated flags accept a trailing comma

#592 made `--env` reject an element that defines no variable, so
`wr add --env "A=1,"` is now an error. `--limit_grps "a,"`, `--modules "x,"`
and `--queues_avoid "z,"` all still accept one silently: `cmd/add.go` does a
bare `strings.Split` on each with no element validation.

The asymmetry tracks blast radius rather than taste, which is why #592 did not
level it: an empty env element crash-looped a scheduler group and made any
`--with_docker` job fail to start, while an empty limit group appears to be
inert. Anyone taking this should FIRST measure what an empty limit group, an
empty module name and an empty queue name actually do, because the right
answer may differ per flag - rejecting is right where the value is used,
silently dropping may be right where it is not.

## 2. Nothing is logged when a read skips a malformed stored environment entry

#592 made four read paths degrade rather than panic on a stored entry that
names no variable: `jobEnvOverrider.overridesFor` (`cmd/runner.go`),
`Job.Getenv` and `containerEnv` (`jobqueue/job.go`), and `prependedPath`
(`jobqueue/client.go`). All four skip silently.

So a legacy job with such an entry now runs instead of crash-looping, but its
owner is told nothing about why a variable they set is absent. The single
right place is the runner, which is on the path of every one of those reads: a
`clog.Warn` there covers all four at once, where a log in any one accessor
would be a fifth style in a function with no logger.

## 3. `exit 125` is reported as "command exited non-zero"

Found in #593. When `docker run` refuses to start - a name conflict, an
invalid `-e` argument, an unreadable image - the command never runs, but wr
classifies the wrapper's 125 as `FailReasonExit`, "command exited non-zero".

Not fixed there, and the reason is worth keeping: 125 is a legal exit code for
a user's own command, so special-casing it would misclassify real jobs, and
telling the two apart needs sniffing docker's stderr, which #593 deliberately
avoided. `wr status` does print `StdErr:` alongside the `Cmd`, so the docker
message is visible; only the classification is wrong. A fix needs a way to
know wr's own wrapper failed rather than the user's command, which probably
means the wrapper reporting that itself.

## 4. `container/run_test.go` uses an unpinned `alpine` in 5 places

#593 pinned `container/docker/docker_test.go` to a multi-architecture index
digest, after establishing that its `cli.ImagePull(ctx, "ubuntu", ...)`
re-pointed a developer's own `ubuntu:latest` tag every run.

`container/run_test.go` was left alone, and the distinction is real rather
than an oversight: it passes the string to `DockerRunCmd` / `docker run`,
which pulls only when the image is ABSENT and therefore cannot re-point an
existing tag - proved by resolving `docker create alpine` against a planted
local tag with no registry contact. What remains is weaker but not nothing:
those tests run whatever alpine the developer happens to have, and create
`alpine:latest` on a machine that has none. 3 of the 5 sites are new on #593.
Pinning them to the same digest constant would be assertion-neutral.

## 5. `github.com/opencontainers/image-spec` is a direct dependency nothing imports

#593 removed the last direct import when it dropped a hardcoded
`Platform: {Architecture: "amd64"}` from a docker test helper - that pin
contradicted the new multi-architecture digest 3 functions above it, and made
the whole real-daemon test silently SKIP on arm64.

`v1.1.1` is still in go.mod's direct require block. A `go mod tidy` moves it
to indirect. `make lint` is `0 issues.` as it stands, so nothing fails today.
Not done on #593 because that item was scoped to test files and go.mod is not
one.

## 6. `cleanorder -min-diff` destructively reorders `jobqueue/utils_test.go`

Hit by 2 separate agents on #592, and confirmed pre-existing by running it on
`HEAD`'s own copy: it hoists `const testJobKey`, `const mkHashedDirSweepTries`
and 2 interface assertions to the top of the file, which strands
`TestCreatedCwdDepthMatchesMkHashedDir`'s doc comment hundreds of lines from
its function, leaving the test undocumented and the constant carrying a
comment about something else. Both agents reverted it and hand-placed their
additions.

`make lint` is `0 issues.` either way, so nothing enforces cleanorder's
preference here. Someone should decide whether that file takes the reorder as
its own commit, or whether cleanorder is simply wrong about a test file that
documents a constant through the test above it.

## 7. `TestReliable4RacBoundedBySchedulable` needs a verdict, not a retry

Seen failing on CI during #591 with `Expected: 5 Actual: 19` at
`So(scanWork, ShouldEqual, limit)`. Provably not that branch's: the commit
changed 2 `.md` files and nothing else, so the compiled code was byte-identical
to one CI had already passed.

It is NOT reproducible here: 20/20 green plain, 12/12 green under 6 spinning
CPU hogs, and green across full-suite runs. A CI re-run passed.

But the assertion is exact by design - `.docs/bugfixes/260725-2.md` added the
test precisely because that count used to be the whole backlog - so a measured
19 against a limit of 5 is either a real bound violation that only a slower,
contended machine exposes, or an assertion too tight to survive scheduling
jitter. Those are very different, and a passing re-run does not distinguish
them: a real violation exposed only under contention would also pass on a
quieter runner. It should not be relaxed before someone establishes which.

## 8. `jobqueue/dependency.go` builds an essence with no container fields

Found by #590's reviewer, and it predates both #588 and #590: command
dependencies build `&JobEssence{Cmd: cmd, Cwd: cwd}`, so a `wr add --deps`
naming a containerised command cannot resolve to it. #588 gave `JobEssence`
the container fields and #590 added `ContainerImageUser`, and this is now the
only remaining place where the "an essence names its job" contract is broken.

`cmd/lsf.go` has the same shape but is harmless: LSF emulation uses no
containers.

## 9. Support `:ro` properly rather than rejecting it

#591 rejects a mount spec with more than one colon, which fixes a silent
docker collapse - `/a:/b:ro` mounted `/a` at `/a` and dropped both the target
and the option - but REMOVES a working capability for singularity users, where
the spec reached `singularity -B` intact. Proved with a real sandbox on
singularity-ce 4.1.1: writing to a `:ro` bind failed with "Read-only file
system", and without it succeeded.

It was rejected for both runtimes because the published contract is 2-field
only and the singularity support was undocumented and accidental. The honest
resolution is to support the option on both: singularity already takes `:ro`,
and docker takes `--mount ...,readonly`. That turns a capability removal into
a capability everyone gets.
