Loose ends found while fixing #588 to #593, first filed here as backlog items
so they were not lost in the fix records that mention them. A later pass
re-checked each against develop cb9bb03 and fixed items 1 to 4 and 8, in the

## 1. `wr add`'s other comma-separated flags accept a trailing comma

#592 made `--env` reject an element that defines no variable, so
`wr add --env "A=1,"` is now an error. `--limit_grps "a,"`, `--modules "x,"`
and `--queues_avoid "z,"` all still accept one silently: `cmd/add.go` does a
bare `strings.Split` on each with no element validation.

The asymmetry tracks blast radius rather than taste, which is why #592 did not
level it: an empty env element crash-looped a scheduler group and made any
`--with_docker` job fail to start, while an empty limit group appears to be
inert. Anyone taking this should FIRST measure what an empty limit group, an
empty module name and an empty queue name actually do, because the right
answer may differ per flag - rejecting is right where the value is used,
silently dropping may be right where it is not.

**Fixed**, by dropping the empty elements everywhere. Measured first: an empty
queue name to avoid matched every queue, because `queueShouldBeAvoided` uses
`strings.Contains(queue, "")`, so `--queues_avoid "interactive,"` made a job
unschedulable on LSF. An empty module reached the runner as
`module load --force mod1 ''`. An empty limit group was stored as a group named
"". None of the 3 means anything, and a trailing comma from a script that joins
a list is the likely cause, so dropping it is kinder than rejecting it.

- Red: `TestAddDropsEmptyListElements` (`cmd/add_test.go`) got
  `[]string{"lg1", "", " ", "lg2", ""}` for `--limit_grps "lg1,, ,lg2,"`.
  `TestLSFQueuesAvoidIgnoresEmptyElements`
  (`jobqueue/scheduler/lsf_queues_avoid_test.go`) got "resource requirements
  are too high" for `scheduler_queues_avoid` `interactive,`, and picked the
  empty queue name from a `scheduler_queue` of `interactive,`.
- Fix: `internal.SplitCommaList` splits and drops empty and whitespace-only
  elements. `wr add` uses it for all 3 flags, `wr mod` for all 3 too, and the
  LSF `determineQueue` for both `scheduler_queue` and `scheduler_queues_avoid`,
  since the REST API reaches it without the CLI. `queueShouldBeAvoided` also
  skips an empty name. Other elements are not trimmed, so `"a, b"` still gives
  `" b"`, as before.
- `wr mod` has no parser-level test: its flag handling lives inside the cobra
  `Run` closure, which needs a live manager. It calls the same helper.

## 2. Nothing is logged when a read skips a malformed stored environment entry

#592 made four read paths degrade rather than panic on a stored entry that
names no variable: `jobEnvOverrider.overridesFor` (`cmd/runner.go`),
`Job.Getenv` and `containerEnv` (`jobqueue/job.go`), and `prependedPath`
(`jobqueue/client.go`). All four skip silently.

So a legacy job with such an entry now runs instead of crash-looping, but its
owner is told nothing about why a variable they set is absent. The single
right place is the runner, which is on the path of every one of those reads: a
`clog.Warn` there covers all four at once, where a log in any one accessor
would be a fifth style in a function with no logger.

**Fixed.** The runner's reserve loop now calls `warnUndefinedEnvEntries`
(`cmd/runner.go`) on the environment it has just read, before
`overridesFor`, and logs `skipping a stored environment entry that defines no
variable` at warn with the job's key and the entry's name part. An entry such
as `=value` logs an empty name, so a value is never written to the log.

- Red: `TestRunnerWarnsOfUndefinedEnvEntries` (`cmd/runner_env_test.go`),
  capturing the log with `clog.ToBufferAtLevel("warn")`, found an empty log
  for both a bare `PATH` and `=value`.
- The call sits where the loop reads the environment, which it does only when
  the runner has overrides to add, as it does whenever it knows its manager's
  address. It is a separate function rather than part of `overridesFor`, which
  stops at the first `PATH` entry and so would miss a later bad entry.

## 3. `exit 125` is reported as "command exited non-zero"

Found in #593. When `docker run` refuses to start - a name conflict, an
invalid `-e` argument, an unreadable image - the command never runs, but wr
classifies the wrapper's 125 as `FailReasonExit`, "command exited non-zero".

Not fixed there, and the reason is worth keeping: 125 is a legal exit code for
a user's own command, so special-casing it would misclassify real jobs, and
telling the two apart needs sniffing docker's stderr, which #593 deliberately
avoided. `wr status` does print `StdErr:` alongside the `Cmd`, so the docker
message is visible; only the classification is wrong. A fix needs a way to
know wr's own wrapper failed rather than the user's command, which probably
means the wrapper reporting that itself.

**Fixed narrowly**: by exit code alone, not by the wrapper
reporting itself or by sniffing stderr.

- Measured singularity's code with singularity-ce 3.11.4 (`module load
  ISG/singularity`): `singularity shell` exits 255 with a `FATAL:` line both
  for a missing image and for a bind whose source does not exist. Docker
  documents 125 for an error in the daemon or client before the container
  runs. No docker was available here to measure it.
- Red: `TestExecOutcomeContainerStartFailure` (`jobqueue/exec_outcome_test.go`)
  runs a real `sh -c 'exit N'` and classifies it with `classifyExecOutcome`
  for a docker, singularity, both-image and no-image job. It got "command
  exited non-zero" for docker/125 and singularity/255.
- Fix: new `FailReasonContainer` ("container failed to start"), given by
  `plainExitFailReason` (`jobqueue/client.go`) in place of `FailReasonExit` when
  a docker job exits 125 or a singularity-only job exits 255. Docker wins when
  both images are set, as it does in `containerRunCmd`. Only the reason
  changes: `plainExitOutcome` still decides release or bury and writes the
  error, so retries are exactly as before.
- The misclassification the paragraph above warns of remains: both runtimes
  pass the inner command's exit code through, so a user command that exits 125
  under docker, or 255 under singularity, is now labelled "container failed to
  start". That was accepted as the cost of a narrow fix, because it changes
  nothing but the label, and the doc comment and CHANGELOG say so.

## 4. `container/run_test.go` uses an unpinned `alpine` in 5 places

#593 pinned `container/docker/docker_test.go` to a multi-architecture index
digest, after establishing that its `cli.ImagePull(ctx, "ubuntu", ...)`
re-pointed a developer's own `ubuntu:latest` tag every run.

`container/run_test.go` was left alone, and the distinction is real rather
than an oversight: it passes the string to `DockerRunCmd` / `docker run`,
which pulls only when the image is ABSENT and therefore cannot re-point an
existing tag - proved by resolving `docker create alpine` against a planted
local tag with no registry contact. What remains is weaker but not nothing:
those tests run whatever alpine the developer happens to have, and create
`alpine:latest` on a machine that has none. 3 of the 5 sites are new on #593.
Pinning them to the same digest constant would be assertion-neutral.

**Fixed.** There are 6 sites now, not 5: 5 `DockerRunCmd("alpine", ...)` calls
and the `docker create` args of the stale-container helper. All 6 use
`testimage.Alpine`, a new one-constant package (`internal/testimage`) that
`container/docker/docker_test.go`'s `testImage` now also comes from, so the 2
test files cannot drift apart onto 2 images.

- No red test: which alpine a test runs changes no assertion, per
  **testing-principles** on changes with no behavioural difference. The check
  is `grep -n '"alpine"' container/run_test.go`, which listed the 6 sites
  before and lists none after.
- The real-docker tests skip on this host, which has no docker, so the pinned
  image was not pulled here. `container/docker`'s tests already pull the same
  digest wherever docker is available.
- `singularityImage` (`docker://alpine`) is left as it is: singularity converts
  the image to a sif in its own cache and writes no docker tag, so it cannot
  re-point one, and item 4 is about docker.

## 7. `TestReliable4RacBoundedBySchedulable` needs a verdict, not a retry

Seen failing on CI during #591 with `Expected: 5 Actual: 19` at
`So(scanWork, ShouldEqual, limit)`. Provably not that branch's: the commit
changed 2 `.md` files and nothing else, so the compiled code was byte-identical
to one CI had already passed.

It is NOT reproducible here: 20/20 green plain, 12/12 green under 6 spinning
CPU hogs, and green across full-suite runs. A CI re-run passed.

But the assertion is exact by design - `.docs/bugfixes/260725-2.md` added the
test precisely because that count used to be the whole backlog - so a measured
19 against a limit of 5 is either a real bound violation that only a slower,
contended machine exposes, or an assertion too tight to survive scheduling
jitter. Those are very different, and a passing re-run does not distinguish
them: a real violation exposed only under contention would also pass on a
quieter runner. It should not be relaxed before someone establishes which.

**Left for the owner.** It needs its own investigation of whether the bound is
really violated under contention, which is outside a batch of small fixes.

## 8. `jobqueue/dependency.go` builds an essence with no container fields

Found by #590's reviewer, and it predates both #588 and #590: command
dependencies build `&JobEssence{Cmd: cmd, Cwd: cwd}`, so a `wr add --deps`
naming a containerised command cannot resolve to it. #588 gave `JobEssence`
the container fields and #590 added `ContainerImageUser`, and this is now the
only remaining place where the "an essence names its job" contract is broken.

`cmd/lsf.go` has the same shape but is harmless: LSF emulation uses no
containers.

**Fixed.** `--cmd_deps` and a REST `cmd`/`cwd` dependency build an essence of
only Cmd and Cwd, whose key could never match a job added with a container
image or mounts, so the old `incompleteEssenceJobKeys` found "nothing live"
and the dependent started at once.

- Red: `TestCommandDependencyMatchesContainerAndMountJobs`
  (`jobqueue/dependency_variants_test.go`), with faked `WithDocker`,
  `WithSingularity` and `MountConfigs` (nothing runs a container): the
  dependent's queue dependencies were `[]string(nil)` where the dependency's key
  was expected, in 7 of its 9 cases.
- Fix: an essence that names only a Cmd and Cwd (`JobEssence.namesOnlyCommand`)
  now resolves to every live job whose `Job.commandKey` - its key computed
  without mounts, image or container mounts, with Cwd included exactly when the
  job has CwdMatters - equals the essence's key. An essence that does give
  mounts or an image still names only that exact job.
- Ambiguity: when several live jobs match (for example the same Cmd plain and
  under docker), the dependent waits for all of them. Picking one would let it
  start while another job running the named command was incomplete.
- Efficiency: `commandVariants` (`jobqueue/cmdvariants.go`) is a sharded
  in-memory index from command key to the live job keys that differ from it,
  held in `depGroupMembers` and maintained at the same 4 points as dep group
  membership: add and recovery (`registerDepGroupMembers`), archive and delete
  (`releaseDepGroupMembership`) and modify
  (`rekeyDepGroupMembershipForModifiedJobs`). A plain job is not indexed, since
  its key is its command key, so the index costs nothing for queues without
  containers or mounts, and a lookup is one shard map read rather than a scan.
  Each candidate is still checked with `checkIfLive`, so an index entry that
  outlives its job by a moment cannot block a dependent.
- Tests cover docker, singularity, mounts, several matches (one finishing
  releases only itself), CwdMatters, an essence that names an image, recovery
  after a restart, a modify that changes the key, and a delete. A mutation that
  drops the modify hook fails the modify case.

## 9. Support `:ro` properly rather than rejecting it

#591 rejects a mount spec with more than one colon, which fixes a silent
docker collapse - `/a:/b:ro` mounted `/a` at `/a` and dropped both the target
and the option - but REMOVES a working capability for singularity users, where
the spec reached `singularity -B` intact. Proved with a real sandbox on
singularity-ce 4.1.1: writing to a `:ro` bind failed with "Read-only file
system", and without it succeeded.

It was rejected for both runtimes because the published contract is 2-field
only and the singularity support was undocumented and accidental. The honest
resolution is to support the option on both: singularity already takes `:ro`,
and docker takes `--mount ...,readonly`. That turns a capability removal into
a capability everyone gets.

**Left for the owner.** This is a feature, supporting `:ro` on both runtimes,
rather than a bug fix.
