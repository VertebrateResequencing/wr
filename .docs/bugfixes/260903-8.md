# Bugfixes 260903-8

RECORDED, NOT FIXED. Findings from adversarial probing of wr, filed as backlog
items. Nothing on this branch changes any code; none of these has a fix or a
test yet.

Topic: container monitoring and container command construction
(`jobqueue/client.go`, `jobqueue/job.go`, `container/`).

## 1. `--monitor_docker "?"` can adopt, and then SIGKILL, an unrelated container

`setupDockerMonitor` remembers the daemon's current containers when
`MonitorDocker == "?"` (client.go:1146-1151), and `findContainerID` then takes
the FIRST container that has appeared since, with no test of ownership
(client.go:1190-1196):

    containers, err := dm.operator.GetNewContainers(ctx)
    if len(containers) > 0 {
        dm.containerID = containers[0].ID
    }

`GetNewContainers` diffs against the remembered set daemon-wide, so any
container started by anyone on that host during the job's run can be the one
adopted. The adopted id is then used for two things: its memory and CPU are
charged to the job (`resolveContainerMem`, client.go:1155-1183), and on any kill
path - out of time, out of memory, out of disk, signalled, or killed by the
manager - `killCmd` calls `KillContainer` on it (client.go:1920-1928).

User experience: a co-tenant's container is killed, and the job's reported peak
RAM is somebody else's. On a shared submission host with several wr jobs, the
containers can be swapped between two of wr's OWN jobs.

There is no cheap correct fix. A container's processes are children of the
docker daemon, not of the job's command, so there is no ancestry to test.
Closing it needs a correlation wr does not currently collect - a label or name
wr itself sets on the container it is asked to monitor, or the container's
creation time compared against the command's start time - plus a stated policy
for the ambiguous case (two new containers, or none). That is a design decision,
not a patch, which is why it is recorded here.

## 2. Container mounts and the image are interpolated into a shell line unquoted

`DockerRunCmd` (container/run.go:108) builds the command by string
concatenation:

    fmt.Sprintf("cat %s | docker run --rm --name %s%s%s -i %s /bin/sh", ...)

and `dockerMounts` (run.go:120-140) emits
`--mount type=bind,source=%s,target=%s` with the paths as given, plus a fixed
`-w $PWD --mount type=bind,source=$PWD,target=$PWD`. Meanwhile
`Job.containerMounts` (job.go:573-579) splits `ContainerMounts` on `","`.

So the separator wr chose is also docker's `--mount` option separator: a mount
path containing a comma is split into two mounts, both malformed. A path
containing a space breaks the shell word instead, and one containing a shell
metacharacter is interpolated into a line that goes through `/bin/sh`. `$PWD` is
unquoted too, so a working directory with a space in it produces a wrong bind.
Paths with spaces are ordinary on shared filesystems.

User experience: `docker run` fails with an unhelpful parse error, or (worse)
mounts something other than what the user asked for.

## 3. `DockerRunCmd` passes no `--user`

Same line, run.go:108-113: no `--user`, so the container's processes run as
root, while `-w $PWD --mount type=bind,source=$PWD,target=$PWD` bind-mounts the
job's working directory read-write. Anything the command creates there is owned
by root.

User experience: after the job, files and directories under the user's own `Cwd`
are root-owned. The user's own cleanup cannot remove them, and neither can wr's:
`Cleanup` behaviours delete through `os.Root` handles as the runner's user, so a
root-owned subdirectory leaves the workspace undeletable and the job's `Cwd`
littered. Adding `--user $(id -u):$(id -g)` is the usual answer, but it changes
what existing containerised jobs can do (images that expect to write to root-owned
paths inside the image break), so it is a behaviour decision.

## 4. The container name is the job key, and a surviving container blocks the retry

`containerRunCmd` (job.go:556-570) passes `j.Key()` as the `--name`. `--rm`
covers the normal case (the daemon removes the container when it exits), but a
container that OUTLIVES its `docker run` client keeps the name: the runner
SIGKILLed, the host lost, the daemon restarted mid-run. wr only removes it via
`KillContainer` from `killCmd` (client.go:1922), which needs a live runner that
has already identified the container. So after a lost run, every retry of that
job fails immediately at `docker run` with "The container name ... is already in
use", and the failure names an opaque 32-character key rather than the job.

Dropped from this record: the same probe reported that `j.MonitorDocker =
j.Key()` (job.go:567) is written without the Job's lock "while the touch
goroutine is live". The write is not concurrent with that goroutine - `CmdLine`
is called at client.go:1577, and the touch ticker and its goroutine start at
client.go:1632 and later - so the claim does not hold as stated. The write is
still the one unlocked write of a field that `buildJStatus` reads under `RLock`
(job.go:1372), so a future concurrent reader in the runner would make it real.

## 5. `SingularityRunCmd` contradicts its own comment

The doc comment on `SingularityRunCmd` (run.go:163-173) promises "The CWD is
always mounted at / in container". The implementation (run.go:174-179) emits
only `cat %s | singularity shell%s %s` with `-B` for each explicitly configured
mount (`singularityMounts`, run.go:182-184): no bind for the working directory
and no `--pwd`, so the command runs wherever singularity puts it, with whatever
the site's `singularity.conf` happens to bind. Typical site defaults bind the
user's real `$HOME` read-write and NOT wr's working directory, which is the
opposite of what a wr job wants - the job writes to its home instead of its
workspace, and `--change_home` has no effect inside the container. (The
singularity-default half of that is a claim about site configuration, not about
this repo; the missing bind and missing `--pwd` are in the code.)

## 6. A cid-file glob can read a large data file once a second

`GetContainerByPath` falls back to `cidPathGlobToContainer` (operator.go:236)
when the configured path does not exist as a file, and that tries each glob
match through `cidPathToContainer` (operator.go:206) -> `file.GetFirstLine` ->
`file.ToString` -> `os.ReadFile` (fs/file/file.go:51-75), i.e. the WHOLE file
into memory to read its first line. `findContainerID` is called from the
1-second resource ticker (client.go:1861, 2006, 2024-2026) for as long as no
container has been identified, so a `--monitor_docker` glob that matches a large
output file - `*.txt`, `out*` - re-reads that file every second for the life of
the job.

The reported-RAM route needs correcting: `currentMemory(job.Pid)`
(utils.go:270) measures the job's own process tree, not the runner, so the read
does not land there. It lands via the runner's own footprint, which wr
deliberately adds to the job's peak: `ourmem, _ := ownMemoryMB()` and
`peakmem += ourmem` (client.go:2125-2130). So a big glob match inflates the
job's recorded PeakRAM, and with it the RAM wr reserves for its next run.

## 7. `container/docker/docker_test.go` uses the developer's real docker

`pullUbuntuImage` (docker_test.go:180-193) calls
`cli.ImagePull(ctx, "ubuntu", ...)` against `client.FromEnv`, and
`createContainers` then starts containers named `container_1` and `container_2`
in that same daemon (docker_test.go:171-178, 246-267). Running the package's
tests therefore pulls `docker.io/library/ubuntu:latest` into the developer's
real docker, re-pointing the `ubuntu:latest` tag if they had built their own,
and takes names that may collide with theirs. A test that needs a real daemon
should at least use a digest-pinned image and unique names.
