Proven by a 245x A/B on the live production manager: 61,000 limit-0 ready jobs = 19,640ms CPU per 25s (0.79 cores, 41.8% in snapshot) vs 1 ready job = 80ms per 25s, for identical zero real work. Fix by memoising the derived strings (key/group/requirements) on the Job. See "Fix constraints for the implementer" items 1-5 in the doc (invalidate on Requirements/LimitGroups/Cmd/Cwd/MountConfigs/container-field writes; `Job.Key()` is invariant after add so cache unconditionally; keep `priority`/`previousGroup` live; do NOT change `schedulerGroupString`'s output format, it is persisted and parsed elsewhere; `prepareReadyJob` legitimately recomputes requirements and must invalidate; DEVELOPERS.md rule 2 - no new server-wide exclusive lock on the transition path).

- [x] Bug 2 (Priority 2, Finding 2) — the archive path is still serialised on the single bbolt write lock: at only ~660 concurrent runners the archive queue was ~600 deep at ~12/s with a MEAN block of 43s against the 60s ClientMinRequestTimeout floor, which is what makes compress jobs land in `delayed` with Exitcode 0. Fold pending archives into ONE `db.Update` and reply to every waiter individually. Honour every constraint in the doc's Priority 2 "Fix constraints" (per-job error semantics like bbolt.Batch's individual-retry-on-error; keep the archive-vs-change guard at db.go:2425; keep db.wg accounting and the close() drain; keep backupDirty set; follow the shape of bestEffortWriter/drainBestEffort at db.go:1156/1185 but note archives are synchronous request/response, not fire-and-forget). Escalation rule: if per-job reply/error semantics turn out to need restructuring of `handleArchive`/`archiveCompletedJob` rather than a contained writer, STOP that bug, write a `/spec-writer` prompt doc under `.docs/reliable4/` instead, mark this item as escalated-not-fixed, and continue to Bug 3.
  - `archiveJob` no longer calls `db.bolt.Batch` (bbolt detaches its batch the
    instant one starts and arms a fresh `MaxBatchDelay`, so under continuous
    arrival the batches stayed tiny — prod showed 234 concurrent `batch.run`
    goroutines for ~600 pending archives, ~2.5 per batch). It now encodes the job
    (still under `job.RLock`, still outside any transaction), hands an `archiveOp`
    with a buffered(1) reply channel to a single long-lived `archiveWriter`
    goroutine, and blocks on its own reply — the same synchronous contract as
    before. Each wake folds EVERY pending archive into ONE `db.Update` and then
    replies to each waiter individually.
  - Per-job error semantics mirror `bbolt.Batch` exactly: on a failed shared
    transaction the offender is swap-removed, the rest are retried together, and
    each offender is re-run in its own transaction so its caller gets its own
    error. Panic isolation (which `bolt.Update` loses versus `Batch`'s
    `safelyCall`) is restored via `applyArchiveOp` + `errArchivePanic`, so a
    panicking op cannot wedge the writer and every future archive.
  - Shutdown: `stopArchiveWriter()` runs from `finaliseBackup` BEFORE `wg.Wait`
    and the final backup, and `swapArchives(true)` latches the queue shut in the
    same critical section as the last drain, so a late archive gets `errDBClosed`
    instead of hanging. This is strictly stronger than before, where an in-flight
    `Batch` could commit after `wg.Wait`.
  - `arMu` is a strict leaf mutex (append/swap only, never held across the bolt
    write lock); the writer takes no `db.Lock`, `db.wgMutex`, job lock or queue
    mutex, so DEVELOPERS.md rule 2 holds. `db.wg` is untouched (archives never
    used it) and `backupDirty.Store(true)` still happens after the write attempt.
  - The `bucketJobsLive` archive-vs-change guards live in `beBatch.applyChanges`
    and `jobExitData.update` (NOT `archiveJobTx`, as the brief had it) and are
    untouched; bolt serialises write txs so the commit-order reasoning is
    unchanged, and the encode-to-commit window actually shrinks 43s -> 764ms.
  - Files: `jobqueue/db.go`, `jobqueue/db_bench_test.go` (added `bolt_txns/job`,
    new `BenchmarkArchiveSpacedArrivals` for the production arrival regime),
