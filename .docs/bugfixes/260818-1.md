- [x] Bug 1 (Priority 1, Finding 3) — 28-42% of the manager's CPU is spent recomputing an invariant: `Job.schedulerGroupSnapshot` (job.go:1139) runs 2 MD5s + a sort + several allocations for EVERY ready job on EVERY rac cycle, from `Server.snapshotReadyJobs` (server.go:2100). Proven by a 245x A/B on the live production manager: 61,000 limit-0 ready jobs = 19,640ms CPU per 25s (0.79 cores, 41.8% in snapshot) vs 1 ready job = 80ms per 25s, for identical zero real work. Fix by memoising the derived strings (key/group/requirements) on the Job. See "Fix constraints for the implementer" items 1-5 in the doc (invalidate on Requirements/LimitGroups/Cmd/Cwd/MountConfigs/container-field writes; `Job.Key()` is invariant after add so cache unconditionally; keep `priority`/`previousGroup` live; do NOT change `schedulerGroupString`'s output format, it is persisted and parsed elsewhere; `prepareReadyJob` legitimately recomputes requirements and must invalidate; DEVELOPERS.md rule 2 - no new server-wide exclusive lock on the transition path).
  - Memoised the derived scheduler-group strings on the `Job`: new `jobDerived`
    struct (`key`, `requirements`, `group`) in an unexported `Job.derived` field,
    guarded by the Job's existing `RWMutex`. `schedulerGroupSnapshot` is now a
    double-checked memo (RLock fast path; per-job write lock only to compute).
    `priority`/`previousGroup` are still read live; `schedulerGroupString`'s
    output format is byte-identical (asserted in the test).
  - Invalidation: `JobModifier.applyTo` (single exit), `handleUserSpecifiedJobLimitGroups`
    (single exit, all 3 callers hold the write lock), and
    `updateJobRequirementsForRetry` via a **`defer` at the top of the function** —
    the first review cycle caught a tail-placed invalidation being skipped by the
    `jobOverrideAlwaysUseJobReqs` early return, which left a permanently stale memo
    that would have made `ensureGroup` seed `sgroup.req` (what the scheduler
    `bsub`s) from stale requirements. `persistModifiedJobs` now holds the job write
    lock across `handleUserSpecifiedJobLimitGroups` (a pre-existing unlocked
    mutation, contrary to that function's own contract).
  - `Job.Key()` itself is deliberately still uncached: it is called with the job's
    write lock already held (`prepareInputJobs`, `modifyJob` before/after
    `applyTo`, and `derivedLocked`), so a self-locking `Key()` would self-deadlock.
    The hot path reads the key from the memo, so this costs nothing.
  - Files: `jobqueue/job.go`, `jobqueue/server.go`, `jobqueue/serverCLI.go`,
    NEW `jobqueue/reliable4_snapshot_memo_test.go`
    (`TestReliable4SchedulerGroupSnapshotMemoised`,
    `TestReliable4SchedulerGroupSnapshotInvalidated`,
    `BenchmarkReadyBacklogSnapshot`), `developers/wrdev.sh` (new
    `idle-backlog-cpu [jobs] [seconds] [pprofPort]` scale mode).
  - RED/GREEN: derivations over 3 steady rac cycles at a 20k limit-0 backlog
    60,000 -> 0; mallocs per ready job per cycle 18 -> 2;
    `BenchmarkReadyBacklogSnapshot` 125,919,705 ns/op / 18,065,944 B/op /
    340,013 allocs/op -> 4,369,676 ns/op / 0 B/op / **0 allocs/op** (28.8x).
  - Scale gate, real-binary A/B at 50,000 limit-0 jobs, no runners, 13 driven rac
    cycles: pre-fix **4,090ms CPU per 25s** (snapshot 2,670ms, 65%; profile
    reproduces the prod signature snapshotReadyJobs -> schedulerGroupSnapshot ->
    schedulerGroupString -> Requirements.Stringify + 22% GC) FAIL, post-fix
    **800ms per 25s** (snapshot 170ms) PASS => 314ms -> 61ms manager CPU per
    cycle. Prod's pre-fix figure was 19,640ms/25s at a 61k backlog.
  - The gate is hardened against vacuous passes: it FAILs `(NOT MEASURED)` if the
    profile has no `Duration:` line, if total CPU is 0/unparseable, or if no rac
