    disjoint by construction; both halves are pinned by
    `TestReliable4ForkExecErrnoWrapping`. So a farm node missing `bash` still
    retries; only an operator-configured absolute shell path buries.

- [x] Bug 5 (Priority 5, Finding 4) — `killExcessCmds` hands `bkill` an unbounded argv with no timeout, blindly retries the identical failing kill every cycle, and spams 75KB/min of log. Chunk `toKill` to a bounded batch (model the cap on the 260722-1 bsub fix), run each bkill under a context/timeout, use the house `backoff` package (DEVELOPERS.md rule 8) so an identical failing kill is not re-issued every cycle, log a summary (counts + a few sample ids) not the whole id list, and make the outcome distinguishable (how many were actually killed vs already-gone) so "no matching job found" can no longer hide un-reclaimed over-provisioned runners.
  - `jobqueue/scheduler/lsf.go`: `killExcessCmds` no longer builds one giant
    `bkill -b <every id>` argv. The collector now yields just element ids, and a
    new `killElements` hands them to `bkill` in batches of at most
    `maxBkillBatchSize` (package var, default `defaultMaxBkillBatchSize` = **1000**,
    the same value and reasoning as the 260722-1 `maxBsubArraySize`: kill mirrors
    the array submission that created the elements, one knob bounds both sides, and
    an argv of ~12KB is far under any ARG_MAX). Each batch is its own
    `exec.CommandContext` under `bkillExecTimeout` (default 1m, much shorter than
    bsub's 5m because this runs inside a scheduling pass) with a
    `WaitDelay` = `bkillGracePeriod`, and the exec context is derived from
    `context.Background()` — the same deliberate detachment `submitToQueue`
    documents, so scheduling-ctx cancellation cannot abort a kill LSF was already
    asked for, while a hung `bkill` can no longer wedge reclamation. A batch that
    does not run to completion stops the cycle issuing further batches (they are
    left un-deferred, so the next cycle picks them up immediately).
  - Back-off (DEVELOPERS.md rule 8, house `backoff.Backoff`): `killDeferred`
    records, per element id wr has asked LSF to kill, the earliest time it may be
    asked again; `dueForKill` skips deferred ids, so the identical failing kill is
    NOT re-issued next cycle (prod re-issued `339390[7..13]` 1s later). The interval
    is the house jittered exponential — `killBackoffMin` 30s (longer than bjobs'
    few-second lag on a killed element), `killBackoffFactor` 2, `killBackoffMax`
    5m — escalating while kills keep having to be repeated and `Reset()` as soon as
    a cycle needs no repeat. It is calculated ONCE per cycle (one backoff step and
    one debug line however many elements are killed) and applied as a DEADLINE, not
    a sleep: `deferredSleeper` is a `backoff.Sleeper` that records the duration
    instead of sleeping, because this path is polled once per scheduling pass and
    parking a goroutine per element (thousands at prod scale) is the goroutine-storm
    anti-pattern reliable4 removed elsewhere. Nothing can be stranded: an element wr
    has never asked about is ALWAYS due immediately (so newly over-provisioned
    runners are killed with zero delay), and a deferred one is retried at worst
    every `killBackoffMax` forever. `sweepKillDeferrals` (rate-limited to once per
    `killBackoffMin`) drops entries more than 2 ceilings past their deadline, so the
    map is bounded and an element that keeps needing killing keeps its escalation.
  - Outcome is now distinguishable, and the log bounded. `killSummary` classifies
    bkill's per-element output (`Job <id> is being terminated` vs `Job <id>: No
    matching job found`/`already finished`) into `killed` / `alreadyGone`, with
    elements bkill said nothing about counted as killed when it exited cleanly
    (`bkill -b` can be silent) and as `unaccounted` otherwise — so "No matching job
    found" can no longer hide un-reclaimed over-provisioned runners. ONE line per
    cycle carries `requested/killed/alreadyGone/unaccounted/retried/deferred/
    abandoned/batches` plus a 3-id `sample` (`bkillSummarySampleIDs`) and, only when
    something needs attention, the reason and a `loggableProcessOutput`-capped
    output excerpt. It is `debug` for the benign case (including the exit 255 LSF
    returns when some elements were simply already gone — which is what the old code
    warned about ~116 times) and `warn` when something is unexplained: unaccounted
    elements, abandoned batches, a bkill that could not be run, or `retried > 0`
    (an element still reported excess after wr already had it killed = the reliable3
    "lost slots never reclaimed" symptom), which the back-off rate-limits to at most
    one line per interval instead of one per cycle.
