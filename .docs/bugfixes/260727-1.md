# 260727-1 — port-isolated scheduler job names (multi-deployment safety)

- [ ] Make scheduler job-name isolation a first-class, port-derived feature so that
      multiple `--deployment production` managers running on DIFFERENT ports can each
      identify and kill ONLY their own LSF/OpenStack jobs, never another manager's.

  Why this matters (the real requirement, not just reproducer scaffolding):
  - wr should support running several production deployments concurrently on different
    ports (e.g. one per team/pipeline). Today every production manager names its LSF
    jobs `wrp_<hash>` (see `jobqueue/scheduler/scheduler.go` `jobName()` and the
    full-scan prefix in `lsf.go`), derived ONLY from the deployment initial. So two
    production managers' jobs are indistinguishable, and any code that cleans up by the
    `wrp_*` prefix (over-provision `killExcessCmds`, `busy()`, dev tooling) can kill a
    DIFFERENT production manager's running jobs. That is a correctness/safety bug for
    multi-deployment use, independent of the reproducer.

  Interim HACK in place now (branch reliable4):
  - `jobName()` inserts a sanitised `WR_JOBNAME_TOKEN` env value after the deployment
    initial → `wrp<token>_<hash>`; empty by default so single-deployment / production /
    all existing tests are byte-identical. `lsf.go`'s full-scan `jobPrefix` matches the
    same layout. `wrdev.sh` sets `WR_JOBNAME_TOKEN=iso<port>` for its isolated prod-mode
    manager and cleans up only `wrp iso<port>_*`, never a real `wrp_*`.

  Proper fix (later):
  - Derive the job-name namespace from the manager's own identity — the managerport is
    the natural key (unique per running manager) — plumbed through `ServerConfig` →
    `scheduler.Config{LSF,OpenStack,Local}` → `jobName()`, NOT from a process-wide env
    var. Each manager then namespaces its scheduler jobs automatically; no env opt-in.
  - Keep the default single-production-manager prefix backward-compatible if feasible, OR
    accept a one-time migration (a manager only ever kills jobs it can now see as its own).
  - Apply the same isolation to the OpenStack scheduler's resource names if they carry the
    same cross-manager collision risk (`ResourceName`/server naming).
  - Regression tests: (a) two managers on different ports produce disjoint job-name
    prefixes and neither's cleanup matches the other's jobs; (b) a lone production manager's
    prefix is unchanged (or migrates cleanly); (c) `busy()`/`killExcessCmds` only ever act
    on the owning manager's jobs.
