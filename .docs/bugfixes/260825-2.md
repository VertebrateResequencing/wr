# Bugfixes 260825-2

Both items come from the live prod investigation in
`.docs/reliable4/prod-restart-260825.md` (Findings 2 and 6). They are the two
bounded transaction-count wins on the prior-state-recovery path. The **memory**
half of Finding 6 (recovery retaining a per-job copy of every dep group's
membership, which OOM-killed the manager four times at 175-181 GB) is a design
change being routed separately — do not attempt it here.

- [x] `Dependencies.incompleteJobKeys` (`jobqueue/dependency.go:159`) calls
  `db.depGroupsEverSeen(...)` unconditionally, and `depGroupsEverSeen`
  (`jobqueue/db.go`) wraps its loop in a bolt `View` transaction — so a job with
  **no dependencies at all** still costs a full bolt read transaction.
  `recoverPriorJobs` calls this once per recovered job, so prod's last recovery
  paid **150,472 pointless read transactions** against a cold-mmap 7 GB NFS DB.
  Skip the lookup when the job has no dep groups.

- [x] The whole dependency-resolution pass is one-or-more bolt `View`
  transactions **per job**: `recoverPriorJobs` -> `recoveredItemDef` ->
  `Dependencies.incompleteJobKeys` -> `depGroupsEverSeen` (one View), plus per
  dep-group dependency `retrieveIncompleteJobKeysByDepGroup` (another View) and
  per essence dependency `checkIfLive` (another). `recoverPriorJobs` already
  holds the complete job list before it enqueues anything, so the pass can run
  inside **one** transaction instead of hundreds of thousands. Transaction-count
  and page-fault fix only: do not change what any of these functions return.

## Red command (both items, proven RED at bf53de0)

Measured with **bbolt's own built-in read-transaction counter**,
`db.bolt.Stats().TxN` — no new instrumentation is needed for this, and the
regression tests should use the same mechanism rather than adding an inert
counter. A throwaway harness in package `jobqueue` opened a fresh dev DB via
`initDB` and called `deps.incompleteJobKeys(db)` 1000 times, once with an empty
`Dependencies` and once with one dep-group dependency spread over 20 distinct
groups, recording the `TxN` delta for each. Runtime **0.01s**:

```
RED MEASUREMENT over n=1000 jobs:
  dependency-free jobs: 1000 bolt read transactions (want 0)
  dep-group jobs:       2000 bolt read transactions (want O(1), ie <= 20 distinct groups)
BUG 1 REPRODUCED: 1000 dependency-free jobs cost 1000 bolt read transactions, want 0
BUG 2 REPRODUCED: 1000 jobs over 20 distinct dep groups cost 2000 bolt read transactions, want <= 20
--- FAIL: TestZZRedDependencyTxCount (0.01s)
```

Scaled to the 150,472 jobs prod recovered: 150,472 transactions for the
dependency-free case, and two per job for the dep-group case. The harness was
deleted after measuring; the regression tests that replace it are part of the
fix.

**Read the dep-group number carefully.** The 2000 above is the cost of the
**per-job control path** (`incompleteJobKeys` called once per job), and item 2
deliberately leaves that path alone — a caller that resolves one job at a time
still pays per job. Item 2's win is on the **recovery pass**, which resolves every
job together: its target is O(chunks) transactions for the whole pass instead of
O(jobs). Measure item 2 there, not on the per-job path, or a later reader will
think it regressed.

An end-to-end timing gate was considered and rejected as the red command: on warm
local disk a bolt `View` costs single-digit microseconds, so 150k of them are
invisible in wall-clock. The cost only becomes minutes in prod's regime (a
brand-new, wholly cold 7 GB file on NFS), which cannot be reproduced on this host
without competing for the same NFS volume that the live production manager is
currently recovering on. The transaction count is the honest measurement.

## Flake occurrence logged (not waived, not attributed to these fixes)

`TestSubscriptionReconnectResync` failed once during this batch's full-suite runs
after **63.49 s**, at `uptime` load 111.16 / 112.95 / 112.29. It passed
standalone immediately afterwards (3.26 s) and in two subsequent full suites on
the same code. It is the known load-dependent flake class documented in
`.docs/bugfixes/260626-3.md` and named with its 3 s bound in
`.docs/reliable4/next-steps-260819.md:479`.

It cannot plausibly be caused by this batch: the test's jobs have no dependencies
and no dep groups, so the only changed code it reaches strictly **removes** work
(the empty-dep-group lookup is skipped, and its single recovered job is resolved
in one transaction instead of several). Its 63 s runtime is a subscription-update
wait timing out, not dependency resolution.


## Both items fixed (2026-08-25, branch `reliable4`)

**Item 1** — the guard went into `depGroupsEverSeen` itself (early return of an
equivalent empty map before `db.bolt.View`), not the `dependency.go` call site, so
all five callers benefit and no future caller can reintroduce the cost.
Dependency-free jobs **1000 tx -> 0**; essence-only jobs 2 -> 1, since they were
paying the same empty lookup.

**Item 2** — the four reads in the chain (`depGroupEverSeen`,
`depGroupsEverSeen`, `retrieveIncompleteJobKeysByDepGroup`, `checkIfLive`) became
tx-scoped functions behind a `depReader` interface, with `txDepReader` answering
all four from one `*bolt.Tx`, and a new `(*db).resolveDependencies(ctx, jobs)`
resolving every recovered job in **one transaction per chunk** of
`dependencyResolutionChunkSize = 1000`. `recoverPriorJobs` calls it once before
the itemdef loop; `recoveredItemDef` takes the pre-resolved `resolvedJob` pair.
The pass is deliberately a **separate sweep** from the itemdef loop, because that
loop calls `scheduler.Recover` (ssh) and `limiter.Increment` and DEVELOPERS.md
rule 1 forbids holding anything across those.

Measured: 100-job pass **156 tx -> 1**; the same pass at chunk size 10 -> **10**;
an end-to-end DB-preserving restart **48 tx -> under 24**. At prod's 150,472 jobs
that is ~151 transactions instead of ~450,000.

**Chunking was required by review, not chosen.** A single read transaction for the
whole pass would hold `mmaplock.RLock()` for the pass's entire duration, so any
write needing to grow the bolt mapping (`DB.mmap` takes `mmaplock.Lock()` when the
high-water mark reaches `datasz`) blocks for the transaction's remaining life -
and because that writer holds `db.rwlock`, every other write queues behind it.
That is a **db-wide write stall** reaching `add`, `archive`, `bury`, `release` and
therefore the RPC handlers holding the queue mutex: precisely the Finding 4
signature in `.docs/reliable4/prod-restart-260825.md` (`jtouch` 16m38.97s, `add`
16m33.76s, 14 `getin` all completing in the same second). Holding it for a whole
pass would have bounded that stall at the whole recovery - 21 min and 42m56s in
prod. Chunked, the exposure is ~1/151 of a recovery, about 8 s at prod's measured
21-minute recovery, and the win survives to within 0.03%.

### Verification

- **Semantic equivalence** - the load-bearing property, since this code decides
  whether jobs run. The reviewer dumped resolved keys and `waitingForDepGroups`
  for **17 dependency shapes** through both entry points, on the working tree and
  on a `git worktree` at `bf53de0`: **byte-identical**, nil-vs-empty included.
  Then a chunk-boundary sweep of 68 jobs cycling all 17 shapes at chunk sizes 0,
  1, 2, 3, 5, 16, 17, 18, 67, 68, 69 and 1000 - 816 resolutions - collapsed to
  exactly 17 distinct answers, identical to HEAD's per-job answers. **No job's
  answer depends on which chunk it landed in.**
- **Mutation-tested**, by the reviewer running each mutation rather than reading a
  mapping: one `View` for the whole pass (the rejected design) fails **only** the
  exact chunk-count assertion at `:346` (10 vs 1), so that assertion is the sole
  guard against regressing; dropping the per-job `ctx.Err()` fails `:371`/`:400`;
  a collect-errors-and-return-late design that opens every chunk's transaction
  fails `:405`; rotating `deps` by one against the jobs fails `:507`, `:568` and
  `:592`.
- **No leaked transactions on cancel:** `OpenTxN == 0` asserted and verified, and
  `db.close` (which needs `mmaplock.Lock()`) completed in 0.16 s in every leaf, so
  a leak would have hung it.
- **Rule 1 confirmed:** `txDepReader` holds no `*db`, so no nested `View` is
  reachable; ssh, `scheduler.Recover` and `limiter.Increment` all stay outside.
- **Gates:** `make lint` 0 issues; `make test` **417 passed - 9 skipped - 29
  packages** (413 baseline + 4 new tests); `go vet -tags netgo ./jobqueue/` clean;
  `gofmt -l` empty; `-race` on the new tests clean. Load 112-115 throughout.
- **Scope held:** no dep-group de-duplication anywhere in the diff.
  `sortedStringSet` still allocates per job and `itemdef.Dependencies` shares the
  same backing array, so the memory shape is unchanged and
  `.docs/dep-granularity/` will not collide. Peak memory grows by
  `len(jobs)` x 32 B (~4.8 MB at prod scale) for the `resolvedJob` slice.

### Findings carried forward (none blocking)

- **`recoverIncompleteJobs` still holds ONE read transaction for the entire
  live-bucket decode** (`jobqueue/db.go:2497`) - ~37 s at prod's size, with
  `mmaplock.RLock()` held throughout. That is the exact mechanism this batch's
  chunking exists to avoid, one function away. It runs before `Serve` returns so
  concurrent writers are less likely, but it deserves its own item.
- **`So()` inside a polled condition, second occurrence.** `depTxJobStates` is
  called from a `pollUntil` closure that can run ~1500 iterations; go-conventions
  bans `So()` in loops over 20. Verbatim the finding already carried in
  `260825-1.md` about `readLogFile`. Fix: return an empty map on error, assert
  once outside the poll.
- **`max(1, dependencyResolutionChunkSize)` is an unpinned guarantee** - no test
  drives the var to 0, so deleting the `max` would fail nothing. Same class as
  `260825-1`'s `case <-ctx.Done():` note: pin it or drop it.
- **`depGroupEverSeen` is dead in production** - `(*Dependency).incompleteJobKeys`'s
  `d.DepGroup != ""` branch is unreachable (its only non-test caller is guarded by
  `dep.DepGroup == ""`), and this change adds a `depReader` method purely for it.
  Separate cleanup.
- `cleanorder -min-diff` was accepted on `dependency.go` (it insists on placing
  `resolveDependencies` at the end of the file, verified genuine and idempotent)
  and deliberately skipped on `db.go`, where it would hoist the
  `archiveTxObserver` / `maxArchivedBytes` declarations that `260825-1`'s open
  items sit on.
