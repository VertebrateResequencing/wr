# Bugfixes 2026-09-07

- [x] `DockerRunCmd` (`container/run.go:119`) passes no `--user`, so a
  containerised job's processes run as the container image's user - normally
  root - while `workDirMountArgs` bind mounts the job's working directory
  read-write at the same path. Everything the command creates under the user's
  own `Cwd` is therefore root-owned. The user's own cleanup cannot remove it,
  and neither can wr's: `Cleanup` behaviours delete through `os.Root` handles as
  the runner's user, so a root-owned subdirectory leaves the workspace
  undeletable and the user's `Cwd` littered.

  The repo owner's decision is **opt-out, defaulting ON**: pass
  `--user <uid>:<gid>` by default, with a flag to turn it off for images that
  genuinely need to write to root-owned paths inside the image. Always-on was
  rejected for having no escape hatch, opt-in for leaving the bad default in
  place. That choice is settled and is not to be re-litigated.

    - Fixed. `container/run.go`'s new `runAsCallingUserArgs` const emits
      ` --user "$(id -u):$(id -g)"` and `DockerRunCmd` gained an `imageUser
      bool` that suppresses it. The uid and gid are shell substitutions rather
      than `os.Getuid()`/`os.Getgid()` for the same reason `$PWD` is one in the
      adjacent `workDirMountArgs`: `Job.CmdLine()` is called from
      `Client.Execute()` (`jobqueue/client.go`) in the runner process on the
      execution host, and that same process's shell then runs the line, so a
      run-time substitution is evaluated as the user that actually runs the
      command - the same user whose `os.Root`-based cleanup has to be able to
      delete the files - and stays correct even if the process that runs the
      line is ever not the one that built it. It also keeps `DockerRunCmd` a
      pure function whose unit tests don't depend on the uid of whoever runs
      the suite. The reasoning is in a comment next to the const.
