- [x] Removed jobs reappear on the status web UI after refreshing the page (regression from the absolute-state status broadcast rework earlier on this branch). Repro: `perl -e 'for (1..10000) { print "echo $_\n" }' | wr add -i echo`; let some complete; then `wr remove -a` while many are still pending. The live view correctly shows the echo repgroup as part red (deleted) + part green (complete). But refreshing the page should then show nothing for echo, because the repgroup now has only complete members (the removed jobs are gone) and complete-only repgroups are not shown by default on a fresh load. Instead, after refresh the removed jobs reappear (echo shows again with the red deleted bar). The fresh-connect seed must match the old `current` semantics: include a repgroup only if it has >=1 live (non-terminal) job, send its live states + complete, never send deleted, and omit complete-only / deleted-only repgroups. Live updates to already-connected clients must still include deleted (transient red) and complete, so 260625-6 "Keep completed repgroups visible" during a live session does not regress.
  - Root cause: `statusState.subscribe()` seeded a fresh subscriber's dirty set with every RepGroup in `s.counts`, and per-RepGroup counts persist the `deleted` state, so a refreshed page's first drain returned echo `{complete, deleted}` and rendered the red deleted bar — reviving removed jobs.
  - Fix (`jobqueue/statusstate.go`): a per-subscriber `seed` map captured atomically under the statusState lock at subscribe time via `liveSeedLocked()` — it includes a RepGroup only if it has >=1 live (non-terminal) job, sends its live states + `complete`, strips `deleted`, and omits complete-only / deleted-only RepGroups (matching the old `current` semantics). `drain()` returns the seed on the first drain (RepGroups that went dirty between subscribe and first drain win), then clears it; subsequent drains are pure live updates.
  - Live behaviour unchanged: transitions to already-connected clients still deliver `deleted` (transient red) and `complete`, so a RepGroup completing while the page is open stays visible (260625-6). The `+all+` live aggregate already excluded complete/deleted.
  - Tests: new `TestStatusStateSeedSemantics` (fails pre-fix: seed contained `deleted`, and complete-only/deleted-only RepGroups were present) and a browser fixture `jobqueue/testdata/removed-jobs-refresh/` reproducing remove-then-refresh (fails in pre-fix `WR_FIXTURE_SEED=unfiltered` mode showing echo's `4000 (deleted)` bar; passes after), wired into `make browser-test`. Corrected one existing reconnect assertion in `statusstate_test.go` that encoded the regressed behaviour (a reconnect is a fresh subscription, so a now-complete-only RepGroup is omitted), keeping the live+complete positive coverage.
  - `statusState.mu` stays a strict leaf; the seed is captured under the same lock that registers the subscriber (no transition lost). Verified by implementor and reviewer: `make lint` clean, `make test` pass, focused `-race` pass, `make browser-test` pass; reviewer independently confirmed the Go test and browser fixture both discriminate the bug.
