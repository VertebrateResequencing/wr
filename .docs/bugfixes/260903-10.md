# Bugfixes 260903-10

Branch `fix-cleanup-sweeps-nested-jobs`: a job's default `cleanup` behaviour
recursed into the workspaces wr had built for the jobs that job itself added,
and through any live mount inside its own working directory, destroying a
running child's output, its TMPDIR and the objects behind the child's mount.

## Where this came from

Not from an adversarial probe: from composing wr's own defaults. Every step is
a default or a hardcoded value, so the loss needs no attacker, no symlink and
no race.

| step | where | value |
| --- | --- | --- |
| a job's `--on_exit` defaults to cleanup | `cmd/add.go:689` | `[{"cleanup":true}]` |
| a job's `--cwd` defaults to the current dir | `cmd/add.go:909` (`defaultCwd`) | `os.Getwd()` when the manager is local |
| a job's Cmd runs IN the working directory wr made | `jobqueue/client.go:1306` | `cmd.Dir = actualCwd` |
| so `os.Getwd()` inside a job IS that job's `ActualCwd` | - | - |
| `wr bsub` hardcodes both | `cmd/lsf.go:146-147` | `Cwd: wd, CwdMatters: true` |
| cleanup runs BEFORE the unmount | `jobqueue/client.go:2164` vs `2171` | `TriggerBehaviours` then `Unmount` |

Composed, that is: a job that adds jobs - the documented `wr add --bsubs`
pattern for nextflow and cellranger - places its children's workspaces inside
the directory its own default cleanup is licensed to wipe, and wipes it while
they are still running and still mounted.

Nothing refuses it, and nothing should: the parent's `ActualCwd` genuinely is
the directory wr built for the parent, so `createdCwdRel`,
`relIsJobCreatedCwd`, `realDirBelow` and the `os.Root` handles all correctly
say yes. The children's trees are simply inside the licensed `RemoveAll`.

## The demonstration

Measured on the branch point (`e8c3e55a`), one parent job with the default
`cleanup` behaviour and two children built the way wr builds them:

- child A: `wr bsub`'s shape - `Cwd: os.Getwd(), CwdMatters: true` - so its
  command runs directly in the parent's working directory, where it had written
  `cellranger_results.txt`.
- child B: a plain `wr add` inside the parent's script - `--cwd` defaults to
  `os.Getwd()` again - so wr made it a workspace of its own INSIDE the parent's
  working directory, with `--mounts`, and its mount point held a live FUSE
  mount of a directory standing in for the user's object store.

```
parent cleanup error: 1 error occurred:
        * RemoveAll cwd: device or resource busy

still there? false <- .../cwd/cellranger_results.txt
still there? false <- .../cwd/jobqueue_cwd/4/8/d/4dad.../cwd/child_results.txt
still there? true  <- .../cwd/jobqueue_cwd/4/8/d/4dad.../cwd
still there? false <- .../cwd/jobqueue_cwd/4/8/d/4dad.../tmp
still there? false <- <backing dir outside the parent's Cwd>/REMOTE_OBJECT
```

The running child's results, its TMPDIR, the parent's own output and **the file
behind the child's live FUSE mount** were all unlinked. Only the mount point
directory itself survived, because `rmdir` got EBUSY - which is also the only
reason the loss was ever visible as an error.

`os.Root`'s `RESOLVE_BENEATH` does **not** imply `RESOLVE_NO_XDEV`, so a
deletion bounded by a root still crosses a live mount inside that root and
unlinks the backing objects.

### The second exposure, same root cause

`keptDirs` is built only from the Job's own `MountConfigs`
(`jobqueue/workspace.go`, `keptDirs()` and `protectCaches`), so any live mount
inside the workspace that wr did not configure - one the job's own command
raised with sshfs or s3fs, or a nested `wr`'s muxfys mount - is described by no
keep set and gets recursed through.

## The fix

Both protections belong in the sweep, not in the CLI: a CLI change would not
protect the jobs already submitted and already configured this way, and the
manager's lost-job cleanup runs the same sweep over a workspace it did not
create.

### 1. Never delete another job's workspace tree

`nestedWorkSpaceBase` (`jobqueue/utils.go`) keeps any entry of a swept
directory whose name ends in `createdCwdBaseSuffix` (`"_cwd"`).

Nothing wr made for the job being swept can be inside such an entry: that job's
own base component is ABOVE its workspace (`<Cwd>/<AppName>_cwd/k0/k1/k2/<leaf>`
is the workspace; the sweep works at `<leaf>` and below), and the sweep never
goes above it. So an entry of that shape belongs to a different job.

The name is matched by SUFFIX, never against `AppName+createdCwdBaseSuffix`:
`AppName` is a mutable package var, `"jobqueue"` by default and `"wr"` only in
`cmd/runner.go:157`, and cleanup runs in both processes, so an equality check
would silently protect nothing in one of them. `relIsJobCreatedCwd`
(`jobqueue/utils.go:1290`) already matches the suffix for that reason, so this
is the consistent rule rather than a new one. Matching a suffix also spares a
user directory that merely ends in `_cwd`, which is the safe direction.

### 2. Never cross a mount boundary

`crossesMountBoundary` compares the device number of an entry against that of
the directory being swept - both `Lstat`ed through the held `os.Root`, both read
as `Sys().(*syscall.Stat_t).Dev` - and refuses to delete or descend when they
differ. That is `RESOLVE_NO_XDEV` semantics done by hand.

It costs one `Lstat` per entry, on a path that was already reading the
directory, and it protects every live mount rather than only the ones wr
configured. Two `os.FileInfo`s are compared rather than a `uint64` carried down,
so no platform-dependent conversion of `Stat_t.Dev` is needed anywhere. A host
that hands back no `*syscall.Stat_t` can tell us no devices, and the answer is
then "no boundary", which leaves the sweep exactly as it was rather than
stranding every workspace on such a host.

### Why both

Protection 2 covers protection 1's case only when the child has a live mount.
A child's plain files - child A above, and a child between mounts - are on the
same device as the parent's working directory, so only the name rule saves
them. Protection 1 covers protection 2's case only when the mount is inside a
wr-made workspace; a mount the job's own Cmd raised anywhere else in its working
directory has no `_cwd` component above it. Neither subsumes the other.

### Applied at every deletion inside the workspace

This file has twice had a bug where one consumer understood something and its
siblings did not, so the guards live in the one function all four sites now go
through, `removeEntryWithExceptions`:

| site | before | after |
| --- | --- | --- |
| the working-directory sweep, no keeps | `wsRoot.RemoveAll(actualCwdName)` | `removeAllGuarded(wsRoot, actualCwdName)` |
| the working-directory sweep, with keeps | `removeAllExcept(actualCwdRoot, keepDirs)` | same call, now guarded per entry |
| `removeWorkSpaceEntries` | `wsRoot.RemoveAll(entry.Name())` | `removeAllGuarded(wsRoot, entry.Name())` |
| `removeTmp` | `wsRoot.RemoveAll(createdTmpName)` | `removeAllGuarded(wsRoot, createdTmpName)` |

A directory is now descended into and then removed, rather than handed to
`os.Root.RemoveAll`, because `RemoveAll` asks neither question of what it finds
on the way down - and the deeper entries are exactly the ones that are another
job's live output or the user's remote objects. That made
`exceptionDirs`' second return value (the set of dirs to recurse INTO to reach
an exception) redundant: every dir is recursed into now, so `keepDirs` alone is
enough.

The upward walk - `dirChain.removeUpward`, `removeEmptyParents`,
`rmEmptyDirsIn` - is deliberately NOT guarded. Every removal it makes is an
`rmdir` that only succeeds on an empty directory, so it cannot destroy data, and
guarding it by name would leave the job's own `<AppName>_cwd` base behind after
every single job. It already tolerates `ENOTEMPTY` via `errIsDirNotEmpty`, which
is what stops when a kept child tree holds the chain open.

### Widening only

Every changed decision can only stop a deletion:

- the two new guards `return nil` without deleting;
- the keep-set check now runs BEFORE the is-it-a-file case, so a keep-listed
  file survives where it used to be removed (exceptions are mount points and
  cache dirs, so this is theoretical, and it deletes less either way);
- descend-then-`rmdir` deletes exactly what `RemoveAll` deleted when nothing is
  kept, and less when something is;
- `ENOENT` on a removal, and `ENOTEMPTY` on the `rmdir` of a directory whose
  contents were just swept, are reported as success instead of as errors. That
  changes error reporting, never what is deleted: the EBUSY error the
  demonstration shows is gone because the mount is no longer recursed into at
  all.

One divergence is worth naming: the entry type now comes from
`dirRoot.Lstat(rel)` rather than from `entry.IsDir()`. On a filesystem that
returns `DT_UNKNOWN`, `DirEntry.IsDir()` lstats through the file's own NAME
rather than through the root handle, so taking the type from the root is
strictly the safer of the two. The only behavioural difference is an entry that
changes type between the readdir and the lstat, and in that race the entry is
inside the job's own workspace with both guards still applied to whatever is
below it.

### The leak this costs

A parent whose children left workspaces behind no longer reclaims its own
workspace fully: the child tree keeps the parent's working directory non-empty,
which keeps the workspace non-empty, which stops the upward walk. So a parent
job's cleanup now leaves behind `<Cwd>/<AppName>_cwd/k0/k1/k2/<leaf>/cwd/` down
to the child's tree, having still deleted its own output files and its own
`tmp`.

That is the correct trade and it is stated in the comment on
`nestedWorkSpaceBase` so nobody "fixes" it back: a workspace left behind is
recoverable by hand, a running job's output is not. `TestCleanupOfNestedJobWorkSpace`
asserts the surviving parent directories, so the trade is pinned by a test as
well as by a comment.

## Review findings

### A: the device the sweep compares against

`removeAllExcept` and `removeAllGuarded` read the swept directory's info with
`os.Root.Stat(".")`, while every entry's side of the comparison comes from
`os.Root.Lstat`. `removeWithExceptions` documents that its `dirInfo` is the
LSTAT of the directory being swept, so the two sources disagreed on paper, and
the whole guard is a comparison of the device numbers they produce.

The dangerous direction - the sweep failing to refuse and crossing a mount
after all - is NOT reachable, and neither is the leak. `.` names the directory
the root's file descriptor already refers to, and a directory entry called `.`
is never a symlink, so `Stat(".")` and `Lstat(".")` resolve the same inode
through the same fd. Measured: identical device and inode for a root opened on
a real directory, for one opened through a symlink to it, for one opened as
`root.OpenRoot(".")`, and for one whose directory was replaced by a symlink to
somewhere else after the root was opened. So the change makes the source
consistent with the contract and changes no behaviour, and no test can
distinguish the two calls: reverting `Lstat` to `Stat` leaves every case green.

What WAS missing is coverage of the value itself.
`TestCleanupCrossesNoMountBoundary` drove only the mount-free sweep, which
lstats each directory as it descends into it and never uses what these two
functions read. It now runs over `nestedSweepCases()`, so the sweep around a
keep set is driven too - `removeAllExcept` is the one caller whose `Lstat(".")`
is the device basis for a DIRECT entry of the swept working directory, and the
live mount is a direct entry of it.

| # | mutation | compiles | red case |
| --- | --- | --- | --- |
| M8 | `Lstat(".")` back to `Stat(".")` at both sites | yes | none, for the reason above |
| M9 | `removeAllExcept` reading `dirInfo` from a directory other than the swept one (`os.Lstat("/proc/self")`, another device) | yes | `TestCleanupCrossesNoMountBoundary` with 1 mount, and not with 0 |

### B, C and D

- B: `mountLoopbackOver` now reports whether the mount was raised and the test
  skips on a refusal, because a host can have `/dev/fuse` and a `fusermount`
  binary and still deny an unprivileged mount; with the mount forced to fail
  the test skips, where the `So(err, ShouldBeNil)` it replaces failed.
- C: `nestedWorkSpaceBase`'s doc says what it matches - a name suffix, on any
  entry, file or directory - and that keeping a user entry whose name merely
  ends in `_cwd` is the deliberately conservative direction.
- D: `canMountFuse`'s doc describes the best-effort availability check it is,
  an openable `/dev/fuse` and a `fusermount` on `PATH`, rather than claiming it
  detects a setuid binary.

## Follow-up bug: the keep-set check moved ahead of the is-it-a-file case

- [x] The restructured sweep leaves a symlink behind that shipped behaviour
  deletes. `removeEntryWithExceptions` now tests `keepDirs[rel]` BEFORE it
  lstats the entry, so a keep-set member that is a symlink survives. On
  `origin/develop` the switch tested `!isDir` FIRST, so a kept NON-directory

## New bug, NOT fixed here: the mount-boundary guard is blind at a mount ROOT

- [ ] `crossesMountBoundary` compares an entry's device against the device of the
  directory it is an entry of, so it sees no boundary when the SWEPT DIRECTORY
  is itself a mount root: every entry of a mount root is on the mount's own
  device. The sweep then walks into the user's remote file system and unlinks
  what is behind the mount. Two sweeps take a device that can be a mount root's:

  | sweep | device from | reachable shape |
  | --- | --- | --- |
  | `removeAllExcept` (`jobqueue/utils.go:1352`) | the WORKING DIRECTORY's own `Lstat(".")` | the Job's Cmd mounts over the working directory wr gave it, while the Job has a `MountConfig` inside that directory, so `inActualCwd` is non-empty and `removeActualCwd` (`jobqueue/workspace.go:964`) takes the `removeAllExcept` branch |
  | `removeAllGuarded` (`jobqueue/utils.go:1368`), `removeWithExceptions` (`jobqueue/utils.go:1404`) | the WORKSPACE's own `Lstat(".")` | the Job's Cmd mounts over the WORKSPACE, which needs no keep set at all: `removeWorkSpaceEntries` (`jobqueue/workspace.go:907`) then wipes the remote's top level |

  The second is the wider hole, and it contradicts the assumption that a
  mount root can only be reached through the keep set.

  None of the four keep-set classifications covers either shape, because the
  mount is one the Job's own Cmd raised (sshfs, s3fs, a nested wr) and so is
  described by no `MountConfig` wr has ever seen:

  - `wholeActualCwd` (`jobqueue/workspace.go:589`) is set only by a
    `MountConfig` or cache that resolves to `.` relative to the working
    directory (`protectInActualCwd`, `:759-771`).
  - `inActualCwd` (`:593`) holds the CONFIGURED mount's rel, which the Cmd's
    mount SHADOWS, so `keepDirs[rel]` (`jobqueue/utils.go:1455`) matches nothing
    the sweep sees. It is what makes the site reachable rather than what
    defends it.
  - `workSpaceEntries` (`:598`) records the working directory's own NAME, which
    protects it from the workspace sweep and says nothing about its contents.
  - `wholeWorkSpace` (`:619`) needs a `MountConfig` at or above the workspace,
    or a `CacheDir` that IS the workspace (`:637-729`).

  The identity proofs do not refuse it either. `ws.actualCwdInfo` is captured in
  `prove()` (`jobqueue/workspace.go:510` -> `proveBelow` `:540` ->
  `proveActualCwd` `:560`) milliseconds before the sweep in the same call, and
  the snapshot (`:140-146`) carries only strings, so a mount that is already up
  when cleanup runs is exactly what gets lstat'ed and `proveSameDir`
  (`jobqueue/utils.go:1119`) compares like with like and passes. The proofs bite
  only on a mount raised in the window BETWEEN `prove()` and
  `actualCwdNow`/`openVerifiedDir`.

  Evidence: three tests over real unprivileged `hanwen/go-fuse` loopback mounts,
  written against `1ee4fe7c` and kept out of this branch at
  `<scratchpad>/mount_root_blindness_test.go.txt`
  (`TestCleanupCrossesNoMountBoundaryAtTheWorkingDir`,
  `TestCleanupCrossesNoMountBoundaryOverAPopulatedWorkingDir`,
  `TestCleanupCrossesNoMountBoundaryAtTheWorkSpace`). Re-run independently in a
  detached worktree at `1ee4fe7c`; all three RED, and the existing
  `TestCleanupCrossesNoMountBoundary` green beside them:

        --- FAIL: TestCleanupCrossesNoMountBoundaryAtTheWorkingDir (0.01s)
          Actual: 'stat .../004/REMOTE_OBJECT: no such file or directory'
        --- FAIL: TestCleanupCrossesNoMountBoundaryOverAPopulatedWorkingDir (0.01s)
          Actual: 'stat .../002/REMOTE_OBJECT: no such file or directory'
        --- FAIL: TestCleanupCrossesNoMountBoundaryAtTheWorkSpace (0.02s)
          Actual: 'stat .../002/REMOTE_OBJECT: no such file or directory'
          Actual: 'stat .../004/cwd/remote_output.txt: no such file or directory'

  `REMOTE_OBJECT` is the loopback's BACKING file, outside the Job's `Cwd`
  entirely, so each of those is a deletion through a live mount and not a
