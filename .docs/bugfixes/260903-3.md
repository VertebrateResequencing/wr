## 1. A workspace that vanishes mid-sweep escapes as an error

`jobWorkSpace.empty` (workspace.go:813) tolerates the workspace having gone by
the time it opens it: `openLeaf`'s ENOENT returns nil (workspace.go:816-818),
and both later lstats do the same (`actualCwdNow`, workspace.go:859;
`removeActualCwd`, workspace.go:962). The last step does not.
`removeWorkSpaceEntries` (workspace.go:903) reads the directory with
`readDirIn(wsRoot, ".")`, whose `Open(".")` on a directory unlinked since
`openLeaf` fails with ENOENT, and that error is returned unfiltered
(workspace.go:904-907). So when a second cleanup of the same job removes the
workspace inside that window, the first one errors - contradicting the comment
directly above `empty` that says a workspace already gone is not a failure.

Impact is a leak, not a deletion: `cleanup` (workspace.go:790-799) returns the
error before `chain.removeUpward()`, so the empty parent directories that
cleanup exists to tidy are left behind, and the error surfaces as a behaviour
warning. Two cleanups of one job is the ordinary state for a lost job (the
runner's own and the manager's).

Outcome: FIXED.

- Red command, on develop `cb9bb032` with go1.27.1:

      CGO_ENABLED=1 go test -tags netgo --count 1 ./jobqueue -run 'TestCleanupWorkSpaceGoneAfterItWasOpened'

  It exited 1, failing on `soPathsGone` for `<cwd>/jobqueue_cwd`, which was
  left behind. The error `cleanup` returned was:

      readdirent <cwd>/jobqueue_cwd/b/b/8/<key>-<uuid>/.: no such file or directory

  So the failure is not at the `Open(".")` described above. On Linux, opening
  "." through a handle whose directory has been removed still succeeds, and the
  `getdents64` behind `ReadDir` is what returns ENOENT.
- Fix: `removeWorkSpaceEntries` (`jobqueue/workspace.go`) now passes an error
  from `readDirIn` through `ignoreGone`, so a workspace removed since `empty`
  opened it counts as already gone, which is how the open already treats it.
  `cleanup` then goes on to `chain.removeUpward()`. The deeper sweeps
  (`removeSweptDir`, `removeMuxfysCacheEntries`) are unchanged.
- Test seam: `workSpaceOpenedHook` (`jobqueue/behaviours.go`, beside
  `cleanupProvenHook`), called by `empty` once it holds the workspace handle
  and before anything is read through it. It is nil in production.
- Regression test: `TestCleanupWorkSpaceGoneAfterItWasOpened`
  (`jobqueue/workspace_test.go`). It builds a real workspace, removes it from
  the hook and runs the `Cleanup` behaviour. It then asserts that the workspace
  and `jobqueue_cwd` are gone and that Cwd and a user file in it survive,
  followed by `So(err, ShouldBeNil)`. It is red without the `ignoreGone` and
  green with it.

## 2. `removeEntryWithExceptions` tests `!isDir` before the keep set

utils.go:1395-1405:

    switch {
    case !isDir:
        return dirRoot.Remove(rel)
    case keepDirs[rel]:
        return nil

So an exception that the keep set protects is deleted anyway whenever its
on-disk entry is not a directory. Judged HARMLESS TODAY, on two counts:
`os.Root.Remove` unlinks a symlink rather than following it, so nothing inside
the target is touched; and every exception reaches the set through
`protectInActualCwd` (workspace.go:759) over `relsBelowDirResolved`
(workspace.go:1048), which contributes both the lexical and the
symlink-resolved spelling, so the real directory is still protected under its
own name. It is recorded because the safety depends entirely on that pairing:
one config change that puts a single spelling into the set, or one caller that
protects a path whose leaf is a symlink to a live mount, and a protected entry
is unlinked.

## 3. Dropped claim: `protectCaches` and `Cache: false`

A probe reported that `keptDirs.protectCaches` (workspace.go:712) records a
`MountTarget.CacheDir` even when that target sets `Cache: false`, entering a
directory that never existed into the keep set. NOT RECORDED AS A BUG: the code
says otherwise. muxfys's `newRemote` forces `cacheData = true` whenever
`cacheDir != ""` (muxfys remote.go:166-168) and then `MkdirAll`s it
(remote.go:180), which is what `MountTarget.CacheDir`'s own doc promises ("If
this parameter is supplied, Cache is forced true", jobqueue/mount.go:126). The
directory does exist, it does hold cache, and keeping it is correct.
