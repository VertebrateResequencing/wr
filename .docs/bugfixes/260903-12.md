# Job.Env() reads EnvC and EnvCRetrieved without the Job's lock

- [ ] `Job.Env()` reads `j.EnvC` and `j.EnvCRetrieved` with no lock held, while
      both are mutated under `job.Lock()`. Two server-side goroutines can
      therefore tear a slice header or observe the bytes and the retrieved flag
      inconsistently.

## Evidence (all verified at file:line, on `origin/develop` = a1a1c861)

The write side takes the lock:

- `jobqueue/serverCLI.go:1873-1883` — `(*Server).jobPopulateStdEnv` does
  `job.Lock(); defer job.Unlock()` and then sets `job.EnvC =
  s.db.retrieveEnv(...)` and `job.EnvCRetrieved = true`.
- `jobqueue/serverWebI.go:814-815` — `resetJobStatusFields` sets `job.EnvC =
  nil` and `job.EnvCRetrieved = false`.

The read side does not:

- `jobqueue/job.go:626-628` — `Job.Env()` reads `j.EnvC` and `j.EnvCRetrieved`
  directly. Only the third field is read under the lock, via
  `envOverrideSnapshot` (`job.go`, which does `j.RLock()` and
  `slices.Clone`).

Both are reachable on the same server-side object: `Job.statusStreams()`
(`jobqueue/job.go:1467`) calls `j.Env()` while building a `JStatus`, and is
called from `jobqueue/job.go:1363`. `jobPopulateStdEnv` populates those same
server-held jobs to serve client requests.

## This is PRE-EXISTING, not introduced by PR #572

Copilot raised this on PR #572 as "Job.Env() **now** reads j.EnvC and
j.EnvCRetrieved without holding the Job's RWMutex". The "now" is incorrect, and
that matters for where the fix belongs. On `origin/develop`, before #572:

- `envWithoutStored` read `j.EnvCRetrieved` with no lock;
- `decodeStoredEnv` read `j.EnvC` with no lock;
- `envCurrentOverrides` already read the overrides under the lock, via the same
  `envOverrideSnapshot`.

#572 restructured those same unlocked reads into one expression and kept the
locked override read. It is locking-neutral: it neither introduced nor widened
the race. So it was recorded here rather than folded into #572, whose subject is
the environment a run behaviour is given.

## Fix sketch (not implemented)

Take the read lock once for all three fields, which is what the existing
`storedEnvLocked` (`jobqueue/job.go:656`, "The caller must hold at least the
Job's read lock") is already shaped for:

```go
func (j *Job) Env() ([]string, error) {
	j.RLock()
	stored := jobEnv{envC: j.EnvC, overrides: slices.Clone(j.EnvOverride), retrieved: j.EnvCRetrieved}
	j.RUnlock()

	return stored.decode()
}
```

**Before implementing, check for a reentrancy deadlock**: Go's `sync.RWMutex` is
not reentrant, so any caller already holding the Job's lock would deadlock. The
callers to clear are `Job.statusStreams` (`job.go:1467`), `Job.Getenv`
(`job.go:773`, called from `jobqueue/client.go:1923`), `cmd/status.go:631`,
`cmd/runner.go:267` and `jobqueue/client.go:1970`. Not yet verified.

No red command was built for this, so it is unchecked. `make race` passes on
#572, which only means no test drives the two paths concurrently.
