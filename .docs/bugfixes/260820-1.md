# Bugfixes 260820-1 — reliable4 batch 2 (item C, diagnostics)

Source: `.docs/reliable4/next-steps-260819.md`, section "ITEM C". That doc is the
authoritative brief. Previous batches: `.docs/bugfixes/260818-1.md` (findings 1-5)
and `.docs/bugfixes/260819-1.md` (items A and B).

This batch is pure diagnostics / log volume, and it is what makes the eventual
live-prod profile legible, so it lands before the farm-scale validation gate.

Quality gates: `make lint` (0 issues), `make test` and `make race` with all `OS_*`
vars unset (baseline at `5b90c53` is 397 passed / 9 skipped / 29 packages, 8
skipped under race, 0 data races).

- [x] Bug C1 — the manager is silent about slow or heavy requests. Prod ran a **12-minute, 12 GB** request and logged **nothing**; the only reason it was ever identified is that a profiling session happened to be attached. Add a warning when a request exceeds a few seconds or allocates heavily. The dispatch point is `handleRequest` (`jobqueue/serverCLI.go:435`), which wraps every client RPC, so one place covers all of them. Log the request method, the repgroup/selector if present, the duration, and ideally an allocation delta. Keep it cheap: this is on the hot path for every RPC, so the fast path must be a single time comparison, not a profile (`runtime.ReadMemStats` around every call is too heavy — consider sampling the alloc figure only once the duration threshold is already crossed). Make the threshold a package var so a test can drive it.
  - Hook: `start := time.Now()` as the first statement of `handleRequest` (before
    the decode, so whole-handler occupancy is measured) plus
    `warnIfSlowRequest(...)` after `replyToClient`. One place covers every RPC.
  - Threshold `slowRequestThresholdDefault = 10s`, live in package var
    `slowRequestThreshold` so tests can drive it. Justified: the slowest
    *legitimate* hot-path RPC measured at scale is an archive at p99 2.75 s
    (`f7e36bc`, 660 archivers on a 9.99 GiB DB), so 10 s is ~3.6x above the worst
    known-good case; `ClientMinRequestTimeout` is 60 s, so it fires at 1/6 of the
    client give-up point — while the manager is degrading, not after clients have
    already failed; prod's silent 12-minute request is 72x over it.
  - **A false positive that would have made the whole warning useless:**
    `serverSubscriptionHoldTime` is **25 s**, so every idle subscription long-poll
    blocks server-side that long *by design*, and a reserve blocks for the runner's
    requested wait. Any flat threshold under 25 s would have emitted one warning per
    subscriber per 25 s forever. The effective threshold is therefore
    `slowRequestThreshold + requestWait(cr)`, and `requestWait` **mirrors the
    server's own clamp**: `reserve` keeps the whole claimed `Timeout` (traced
    `reserveWithLimits` -> `incrementReserveLimit` -> `q.Reserve`, never clamped),
    while `waitForUpdates` reproduces `waitForSubscriptionUpdates`' clamp exactly
    (`<= 0 || > hold` -> `hold`). Review cycle 1 caught the first version doing
    neither, which left two holes: a client sending `Timeout: 0` (which the server's
    contract accepts, and still holds 25 s for) got spurious warnings, and a client
    claiming an hour could **hide** a genuinely wedged `waitForUpdates` for an hour.
  - **`runtime.ReadMemStats` deliberately not called at all**, even on the slow path,
    despite the doc asking for "ideally an allocation delta": it stops the world, and
    the slow path is exactly when that is unaffordable — under degradation *every*
    request crosses the threshold, so a per-slow-request STW amplifies the stall
    being diagnosed (the same observer effect that ruined the 2026-07-28 CPU
    profile). A process-wide cumulative counter also cannot be attributed to one
    request across N concurrent RPC readers. The substitute is exact,
    correctly-attributed and free: `reply` now returns `len(encoded)`, so the
    warning carries `replyBytes`/`replyJobs` — which names prod's actual case
    (`handleGetByRepGroup` encoding a multi-GB reply for a client that had already
    given up). The reviewer judged this "an honest and better answer, not a silent
    narrowing".
  - Measured hot-path cost: **83.6 ns/op, 0 B/op, 0 allocs/op** for the added work
    (re-measured independently by the reviewer); end-to-end `handleRequest` A/B
    against a pristine worktree at `5b90c53` was **allocation-identical in both
    directions** (3,832 B/op, 18 allocs/op). ns/op on this load-90+ host has an
    8.4-16.7 us spread on the *same* tree, so the isolated figure is the honest one.
  - A redundant two-stage pre-check the first draft had was **deleted**, not kept:
    mutation showed no test could fail when it was removed, because a wait is never
    negative — it was unfalsifiable by construction.
  - Review cycle 1 caught the **warning's log level being unpinned**: demoting
    `clog.Warn` to `clog.Debug` passed every test, and since `cmd/manager.go` runs
    the manager at `logLevel "warn"` unless `--debug`, that one word would have
    silently restored the exact production silence C1 exists to fix. Now pinned by
    `So(out, ShouldContainSubstring, "lvl=warn")` — materially the same lesson
    `0d22eda`'s reviewer recorded ("must reach an operator at the default log
    level"), recurring in new code.
  - The **decode-failure gap** was closed rather than documented: `handleRequest`
    returns early on a decode failure, so a request that spent minutes *failing to
    decode* was never warned (`dispatchClientRequest` logged the error, but only
    under `ServerLogClientErrors` and never with a duration or a size). New
    `warnIfSlowDecode` carries duration, `requestBytes` and the codec error, with
    the message built from `slowRequestLogMsg` so one grep finds both. Its test uses
    a **truncated valid encoding**, which is load-bearing: the reviewer confirmed
    arbitrary junk *decodes fine* under binc and dies later at token validation, so
    a naive junk-body test would have exercised the wrong path entirely.
  - Accepted, recorded trade-off: on a wedged manager the warning emits one
    ~250-400 byte line per in-flight RPC per 10 s (~10 MB/min at 5,000 clients,
    the same order as prod's debug logging). Inherent to the brief; a dedup counter
    would put state and locking on the RPC hot path, against DEVELOPERS.md rule 2.
  - No scale gate for C1, deliberately: the wiring test drives a real stall through
    the real `handleRequest`, and a gate asserting "the log is quiet" cannot fail
    pre-fix. The reviewer agreed.
- [x] Bug C2 — runner logs carry full command lines. `cmd/runner.go:246` (`clog.Info(..., "reserved a job", ..., "cmd", job.Cmd)`) and `cmd/runner.go:304` (`info("will start executing [%s]", job.Cmd)`) each log the entire command line — ~130 KB x 2 per job for the pathological cases; the profiling run measured a `reserved a job` p99 of 24,261 bytes and a max of **1,345,498 bytes**. `0d22eda` cut the multiplier (an unrunnable job is now attempted once instead of forever) but not the per-line size. Reuse the helper `0d22eda` already added — `abbreviateCmdLine` / `startFailureCmdMax` in `jobqueue/client.go` — rather than writing a second truncator; if it needs exporting or relocating, do that. Keep the job key in the log line so an operator can still get the full command from `wr status`.
  - Reused rather than re-written, as instructed: `abbreviateCmdLine` /
    `startFailureCmdMax` moved out of `jobqueue/client.go` into new
    `internal/abbreviate.go` as `internal.Abbreviate` / `internal.AbbreviateMax`
    (still 200) — go-conventions' home for a helper shared by two packages, no
    import cycle, and it removed the duplicate instead of adding a second
    truncator. One thin `Job.loggableCmd()` inside `jobqueue`; `cmd/runner.go` calls
    `internal.Abbreviate` directly, so `Job`'s public API is unchanged. Verified
    byte-for-byte identical to the old helper, so `0d22eda`'s permanent-bury text is
    unchanged and `exec-impossible-retries` still reports `command line too long`
    on 20/20.
  - **Truncation is presentation-only** — the reviewer verified this directly rather
    than accepting it, because a persisted abbreviation would be a user-visible data
    change: the `myerr -> finalStdErr` append at `client.go:2243` is commented out;
    `jes.Stderr` carries only the command's real stderr; `reportFinalState` passes
    only `jes` plus a `FailReason*` constant; and no REST/web/`ToStatus` path touches
    `loggableCmd`. The only persisted abbreviated string is the permanent bury's,
    which `0d22eda` already abbreviated identically.
  - Runner-side sites bounded: `cmd/runner.go`'s three per-job lines (via a new
    `logJobLine` that always carries `key` + bounded `cmd`), `Execute`'s
    "started executing" (a **third** copy of the same command line in the same
    runner log per job), `reportStartFailure`'s **transient** branch (`0d22eda`
    abbreviated only its permanent twin, leaving the actual 1.3 MB-class line
    unbounded), and the exit-outcome error family via `job.loggableCmd()`.
  - **Manager-side sites bounded too, after review pushed back on skipping them.**
    They were first skipped as "exceptional path / Debug level"; they are neither —
    `serverCLI.go`'s "reserved job" and "completed job", plus `server.go`'s
    "released/buried job", "unburied job" and "removed job", each fire **once per
    job on the manager**, and prod may still be running with `--debug` at ~12
    MB/min. That put 2x the full 130 KB `Cmd` per job into **the manager's own
    log** — the log the next profiling round has to read, which is C1's entire
    purpose. All now use `job.loggableCmd()` **and carry the job key**, so an
    operator can still recover the full command from `wr status` (the absence of a
    key had been offered as a reason to skip them). The "removed job" site was found
    by the implementor looking for the *class* rather than working the list it was
    given, and flagged as its own judgement call.
  - Kill-path sites (`client.go`'s killed/failed-to-kill cmd and child) also
    bounded: they are Info/Warn, so visible at the shipped level, and
    "killed child of cmd" fires **once per child process per killed job** — a kill
    storm turns "exceptional" into a multiplier, which is this branch's recurring
    failure mode. Honestly recorded: three of the four are **bounded but unpinned**,
    living inside error-of-an-error branches (gopsutil `getChildProcesses` failing,
    or `Terminate()` failing) that no test can reach without faulting the library.
    The reviewer adjudicated this acceptable — the guarantee is pinned five lines
    away in the same closure and the whole captured log is sentinel-checked — and
    recorded the cheap future pin (fold each Info/Warn pair into one
    `logKillOutcome` helper a unit test can drive).
  - Deliberately NOT touched, and listed rather than swept: pipe-creation failure,
    the 24 h-server-unreachable paths, `scheduler`'s separate
    `loggableProcessOutputMax` (a different truncator for external process output,
    not a `Cmd` site), and `execCmdOutput`'s unbounded embedded stdout/stderr
    (a separate log-volume defect).
  - RED/GREEN, same shape both trees, 20,023-byte `Cmd`: runner log for one
    successful `Execute` **20,142 -> 355 B**; non-zero-exit error 20,087 -> 298 B;
    transient start failure 20,152 -> 365 B; one `reserved a job` line 20,135 ->
    348 B; the three `cmd/runner.go` lines 60,321 B -> ~1.0 kB. The job's `Cmd` is
    asserted unchanged **on the job itself** in both packages, so truncation cannot
    have mutated it.
  - Scale gate: NEW `developers/wrdev.sh runner-log-bytes [jobs] [seconds] [cores]
    [padKB]`. The handoff doc said "probably none needed"; the implementor
    **disagreed on evidence** and was right — mutation M10 shows the three
    `cmd/runner.go` call sites are unreachable by any unit test (they live inside a
    cobra `Run` closure), so reverting one leaves the whole suite green. It measures
    runner-log bytes per completed job **and** lines carrying the `Cmd`'s tail
    sentinel; the sentinel is the sharp half, because a byte threshold alone could be
    satisfied by deleting a log line rather than bounding it. After review it also
    measures the **manager** log with the manager started under `--debug` (prod's own
    state; `--debug` does not propagate to runners, confirmed empirically).
    Three-way A/B, the third row reproduced independently by the reviewer:
    post-fix `runner 1,415 B/job, sentinel 0; mgr 2,250 B/job, sentinel 0` (PASS);
    pre-fix pristine worktree at `5b90c53` `runner 82,427, sentinel 120; mgr 42,722,
    sentinel 60` (**FAIL, rc=1**); **manager sites only reverted** `runner 1,415,
    sentinel 0; mgr 42,796, sentinel 60` (**FAIL**) — proving the manager half is not
    a passenger riding on the runner half. Its `FAIL (NOT MEASURED)` branches were
    fired deliberately in both halves.
  - Mutation-tested throughout; each guarantee pinned to one named assertion,
    including five separate per-site mutations for the bounded `Cmd` and five more

    returning a length; the transient start-failure line) and one **survived** — all

## Follow-ups recorded from this batch (not scheduled)

- `jobqueue/server.go` `recoverRunningJob`'s two "recovery of an old cmd
  skipped/failed" lines still quote the whole `Cmd` with no key, once per recovered
  running job, and one is `clog.Warn` (visible at the shipped level). Unreachable
  on LSF (`lsf.recover()` returns nil unconditionally) but reachable on
  openstack/local.
- `jobqueue/client.go`'s two "jobqueue server error" texts still quote the whole
  `Cmd`, and `cmd/runner.go` warns them verbatim, so each affected job writes one
  unbounded copy into its runner log — and this fires precisely in the
  churn/saturation regime. Same class as the exit-outcome errors this batch bounded,
  so the inconsistency is worth closing.
- The manager half of `runner-log-bytes` has no positive precondition that the
  `--debug` per-job lines were actually written: with the manager sites reverted AND
  `--debug` dropped from the gate's own start line it reports `mgrBytesPerJob=9` and
  PASSes, because Info-level startup lines keep the file non-empty. One more
  `unmeasured` branch (e.g. requiring `grep -c 'msg="reserved job"' >= jobs`) would
  close it. Not blocking, because the same guarantee is unconditionally pinned in
  the main suite by `TestReliable4ManagerLogsBoundedCmd`.
- The three unpinned kill-path log lines above; cheapest pin is a
  `logKillOutcome(ctx, job, pid, killedMsg, failedMsg, err)` helper a unit test can
  drive directly.
