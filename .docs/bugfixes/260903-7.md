Topic: environment propagation into a job
(`jobqueue/utils.go`, `cmd/runner.go`, `jobqueue/job.go`).

## 1. `envOverride` overrides only the FIRST occurrence of a duplicated name

utils.go:645-667. The overrides are collected into a map keyed by name, then the
original slice is walked and each match is replaced - and the map entry is
DELETED as it is used:

    if replace, do := override[pair[0]]; do {
        env[i] = replace
        delete(override, pair[0])
    }

A second entry with the same name therefore keeps its original value, and no
appended copy is added either. `os.Environ()` normally has no duplicates, but a
Job's stored environment is whatever the client sent (compressed at add time)
and can, so a job whose environment contains two `HOME=` or two `TMPDIR=`
entries ends up with one overridden and one not.

That matters because the overrides on this path are wr's own guarantees, not
user preferences: `TMPDIR=<tmpDir>` and `HOME=<actualCwd>` for `--change_home`
(client.go:1779-1783), the bsub PATH prepend (client.go:1220) and
`WR_MANAGER_HOST`/`PORT` (client.go:1227-1231). Which value the command
actually sees is then up to the child: libc `getenv` returns the first match
(so the override wins), while some shells and runtimes rebuild their
environment last-wins (so the stale one wins). Either way wr has stopped
controlling the answer. Deleting the map entry is what causes it; nothing needs
it deleted.

## 2. `cmd/runner.go` accumulates `envOverrides` across reserve-loop iterations

`envOverrides` is declared once, OUTSIDE the reserve loop (cmd/runner.go:183),
and appended to INSIDE it (cmd/runner.go:279-288): for each job the runner reads
that job's own `PATH`, and if it does not already contain the runner's exe
directory, appends `PATH=<this job's PATH>:<exePath>` to the shared slice.
Nothing resets it between jobs.

The consequence is not that the LAST append loses - `envOverride` builds its map
last-wins, so a job that appends its own `PATH` gets the right one. It is the
job that appends NOTHING: a job whose `PATH` already contains `exePath` skips
the append (the `if !strings.Contains` at cmd/runner.go:282), and
`EnvAddOverride` (job.go:719, its `envOverride` call at job.go:725) is then handed the PREVIOUS job's `PATH` line, so
the command runs with an unrelated job's `PATH` and can resolve the wrong
binaries. Since a runner executes many jobs in sequence, one job with a
different `PATH` poisons every later job in that runner that would otherwise
have needed no override. The overrides also grow one `PATH=` entry per job for
the life of the runner.

The fix shape is a per-iteration copy of the base overrides; the base
(`WR_MANAGERHOST`/`PORT`/`CERTDOMAIN`, cmd/runner.go:190-194) is genuinely
loop-invariant, the `PATH` line is not.

## 3. `containerEnv` splits `K=V` on ":" and truncates the value

job.go:583-597 means to reduce the job's overridden environment to the NAMES of
the variables, so `DockerRunCmd` can emit `-e NAME` and let docker copy the
value in. It splits on the wrong character:

    parts := strings.Split(envvar, ":")
    names[i] = parts[0]

Entries are `K=V`, so for `PATH=/usr/local/bin:/usr/bin` the "name" becomes
`PATH=/usr/local/bin`, and `dockerEnv` (container/run.go) emits
`-e PATH=/usr/local/bin`. docker treats `-e K=V` as an assignment, so a
`--with_docker` job runs with its `PATH` truncated at the first colon - and the
same for any other colon-bearing value (`LD_LIBRARY_PATH`, `MANPATH`,
`PYTHONPATH`). A value with no colon is passed as a full `K=V` assignment too,
which happens to be harmless. Splitting on `"="` and taking `parts[0]` is what
the comment describes.

User experience: a containerised job cannot find binaries that are on its
`PATH` outside the container, with a "command not found" that does not mention
the environment.
