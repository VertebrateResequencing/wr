# Bugfixes 260824-1

- [x] The LSF scheduler reports **successful** `bsub` and `bkill` invocations as
  failures, because `Cmd.WaitDelay` is set to a 2-second "kill grace period" that
  Go also applies to a normally-exited process. Observed live on farm22 (branch
  `reliable4`, wr v0.37.2) on an utterly ordinary 2-element array:

  ```
  t=2026-08-24T10:52:02+0100 lvl=eror msg="schedule recall" schedulertype=lsf
  err="scheduler(lsf) schedule(): failed to run <LSF>/bin/bsub [-q normal -M 500
  -R select[mem>500] rusage[mem=500] span[hosts=1]
  -J wrp_2169083665f482fadf59aca0953541dc_bR09lRSK[1-2] -o /dev/null -e /dev/null
  <env> wr runner -s '500:30:1:1:<hash>~results_portal' --deployment production
  --server '[REDACTED]:56669' --domain localhost -r 1 -m 720]:
  exec: WaitDelay expired before I/O complete" caller=clog.go:344
  ```

  The error is Go's `exec.ErrWaitDelay`, from `bsubcmd.WaitDelay =
  bsubKillGracePeriod` in `submitToQueue` (`jobqueue/scheduler/lsf.go:1511`;
  `bsubKillGracePeriod = 2 * time.Second`, `lsf.go:154`). It is **not**
  `bsubExecTimeout` (5m) firing. `bkillGracePeriod` (`lsf.go:176`, also 2s) has
  the identical defect on `killcmd.WaitDelay` in `bkillBatch` (`lsf.go:874`).

  **Root cause.** Both constants' names and doc comments assert they are
  post-kill-only windows ("how long, *after the bsub exec timeout kills bsub*, we
  wait before force-closing its output pipes"). Go's actual contract is broader:
  "The WaitDelay timer starts when either the associated Context is done **or a
  call to Wait observes that the child process has exited, whichever occurs
  first**", and "If pipes are closed due to WaitDelay, no Cancel call has
  occurred, and the command has **otherwise exited with a successful status**,
  Wait and similar methods will return ErrWaitDelay instead of nil." So the 2s
  window is really a hard cap on how long *any* LSF command may take to close its
  stdout pipe after exiting - and a real farm22 `bsub` leaves a descendant
  holding that pipe marginally longer than 2s.

  **Impact.** `submitToQueue` returns before parsing bsub's output, so wr never
  learns the job id of an array LSF *did* accept, `waitForBjob` never runs, and
  the caller applies `sgroup.failures` backoff (escalating Warn->Error, deferring
  that scheduler group's scheduling by up to 30m). `bsubStderr` also yields ""
  because `ErrWaitDelay` is not an `*exec.ExitError`, which is why the prod log
  carries no stderr. On the kill path, `ranToCompletion` sees `execCtx.Err() ==
  nil` and a non-`ExitError` err, so it calls `k.fail` and returns false, which
  abandons every remaining kill batch in the cycle.

  **Red commands** (both proven to fail before any fix; probes saved outside the
  repo, recipe below):

  1. bsub: a fake bsub that records its `-J` arg, prints `Job <321>`, backgrounds
     `( sleep 4 )` (inheriting the stdout pipe) and exits 0; then
     `s.schedule(ctx, "false", req, 0, 2)` must return nil and record one `[1-2]`
     array. Currently, after exactly 2.01s:

     ```
     Line 32:
     Expected: nil
     Actual:   'scheduler(lsf) schedule(): failed to run <tmp>/bsub [-q normal
     -M 100 ... -J wrd_f96aabac0fe0acbad135d59e1aa745a4_Xn0KpDLt[1-2] -o /dev/null
     -e /dev/null false]: exec: WaitDelay expired before I/O complete'
     --- FAIL: TestWaitDelayRepro (2.01s)
     ```

  2. bkill: `newBkillHarness(t, bkillTestElements, <body>)` with a fake bkill that
     terminates every id, backgrounds `( sleep 4 )` and exits 0, then
     `killExcessCmds(ctx, bkillTestPrefix, 0)`. Currently only the first of four
     batches is issued and a fully successful kill is reported as reclaiming
     nothing:

     ```
     lvl=warn msg="checkCmd bkill did not reclaim all excess runners"
     requested=500 killed=500 alreadyGone=0 unaccounted=0 retried=0 deferred=0
     abandoned=1400 batches=1 err="exec: WaitDelay expired before I/O complete"
     Line 37: Expected: 4 Actual: 1 (Should equal)
     --- FAIL: TestWaitDelayBkillRepro (2.03s)
     ```

  **Required fix** (all three parts, decided by the user):

  1. Raise the bsub pipe-close grace to **1 minute** (still well inside the 5m
     `bsubExecTimeout`, so a killed hung bsub is still guaranteed to return), and
     raise the bkill one to a value justified against its own 1m
     `bkillExecTimeout`.
  2. Rename both constants and rewrite their doc comments: they bound pipe-close
     latency for *every* exec, not only a cancelled one. State the real Go
     semantics so the value cannot be mis-set the same way again.
  3. Treat `ErrWaitDelay` after a successful exit as success, which is what makes
     the fix correct however long an LSF descendant holds the pipe:
     `submitToQueue` accepts the submission when `errors.Is(err,
     exec.ErrWaitDelay)` and the captured stdout has a parseable job id (logging
     the lingering pipe so it stays visible); `ranToCompletion` counts an
     ErrWaitDelay with no exec-timeout expiry as having run to completion.

  Do **not** simply drop `WaitDelay`: per `.docs/bugfixes/260722-1.md` it is what
  makes `bsubExecTimeout`/`bkillExecTimeout` effective at all, since with it zero
  "I/O pipes will be read until EOF, which might not occur until orphaned
  subprocesses of the command have also closed their descriptors".

  **Fixed (2026-08-24, branch `reliable4`):**
  - `jobqueue/scheduler/lsf.go`: `bsubKillGracePeriod`/`bkillGracePeriod` became
    package vars `bsubPipeCloseGrace` (1m, a fifth of `defaultBsubExecTimeout`)
    and `bkillPipeCloseGrace` (15s, a quarter of `defaultBkillExecTimeout`), in
    the file's existing test-lowerable idiom. Their doc comments now state Go's
    real contract (the timer starts when the child exits, not only on
    cancellation; `ErrWaitDelay` means the command *succeeded*), that the grace
    is **added** to the exec timeout rather than contained by it, and why it must
    stay non-zero (260722-1: with `WaitDelay` unset the exec timeout bounds
    nothing).
  - New shared predicate `lingeredOnPipes(err)` (`errors.Is(err,
    exec.ErrWaitDelay)`). `submitToQueue` accepts such an error, warn-logs the
    lingering pipe, and parses the job id as usual; `killSummary.ranToCompletion`
    counts it as a completed kill so the cycle's remaining batches still go out;
    `killSummary.account` credits its elements as killed, since `ErrWaitDelay`
    implies a clean exit and `bkill` exits non-zero if any element was already
    gone. An `ErrWaitDelay` with no parseable job id still fails, as do a genuine
    bsub rejection (`TestLSFSubmitToQueueStderr`, untouched) and an exec-timeout
    kill (which yields `*exec.ExitError`, not `ErrWaitDelay`).
  - `killSummary` gained a sticky `lingered` flag included in `needsAttention()`,
    so a lingering kill escalates its summary to warn rather than sitting at
    debug: the output it cut short is the output the counts came from.
  - `submitToQueue` split into `runBsub` + `bsubFailure` to stay inside the
    file's funlen/cyclop limits and mirror `bkillBatch`'s no-ctx exec shape.
  - Regression tests `TestReliable4BsubPipeLinger` /
    `TestReliable4BkillPipeLinger`
    (`jobqueue/scheduler/reliable4_waitdelay_test.go`), reusing
    `newFakeLSFScheduler`/`newBkillHarness`. Fakes print their normal output,
    background a subshell inheriting the pipe, and exit 0. Both assert the trace
    the descendant leaves in what wr reports, so they fail if the fixture stops
    producing one (proved: giving the subshell its own pipes fails them).
  - Mutation-tested: reverting the `submitToQueue` acceptance reproduces the prod
    error text verbatim; reverting the `ranToCompletion` arm gives 1 batch of 4;
    reverting the `account` clause gives `killed=0 unaccounted=1900` at warn.
  - Touched pre-existing tests, each still discriminating: `TestLSFArrayChunking`
    and `setBkillTunables` lower the grace (necessary - the shipped values exceed
    their own bounds, and their hang pins still fail if `WaitDelay` or the exec
    timeout goes); `newFakeLSFScheduler` takes a `fakeBsubDelays` struct;
    `bkScaleHangBoundMs` 90000 -> 100000, measured worst case 75146ms, still far
    under the 120s an unbounded hang costs.
  - Not pinned by a default-suite test: the shipped grace *values*. With
    `ErrWaitDelay` accepted, a lingering descendant passes at any grace, so the
    low direction - the one this bug came from - has no observable consequence
    left to assert; the only observable is the elapsed time of a timed-out exec,
    which would cost ~15s (bkill) or ~60s (bsub) per run to pin. The
    `reliability_repro` scale gate keeps the bkill upper bound checkable on
    demand.
  - Gates: `make lint` 0 issues; `./jobqueue/scheduler/` ok 27.1s and 29.0s
    `-race`; `./jobqueue/` ok 504s; `go vet -tags reliability_repro` clean.
