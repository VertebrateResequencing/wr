- [x] A runner can deadlock forever when it starts a command whose working directory is on a muxfys mount the runner itself serves. That is the default for a job with mounts and no explicit Mount. Go forks with CLONE_VFORK. The child chdirs to cmd.Dir (jobqueue/client.go:1986-2006, cmd.Start at ~:2510) before exec, and that sends a FUSE_ACCESS request to the parent. If a GC stop-the-world starts meanwhile, it can never preempt the vforking thread, so no goroutine answers the request and the process wedges. SIGTERM and SIGQUIT don't help, the test timeout never fires, and the mount is left stuck. The `run` behaviour (behaviours.go:357, cmd.Dir=/proc/self/fd/N) is a second trigger. Upstream: golang/go#11155; go-fuse fs/api.go:152-176 and hanwen/go-fuse#261. Seen as a local `make test` hung for over an hour in TestJobqueueWithMounts on 2026-09-25.
  - Red command, a standalone reproducer: `cd scratchpad/fusefork && GOPROXY=off go test -c -o fusefork.test . && FUSEFORK_EXECS=5000 FUSEFORK_BASE=$PWD FUSEFORK_TRIALS=10 FUSEFORK_TIMEOUT_S=5 timeout -k 5 300 ./fusefork.test -test.run '^TestWedge$' -test.v`. It wedged 10/10 trials, and 40/40 across runs, on Go 1.26.3. It also wedged on 1.25.5, 1.26.8 and 1.27.1. `FUSEFORK_SHELLCD=1` (the chdir done by the shell after exec) wedged 0/5 on 1.25.5.
  - Owner decision (2026-09-25): option A. Stop giving a forked child a cwd inside a self-served mount, and let the shell cd after exec instead. This is conditional on no command behaving differently.
  - Known residual, NOT fixed by A: on Go 1.26 and 1.27.1 an in-process FUSE server can still wedge under stop-the-world with no vfork involved. FUSEFORK_SHELLCD=1 wedged 8/10 on 1.26.3, 4/5 on 1.26.8 and 4/5 on 1.27.1. The robust fix, serving mounts from a helper process, is tracked separately.
  - Option A was rejected and never implemented. A 3705-case differential audit found user-visible differences that could not be neutralised: `/proc/<pid>/cmdline`, `BASH_EXECUTION_STRING`, the echoed text of a syntax error, xtrace output, `E2BIG` headroom, and tcsh behaviour.
  - Fixed in muxfys v5.1.1 instead (muxfys PR #41): `Access` returns `ENOSYS`, so the kernel stops sending `FUSE_ACCESS`, and `Mount` warms it up with one access(2) on the mount point. This branch bumps wr to v5.1.1.
  - This covers wr's default layout, where the cwd is the mount root. A job that cds into a subdirectory after exec is outside the vfork window.
  - Red/green: muxfys's regression test `TestMountForkChdir` wedged 3/3 before the fix and passes after it. wr adds no test of its own: its change is only the dependency bump, no wr code or behaviour changes beyond muxfys, and the existing `TestJobqueueWithMounts` runs through this path.
  - The residual go-fuse-free Go runtime wedge is reported as golang/go#81759. The STW never completes while goroutines are blocked in read(2) on an fd fed by an external process. It happens on Go 1.26+, not 1.25. There is no wr-side fix, so a small residual risk remains on Go 1.26+.
