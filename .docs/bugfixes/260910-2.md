# Bugfixes 2026-09-10

fix-readonly-db-not-corrupt

- [x] A database file wr cannot OPEN is treated as corrupt, deleted, and
  replaced from an older backup - so `chmod 0400` on the manager's database
  loses everything since the last backup.
    - `initDB`'s existing-db branch (`jobqueue/db.go`) reacts to ANY
      `openManagerBolt(dbFile)` failure by trying the backup, and if the backup
      opens cleanly it does `os.Remove(dbFile)` then `copyFile(bkPath, dbFile)`.
      `EACCES` from a mode-0400 file takes that path exactly as corruption
      does.
    - The remove succeeds whatever the file's own mode, because the containing
      directory is writable.
    - What the user did to deserve it: made the database read-only before
      copying or inspecting it, which is the ordinary careful thing to do.
    - What they are then told is wrong as well as unhelpful: "recreated corrupt
      (?) db file ... from backup file ...". The file was not corrupt, it was
      unreadable, and the message sends them looking for the wrong problem.
    - Re-verified on `develop` at `d82db55` before this branch started. The
      record that filed it (`origin/record-cli-and-db-paths`,
      `.docs/bugfixes/260903-9.md` item 5) cites `db.go:471-520`; the code has
      moved since, which is why this file names functions instead.
    - THE PRECEDENT IS ALREADY IN THE SAME FUNCTION, and it is the strongest
      argument that this is a bug rather than a design choice. A guard above
      the backup path already special-cases `berrors.ErrTimeout`, with a
      comment saying why in terms that describe this defect exactly:

      ```
      // a lock timeout means another wr manager is running, NOT that the
      // file is corrupt, and it must never reach the restore path below:
      // that path treats any open error as "corrupt (?) db file", so it
      // would unlink the live database out from under the running manager
      ```

      So the hazard was understood, and one instance of it was closed. A
      permission error is the same shape and was not.
    - Fix shape: distinguish an error that means "cannot read this file" from
      one that means "this file is damaged", and refuse to destroy the
      database for the former. `errors.Is(err, fs.ErrPermission)` is the
      obvious first case, but whoever takes this should ask which OTHER open
      failures are equally not-corruption - the `ErrTimeout` guard already
      shows the list is longer than one.

## As fixed

- The inline `ErrTimeout` check became one `openErrorThatIsNotCorruption`
  function, so the 2 cases are one rule in one place and the next person has
  one switch to add to. Its doc says what stays on the corrupt side.
- Classes now treated as NOT corruption: `berrors.ErrTimeout` (unchanged),
  `fs.ErrPermission`, `syscall.EROFS`, `EISDIR`, `EIO`, `EMFILE`, `ENFILE`,
  `ENOMEM`, `ESTALE`, `ELOOP`.
- Everything unnamed stays CORRUPT, deliberately. Today's restore behaviour is
  preserved exactly rather than narrowed by an allowlist nobody can make
  complete.
- `EROFS` needs its own case and would otherwise have been missed: Go 1.26's
  `syscall.Errno.Is` maps only EACCES and EPERM to `fs.ErrPermission`, so a
  read-only MOUNT would have sailed past an `fs.ErrPermission`-only guard. The
  reviewer confirmed this empirically over 21 errnos, bare and wrapped in
  `fs.PathError`.
- `ENOMEM` is in because bolt mmaps the whole file, so "this machine cannot map
  7GB" must never read as "this file is damaged".
- `EIO` was the contested one, and the reviewer traced every path by which
  `bolt.Open` can fail (bbolt v1.4.3) before agreeing: content damage NEVER
  surfaces as EIO. `getPageSizeFrom*Meta` swallow every `ReadAt` error and
  return `ErrInvalid`; meta validation returns
  `ErrInvalid`/`ErrVersionMismatch`/`ErrChecksum`; a bad sector through the
  mmap raises SIGBUS, not an error. So EIO out of `bolt.Open` means the DEVICE
  is failing - and treating that as corruption is actively worse, because
  `os.Remove` is a directory metadata op that can succeed on a dying device
  while the following `copyFile` fails on it, leaving NO database at all.
- `ESTALE` added because wr runs on cluster filesystems: a stale NFS handle on
  open is realistic, and `os.Remove` by name can revalidate and succeed,
  unlinking the live database.
- `ELOOP` added, and the deciding argument is not likelihood: the restore path
  can never do anything USEFUL for it. If the chain is deep but real, the
  database sits at the end of it untouched while wr unlinks the last symlink
  and comes up on a stale backup; if it is a genuine loop, there is no
  database there at all. Either way restore destroys something and recovers
  nothing. `os.Remove` does not follow a final symlink, which is what makes
  that damage possible.
- Red proved the DATA LOSS, not a wrong branch:

  ```
  Line 106: Expected: []string{"db-unreadable", "depgranularity-dblock"}
            Actual:   []string{"depgranularity-dblock"}
  ```

  The job stored after the backup was taken is gone from everywhere.
- The message was corrected twice. It first said "resolve the problem with the
  FILE", which is wrong for `EMFILE`, `ENFILE` and `ENOMEM`, where the file is
  blameless - a smaller version of the very complaint this item makes about
  the old "corrupt (?)" wording. It now says "resolve the REPORTED problem",
  pointing at the errno the message already carries, and the function's doc
  says why, so nobody helpfully puts the file back.
- Where it reaches a user, traced rather than assumed: `initDB` -> `Serve` ->
  `startJQ`'s `serveManager` -> `die("wr manager failed to start : %s")`, and
  in daemonized mode the parent also prints the bad log lines.
- A genuinely corrupt database still restores.
  `TestDepGranularityCorruptDBStillRestores` passes, and so do the 3
  `ErrTimeout` tests. CORRECTION worth recording: the first implementor
  reported that this test is not matched by the gate's `-run` pattern and that
  it ran it separately. That was wrong - `TestDepGranularity` is an unanchored
  regex and the test runs in the gate. Wrong in the safe direction, but it
  meant one stated verification rested on a false premise.
- Test coverage of the arms is honest about its limits: `fs.ErrPermission`,
  `ErrTimeout` and now `EISDIR` are exercised. `EISDIR` was cheap and worth it
  - and it was a live hazard, since on an EMPTY directory the old path's
  `os.Remove` succeeds; proved red by deleting just that arm, whereupon the
  restore removed the directory and opened the backup copied over it.
  `EROFS`, `EMFILE`, `EIO` and `ENOMEM` stay unexercised: `EMFILE` is
  reachable via `RLIMIT_NOFILE` but that limit is process-wide and would flake
  the rest of the package.
- The permission tests skip with a named reason under root, since root bypasses
  file modes, and the setup asserts the chmod really denies `O_RDWR` so the
  test cannot pass vacuously. The `EISDIR` test needs no such guard.
- Follow-up NOT done here, and the right end state: invert the rule. Treat a
  database as corrupt ONLY for `ErrInvalid`, `ErrVersionMismatch`,
  `ErrChecksum` and a `Stat`-based short-file check, so an unnamed errno can
  never reopen this bug. The allowlist shipped here fixes the reported case
  and 9 neighbours but leaves the class open. The inverse needs care: bbolt's
  short-file error is a bare `fmt.Errorf` with no sentinel, so it wants an
  independent `os.Stat` size check rather than a string match, and it is a
  behaviour flip with its own availability risk.
- Tooling note, hit by 2 agents: `cleanorder -min-diff jobqueue/db.go`
  reorders 90-146 lines of unrelated declarations. Both reverted it and
  reapplied their own change by hand.
- CHANGELOG entry added under `[Unreleased]` -> `Fixed`. Writing it caught 2
  overstatements that the code review had not: "ANY open failure counted as
  corruption" was false, because develop already spared `berrors.ErrTimeout`;
  and "was enough to LOSE STATE" was false for part of the list, because
  `EROFS` and `EMFILE`/`ENFILE` send wr down the restore path but cannot
  finish it - `os.Remove` fails on a read-only filesystem, and opening the
  backup needs the descriptor you have just run out of. So those 2 MISREPORT
  rather than destroy. `EACCES` and `EISDIR` do destroy, both proved red. The
  entry now states the data loss once, of the bug as a whole, and says of the
  list only that each member took that path.

## Review finding on PR #595

- [x] `openErrorThatIsNotCorruption`'s doc comment made the reader work out a
  relative pronoun's referent.
    - Copilot review thread on `jobqueue/db.go:2078`, PR #595. It reported a
      typo, "which mean" should be "which means".
    - Copilot's CORRECTION is wrong, and taking it would have changed what
      the sentence claims. The subject is "any of the rest", singular, hence
      "is" - but "which" was picking up "THE REST", the remaining error
      classes, which is plural. "means" would have re-pointed the clause at
      "any". So "mean" was defensible.
    - The real defect is that a reader has to resolve the referent at all, so
      the sentence was reworded rather than the verb swapped: "Nor are the
      rest: they all mean the file could not be reached at all". A plural
      subject, an explicit "they", and a colon that mirrors the sentence
      before it. Nothing is left to decide.
    - The SAME defect one sentence earlier was fixed in the same pass, because
      leaving it means the next reviewer re-reports it: "still writing to the
      file, which would keep writing to a deleted inode" reads as the FILE
      doing the writing, since a relative "which" attaches to the nearest
      noun. Now "and it would keep writing", a coordinated clause whose
      pronoun resolves to the clause subject, the other manager - the only
      thing in the sentence that can write.
    - The rest of the doc comment was checked at the same time and every
      claim holds: the spec E7 account matches `.docs/dep-granularity/spec.md`,
      `ErrInvalid`/`ErrVersionMismatch`/`ErrChecksum` all exist under those
      spellings in bbolt v1.4.3, the short-file error really is a non-sentinel
      `fmt.Errorf` and so really does still restore, and `"corrupt (?)"` is
      the exact logged string.
    - Comment text only, 4 lines, no code. Deliberately NOT changed: the
      inline `ELOOP` gloss. It says the same thing as the conventional
      wording, so rewording it is churn a reviewer would have to read for no
      gain.
- Second review finding on #595, on the CHANGELOG entry itself: "so does one
  wr could not open" is missing its relative pronoun. Correct, and taken as
  offered - "so does one THAT wr could not open", which also makes the half
  parallel with "A database THAT really is damaged" earlier in the sentence.
- Found in the same pass and fixed with it: the entry opened with 2 adjacent
  "it"s having DIFFERENT referents - "copy an older backup over IT just
  because IT failed to open the file", where the first is the database and
  the second is wr. Only semantics rescued it, so the reader had to stop and
  re-assign. Now "just because WR failed to open the file", which keeps the
  echo of "every way of failing to open the file" in the next sentence.
- That is 4 rounds of correction on 1 CHANGELOG entry. The pattern in every
  round was the same - a pronoun whose referent the reader has to work out -
  and it is worth naming as the thing to check FIRST when writing one of
  these, rather than discovering it a reviewer at a time.
