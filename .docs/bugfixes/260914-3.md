fix-existing-upload-tree-perms

BASED ON `fix-world-readable-manager-dir`, not on develop: it reuses that
branch's `managerDirOtherWritePerms` and `errDirIsSymlink`, and it hangs its
repair off the `createWorkingDir()` that branch reshaped. Merge that one
first. `fix-upload-dirs-world-readable` makes the same directories 0700 when
wr CREATES them; this one repairs the ones an older wr already made, and the
two do not touch the same files.

- [x] An `uploads` tree an older wr made keeps its 0777, so another local user
  can still rename a level of it aside and substitute their own cloud
  credentials.
    - `createUploadTempFile` (`jobqueue/server.go`) only creates when
      `os.Stat` says the directory is missing, and `os.MkdirAll` never chmods
      one that already exists. So making new directories 0700 protects a fresh
      install and does nothing at all for the install that has been running
      for years - which is the population the repair in
      `closeWorkingDirToOthers` exists for.
    - RED, with the real binary, a pre-existing 0777 tree and the
      manager-directory fix in place:

      ```
      before: .wr_development=777 uploads=777 uploads/7=777 uploads/7/a=777
      after:  .wr_development=755 uploads=777 uploads/7=777 uploads/7/a=777
      ```

      The working directory is closed to 0755 and the tree below it is not,
      and 0755 still grants `o+x`, so another user can walk in and rename
      `uploads/7` aside. What that substitutes is
      `wr add --cloud_config_files`, copied to every cloud server the manager
      spawns and defaulting to `~/.s3cfg,~/.aws/credentials,~/.aws/config`.

## As fixed

`closeUploadDirToOthers` in `cmd/root.go`, called from `createWorkingDir`
beside `closeWorkingDirToOthers`, so it runs on every `wr manager start` and
every `wr cloud deploy`.

- EVERY level is closed, not just the top. Renaming a directory needs write
  permission on its PARENT, so closing only `uploads` would leave it 0755 -
  traversable - with the hashed levels below still writable, and renaming one
  of THOSE is the same attack one directory down.
- The CHMODS are bounded by the hash fan-out, not by the upload count, and the
  code comment says so rather than hand-waving about "a few config files":
  `calculateHashedDir` splits an md5 into `mkHashedLevels` (4) parts, so the
  tree is 3 single-hex-character levels deep and can never exceed
  16 + 256 + 4096 = 4368 directories however many files are uploaded. Nothing
  prunes the upload directory, so a count-based bound would have been enforced
  by nothing. The READDIR work is a different matter and an earlier draft
  claimed the fan-out bounded that too: `fs.WalkDir` reads and sorts every
  entry at every level, so it does grow with the number of files uploaded.
  Both are paid once per manager start, and neither is worth optimising for a
  tree that holds config files.
- It is in `cmd` because that is where the containment check can be made. The
  server knows `s.uploadDir` but not the working directory, and `s.uploadDir`
  falls back to `/tmp` when a `Server` is built without one
  (`defaultUploadDir` in `jobqueue/server.go`, and the `cmp.Or` that applies
  it; cited by name because the line moves once
  `fix-upload-dirs-world-readable` lands). A chmod of `/tmp` would take the
  machine out, which is an unacceptable failure mode for a hardening patch,
  and no guard the server can make rules it out as cleanly as "is this inside
  the working directory wr owns". A real `wr manager` never has that fallback
  - `cmd/manager.go:1477` always passes `config.ManagerUploadDir` - but "never
  in production today" is not a safe thing to build a chmod on.
- So a `manageruploaddir` pointed OUTSIDE `~/.wr_<deployment>` is left alone,
  and the CHANGELOG tells that operator to check it themselves.
- Consequence worth stating plainly: an embedded or test `Server` used without
  `wr manager start` gets no repair, only the 0700 creates from
  `fix-upload-dirs-world-readable`. Nothing ships that way.

## The symlink bypass this branch had to close

The first draft of this walk was a straight `filepath.WalkDir` over
`config.ManagerUploadDir`, on the reasoning that `WalkDir` lstats and so never
follows a symlink. That reasoning is WRONG, and the review demonstrated it
with the real binary: `WalkDir` lstats WITHIN the tree, and nothing lstats the
ANCESTORS of the walk root. The upload directory is `<ManagerDir>/uploads`, so
a symlink standing where the working directory should be - the exact thing
`takeOtherWriteOff` refuses to follow - is resolved on the way in:

```text
WARN  the working directory '.../home_slink/.wr_development' is a symlink ...
INFO  took other users' write permission off 3 directories in the upload ...
```

Three directories chmodded THROUGH the link wr had refused to follow, one line
later. Worse than the single chmod it was meant to complement: the walk aims
the same primitive at N targets instead of 1.

Closed by `openManagerDirRoot`, which `os.Lstat`s the working directory and
refuses a symlink before anything below it is touched, then opens it as an
`os.Root` so that every path resolved below it is checked against escaping it.
Verified with the real binary on the review's own scenario: the warning fires
and all four directories are still 777 afterwards.

A symlinked working directory therefore gets no upload-tree repair at all,
silently. That is deliberate: it is a layout somebody chose, wr refuses to act
through a link it cannot vouch for, and the dangerous case - a symlinked
working directory whose target is group- or world-writable - already produces
the warning above from `closeWorkingDirToOthers`. Warning a second time, every
start, about a legitimate symlink would be nagging.

## F3: the TOCTOU window, and why os.Root earns its place here

The earlier dismissal of `openBaseRoot`/`os.Root` was argued about ONE chmod of
wr's own directory. It does not carry over to a walk of N directories through a
tree whose whole premise is that another user can write to it: that user can
swap a directory for a symlink between the stat that reads the mode and the
chmod that sets it.

`otherWriteTakenOffIn` therefore OPENS each directory once and does both
through that one descriptor - `dir.Stat()` is an fstat and `dir.Chmod()` an
fchmod, neither of which re-resolves the path - and the descriptor comes from
an `os.Root` rooted at the working directory, which will not resolve a path out
of it.

What that buys is a BOUND, not an elimination, and the code comment says so: a
swap made before the open can still point wr at a different directory INSIDE
its own working directory, which is wr's to chmod anyway. The window that
mattered - being redirected to an arbitrary path outside - is gone. The repo's
own idiom is followed (`openBaseRoot`, `jobqueue/utils.go:1045`), and no test
pins the race, because a deterministic one would need to schedule the swap
between two syscalls; what is pinned is the containment that makes the race
uninteresting.

## Verified by test

- `cmd/working_dir_test.go`, `TestCreateWorkingDirClosesUploadDir`, covers the
  repair and the containment around it. RED without the
  `closeUploadDirToOthers` call at `:179`,
  `Expected: fs.FileMode(493) Actual: fs.FileMode(511)`.
    - Its second Convey, the relocated `manageruploaddir` at `:191`, pins the
      CONTAINMENT AS A WHOLE and not the `uploadDirInManagerDir` guard on its
      own. Removing that guard leaves the test green, measured: the relative
      path then escapes the working directory, `os.Root` will not resolve it,
      and the walk quietly does nothing. An earlier draft of this file
      recorded a 511-vs-493 RED for that mutation, which was true of the
      pre-`os.Root` design and is not true now.
    - The guard stays anyway, as the statement of intent: "wr repairs the tree
      it owns" should be visible where the decision is made, not left as an
      emergent property of a handle two functions away. It is also the only
      one of the two that would still hold if the walk were ever rewritten
      without the root.
- `TestCreateWorkingDirWalksNoSymlink` is the regression test for the bypass,
  and it needs what the working-directory symlink test lacks: an `uploads`
  tree under the symlink target. That test points at `/tmp`, which has no
  `uploads` in it, which is exactly why it missed this. RED without
  `openManagerDirRoot`'s refusal, at `:211`,
  `Expected: fs.FileMode(511) Actual: fs.FileMode(493)` - the tree chmodded
  through the symlink.
- Both were also run against the real binary, in the layout the review used:
  `HOME=.../home_slink` with `.wr_development` a symlink to a 0777 tree leaves
  all of it 777, while the same tree reached directly comes back
  `755 755 755 755` with the one summary line.

## Naming and wording corrected on the way

- The claim that write on a level lets you rename "that level" aside was
  backwards: renaming a level needs write on its PARENT. The code comment and
  this file now say it the way the CHANGELOG already did.
- `pluralYIes`, a bespoke helper that existed to say "directory" or
  "directories" in one log line, is gone. The message that replaced it read
  "off 1 directories" in the common single-directory case, which is
  user-facing sloppiness, so it now says "off %d OF THE directories" - the
  count no longer has to agree with the noun after it, and no helper comes
  back.
- `createWorkingDirUnderUmaskWithUploads` existed only to discard a return
  value. Gone; the 3 callers use the one helper and ignore the mode.
- `otherWriteTakenOff` was named as a predicate but mutated. Its replacement,
  `otherWriteTakenOffIn`, reports what it did rather than what is true, and
  the doc comment leads with the mutation.
