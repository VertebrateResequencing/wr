# Bugfixes 2026-09-14

fix-existing-upload-tree-perms

Rebased onto develop `1c75ffb`, which now has both branches this one was
written against: `fix-world-readable-manager-dir` as PR #599 and
`fix-upload-dirs-world-readable` as PR #601. #601 makes the upload
directories 0700 when wr CREATES them; this one repairs the ones an older wr
already made. "Rebased onto develop" at the end says what the rebase changed.

- [x] An `uploads` tree an older wr made keeps its 0777, so another local user
  can still rename a level of it aside and substitute their own cloud
  credentials.
    - `createUploadTempFile` (`jobqueue/server.go`) only creates when
      `os.Stat` says the directory is missing, and `os.MkdirAll` never chmods
      one that already exists. So making new directories 0700 protects a fresh
      install and does nothing at all for the install that has been running
      for years - which is the population the repair in
      `closeWorkingDirToOthers` exists for.
    - RED, with the real binary, a pre-existing 0777 tree and the
      manager-directory fix in place:

      ```
      before: .wr_development=777 uploads=777 uploads/7=777 uploads/7/a=777
      after:  .wr_development=755 uploads=777 uploads/7=777 uploads/7/a=777
      ```

      The working directory is closed to 0755 and the tree below it is not,
      and 0755 still grants `o+x`, so another user can walk in and rename
      `uploads/7` aside. What that substitutes is
      `wr add --cloud_config_files`, copied to every cloud server the manager
      spawns and defaulting to `~/.s3cfg,~/.aws/credentials,~/.aws/config`.

## As fixed

`closeUploadDirToOthers` in `cmd/root.go`, called from `createWorkingDir`
beside `closeWorkingDirToOthers`, so it runs on every `wr manager start` and
every `wr cloud deploy`. It clears every group and other bit from each level,
so 0777 becomes 0700, the mode #601 creates them with; "0700, not 0755" below
says why it no longer stops at the write bits.

- EVERY level is closed, not just the top. Renaming a directory needs write
  permission on its PARENT, so with the old write-only mask, closing only
  `uploads` would leave it 0755 - traversable - with the hashed levels below
  still writable, and renaming one of THOSE is the same attack one directory
  down. At 0700 a closed `uploads` does stop anyone new from walking in, but
  path checks happen only at lookup: a process that already has its cwd, or
  an open descriptor, on a hashed level keeps using it after the parent
  closes. Closing every level also leaves the whole tree at the mode #601
  gives new levels.
- The walk is bounded by the hash fan-out, not by the upload count, and the
  code comment says so rather than hand-waving about "a few config files":
  `calculateHashedDir` splits an md5 into `mkHashedLevels` (4) parts, so the
  tree is 3 single-hex-character levels deep and can never exceed
  16 + 256 + 4096 = 4368 directories however many files are uploaded. Nothing
  prunes the upload directory, so a count-based bound would have been enforced
  by nothing.
    - The READDIR work used not to be bounded that way: `fs.WalkDir` reads and
      sorts every entry at every level, and the deepest level is where the
      files are, so it grew with the number of files uploaded. Review asked
      for it to be capped. The callback now returns `fs.SkipDir` for a
      directory `uploadHashedLevels` (3) below the upload directory, after
      closing it, so that level is chmodded but never read. `fs.WalkDir` calls
      the callback on a directory before reading it, so the skip costs
      nothing. `uploadHashedLevels` is a `cmd` constant because
      `mkHashedLevels` is unexported in `jobqueue`; its doc comment names
      where the 3 comes from. The walk moved into `closeUploadTreeIn` to keep
      `closeUploadDirToOthers` under the `gocognit` limit.
- An upload directory that IS the working directory is refused, found in
  review. `filepath.Rel` gives "." and `filepath.IsLocal(".")` is true, so
  `manageruploaddir` set to `~/.wr_<deployment>` would have made the working
  directory itself 0700, overriding a deliberate 0750 that
  `closeWorkingDirToOthers` leaves alone, along with every directory in it.
  `uploadDirInManagerDir` now also rejects `rel == "."`.
- It is in `cmd` because that is where the containment check can be made. The
  server knows `s.uploadDir` but not the working directory, and `s.uploadDir`
  falls back to `/tmp` when a `Server` is built without one
  (`defaultUploadDir` in `jobqueue/server.go`, and the `cmp.Or` that applies
  it). A chmod of `/tmp` would take the
  machine out, which is an unacceptable failure mode for a hardening patch,
  and no guard the server can make rules it out as cleanly as "is this inside
  the working directory wr owns". A real `wr manager` never has that fallback
  - `cmd/manager.go:1513` always passes `config.ManagerUploadDir` - but "never
  in production today" is not a safe thing to build a chmod on.
- So a `manageruploaddir` pointed OUTSIDE `~/.wr_<deployment>` is left alone,
  and the CHANGELOG tells that operator to check it themselves.
- Consequence worth stating plainly: an embedded or test `Server` used without
  `wr manager start` gets no repair, only the 0700 creates from #601.
  Nothing ships that way.

## The symlink bypass this branch had to close

The first draft of this walk was a straight `filepath.WalkDir` over
`config.ManagerUploadDir`, on the reasoning that `WalkDir` lstats and so never
follows a symlink. That reasoning is WRONG, and the review demonstrated it
with the real binary: `WalkDir` lstats WITHIN the tree, and nothing lstats the
ANCESTORS of the walk root. The upload directory is `<ManagerDir>/uploads`, so
a symlink standing where the working directory should be - the exact thing
`takeOtherWriteOff` refuses to follow - is resolved on the way in:

```text
WARN  the working directory '.../home_slink/.wr_development' is a symlink ...
INFO  took other users' write permission off 3 directories in the upload ...
```

Three directories chmodded THROUGH the link wr had refused to follow, one line
later. Worse than the single chmod it was meant to complement: the walk aims
the same primitive at N targets instead of 1.

Closed by `openManagerDirRoot`, which `os.Lstat`s the working directory
(through #599's `isFinalSymlink`) and refuses a symlink before anything below
it is touched, then opens it as an
`os.Root` so that every path resolved below it is checked against escaping it.
Verified with the real binary on the review's own scenario: the warning fires
and all four directories are still 777 afterwards.

A symlinked working directory therefore gets no upload-tree repair at all.
That is deliberate: it is a layout somebody chose, and wr refuses to act
through a link it cannot vouch for. An earlier version of this file said the
refusal could also be silent, because `closeWorkingDirToOthers` already warns
when the target is group- or world-writable. That missed a 0755 target with an
old 0777 tree below it, which got no warning at all. Since the Copilot items
below, wr warns about the upload directory too, but only when its mode, read
through the link, grants other users anything.

## F3: the TOCTOU window, and why os.Root earns its place here

The earlier dismissal of `openBaseRoot`/`os.Root` was argued about ONE chmod of
wr's own directory. It does not carry over to a walk of N directories through a
tree whose whole premise is that another user can write to it: that user can
swap a directory for a symlink between the stat that reads the mode and the
chmod that sets it.

`closedToOthersIn` therefore OPENS each directory once and does both through
that one descriptor - `dir.Stat()` is an fstat, and #599's `chmodWorkingDir`
fstats and fchmods it, none of which re-resolves the path - and the descriptor
comes from an `os.Root` rooted at the working directory, which will not
resolve a path out of it.

What that buys is a BOUND, not an elimination, and the code comment says so: a
swap made before the open can still point wr at a different directory INSIDE
its own working directory, which is wr's to chmod anyway. The window that
mattered - being redirected to an arbitrary path outside - is gone. The repo's
own idiom is followed (`openBaseRoot`, `jobqueue/utils.go:1045`), and no test
pins the race, because a deterministic one would need to schedule the swap
between two syscalls; what is pinned is the containment that makes the race
uninteresting.

## 0700, not 0755

Before #601 landed, this repair cleared only the other-user write bits, so a
0777 level became 0755, with a CHANGELOG line saying another user could still
list it. That copied the working directory's policy. It is now 0700, the mode
#601 gives a new upload directory, for three reasons:

- The working directory keeps its read bits because somebody can have a use
  for them: a deliberate 0750 lets a colleague read `ca.pem`. Nothing in the
  upload tree is readable by anybody but the owner, since every file in it is
  0600 (`os.CreateTemp`, and #601's chmod for a caller-named path). #601's own
  checklist makes the same argument for new directories: their mode "cannot
  widen access to [the file], only expose it to tampering, so 0700 costs
  nothing". It holds just as well for an old one.
- Leaving read and search on is not quite harmless. The file names are md5s
  of their content, so another user can list what was uploaded and when, and
  confirm a guess at a file's content by hashing it.
- At 0755 a tree would have ended up with a mix of modes: 0755 for levels made
  before the upgrade and 0700 for levels made after. Someone auditing it could
  not tell a repaired level from a broken one.

The cost: an install whose tree was 0755 all along, as it would be under the
common umask 022, now has it changed on first start and gets one info line.
At 0755 it would have been left alone, which was fine for tampering, since
0755 grants no write. An operator who opened the tree up deliberately loses
that on every start, but nothing in it was readable to anyone else anyway.
