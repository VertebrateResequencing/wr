# Bugfixes 260825-1

- [x] On a default `wr manager start`, prior-state recovery logs **nothing**, so
  an operator cannot tell a recovering manager from one that has lost every job.

  This is a spec-conformance gap, not a new feature. `.docs/reliable/spec.md`
  section B1 requires: *"Lightweight progress reporting: expose
  recovering/`restored`/`total` (via `manager status` and/or a 'recovering: N/M
  restored' log line) so a slow recovery is not mistaken for a hang."* Both
  channels are unimplemented: the two `clog.Info` milestones are filtered out at
  the default log level, and `recoveryProgress()` is never sent to a client.

  **Mechanism.** `setupManagerLogging` (`cmd/manager.go:1288-1306`) calls
  `clog.CreateFileHandlersAtLevels(config.ManagerLogFile, "info", logLevel)` with
  `logLevel = "warn"` unless `--debug`. `fileHandlers[0]` (info) becomes a
  *global* handler; `fileHandlers[1]` (**warn**) is the one attached to the
  context handed to the jobqueue server via `clog.ContextWithLogHandler`. So
  every server-side `clog.Info(ctx, ...)` is dropped at the default level,
  including both milestones in `recoverPriorJobsAndNote` (`jobqueue/server.go`):
  `"recovering prior state" total=N` and `"recovering: prior state recovered"
  restored=N total=N`. Only the failure path (`clog.Error`) would be visible.

  **Live incident (2026-08-25, prod, `reliable4` @ d11b83b).** After a DB
  compaction the manager spent 15+ minutes recovering 148,393 live jobs (a
  freshly written file, so every page cold on NFS). For that whole window the log
  held exactly one info line ("wr manager ... started on ...", from `cmd`) plus
  106 `lvl=eror ... jobqueue jtouch(...): server is recovering prior state,
  please retry` lines. `wr status` showed 10 jobs (new adds accepted during the
  window, since the re-enqueue is a single batch at the end). It read as total
  job loss and nearly triggered an unnecessary restore from a DB backup. Nothing
  was wrong: `jobslive` held all 148,393 keys, verified read-only in the
  pre-compact backup.

  **Red command** (proven RED at d11b83b; drives the real binary with default
  logging in an isolated production-mode deployment, no LSF, nothing shared with
  a real manager):
  `RED_ROOT=<scratch> NJOBS=12 bash red-recovery-visibility.sh`
  — adds 12 `sleep 600` jobs, `kill -9`s the manager so the live bucket keeps
  them, restarts with no `--debug`, then greps the new log. Exit 1 today:

  ```
  counts before kill: running:8 ready:4
  == phase 3: restart with DEFAULT logging and read the NEW log ==
  --- new log, all distinct msgs ---
        1 msg="wr manager  started on [REDACTED]:51982, pid 2264557
        1 msg="wr manager  started on [REDACTED]:51982, pid 2264300
        1 msg="wr manager : created a new key and certificate for TLS. crea
  --- lines mentioning recover ---
  (none)
  recovery-start lines:    0
  recovery-finish lines:   0
  RED: a default `wr manager start` never says it is recovering prior state
  ```

  Script kept at `.docs/bugfixes/260825-1-red-recovery-visibility.sh`.

  **Fixed (2026-08-25, branch `reliable4`):**
  - `jobqueue/server.go`: both milestones now `clog.Warn` instead of `clog.Info`,
    which is the level the manager's server context is already filtered at, so no
    handler level changed and no other server-side Info logging was unfiltered.
    The message strings are byte-identical to before, so anything already
    grepping them keeps working. The alternative (hand the server the info
    handler) would have regressed exactly what 53c323f bought.
  - New `startRecoveryHeartbeat` logs `recovering: still recovering prior state
    total=N elapsed=...` every `recoveryHeartbeatInterval` (a package var,
    1 minute, so tests can shrink it), wrapped by `recoverPriorJobsWithHeartbeat`
    whose deferred stop closes a channel **and waits for the goroutine**, so no
    heartbeat line can follow the outcome line. Elapsed time, not a count: the
    single-batch enqueue makes `restored` jump 0 -> total in one step. One minute
    is longer than a whole warm restart, so ordinary restarts stay silent.
  - `recoveryPauseHook` moved into `recoverPriorJobsWithHeartbeat` so a test can
    hold the window open from inside the heartbeat's span. `setRecoveryTotal`
    still runs before the goroutine, so spec B1 acceptance test 4 is unchanged;
    nil in production.
  - Tests `TestReliable4RecoveryVisibleInManagerLog` /
    `TestReliable4LongRecoveryReportsStillWorking`
    (`jobqueue/reliable4_recovery_log_test.go`) assert on the real log file under
    production's own handler pair (`CreateFileHandlersAtLevels(path, "info",
    "warn")`, info on the root logger, **warn** on the server context), so a
    line logged below warn cannot reach the assertion. The package's existing
    capture helpers all use unfiltered handlers and would have passed at `info`.
  - Mutation-tested by the reviewer: reverting both milestones to `Info` fails
    line 103 and line 170; heartbeat `Warn`->`Info` fails line 148; dropping
    `defer stopHeartbeat()` fails the ordering assertion at line 171.
  - Measured cost: **415 bytes for two manager starts** (~207/start), and a
    prod-scale heartbeat line is **133 bytes**, so the 15-minute incident would
    have cost ~2 KB. O(1) per start and O(minutes of recovery) - it touches
    neither 53c323f's per-job nor 260820-1's per-RPC budget.
  - Gates: `make lint` 0 issues; `make test` **413 passed - 9 skipped - 29
    packages** (pristine `d11b83b` measures 411, so +2 = the two new tests);
    `make race` 413 passed, 0 data races; `go vet ./jobqueue/ ./cmd/` clean.
    Verified twice independently, and the reviewer reconfirmed RED on a pristine
    `d11b83b` build rather than taking it on trust.
  - Verified on the real binary: with the interval shortened, a default-logging
    manager log shows start, heartbeat and finish in the correct order at warn.

  **Review findings carried forward (none blocking, recorded per the batch's own
  mutation-test rule):**
  - The window *before* the start line is still silent: `recoverIncompleteJobs`
    runs synchronously inside `Serve`, while `setRecovering(0)` is already true
    and `jtouch` is already returning `ErrRecovering`. **Measured against the
    2026-08-25 prod incident: the process started 09:22:51 and logged "started
    on" at 09:23:28, so that silent scan was ~37 s of a 21-minute recovery** -
    the fix covers the rest. Checklist item 2 (`manager status`) closes this
    window for free, since `setRecovering(0)` precedes the scan.
  - `case <-ctx.Done():` in `startRecoveryHeartbeat` is an **unpinned
    guarantee** (all five tests stay green without it). Pin it or drop it.
  - `readLogFile`'s `So(err, ShouldBeNil)` sits inside `pollUntil`'s condition,
    so a failure fires ~1500 assertions; go-conventions bans `So()` in loops
    over 20 iterations. Return `""` on read error and assert once outside.
  - `warmRestartRecovery = 40 * time.Second` states an unrecorded production
    measurement as fact, and `So(recoveryHeartbeatInterval, ShouldBeGreaterThan,
    warmRestartRecovery)` asserts on a package var. Cite the figure or soften it.
  - `recoveryLogFixtureConfig` is a third copy of a fixture-config block already
    inlined twice in `reliable2_dbcompat_test.go`.

- [ ] `wr manager status` and `wr status` cannot distinguish "recovering" from
  "the queue is empty". `recoveryProgress()` (`jobqueue/server.go:1281`) is read
  in exactly one place — the filtered completion log line — and
  `reportLiveStatus` never mentions recovery, so during the window `wr status
  -o counts` reports counts that silently omit every unrecovered job. This is the
  `manager status` half of the same spec B1 sentence, and it is what actually
  misled the operator in the incident above. Red command to be built before this
  item is briefed.

  Note: blocking startup until recovery completes is **not** the fix. Spec B1
  deliberately made startup non-blocking ("answer ping/status/add within ~1 s of
  start regardless of history/running-jobs, so a `kill -9` restart is never
  stuck") to kill the 190 s startup stall; C2 ("Fast startup") reinforces it.
  The spec's answer to a slow recovery being mistaken for a hang is progress
  reporting, not a blocking start.

- [ ] Same class of invisibility in the DB-upgrade reporter (found while fixing
  item 1, not yet fixed). `dbUpgradeReporter` (`jobqueue/db.go:1810-1930`) logs
  every progress and phase line via `clog.Info` on the same warn-filtered server
  context, so a long index rebuild or DB upgrade at startup is as silent to an
  operator as recovery was. It does write a status file
  (`internal.WriteDBUpgradeStatus`), so it is not wholly unobservable, but the
  log says nothing. Red command to be built before this item is briefed.

  load-dependent flake class (`.docs/bugfixes/260626-3.md`) with none of this
  batch's changes applied. Recorded as evidence, not attributed to item 1.

- [ ] **Prod died 2026-08-25 10:05, and the log shows a 16m39s server-wide stall
  immediately after recovery finished** (found while item 1 was in review; needs
  investigation, not a blind fix). Timeline from
  `/nfs/hgi/wr/lsf/.wr_production/log` (manager `v0.37.1-66-gd11b83b`, started
  09:22:51 on the freshly compacted 7 GB DB):

  | time | what |
  |---|---|
  | 09:23:28 | serving; recovery of 148,393 live jobs begins (silent - item 1) |
  | 09:44:32 | last `ErrRecovering` reject, so recovery finished: **21 min** |
  | 09:44:46 | first RPC blocks (derived: 10:01:25 minus the 16m38.97s max) |
  | 10:01:25 | **113 slow requests all complete in the same second** |
  | 10:03-10:05 | degraded: `reserve` 14-17s, `add` 11.3s, `jarchive` 10.6s |
  | ~10:05:19 | silent death mid-backup; `db_bk.tmp` abandoned at 1.1 GB |

  The stall was **waiting, not working**: all 14 `getin
  repgroup=ibackup_fofn_ match=prefix` calls returned the *identical* trivial
  result (`replyJobs=92 replyBytes=127994`) yet ran 1m05s, 2m05s, 3m05s ...
  13m57s - one arriving per minute from a polling client, every one released in
  the same second. `jtouch` (max **16m38.97s**), `add` (16m33.76s) and `getin`
  are three unrelated code paths that share the **queue mutex**, so a single
  server-wide holder is implied. It began 14 s after `finishRecovering`.

  Leading suspect: the post-recovery scheduling pass -
  `rescheduleReadyAfterRecovery` -> `triggerReadyAddedCallback` over 148,393
  freshly recovered ready jobs, with a cold scheduler-group memo (`8087866`) on a
  cold-mmap DB. **Not confirmed** - a block/mutex profile during the window
  settles it in seconds, so the next prod start should set `WR_PPROF_ADDR`.

  Two consequences worth noting: a `jtouch` blocked 16m39s is far past TTR, so
  the unblock can hand the false-lost machinery a pile of "lost" jobs; and no
  panic or error preceded the death, so it was a signal (OOM killer is the
  leading candidate) rather than a Go-level failure - confirm with `dmesg -T |
  grep -iE 'killed process|out of memory'` on the manager's host (172.27.71.193).

  Red command: none yet. This is backlog-size-driven, so it likely needs a
  `developers/wrdev.sh` mode that recovers ~150k live jobs on an isolated
  prod-mode manager and measures control-RPC latency across the window.
