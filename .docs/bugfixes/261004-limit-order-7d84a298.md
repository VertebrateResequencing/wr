- [x] A limit that really changed, or is stored for the first time, is applied
  to the limiter after its DB transaction and outside any lock, so two
  requests that both change a group (two adds first-storing different values,
  or an add storing `g:5` racing `wr limit -g g:3` or `g:-1`) can apply their
  limits in the opposite order to their DB commits, leaving memory and the DB
  disagreeing until the group is next set.
  - Source: deferred incidental of `261004-limit-uncounted-6a3d4650.md`
    (review of 74134b6f).
  - Paths that store a limit group and then call `SetLimit`/`RemoveLimit`:
    `Server.storeLimitGroups` (`jobqueue/server.go`), called by `createJobs`
    (`wr add`, REST add, web interface add), `persistModifiedJobs`
    (`jobqueue/serverCLI.go`, `wr mod`) and `storeModifiedLimitGroups`
    (`jobqueue/serverREST.go`, REST modify); and `Server.setLimitGroup`
    (`wr limit`, via `getSetLimitGroup`). No other caller of
    `db.storeLimitGroups` or of the limiter's `SetLimit`/`RemoveLimit` exists
    outside tests.
  - Red: `go test -tags netgo -count 1 ./jobqueue -run
    'TestLimitStoreAppliedInCommitOrder|TestLimitAddKeepsNewerLimit'` exits 1
    on `8d5cfb58` with the new test, plain and `-race`:

    ```text
      Line 240:
      Expected: 3
      Actual:   5
      Line 250:
      Expected: -1
      Actual:   5
      Line 262:
      Expected: 3
      Actual:   5
    --- FAIL: TestLimitStoreAppliedInCommitOrder
    ```

    Each case adds a job first-storing `lu-lg:5`, and, through the existing
    `limitGroupsStoredHook` (after the add's database write, before its
    limiter update), starts in another goroutine `setLimitGroup` with 3
    (line 240), with -1 (line 250), or a second add's `storeLimitGroups` with
    3 (line 262), holding the add for up to 1s while it runs. `wr limit`'s
    output is then compared with the database. On the old code the racing
    change completes during the hold, then the add applies 5 over it.
  - Cause: `Server.storeLimitGroups` and `Server.setLimitGroup` store in the
    database and then update the limiter as two unrelated steps, so a request
    that stored second could update the limiter first.
  - Fix: `jobqueue/server.go`: a new `Server.lgmutex` is held across the
    database store and the limiter update in `storeLimitGroups` and in the new
    `storeAndApplyLimitGroup`, which `setLimitGroup` calls before
    `triggerReadyAddedCallback` (kept outside the lock). `storeLimitGroups`
    returns at once for an empty map, so an add without limit groups does not
    take the lock (`db.storeLimitGroups` did nothing for one already); an add
    with limit groups takes it once per batch.
  - Lock order: under `lgmutex` only `db.storeLimitGroups` (a bolt `View`,
    then a bolt `Batch` if a write is needed) and the limiter's `mu` (in
    `SetLimit`/`RemoveLimit`) are taken. Neither is held by anything that then
    takes `lgmutex`: no bolt transaction function calls these paths, and the
    limiter never calls out while holding `mu` (its database callback runs with
    `mu` released, and takes no server lock). So `lgmutex` is a leaf below
    whatever its callers hold (job locks are released before the modify paths
    call it; `createJobs` holds none of `psgmutex`, `racmutex`, `ssmutex` or
    the queue's locks across it), and cannot deadlock.
    `triggerReadyAddedCallback` stays outside it.
  - Tests: `jobqueue/limit_uncounted_test.go`: new
    `TestLimitStoreAppliedInCommitOrder` (three cases above), each also
    asserting that the racing change did not complete while the add was held;
    the shared `addRacingLimitChange` helper runs the change in its own
    goroutine with the hold bounded by `limitRaceHold`, so the test cannot
    deadlock on the lock, and waits up to 30s for the change after the add.
    `TestLimitAddKeepsNewerLimit` uses the helper too: its old hook ran
    `setLimitGroup` synchronously inside the add, which would deadlock on the
    lock. Its assertions are unchanged.
  - Mutants, each in a scratch copy, each failing the new test plain:
    no lock in `storeAndApplyLimitGroup` (lines 240, 250); no lock in
    `storeLimitGroups` (240, 250, 262); `storeLimitGroups` unlocking straight
    after the database store (240, 250, 262). #676's mutant (`SetLimit` for
    every count group, not only changed ones) now passes every limit test: the
    lock keeps the add's database read current until it applies, so
    re-applying an unchanged limit can no longer bring back an older one.
