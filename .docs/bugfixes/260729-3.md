# 260729-3 — reliable4 confirm-dead SSH checks: group by host (Fix 5 follow-up)

Follow-up to the leak fix (260729-2). Design in `.docs/reliable4/freeze-fix-plan.md`
Fix 5. This GROUPS confirm-dead checks by host so all of a dead host's pid checks
share ONE ssh connection, instead of one connection per check. CRITICAL PATH
(job liveness) — every invariant below must be preserved and every guard test
must stay green.

- [x] Group confirm-dead ssh checks by host. Today `markJobLost` spawns `confirmOrReleaseLostJob` per lost job → `confirmJobDead` → up to 2 `ProcessNotRunningOnHost` calls, each `getHost`+dial+close ⇒ ~2 connections per lost job. When a whole node dies (K jobs lost at once, all on that host) that is ~2K connections. FIX (agreed design): a confirm-dead coordinator that COLLECTS pending checks, GROUPS by host, and processes each host's batch over ONE connection (a new scheduler primitive `ProcessesNotRunningOnHost(ctx, host, pids)` that `getHost`s once, checks all pids over the reused connection, closes once), then applies each job's verdict. RED test (uncommitted) `jobqueue/reliable4_confirmdead_grouping_test.go` (`TestReliable4ConfirmDeadGroupsByHost`: 50 jobs × 2 pids on one host → currently 100 connections, must be ≤ 10) must go GREEN, plus the mock `GetHostHook` seam (uncommitted, in `jobqueue/scheduler/mock.go`).
  - `jobqueue/scheduler/scheduler.go`: new `ProcessesNotRunningOnHost(ctx, host, pids) map[int]bool` (getHost once, ps each pid over the one reused connection, one `defer host.Close`); shared `processNotRunningOnHost` helper so `ProcessNotRunningOnHost` keeps the exact ps CONTRACT + the leak-fix Close.
  - `jobqueue/confirmdead.go` (NEW): `confirmDeadCoordinator`. `enqueue` appends to `pending[host]` under `mu`; at most one worker per host via `active[host]` (single-active, re-check-pending-before-clear handshake — race-safe both ways). Worker: ~50ms coalesce, drain batch, one `ProcessesNotRunningOnHost`, per-job verdict via `jobConfirmedDead` (identical both-pid semantics), dead⇒`go killLostJobAndTriggerBehaviours`, not-dead⇒`retryAfter` (checkRetryTime → backstop-kill if lostFor>LostRunnerBackstop → re-enqueue, so retries group too). Bounded by `confirmDeadLimiter` repurposed to concurrent HOSTS; all paths honour `stopClientHandling`; panic-recovered.
  - `jobqueue/server.go`: `confirmOrReleaseLostJob` enqueues on the confirm branch (killCalled release branch unchanged); removed the now-unreachable `confirmJobDead`/`confirmJobDeadAndKill`/`confirmJobDeadAndKillAfterRetryTime`; added the coordinator field + init. Bound test switched to DISTINCT hosts so it still exercises the per-host bound.
  - RESULT: grouping test GREEN (50 jobs × 2 pids → **1** connection, bound 10; reliable 10/10 + 4/4 -race). Guards GREEN: ConcurrencyBound, RunnerPidLiveness, LostRunnerBackstop, RecoveredRunnerDead, TtrMissChurn (NO CHURN), TtrBackstopKill, and the confirm-dead-leak repro (leaked 4). `make test` PASS, `make race` PASS (0 data races), `make lint` 0 issues, `go build` OK. Reviewer PASS (independently verified the enqueue↔worker handshake loses no check / strands no job, verdict semantics, slot safety, shutdown, no dangling refs).
  - KNOWN MINOR (non-blocking, reviewer-noted): a panic INSIDE `ProcessesNotRunningOnHost` would strand that one batch (no verdict/retry until manager restart) — but strictly better than the old path (an unrecovered per-job panic crashed the whole manager), and only reachable via an unexpected panic on a path written to return false not panic. Potential future hardening: re-enqueue the batch inside the worker's recover.
