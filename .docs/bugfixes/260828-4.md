- [x] BUG 4 (PRODUCT bug, found and reproduced during LAYER 6's review — the flaky-test fix models around it, so it must not be forgotten): a client reconnecting to a manager that is mid-`Stop` can hang for up to 60s, far past its own retry budget. Two causes. (1) `shutdown` (jobqueue/server.go:6052) calls `closeClientSubscriptions()` at :6102 BEFORE `close(s.stopClientHandling)` (:6103), `waitForClientHandling` (:6104), `time.Sleep(ShutdownSocketWait)` (:6105, default 50ms) and `s.sock.Close()` (:6107) — so for >=50ms every client subscription has been killed while the command port still accepts connections. `handleSubscribe` (serverCLI.go:690) / `registerClientSubscription` (server_subscription.go:444) have NO shutdown guard, so a subscribe arriving after the :6102 sweep repopulates `s.clientSubscriptions` with a `serverSubscription` nothing will ever `close()`, and the client long-polls a manager that is gone.   - Fix, server half: the `up == false` guard already existed at `validateRequest` (serverCLI.go:477-487, from #551); what was missing was ATOMICITY, since `handleRequest` snapshots `up` at the top of the dispatched goroutine, so a subscribe whose snapshot predates `beginShutdown` could still reach `registerClientSubscription` after the sweep and leave an entry nothing would ever close, plus its `deliverQueuedUpdates` goroutine. `storeClientSubscription` now checks a `subsClosed` flag set by `closeClientSubscriptions` under the same `csmutex`, so there is no window; refused subs are closed outside the lock and `handleSubscribe` maps the refusal to `ErrClosedStop`, matching what `validateRequest` already returns.
