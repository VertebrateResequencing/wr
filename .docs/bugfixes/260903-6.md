# Bugfixes 260903-6

RECORDED, NOT FIXED. A finding from adversarial probing of wr, filed as a
backlog item. Nothing on this branch changes any code.

Topic: `s.recoveredRunningJobs` is never cleared (`jobqueue/server.go`).

## The mechanism

`recoverRunningJob` (server.go:3380) records a key when the manager restarts with that job still
running (server.go:3404-3406):

    s.rrjMu.Lock()
    s.recoveredRunningJobs[job.Key()] = true
    s.rrjMu.Unlock()

That is the only write. There is no `delete` from the map anywhere in the tree
(`grep -rn recoveredRunningJobs` finds the declaration at server.go:985, the
`make` at server.go:2909, that write, and one read), and the map is not rebuilt
after recovery finishes.

The one read is `confirmOrReleaseLostJob` (server.go:3901-3921):

    switch {
    case !d.killCalled && !recovered:
        s.confirmJobDeadAndKill(ctx, d)
    case d.killCalled:
        ...
    }

There is no third case. So for a key in the map and a lost run the user did not
kill, the goroutine `markJobLost` started (server.go:3873) does nothing at all:
no `confirmJobDead` ssh check, no `killLostJobAndTriggerBehaviours`, no pinned
behaviours. Since the entry is permanent, this is true not just for the
recovered run but for EVERY later run of that key, for the life of the manager
process - including runs the recovered manager itself scheduled long after
recovery ended.

## What a user experiences

After one manager restart with a job running, that command is permanently
fragile: any subsequent lost run of it is parked in the lost state and stays
there. The job is never confirmed dead, never killed, and its `OnFailure` /
`Cleanup` behaviours never trigger, so its workspace (working directory and
TMPDIR under `<Cwd>/<AppName>_cwd/...`) is leaked, and disk use grows one
workspace per lost run. `wr status` shows the job lost with no progress; the
user has to kill or delete it by hand.

## The nuance worth carrying forward

The permanence is at least partly deliberate. The recovery window exists so a
runner whose command finished while the manager was crashed is not double-run,
and a test comment states the current behaviour outright:
"confirmOrReleaseLostJob permanently protects recovered jobs via
recoveredRunningJobs" (jobqueue/reliable2_release_test.go:144-145). So a fix
cannot simply drop entries on a timer - it has to distinguish the RECOVERED RUN
from later runs of the same key (the run identity already carried in
`lostJobDetails.pin` is the obvious hook), and it needs a test that a re-sent
archive from a pre-crash runner is still accepted.

## Evidence

Read from the code at the line numbers above; no probe harness re-run. The
observable claim (a second lost run of a recovered key is never killed) has no
test in the tree either way.
