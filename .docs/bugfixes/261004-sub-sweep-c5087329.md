- [x] A server-side subscription (`serverSubscription`, registered by
  `registerClientSubscription` for `WaitForJobs`, `SubmitJobsAndWait` and
  `AddAndWait`) can be stranded until the manager restarts: (a) a resubscribe
  registers on the manager but its reply is lost, so the client keeps naming
  the old id; (b) an `Unsubscribe` gives up after 5s. Each stranded
  subscription keeps its `deliverQueuedUpdates` goroutine, key maps and
  bounded channels.
  - Source: `260927-subscription-reconnect-leak.md`, "Residual, not fixed";
    Backlog of `261004-checklist-tidy-8e94211c.md`, item marked "QUEUED
    (branch 3 below), simpler design".
  - Red: `go test -tags netgo -count=1 -run 'TestSubscriptionIdleSweep'
    ./jobqueue/` exits 1 before the fix. `TestSubscriptionIdleSweep` fails
    where the never-polled subscription should be gone (`Expected: true /
    Actual: false`), and `TestSubscriptionIdleSweepLiveClient` fails with
    `Expected 'the live subscription was never swept' to be blank`. With
    `-race` and the sweep disabled, the same two failures, exit 1.
  - Cause: nothing but an unsubscribe, a resubscribe naming the id, or
    shutdown removes an entry from `Server.clientSubscriptions`, and a client
    that lost the id can send none of them.
  - Fix: each `serverSubscription` records its last activity in an
    `atomic.Int64`, set when it is created and at the start of each
    `waitForSubscriptionUpdates`. Those are the only requests that reach a
    client subscription by id; subscribe and unsubscribe remove the id they
    name, and `addKeys`/`removeKey` serve status subscriptions only. Serve
    starts a `time.AfterFunc` sweep that runs every
    `SubscriptionIdleTimeout / 6` and, under `csmutex`, removes every client
    subscription idle for `SubscriptionIdleTimeout`, then closes each as
    `unregisterClientSubscription` does, which ends its goroutine. It logs the
    count at info level. `closeClientSubscriptions` stops the timer under
    `csmutex`, and a sweep that finds `subsClosed` set does not reschedule.
    The timeout is a new `ServerTimings.SubscriptionIdleTimeout`, default
    `serverSubscriptionIdleTimeout` (30 minutes), following the other
    per-server timings so tests shorten it per server. Status websocket
    subscriptions (`stateChanges`) are never swept: the server polls them
    itself and its websocket handler unregisters each when the connection
    closes, so they cannot be stranded this way, and a swept one would end
    the page's job pushes with no resubscribe. Comments in `subscription.go`
    that said the manager has no reaper now name the sweep.
  - Safety argument, checked:
    - Hold time against interval: `waitForSubscriptionUpdates` clamps every
      poll to `serverSubscriptionHoldTime` (25s), and the client polls again
      as soon as it has published a reply's updates. A live client's
      subscription is therefore at most about 25s idle, against 30 minutes.
    - A swept live client recovers: any poll error, whether
      `subscription closed` (swept mid-poll) or `unknown subscription` (swept
      between polls), goes to `reconnectAfterPollError`. That reconnects,
      resubscribes with the same keys and rep group, publishes
      `JobUpdateResync`, then the subscribe reply's `JobUpdates` catch-up of
      current state. `TestSubscriptionIdleSweepLiveClient` holds the client's
      reconnect, after its subscription was swept, while the job completes,
      and `AddAndWait` still returns that job complete with no error.
      `TestSubscriptionStaleIDResync` covers the `unknown subscription` poll.
      0.38.0 clients have the same poll loop.
    - Outages: a manager restart already drops every subscription. A client
      that cannot reach a running manager for over 30 minutes keeps retrying
      for `RetryTime` (24h by default, #665), finds its subscription swept,
      and resubscribes and catches up as above.
    - Updates lost with a swept subscription are intermediate ones; the
      catch-up gives each key's current state, as after a restart.
  - Tests (`jobqueue/subscription_sweep_test.go`): `TestSubscriptionIdleSweep`
    registers a never-polled subscription, one polled every 20ms and a status
    one, with a 300ms timeout. It asserts the idle one is gone and the
    count of `deliverQueuedUpdates` goroutines falls by exactly one, then that
    after three more timeouts the polled one's polls never failed and it and
    the status one are still registered. `TestSubscriptionIdleSweepLiveClient`
    is the live-client test above.
  - Mutants, each run with both tests, each failing:
    - sweep never started: both tests fail (idle never gone; live client
      never swept).
    - poll does not record activity (sweeps active subscriptions):
      `TestSubscriptionIdleSweep` fails, as the goroutine count falls by two.
    - sweep removes but does not close (goroutine not stopped): both fail
      (goroutine count unchanged; live client's poll never broken).
    - status subscriptions swept: `TestSubscriptionIdleSweep` fails.
    - Not covered: dropping the touch at registration. A sweep would have to
      land between a subscribe and its first poll, which tests cannot hold
      open.
  - Perf: the poll path gains one `time.Now().UnixNano()` and an atomic store,
    about 60ns measured alone, with no allocation; no existing benchmark
    covers `waitForSubscriptionUpdates`. A throwaway benchmark of a poll with
    an update ready, interleaved 8 runs each on a host at load 12-17, gave
    medians of 868ns (base) and 1052ns (fix), both 256 B and 4 allocs per op,
    with overlapping ranges. Each poll is a network round trip. The sweep
    takes `csmutex` once per interval (5 minutes by default) for one pass
    over the subscription map.

- [x] Review findings (caller review of the first commit):
  1. Two mutants survived both sweep tests: the sweep using its interval as
     the cutoff instead of the idle timeout, and no `touch()` when a
     subscription is created.
     - Fix: a new Convey in `TestSubscriptionIdleSweep` gives its own server a
       2s timeout (sweeps every ~333ms), registers a subscription it never
       polls, and asserts it is still registered 1s after registration,
       measured from registration, a whole second before it may be dropped.
     - Mutants now killed, each `go test -tags netgo -count=1 -run
       'TestSubscriptionIdleSweep' ./jobqueue/` exit 1: interval as cutoff
       fails that assertion (`Expected: true / Actual: false`), and also
       breaks the 20ms poller (`subscription closed`); no touch at creation
       fails the same assertion.
  2. The CHANGELOG entry now leads with the main case: a client killed
     while waiting, such as `wr add --sync` (which has no signal handling)
     stopped by Ctrl-C or a killed pipeline. Clients from 0.38.0 on recover
     a swept subscription the same way, so the entry has no caveat for older
     clients.
  3. `SubscriptionIdleTimeout` was unchecked. A value under the 25s long-poll
     hold dropped live clients' subscriptions mid-poll, and one under 6ns gave
     a zero sweep interval, a busy loop.
     - Fix: `withDefaults` still replaces a non-positive value with the
       default, as for the other timings, and now raises any value under
       `subscriptionIdleTimeoutMin` to it. That floor is
       `defaultSubscriptionIdleTimeoutMin`, twice `serverSubscriptionHoldTime`
       (50s), so the sweep interval is at least about 8s. It is a package var
       only so the sweep tests can lower it (`allowShortSubscriptionIdleTimeouts`,
       restored by `t.Cleanup`), the package's usual pattern for an internal
       tuning knob; nothing outside Go callers sets this timing. The field's
       doc states the floor.
     - Red: a new Convey asserts 1ns, 1s and 25s are raised to 50s, zero
       gives 30 minutes and 1h is kept. With the clamp removed it fails,
       exit 1: `Expected: time.Duration(50000000000) / Actual:
       time.Duration(1)`.
