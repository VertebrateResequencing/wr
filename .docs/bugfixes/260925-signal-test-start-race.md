- [x] Flake: TestJobqueueSignal (lane signal_b) fails at jobqueue/jobqueue_test.go:2178 with `Expected: jobqueue.JobState("lost") Actual: jobqueue.JobState("running")` after about 181s. Seen on GitHub CI on PR #617 (head b0247a2) on 2026-09-25. Earlier sightings are recorded in .docs/bugfixes/260917-start-durability.md: PR #558, PR #555 and develop 52314859. It is also BUG 20 in 260829-1.md, where the test was deliberately left alone ("What is NOT fixed", about line 416). The owner has now asked for the test to be fixed.
  - Cause: the test kills the manager as soon as the lost job's command writes its `lost_started` marker. The runner starts the command before it sends Started (jobqueue/client.go:~2516, then the request at ~2567). handleStart sets `running` in memory (applyJobStart, serverCLI.go:~1082) and only then waits for the durable write (updateJobAfterChangeDurable, serverCLI.go:~1101). If the manager dies before that write commits, the database still has State "", so recoveredItemDef (server.go:~4749) puts the job on the ready queue. A new runner re-reserves and runs it, so it reads "running" and never goes lost. It fails more on CI because the test's /proc sweep between the marker and the kill is only a few ms there.
  - Not a regression: it reproduces identically on 1c75ffb and on 619099e.
  - Red command: apply this scratch-only seam (`red.patch` below; not committed) in jobqueue/client.go, just before `if _, err = c.request(startReq); err != nil {` in Execute: `if sub := os.Getenv("WR_RED_DELAY_STARTED"); sub != "" && strings.Contains(job.Cmd, sub) { time.Sleep(3 * time.Second) }`. It delays the Started request by 3s for commands containing $WR_RED_DELAY_STARTED, then run `WR_RED_DELAY_STARTED=lost_started WR_TEST_SHARD=b WR_TEST_LANE=14 CGO_ENABLED=0 go test -tags netgo -count=1 -run '^TestJobqueueSignal$' ./jobqueue/`. It fails at :2178 with the CI message after about 183s, every time. With the patch applied and the variable unset it passes in 2.7s.
  - The production counterpart (a manager killed before it acknowledges a start re-runs the job while its first command is still alive) remains the open item at 260917-start-durability.md:~453. It is out of scope here.
  - FIXED in the test, via a test-only seam. `handleStart` (`jobqueue/serverCLI.go`) now calls `startPersistedHook` with the job's key once `updateJobAfterChangeDurable` has committed, before it acknowledges the start. The hook is a nil package var in production, like `deleteOnFailureHook` and the other seams in `jobqueue/server.go`. The `--servermode` daemon is this test binary, so `runServer` installs the hook and has it create `start_persisted.<key>` in the manager dir (`startPersistedMarker`). After both command markers appear, the test fetches each job's key and waits for both start-persisted markers before it sweeps /proc and kills the manager. Its intent is unchanged: the lost runner still dies across the crash and its job still has to come back lost, and the surviving runner still has to finish.
  - It waits for the recover job's start as well. That job has the same race: if its start never reaches disk, it comes back as never started instead of as a running job whose runner survived.
  - Why not the other options. Polling the manager for `running` doesn't work, because `applyJobStart` sets that in memory before the write. Nothing the runner does after `Started` returns is reliably visible from outside: the touch loop runs from before `Started`, and resource reporting also continues after a transient `Started` failure that was never persisted. Reading the database while the manager runs is ruled out by bolt's file lock. The hook marks exactly the point the precondition needs.

With the patch reverted, 10 of 10 full `TestJobqueueSignal` runs passed, in 16-17s each.
