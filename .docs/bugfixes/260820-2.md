# Bugfixes 260820-2 — reliable4 batch 5 (item D + two findings from the validation gate)

Sources: `.docs/reliable4/next-steps-260819.md` section "ITEM D" (investigated and
**reproduced** — see the diagnosis below), plus two findings from the farm-scale
validation gate run on 2026-08-20 at `53c323f`

Previous batches: `.docs/bugfixes/260818-1.md` (findings 1-5),
`.docs/bugfixes/260819-1.md` (items A and B), `.docs/bugfixes/260820-1.md` (item C).

Quality gates: `make lint` (0 issues), `make test` and `make race` with all `OS_*`

- [x] Bug D — the web status page over-counts `running` (prod: **274 shown vs 4 actually running**), and a page refresh hides it. **Root cause reproduced 100% of runs, and it is NOT the doc's hypothesis**: no delta is dropped and none is missing. `setupUpdateListener` (`jobqueue/serverWebI.go:857`) joins `s.statusCaster` as its *first* act, so the client is on the live delta feed before its `"current"` request arrives; `sendCurrentStatusCounts` (`jobqueue/serverWebI.go:577`) then answers by snapshotting the queue and writing one `new->{state}` seed per state directly to the conn, on a different path from the caster. The snapshot and the feed are not a consistent cut (emission is `go queue.changedCb(...)`, `queue/queue.go:530`, not even ordered against `queue.mutex`), so **any transition emitted after the join and before the snapshot is counted twice** — once as its own delta, once inside the seed. The client cannot detect it because deltas are anonymous counts, not job identities: the duplicate parks in `pending[ready][running]`, is satisfied by the seed's `ready` occupancy, and permanently moves one unit from `ready` to `running`. Total occupancy stays correct, which is why nothing noticed. Direction matters: during ramp-up the error inflates `running`, in steady state it cancels, during a drain it deflates - so the prod `limit -> 0` mass exit was **not the cause**, it is what made a pre-existing offset glaring when the true count fell to 4. **Chosen fix (operator's decision, 2026-08-20): the bounded seed-boundary/epoch marker** - the server brackets the seed, the client resets `occ` to the seed and discards everything before the marker (`resetLiveCounts` already does the reset on reconnect). Residual error shrinks from the whole connect window to the seed-walk duration. No server-side counter, no hot-path lock, no history scan, so DEVELOPERS.md rules 2 and 6 are untouched.
  - Fix: **bounded seed-boundary marker**. New wire type
    `jstatusSeedBoundary{SeedBoundary string}` (`"begin"`/`"end"`) written by
    `writeSeedBoundary`; `sendCurrentStatusCounts` takes the connection's write
    mutex **before** the queue snapshot and holds it until after the closing
    marker, so the bracket is one uninterrupted run. Client `onmessage` became a
    router `applyStatusMessage` which routes `SeedBoundary` first and, on
    `"begin"`, calls the **existing** `resetLiveCounts` (the reconnect reset,
    reused not duplicated).
  - Also replaced the seed's `getJobsCurrent` walk with `statusSeedCounts`, which
    counts `(RepGroup, display state)` straight off queue items instead of
    deep-copying every Job — on prod that removes ~118k Job clones **per status
    page connect**, and the shorter walk is what shrinks the residual. The
    reviewer verified the counts are identical **by construction**, not merely by
    test: the old path's `limitJobs` early-returns unchanged for the seed's
    argument shape, and `itemStateToJobState` maps only `ItemStateRun` to
    reserved, so `itemToJob`'s reserved+StartTime->running followed by
    `statusStateCounts`' reserved|running->running collapses to exactly
    `itemDisplayState`'s unconditional reserved->running. `lost`, `dependent`,
    `delayed`, `suspended` and `complete` come from the same map lookup in both.
  - **Rules 2/6/10 satisfied, and hold time went DOWN.** No server-side counter,
    no lock on the transition path, no history scan added. The only lock involved
    is the pre-existing **per-connection** websocket write mutex, moved earlier by
    one function call; it can never back-pressure `emitJobTransition`, because the
    status caster is `newCaster(true)` and `trySend` appends to an unbounded queue
    (so deltas buffer and flush after `end` — rule 3 preserved, never dropped).
    `jobtransition.go`, `server_subscription.go` and `queue/` are byte-identical
    to `53c323f`. The walk now inside the mutex measures 7.9-10.1 ms, replacing a
    materialising walk of 19.4-27.1 ms — and the archived-history fetch was
    **already** inside that mutex before this batch, so the net effect is a 2-3x
    reduction in hold time, not an increase.
  - Wire back-compat verified in **both** directions on identical streams: an old
    client dispatches on `FromState`/`State`/`IP`/`Msg`, none of which the marker
    carries, so it is dropped (driving the `53c323f` handler over marker-bearing
    streams reproduced its exact pre-fix numbers); a new client against an old
    server never sees a marker and behaves as before. The feed is
    `conn.WriteJSON` (encoding/json), so unknown fields are ignored, and a marker
    decodes into `jstateCount` as a zero value with `RepGroup == ""` — which
    `wsprobe` (`main.go:92`), the pre-existing Go readers (`deltaCounts.apply`)
    and `replay-stream.mjs` all already skip.
  - **The residual is quantified, and exactness is NOT claimed.** Two components:
    (1) the seed walk is not a point in time, so worst-case error = walk duration
    x transition rate, measured at 10.1 ms and 2,377 starts/s on a 13.5k-job queue
    (predicted 24.1, observed 22), growing linearly with live-job count; (2)
    emission jitter — `go queue.changedCb(...)` can be descheduled past the
    snapshot, which **no** boundary can close (measured 9 vs 14 for a
    boundary-blind client). The forced shape, which isolates the window that
    dominated in prod (remote browser to a CPU-bound manager), goes **121 -> 0**.
  - RED/GREEN: new always-built guard `TestReliable4StatusSeedBoundary` is GREEN
    here and RED on a pristine worktree at `53c323f` (`:367`, `Expected 1, Actual
    0` — no bracket). The reproducer's forced shape: shown_running **125 -> 4**
    against a truth of 4.
  - Mutation-tested; the most informative result: taking the write mutex **after**
    the snapshot does not merely weaken the fix, it makes transitions go
    **missing** (`awareErr` goes to **-4**), which is a rule-3 violation. That is
    pinned by an explicit `ShouldBeGreaterThanOrEqualTo 0` assertion, so a later
    "simplification" of the lock ordering cannot pass silently.
  - Scale gate `developers/wrdev.sh status-seed-overlap`: **FAIL pre-fix** (forced
    over-count 121, `GATE_EXIT=1`), PASS post-fix (4 vs 4, bracket 1/1). Its
    `FAIL (NOT MEASURED)` branch was fired deliberately and returns 1 even when
    the Go test itself passes.
- [x] Bug D2 — the existing regression harness **cannot fail on Bug D**. `jobqueue/testdata/status-count-reconcile/reconcile-harness.mjs` scenario B (`:171`) does model the seed race, but scores it only on the per-RepGroup **total** and the final `complete` count - both of which the client's occupancy model conserves by construction (total occupancy == sum of `new->` creations), so a per-bucket misdistribution is invisible. - [x] Bug D3 — item B's recorded residual is reachable and still a ~12 GB heap bomb. `cmd/status.go:194` zeroes `statusLimit` for the ungrouped output formats, so `wr status -i <rg> -z -o plain` (and any explicit `--limit 0`) keeps the **unbounded** archived decode that `5b90c53` removed from the default path. Measured in the validation gate on only 154,000 archived records: `-o plain` took **6,975 ms** with VmHWM **+905 MB** (heap 380 -> 670 MB), against 1,377 ms and heap step 0 for the same query without `-o plain`. That extrapolates to **~12.6 GB on prod's ~2.15M complete jobs** - i.e. the original 12.1 GB excursion is one flag away today. Bound it, or make the unbounded case explicit and refuse/stream it; do NOT change what `wr status` returns.
  - **Operator-approved deliberate behaviour change** (2026-08-20), and only in the
    regime that currently melts the manager. There is no result-preserving bound
    for these shapes: `-o plain` prints one line per job **key** and `-o summary`
    accumulates per-job statistics, so neither can be served from the folded
    representatives the grouped formats use.
  - Approach: a **decode-free pricing pass** plus an explicit refusal.
    `getJobsByRepGroup` prices first — `checkArchivedHistoryFits` ->
    `priceArchivedHistory` -> `db.spendArchivedBytesByRepGroup` walks the same
    `bucketRTK` index reading each record's **encoded length only** (no decode, no
    allocation) against one `archivedBytesBudget` spanning **all** matched
    RepGroups, default **256 MiB** (`maxArchivedBytesDefault`, a var so tests can
    drive it). It applies only when the limit could not be pushed down and
    complete jobs were asked for — the reviewer confirmed that gate is the exact
    complement of `getDBJobsByRepGroup`'s three early-outs. A **byte** budget, not
    a job count, because records vary 1.5 KB-134 KB.
  - Above the cap the request fails with `too much completed-job history to return
    at once: re-run with --limit, or a state filter, or -o counts (over N bytes at
    M complete jobs)`, delivered via `srerr` so `wr status` dies with it
    (`cmd/status.go` `die(...)`). A refused request decodes **nothing**.
  - **Every query that fits is byte-identical to before**: `jobqueue/db.go`'s diff
    is **94 insertions / 0 deletions** and nothing on the fetch path changed, so
    `5b90c53`'s equivalence (proven across 2,192 shapes) is untouched. The
    reviewer spot-checked the grouped paths and a fitting `-o plain` query.
  - The pricing walk is **bounded**: nothing anywhere deletes from
    `bucketJobsComplete`/`bucketRTK`, so every RTK key has a non-empty record and
    the budget always trips after at most `maxArchivedBytes / recordSize` records
    (~175k at prod's ~1.5 KB records). Measured overhead on a request that fits
    (10,000 records / 42.8 MB): 385 ms -> 598 ms; ~1 s worst case at the cap. It
    can never cost more than the fetch it guards.
  - **REST now answers 400, not 500.** `parseRESTStatusQuery` defaults `limit` to
    0, so `GET /rest/v1/jobs/<repgroup>` over a large history hit the refusal and
    returned HTTP **500** — telling the caller the server was broken when the
    request was the problem. Mapped to **400 Bad Request** via
    `restStatusErrorCode`, matching what that same endpoint already returns when
    it cannot use a supplied `limit`; 413 was rejected because RFC 9110 scopes it
    to *request* content size. `.docs/issue-197/spec.md` was checked and does not
    constrain GET status codes (it is the PATCH modification contract). Pinned by
    a sub-Convey driving the real `restJobs` handler over `httptest`.
  - Review found and closed two unpinned/ineffective guards: the
    "budget spans the report groups" sub-test used a budget so small that **each
    group busted it alone**, so it never tested spanning and the per-RepGroup
    mutation passed the whole package — the budget now sits between the largest
    single group and the total, plus a control asserting the larger group alone is
    served in full; and **an unlisted guarantee**, that a non-complete state filter
    must never be refused (`wr status -b` is Limit 0 + `State: buried` +
    `IncludeComplete`), where mutating the predicate to always-refuse survived the
    entire package — now pinned for both `ready` and `buried`.
  - RED/GREEN: archived decodes for the `-o plain`/`--limit 0` shape **5,000 -> 0**
    (and **8,000 -> 0** for `-z`); scale gate `control-rpc-history` extended with
    the `-o plain` shape is **FAIL pre-fix** (9,059-9,219 ms, **+2,206-2,393 MB**
    VmHWM, 200,000 lines, `refused=0`) and **PASS post-fix** (~155 ms, ~0 MB,
    `refused=1`, 0 lines).

## Follow-ups recorded from this batch (not scheduled)

- **One item, sized by the first half.** (a) The status seed's per-RepGroup step
  calls `getCompleteJobsByRepGroup`, which **decodes every RepGroup's entire
  archived history on every status page connect** (~2.15M records on prod) — a
  rule-6-class cost on a control path, held under the per-connection write mutex.
  This is **pre-existing**, not introduced here: `git show 53c323f` puts the write
  mutex before that loop already, and this batch strictly reduced hold time.
  (b) That same step makes the seed **internally inconsistent**: live counts come
  from the snapshot at T0, but each RepGroup's `complete` count comes from a
  history fetch at T1 > T0, so a job archived in between is counted twice within
  one seed (once `running`, once `complete`); the post-`end` `running->complete`
  delta then corrects `running` and leaves `complete` **+1 permanently**. So the
  "residual = walk duration x transition rate" bound holds for the live buckets and
  `+all+`, but a RepGroup's `complete` bucket has a window of (a)'s duration —
  minutes on prod. Direction is one-way (over-count), never a loss, and it existed
  identically pre-fix. Bug D's fix still stands: prod's symptom was `running`, and
  that is now exact in the discriminating shape. **Fixing (a) collapses T1-T0 to
  microseconds and (b) disappears with it**, so they should be one item: bound or
  drop the per-RepGroup archived `complete` seed (an index count, a limit, or defer
  it to the client's own drill-down — it is the same decode `5b90c53`/`5c75a15`
  removed elsewhere).
- `wr status --recent` remains an unbounded archived decode
  (`retrieveCompleteJobsRecent`, no pushdown, outside the new budget) — the same
  class of heap bomb as Bug D3, one flag away.
- `sendJobDetails` (`serverWebI.go`) fetches with `IncludeComplete` and, on error,
  simply returns — so a web drill-down with `Limit 0` over a >256 MiB history would
  silently show nothing rather than surfacing the refusal text. Unreachable from
  the shipped UI (`repgroup-handler.js` always sends `Limit: 1` or `Limit: 5`), so
  recorded rather than fixed.
- Narrow, cosmetic side effect of the `begin` reset: a RepGroup whose only news was
  a pre-seed delta and which has **no** live jobs at snapshot time is absent from
  the seed (deliberate terminal-hiding), so its row renders all-zero where pre-fix
  it showed `complete=N`. Consistent with post-refresh behaviour.
- `need_bin` in `developers/wrdev.sh` only checks that the binary **exists**, it
  never rebuilds — so a gate run in a fresh `WRDEV_ROOT` that already holds an old
  `wr` silently measures the **old** binary. This produced two false FAILs during
  this batch (a Jul-29 binary predating the whole batch). Always
  `wrdev.sh build` first; consider making `need_bin` compare against HEAD.
