- [ ] Bug D — the web status page over-counts `running` (prod: **274 shown vs 4 actually running**), and a page refresh hides it. **Root cause reproduced 100% of runs, and it is NOT the doc's hypothesis**: no delta is dropped and none is missing. `setupUpdateListener` (`jobqueue/serverWebI.go:857`) joins `s.statusCaster` as its *first* act, so the client is on the live delta feed before its `"current"` request arrives; `sendCurrentStatusCounts` (`jobqueue/serverWebI.go:577`) then answers by snapshotting the queue and writing one `new->{state}` seed per state directly to the conn, on a different path from the caster. The snapshot and the feed are not a consistent cut (emission is `go queue.changedCb(...)`, `queue/queue.go:530`, not even ordered against `queue.mutex`), so **any transition emitted after the join and before the snapshot is counted twice** — once as its own delta, once inside the seed. The client cannot detect it because deltas are anonymous counts, not job identities: the duplicate parks in `pending[ready][running]`, is satisfied by the seed's `ready` occupancy, and permanently moves one unit from `ready` to `running`. Total occupancy stays correct, which is why nothing noticed. Direction matters: during ramp-up the error inflates `running`, in steady state it cancels, during a drain it deflates - so the prod `limit -> 0` mass exit was **not the cause**, it is what made a pre-existing offset glaring when the true count fell to 4. **Chosen fix (operator's decision, 2026-08-20): the bounded seed-boundary/epoch marker** - the server brackets the seed, the client resets `occ` to the seed and discards everything before the marker (`resetLiveCounts` already does the reset on reconnect). Residual error shrinks from the whole connect window to the seed-walk duration. No server-side counter, no hot-path lock, no history scan, so DEVELOPERS.md rules 2 and 6 are untouched.
- [ ] Bug D2 — the existing regression harness **cannot fail on Bug D**. `jobqueue/testdata/status-count-reconcile/reconcile-harness.mjs` scenario B (`:171`) does model the seed race, but scores it only on the per-RepGroup **total** and the final `complete` count - both of which the client's occupancy model conserves by construction (total occupancy == sum of `new->` creations), so a per-bucket misdistribution is invisible. It passes today on the same handler the Bug D reproducer shows over-counting by 121. Make scenario B assert **per-bucket** accuracy.
- [ ] Bug D3 — item B's recorded residual is reachable and still a ~12 GB heap bomb. `cmd/status.go:194` zeroes `statusLimit` for the ungrouped output formats, so `wr status -i <rg> -z -o plain` (and any explicit `--limit 0`) keeps the **unbounded** archived decode that `5b90c53` removed from the default path. Measured in the validation gate on only 154,000 archived records: `-o plain` took **6,975 ms** with VmHWM **+905 MB** (heap 380 -> 670 MB), against 1,377 ms and heap step 0 for the same query without `-o plain`. That extrapolates to **~12.6 GB on prod's ~2.15M complete jobs** - i.e. the original 12.1 GB excursion is one flag away today. Bound it, or make the unbounded case explicit and refuse/stream it; do NOT change what `wr status` returns.
