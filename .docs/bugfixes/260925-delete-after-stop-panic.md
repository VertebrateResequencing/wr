  - Fixed in `jobqueue/server.go`. `deleteJobIfRequested` now puts its goroutine on `s.wg`, like `scheduleRunnersAsync`, so shutdown's `wg.Wait` (which has no deadline, it only logs) waits for the delete before `s.q.Destroy` and `resetStateAfterShutdown`. It doesn't spawn once `inShutdown` is set, and holds `krmutex` across that check and the `wg.Add`, so every Add is ordered before `wg.Wait` even from callers not on `s.wg` (the lost-job release). It uses `krmutex` rather than `ssmutex`, the `storeWebSocketConnection` pattern, because `beginShutdown` holds `ssmutex` while `unscheduleAllGroups` can reach `buryImpossibleItem`, so `ssmutex` could self-deadlock.
  - `deleteJobs` gets the queue once through `queueIfPresent` and does nothing if it is gone. It passes that queue to `removeDeletableJobs` and to `jobHasDependents`, which is now a plain function. The per-job removal moved to `deletePass.remove` to keep `gocognit` under its limit.
  - Regression test `TestStopWaitsForARemoveOnFailureDelete` (`jobqueue/delete_after_stop_test.go`) holds the delete goroutine at a new `deleteOnFailureHook` seam, stops the manager, waits for the database close, then releases the goroutine.
