## Notes

- All customdb work ships as one PR from this branch, so Phase 1's mixed state (log plus bbolt history) never reaches a release and needs no Phase 1 to Phase 2 on-disk migration. The Phase 0 per-writer stats land on this branch, not separately on develop.
- An existing production bbolt DB is converted automatically on the first `wr manager start`, with progress reported through the existing upgrade status sidecar (`internal/db_upgrade_status.go`); a conversion phase is added there and classified in `IsDBUpgradeState`. The converter accepts any bbolt schema version (1 and 2) and strips the std out/err stored by 0.37.x, so there is no compact-first step.
- Rollback: the old bbolt file is kept untouched under a new name (e.g. `db.bolt-pre-<version>`). There is no reverse converter. Documentation states that rolling back loses everything done since the conversion.
- Location: `managerdbfile` (default `db`) becomes the new store's directory; no new config key. A downgraded wr (v0.38.0+) refuses a directory and leaves it untouched (EISDIR is "not corruption", `jobqueue/db.go:3540`).
- Backup: `managerdbbkfile` becomes a directory (or an S3 prefix) that newly sealed files are shipped to incrementally. `wr manager backup -p` writes one self-contained file (e.g. a tar of a consistent snapshot plus segments) that startup restore also accepts, so the CLI and the cloud bootstrap/teardown path (`cmd/cloud.go:582-605`, `:1106-1150`) keep their one-file expectation. Startup restore from backup when the store is missing or corrupt (today `jobqueue/db.go:1384-1550`) is preserved, as is the dev-mode wipe and production-only backups.
- Config: remove `managerdbbatchdelay`, `managerdbbatchsize` and `ServerTimings.DBBatchDelay`/`DBBatchSize` and `ReserveWriteWait` (its bound becomes an internal constant, see the reservation note); add no new user knobs. Checkpoint interval, segment size and codecs are constants or test-only timings. configor ignores unknown keys, so old config files still load.
- `wr manager compact` becomes an offline "checkpoint, drop old logs, merge history segments" for the new store, still refusing to run while a manager is up.
- Tooling: developer tools only. Reimplement `developers/soak/dbstart` over the new interface (its `dbstart.tsv` feeds `soakgate.py`, `starttimes.py`, `relburycheck.py`); retire `bboltexp` and `statinspect`. No user-facing inspection command. Soak fixtures are bbolt files (`wrdev.sh add-storm-fixture`, `runstate-gate/fixtures/prod.db`), so the converter is also how fixtures reach the new store.
- Acceptance gates:
  - the prototype's kill -9 crash test ported to jobqueue, driving the interface, plus a fuzz test of the log scanner;
  - record/replay equality between the bbolt and log implementations over a prodsim recording;
  - a crash soak at production LSF concurrency with a staged ramp (battery10 shape, about 6,000 runners, at least 3h, injected stalls and crashes) with 0 acknowledged writes lost, 0 non-durable hand-outs (including during injected stalls) and 0 double runs outside injected stalls;
  - `make speed-full` with no regression above 10%;
  - daytime NFS targets: reserve p99 at most 50ms and 1000-job add p50 at most 200ms;
  - Phase 2 repeats the soak and adds status timings for the biggest rep group.
- Facts for the author: the periodic backup today is a whole-file `tx.WriteTo` copy at least 30s apart (`jobqueue/db.go:75`, `:6322`, `:6536`) and the client stages it to one file (`jobqueue/client.go:2661`); schema version lives in `meta` (`jobqueue/db_schema.go:47-58`, `:185`); bbolt is imported outside tests by `jobqueue/{db,db_runstate,dependency,writeturns,reqstat_cache,running_dependent,db_compact,db_prefetch,db_schema}.go` and `developers/soak/{dbstart,bboltexp}`; `ServerConfig.DBFile` is public (`jobqueue/server.go:5160`); `make speed`/`speed-full` exist (`Makefile:108-112`, `developers/speed.sh`) with a 10% threshold.
- Reservation durability: reserve waits for its reservation record to become durable for at most an internal bound (a quarter of `ClientMinRequestTimeout`, `jobqueue/server.go:240-241`, `:777-781`). If the bound passes, it appends a release record and returns "no job"; the runner retries. Log order makes the release win over the late reserve record, so a job is never handed out before its reservation is durable, even during a stall. The behaviour of `persistReservation`/`handOutReservation` (`jobqueue/serverCLI.go:1117-1175`, rationale in `.docs/bugfixes/260928-reserve-durability.md`) that must survive includes restarting the TTR after the wait.
- The completed-job key index (key to segment and offset, used by `checkIfComplete` for add dedup) is held fully in memory: about 50-100MB at production's 2.15M completed jobs, growing with history. On-disk sorted per-segment key indexes with a per-segment bloom filter are documented as the fallback if memory becomes a concern.
- Delivery-queue row 15 (concurrent key-changing modifies lose one job's persist) is fixed by this work: concurrent key-changing modifies must persist both jobs, with a regression test. Row 18 (archive-fold log drops archives, `archivefold.go`) disappears with bbolt.
- The PR base is develop (`.docs/delivery-queue.md:29`).
- The new store needs an exclusive lock file so two managers cannot share one store, keeping today's `ErrDBLocked` behaviour (`jobqueue/db.go:3536-3537`).
- `klauspost/compress` v1.20.0 is already in `go.mod` (indirect), so s2 and zstd add no new module.
- Phase 0's per-writer stats follow the definition in dropped delivery-queue row 6: per-writer lock use plus reservation wait p50/p99/max, logged like the archive fold line (`runstate-gate/analysis/bursts-findings.md` option C).
- Single-path deletes must become recursive or prefix deletes: the dev-mode wipe and restore/corruption handling call `os.Remove(dbFile)`, `os.Remove(dbBkFile)` or `accessor.DeleteFile(dbBkFile)` (`jobqueue/db.go:1455-1469`, `:1515`, `:1533`), which silently fail on a directory or S3 prefix. Each site needs an acceptance test.
- The upgrade sidecar stays at `dbFile + ".upgrade"` (`internal/db_upgrade_status.go:219-221`), a sibling of the store directory; `cmd/manager.go:943-1003` already reports it during startup.
- Conversion is crash-safe: rename the bbolt file to its `db.bolt-pre-<version>` name, build the store in a temporary sibling directory, and rename it to `db` only when complete. A crash at any point leaves either the untouched bbolt file or a complete store, and a restart resumes or redoes the conversion. The converter checks free space before starting and fails cleanly if there is not enough (production's bbolt file is about 15GB and is kept alongside the new store).
- Cloud: `cmd/cloud.go:587` renames `ManagerDBFile` to `+".old"`, which works on a directory; `:1132-1142` uploads the DB as one file and must use the self-contained `backup -p` file instead.
- In Phase 1 history queries (`checkIfComplete`, `retrieveCompleteJobs*`, recent completions, last completion time) also see completions in the log that the folder has not yet folded, so status straight after an archive is unchanged. This needs an acceptance test.
