A --cwd_matters job must report that wr created no directory for it.
A new feature made every one of them report the user's own directory,
and cleanup deletes the parent of whatever gets reported.

5 · The traps · 1 of 3

A string carrying a permission, with no owner

Trap 1 · the sentinel

"" did not mean unknown. It meant you may not delete anything.

A string cannot express that, and nothing at the assignment site hinted at it.

Trap 2 · no single writer

Four separate places turned a JobEndState into an ActualCwd, each with its own copy of the same line:

if jes.Cwd != "" { j.ActualCwd = jes.Cwd }

Four writers means no owner, and no owner means nowhere for a check to live. Nothing in the code said empty iff CwdMatters. That rule existed only as prose, ~1,100 lines from the line that broke it.

--on_exit defaults to [{"cleanup":true}], stored on every job, including the ones where cmd/add.go promised:

The documentation was right about the intent and wrong about the code, and was believed for two releases.

6 · Why the line got written

Three facts you must hold at once to see it

The framing picked the variable

The feature was “show the working directory of a running job”. cmd.Dir is the working directory, the honest answer to the question as posed.

A matching field name hid a meaning

JobEndState.Cwd is not “a cwd”; it is the wr-created cwd, or empty. Reusing the struct that already travelled on every touch saved a type and a round of plumbing.

9 · Residual risk & what changes next time

What is closed, and what is written down

  • 1Types, not prose, for anything that authorises destruction. provenDirs is the change that actually does the work. The doc comment it replaced was correct, and ignored for two releases.
  • 2“No effect in case X” in docs is a smell. If a behaviour is inert in a configuration, don't store it. The gap between inert and catastrophic was one wrong field.
  • 3Test the combination, not the ingredients. cwd_matters, lost jobs and cleanup were each well covered; nothing crossed them. And distrust any test whose name contradicts its fixture.
  • 4For AI-written changes: a change touching a field consumed by a destructive path must name the consumer in its description. The author cannot see three hops downstream, and nor, in practice, can the reviewer.
  • 5Verify severity before recording it. Several deferrals in this work were wrong on facts that took one command to check.

What is left

Everything recursive or destructive is fully closed.

The upward empty-dir walk is not inode-verified. Worst case: unlinking one empty directory or one symlink, bounded to inside the job's own Cwd.
